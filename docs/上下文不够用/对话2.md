## L0：基础原则层

这是所有后续系统都必须遵守的规则。

| 规则 | 说明 |
|---|---|
| 后端是权威状态源 | 生命、背包、财富、修为等真相在后端 |
| Godot 是状态镜像和表现层 | Godot 可显示、表现、本地预测，但默认不改真相 |
| 静态档案和动态状态分离 | 档案是角色本来是谁，动态是角色现在怎样 |

| 所有变化要有来源 | 伤害、加钱、学技能、获得物品都要有 source/ref |
| 有效状态是计算结果 | 档案 + 动态 + 装备 + 技能 + 状态标签 = 最终数值 |

当前代码实现的核心判断：

**现在代码已经实现了“角色心智运行时 + 档案投影 + 技能 advisory + 部分 Godot runtime bridge”。但还没有实现你现在定义的“完整游戏角色状态基础设施”。**

换句话说，现在的角色更像：


还不是：

```text
有生命条、背包、财富、修为、装备、负重、状态标签，并能完整映射到 Godot 的游戏角色实体
```

## 一句话结论

现在的 `CharacterDynamicState` 是“角色心理/认知动态状态”。

你要的完整游戏状态应该是：

```text
CharacterGameRuntimeState
= CharacterDynamicState
+ NeedTensionState
+ BodyRuntimeState
+ ResourceState
+ StatusTagState
+ InventoryState
+ OwnershipLedger
+ CultivationState
+ RelationshipState
+ SkillRuntimeState
+ EffectiveStats
```

也就是说，不是把所有东西塞进 `CharacterDynamicState`，而是让它成为完整游戏状态里的一个子系统。

## 3. 动态状态怎么成为完整游戏状态

```text
CharacterGameRuntimeState

    dynamic_state

    body_runtime_state

  resources:
```

## 4. 运行时变化流

完整游戏状态应该这样流动：

```text
1. 档案提供基础值
   CharacterDossier / CharacterProfile

2. 当前系统写入动态状态
   DynamicStateStore
   NeedTensionStore
   BodyRuntimeStateStore
   InventoryStore

3. Resolver 计算有效状态
   CharacterEffectiveStatsResolver

4. 后端生成快照/增量
   CharacterGameRuntimeStateSnapshot / Delta

5. Godot 接收
   BackendBridge -> RuntimeStateMirror

6. 前端消费
   UI / 动画 / 战斗 / 移动 / 调试面板
```

## 6. 最小升级路径

第一步不要做全量经济/修炼/背包。

先做：

```text
CharacterGameRuntimeState v1
  resources
  status_tags
  body_runtime
  mental_state_ref
  effective_stats
  snapshot/delta
  Godot mirror
```

然后再接：

```text
v2: inventory + load/container
v3: ownership/wealth/assets
v4: cultivation
v5: relationship/ability graph
```

这样动态状态就不会继续停留在“后端心理状态”，而会变成游戏角色统一状态的一部分。

最终关系是：

```text
CharacterDynamicState 不是完整游戏状态。
CharacterGameRuntimeState 才是完整游戏状态。
CharacterDynamicState 是其中的 mental 子状态。
```


想支持所有的游戏玩法类型，我们还缺什么？ 玩法系统对于我们来说其实是在各层各部分都配上相应的脚本补丁，我们希望能支持更多的。

想支持“尽可能多的游戏玩法类型”，我们缺的不是某一个玩法系统，而是一个统一的：

**Gameplay Patch / Rule Extension Infrastructure**

也就是：玩法不是硬写死在某个模块里，而是通过“脚本补丁”挂到角色、世界、物品、技能、结算、UI、Godot 表现等不同层。

大白话说，你要的底层应该允许这样做：

```text
某个玩法包
  改角色状态
  加资源条
  加状态标签
  加物品规则
  加技能动作
  加结算规则
  加 UI 面板
  加 Godot 表现
  加 AI 决策影响
  加存档字段
  加验证脚本
```

现在我们还缺的是把这些“可挂载点”系统化。

**1. 缺统一的玩法补丁模型**

需要一个核心对象，例如：

```text
GameplayPatch
```

它描述：

- 它修改哪些状态组
- 它注册哪些资源条

- 它注册哪些物品/容器/装备规则
- 它注册哪些技能/动作/结算规则

- 它依赖哪些其他补丁
- 它的权限边界是什么

**3. 缺统一事件/触发器系统**

玩法系统本质上经常是：

```text
当 X 发生时，如果 Y 条件成立，就产生 Z 效果
```

需要一个通用事件和触发器层：

```text

on_skill_used
on_trade_completed

```

然后玩法脚本可以挂：

```text
trigger -> condition -> effect
```

例如：

```text

-> add_status_tag(exhausted)
-> reduce_effective_move_speed(30%)
```

**4. 缺统一效果系统**

玩法补丁最终要改变东西，但不能乱改。

需要：

```text
EffectSystem
```

支持：

- 改资源：加血、扣蓝、恢复耐力
- 加 tag：中毒、眩晕、修炼中
- 改物品：获得、消耗、损坏
- 改财富：加钱、扣钱、产生债务
- 改关系：增加信任、增加怀疑
- 改技能证据：记录练习、失败、突破
- 改修为：增加进度、触发瓶颈
- 改世界：打开门、改变天气、生成对象
- 改 UI/表现：触发提示、特效、动画

但所有 effect 都要走权限和结算边界，不能让脚本随便写世界真相。

**5. 缺玩法权限和安全边界**

不同脚本不能拥有同等权限。

例如：

| 脚本类型 | 能做什么 |
|---|---|
| UI patch | 只能读状态和显示 |
| Presentation patch | 播动画、特效、音效 |
| Local prediction patch | 本地预测，但不能写真相 |
| Gameplay rule patch | 可请求状态变化 |
| Authority patch | 可参与后端结算 |
| Admin/debug patch | 可强制改状态 |

需要明确：

```text
read_scope
write_scope
authority_level
sync_scope
persistence_scope
```

否则后面玩法一多，状态会被乱写。

```text
CharacterGameRuntimeState
```

