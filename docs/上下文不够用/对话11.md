3. 元规则的配置化实现
所有元规则以结构化配置文件或数据库条目的形式存在，由元规则引擎在运行时读取和执行。
规则匹配引擎的工作流程：
1. 事件监听：系统持续监控所有实体（角色、事物、环境）的状态变化
2. 条件匹配：当某个变化发生时，引擎扫描所有元规则，找出条件匹配的规则
3. 优先级排序：匹配的规则按优先级排序
4. 冲突仲裁：若规则效果冲突，按优先级和规则类型仲裁
5. 效果执行：依次执行规则效果，更新目标状态
6. 链式触发：效果可能导致新的状态变化，递归匹配新规则
4. 元规则的动态演进
司命可以在运行时修改元规则，这是世界“成长”的关键机制：
• 参数调校：如调整“信任衰减率”以适应文明演变
• 新规则注入：当出现未覆盖的情境（如“防护物攀比”），司命生成临时规则
• 规则废弃：长期未触发的规则可能被标记为“休眠”，腾出计算资源

3. 标签的继承与覆盖规则
• 向上继承：子标签自动继承所有父标签的交互规则
• 向下覆盖：子标签可以覆盖继承来的规则，定义自己的特有交互
• 多重继承：一个标签可以有多个父标签，同时继承多组规则
• 冲突消解：若多重继承导致规则冲突，取优先级最高的；优先级相同则取第一个定义的
示例：
• 火焰继承热能的所有交互（如对冰有克制），也继承能量的通用属性
• 神力继承超自然能量的规则，但覆盖了“vs科技护甲”的交互（神力对科技有额外穿透）
• 神圣同时继承神力和光，因此同时对亡灵和黑暗生物有克制
4. 标签的动态赋予与移除
实体（角色、事物）可以在运行时动态获得或失去标签：
• 环境赋予：站在火中→获得燃烧标签
• 技能赋予：被诅咒→获得诅咒标签
• 装备赋予：穿上防火斗篷→获得防火标签
• 状态移除：火焰被水浇灭→失去燃烧标签
程序检测到标签变化时，立即触发元规则重新匹配，可能导致连锁反应。

五、标签体系的扩展接口
当设计师需要添加全新的力量体系时：

全程无需修改任何代码。 元规则引擎和标签系统在运行时读取配置，自动支持新力量体系。

三、元规则的设计哲学
元规则系统的核心设计原则是：
1. 声明式而非过程式：元规则描述“当条件满足时，应该发生什么”，而不是“怎么一步步去做”。具体执行由程序引擎完成。
2. 配置化而非硬编码：所有规则存储在配置文件或数据库中，可在运行时修改。设计师添加新世界观时，只需编写新的规则配置。
3. 可解释性：每一条元规则都有description字段，解释它代表什么现实逻辑。任何结算结果都可以追溯到具体的元规则条目。
4. 分层继承：规则有优先级和继承关系。通用规则（如“损失触发焦虑”）在下层，具体规则（如“老石对农田的损失触发额外愧疚”）在上层覆盖。
5. 司命可干预：司命可以在运行时注入临时规则、调整参数、废弃过时规则，但不能违反元规则自身的核心约束（如能量守恒）。
￼

二、物理层在施法中的处理
物理层不只处理固体碰撞，它还处理：
投射物飞行：火球从施法者飞向目标，有速度、轨迹、碰撞体。击中目标或到达最远距离时触发爆炸判定。
范围场判定：暴风雪是持续范围场，物理层检测哪些实体进入该区域，以及滞留时长。每秒对区域内实体触发一次L3-L5链。
目标锁定射线：诅咒或心灵控制需要视线。物理层从施法者向目标发射射线，检测是否有障碍物阻挡。
空间坐标锚定：传送术在目标位置放置一个不可见的空间锚点，物理层负责维持其世界坐标。

三、两个完整实例
实例一：火球术（投射物型）
• L1：法师吟唱，动作基元“施法”，指定目标区域
• L2：生成火球投射物，沿抛物线飞行。物理引擎检测到火球碰撞体与地面相交
• L3：爆炸源标签[火焰, 魔法, 爆炸]，范围内目标有哥布林[生物, 可燃]、水洼[水]
• L4：查询效应模板。火焰+生物→火焰伤害+点燃；火焰+水→蒸汽爆发
• L5：元规则结算。哥布林受到火焰伤害并燃烧；水洼产生蒸汽致盲；火焰抗性减免；燃烧状态叠加
实例二：诅咒术（射线型）
• L1：术士吟唱，指定视线内的一名骑士
• L2：从术士向骑士发射视线射线。物理引擎检测射线未被障碍物阻挡，判定命中
• L3：诅咒标签[暗影, 诅咒, 精神]，骑士标签[生物, 人类, 重甲, 无魔法抗性]
• L4：效应模板：暗影+人类→持续伤害+属性削弱；诅咒+重甲→无视护甲（诅咒穿透物理防御）
• L5：骑士受到持续暗影伤害，力量-15%，持续30秒。无魔法抗性则无法豁免

五、这证明了结算链的通用性
五层链之所以能同时容纳物理攻击、施法、炸山、砍树，是因为每一层都严格完成了自己的抽象职责：
• L1：我不管你怎么做到，我只知道你发出了一个意图
• L2：我不管这是什么能量，我只负责判断它是否接触到了目标
• L3：我不管接触是怎么发生的，我只负责识别双方是什么
• L4：我不管你们是谁，我只负责给出这些标签相遇可能产生什么效应
• L5：我不管效应怎么来的，我只负责根据规则算出最终结果
施法不是结算链的例外，而是它的另一种输入。只要能被“意图”触发、能在空间中被“定位”、能用“标签”描述，就能走这条链。

我们被要求详细解释战斗结算链（意图-结果结算链）与其他系统之间的耦合关系。需要说明哪些系统是紧密耦合的，哪些是松散耦合的，如何通过接口隔离。可能还需要图示。
关键点：结算链本身是一个流程，它需要从动作系统、物理引擎、标签系统、元素效应系统、元规则引擎获取服务。这些系统之间应该是松散耦合的，通过事件或接口调用。我们可以描述为：
• 意图层调用动作系统，动作系统发出事件
• 物理层接收事件，进行物理模拟，输出碰撞结果事件
• 语义层监听碰撞事件，查询标签系统获取标签，输出语义事件
• 效应层监听语义事件，查询元素效应系统获取效应模板，输出效应实例列表
• 规则层监听效应列表事件，调用元规则引擎进行结算，输出状态变更事件
• 状态变更事件被其他系统（如情绪系统、社会系统、事物档案）消费
这样每个系统都只与上一层和下一层有直接依赖，但通过事件总线解耦，可以替换。同时，因为各个系统本身需要访问角色档案、事物档案等数据，这些是共享的数据层。
需要强调耦合度的控制：标签系统、元规则引擎是相对独立的配置驱动模块；物理引擎是外部库的封装；动作系统是角色状态机的部分。结算链本身是一个流程编排器，它依赖于这些系统的接口，但不绑定具体实现。

二、各层与外部系统的具体耦合
L1 意图层 ← 动作系统
耦合关系：动作系统是实现意图层的唯一方式。任何想让世界发生点什么的行为，都必须通过动作系统发出一个标准化的动作指令。
依赖：
• 角色档案：读取当前角色的体力、姿态、可用技能列表、装备信息，判断动作是否可行
• 智能体系统/玩家输入：提供意图来源。智能体决策模块或玩家按键被转换为动作指令
输出：一个ActionIntent对象，包含动作类型、目标（实体ID或坐标）、消耗资源、基础动画标识
解耦设计：动作系统不关心这个动作最终会造成什么后果，它只负责“这个人想做这件事”。战斗、生产、社交都是同一种动作指令格式。
￼
L2 物理层 ← 物理引擎
耦合关系：物理引擎是实现物理判定的唯一方式。所有涉及空间交互的判定（碰撞、射线、范围检测）都通过物理引擎完成。
依赖：
• 事物档案：读取所有实体的碰撞体形状、尺寸、位置、物理材质
• 环境系统：读取地形高度、水体区域、风力等环境物理参数
• 动作系统输出：接收ActionIntent，转换为物理世界中的具体操作（生成投射物、启动碰撞检测、发射射线）
输出：一个PhysicalResult对象，包含命中/未命中、命中位置、力道、受影响实体列表、各自的冲击参数
解耦设计：物理引擎可以替换（PhysX换Bullet），只要提供相同的查询接口（射线检测、范围查询、碰撞检测）。L3-L5完全不感知物理引擎的存在。
￼
L3 语义层 ← 标签系统
耦合关系：标签系统是物理事实转化为语义信息的唯一翻译器。
依赖：
• 事物档案：读取所有参与实体的标签列表（武器标签、目标标签、环境标签）
• 物理层输出：接收PhysicalResult，提取其中的实体ID列表，去查询标签
输出：一个SemanticEvent对象，包含源标签集合、目标标签集合、环境标签集合、物理参数（力道、距离等）
解耦设计：标签系统是完全配置驱动的，不包含任何硬编码的标签枚举。L4和L5通过字符串标签匹配，不依赖标签的创建方式。
￼
L4 效应层 ← 元素效应系统
耦合关系：元素效应系统是标签组合转化为可能效应的唯一查询服务。
依赖：
• 元素效应配置表：存储所有标签对的效应模板（如“火焰+水=蒸汽爆发”）
• 标签层级树：用于标签继承查询（如“神力”找不到直接交互时，向上查找“超自然能量”的交互）
• 语义层输出：接收SemanticEvent，用其中的标签组合去查询效应模板
输出：一个EffectTemplateList对象，包含若干EffectTemplate（效应类型、基础数值公式、附加标签、范围、持续时长模板）
解耦设计：元素效应系统只做“查询”操作，不修改任何状态。它像一个可扩展的词典，新增标签对只需添加词典条目。L5不关心这个词典是如何维护的。
￼
L5 规则层 ← 元规则引擎
耦合关系：元规则引擎是将效应模板转化为精确状态变更的唯一执行环境。
依赖：
• 元规则配置库：存储所有元规则（条件匹配→状态变更）
• 世界状态快照：读取当前角色状态（生命值、情绪、关系）、环境状态（天气、区域灵力浓度）、事物状态（耐久、元素状态）
• 效应层输出：接收EffectTemplateList，将其中的每个模板与当前世界状态结合，匹配具体元规则
输出：一个StateChangeBatch对象，包含一系列原子状态变更指令（扣减生命值、添加状态标签、修改情绪数值、触发司命叙事标记）
解耦设计：元规则引擎是纯计算模块，输入结构化数据，输出结构化变更指令。它不直接操作数据库，而是生成“变更批文”，由下游的状态管理模块执行。

五、结算链与三大核心系统的关系
• 群体模拟引擎：群体模拟中所有需要物理交互的行为（劳作、战斗、意外）都走这条链。群体模拟引擎是结算链的最大消费者——它发起大量结算请求，并消费产生的状态变更来更新角色档案。
• 角色智能体系统：智能体在决策时，需要预测行为后果。它调用结算链的模拟模式（只计算L1-L5但不实际应用状态变更），以评估选项。智能体是结算链的查询者和意图发起者。
• 司命系统：司命不参与结算链的任何计算。它只监听结算链产生的“叙事触发标记”，在合适的时机异步生成记忆和故事。司命是结算链的观察者和故事叙述者。
￼
这条结算链是整个世界的因果总线。它以极低的耦合度，将动作、物理、标签、元素、元规则五个独立系统串联成一个完整的因果推理机，同时保持各系统的可替换性和可扩展性。这就是“一个底座，无尽场景”的架构基础。
