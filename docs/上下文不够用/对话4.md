> 项目跑起来,会是一个怎么样的智能体游戏底座? 大白话举例说明

简单说，这个项目跑起来后，像是一个“AI 角色和世界规则的游戏操作系统”，不是一款已经内容完整的 RPG。

**玩家看到的基本体验**

你进入 Godot 场景，里面有几个角色和一些可交互物体。你可以：

- 和角色说话；
- 让角色尝试拿、放、搬、交换、购买、装备物品；
- 观察角色之间互相听到什么、产生什么反应；
- 看到成功或失败的交互结果；
- 看到椅子、物品、装备或环境状态发生变化；
- 在 Observatory 中查看角色、世界和 Siming 的运行状态。

**举个完整例子**

你对角色 A 说：

> “把桌上的椅子搬到门口。”

系统大致这样工作：

1. Godot 把你的输入转换成结构化意图。
2. Backend 判断角色 A 是否知道这把椅子、是否有能力搬动、距离是否足够。
3. 如果条件满足，Backend 执行抓取、搬运、放置的权威结算。
4. 世界状态变成“椅子在门口”。
5. Godot 根据这个结果更新画面。
6. 角色 B 如果在现场，可能收到这件事并产生自己的对话或反应。
7. Siming 可以观察到“场面发生变化”，提出高层次的催化建议，例如让某个角色注意到椅子被移动。

如果条件不满足，例如椅子不可搬、角色没有权限或目标位置无效，系统不会假装成功，而是返回类似：

> “无法搬运：角色当前不具备该能力。”
> “无法放置：目标位置被占用。”

**再举一个经济玩法例子**

玩家让角色购买一件装备：

> “买下这把剑并装备。”

Backend 会检查：

- 钱够不够；
- 商品是否仍可购买；
- 物品归属是否正确；
- 角色是否能装备；
- 装备后属性是否变化。

成功后，钱、物品归属、装备状态和角色属性都会通过事件记录下来，而不是只在 Godot 画面上显示一个假结果。

**它和普通游戏的区别**

普通游戏通常是：

> 玩家按键 → 本地脚本直接改场景。

这个项目希望变成：

> 玩家意图 → AI 角色理解 → Backend 权威判断 → 世界状态改变 → Godot 展示结果。

所以 Godot 更像“身体和眼睛”，Backend 才是：

- 世界规则；
- 角色行为权限；
- 物品和经济状态；
- 事件记录；
- 交互成功/失败裁决。

**当前阶段的真实边界**

现在已经能跑的是“固定场景中的智能体垂直切片”：

- 对话链路已经存在；
- 角色之间可以互相感知；
- 物体交互有成功和失败路径；
- 有抓取、搬运、放置等窄闭环；
- 有最小 Siming 反应；
- 有调试和观察面板。

但它还不是：

- 任意物体都能自然交互的开放世界；
- 每个角色都能长期自主生活的模拟器；
- 真实物理、IK、NavMesh、动作动画都完整接入的游戏；

> 帧级运动、动画、碰撞和网络系统需要做到什么?

核心原则是：

> AI 只负责决定“做什么”，不能负责每一帧怎么移动。每帧运动必须由本地实时控制器、动画系统和碰撞系统完成。

例如 AI 输出：

> “角色 A 向椅子移动并踢它。”

之后由 Godot 在每秒 60 次左右的物理更新中完成具体移动、转身、接触和动画。Backend 只负责确认动作是否合法、结算世界结果。

**1. 帧级运动**

至少需要：

- 固定物理 tick，例如 30 或 60Hz；
- CharacterMotor；
- 胶囊体移动和碰撞滑动；
- 加速度、减速度、转向、跳跃、落地；
- 地面检测、斜坡、台阶和障碍处理；
- 移动状态机，例如 idle、walk、run、attack、hit、fall；
- 动作中的移动限制和打断规则；
- 网络环境下的预测、校正和状态同步。

例如攻击动作开始后，角色不能继续以正常速度跑动；被击中时要能中断攻击并进入受击状态。

**2. 帧级动画**

每个动作不能只有一个动画文件，而要有明确的动作阶段：

```text
准备阶段  0-12 帧
攻击阶段  13-18 帧
收招阶段  19-35 帧
```

还需要：

- 动画状态机；
- 动画混合和转场；
- root motion 或代码驱动移动；
- 攻击生效帧；
- 接触帧；
- 可打断帧；
- 受击、倒地、恢复；
- IK 和手脚目标对齐；
- 不同身高、武器、姿势的动作适配。

重要的是，动画事件不能单独决定世界结果。动画显示“脚踢到了椅子”，还要由碰撞和 authority 系统确认确实发生了有效接触。

**3. 帧级碰撞**

简单动作游戏至少需要：

- 角色胶囊碰撞体；
- 环境碰撞体；
- hitbox，例如拳头、脚、武器；
- hurtbox，例如角色身体、头部；
- 碰撞层和过滤规则；
- sweep/cast 检测，避免高速动作穿透目标；
- 接触点、方向、法线和冲击结果；
- 伤害、击退、倒地、物体状态变化；
- 动态刚体的状态回流。

例如踢椅子时，需要判断：

- 脚是否进入攻击生效阶段；
- 脚和椅子的碰撞体是否真实接触；
- 接触方向和力度是否满足要求；
- 椅子是否可推动；
- 推动后的位置和旋转是什么。

当前项目中的踢椅子切片已经有动作阶段和权威结算，但还缺少完整的真实 CharacterMotor、接触检测和物理结果回流。

**4. 网络系统**

如果只是单机或本地演示，不需要一开始就做完整网络同步。

如果要支持多人或远程 AI，则需要：

- 服务器权威世界状态；
- 每个动作有 `action_id`、`actor_id`、`target_id`、`tick` 和序号；
- 输入或动作命令的确认机制；
- snapshot、插值和延迟补偿；
- 本地预测与服务器校正；
- 断线重连和 resync；
- gap/out-of-order 检测；
- authority ownership 和 handoff；
- backpressure 和过载策略；
- 只同步必要的结构化状态，不发送无意义的每帧键盘噪声。

对于这个项目，正确分工应该是：

```text
玩家输入 / AI 意图
        ↓
结构化动作请求
        ↓
Godot 本地 60Hz 运动、动画、碰撞
        ↓
Backend 权威校验和世界结算
        ↓
事件、状态快照、Godot mirror
```

而不是：

```text
LLM 每帧决定角色坐标
        ↓
Backend 每帧转发坐标
        ↓
Godot 被动播放
```

**最小可行版本**

要做一个简单的动作 RPG，第一阶段只需要：

- 单机本地 60Hz 运动；
- 一个角色状态机；
- 几个动作阶段；
- 胶囊体和简单 hitbox/hurtbox；
- 一种攻击、一种受击、一种物体交互；
- Backend 负责动作开始和结束结算；
- Godot 播放真实动画并显示结果。

例如先完成：

> 角色靠近椅子 → 播放踢击 → 真实碰撞 → 椅子被推开 → 附近 NPC 收到事件并反应。

这已经足够构成一个简单动作玩法的核心闭环。

因此，当前项目已经具备“动作玩法的权威事件和动作阶段底座”，但还需要补齐实时运动、动画和碰撞层。网络同步则应放在单机动作闭环稳定之后，否则会同时调试太多变量。

**2. `EmbodiedActionController`：主要是动作流程编排器**

[EmbodiedActionController.gd](/D:/Users/User/Documents/paralls-phase-0-demo/scripts/interaction/EmbodiedActionController.gd:5) 目前定义了完整的动作阶段：

```text

预留站位
规划接近
导航
对齐
准备
执行接触
观察结果
恢复
结束
```

它能完成：

- 校验动作路线；
- 校验 controller grant、connection epoch、outcome nonce；
- 根据 action registry 选择动作 atom；
- 按阶段调用本地播放适配器；
- 生成 trace；
- 返回成功、失败、打断、取消等结构化结果；
- 失败后恢复本地控制权。

这部分的 authority 合同和失败路径已经做得比较完整，相关 Godot probe 也已通过。

```gdscript
for phase in ORDERED_PHASES:
    _enter_phase(phase)
    _terminal_for_scenario(scenario, phase)
```

它会同步遍历所有阶段，不会真正等待角色移动、动画播放、碰撞发生或物理结算。

> 动作请求 → 播放对应阶段 → 返回“接触成功” → 权威状态变为椅子倒下

而不是：

> 角色真实走到椅子前 → 脚部 hitbox 在某一帧触碰椅子 collider → 物理系统计算冲击 → 椅子真实倒地。

`NavigationAgent3D` 和 `CollisionShape3D` 当前主要用于 probe/契约验证，并没有形成完整的导航和物理接触闭环。

| 真实导航 | 未闭合 |
| 真实接触检测 | 未闭合 |
| 真实物理反馈 | 未闭合 |
| 攻击/受击/伤害系统 | 未完成 |
| 通用动作状态机 | 未完成 |
| 网络预测与帧同步 | 未完成 |

所以当前控制器已经足够作为：

> “AI 角色提出高层动作，Godot 执行基础移动和阶段化表现，Backend 负责权威结果”的第一版底座。

但还不能直接作为：

> “角色可以实时打斗、真实碰撞、自动寻路、被击退、连招、受击和网络同步”的完整动作控制器。

下一步最关键的技术闭环不是继续增加更多 action tag，而是把 `EmbodiedActionController` 接到真实的：

1. `CharacterMotor`；
2. `NavigationAgent3D`；
3. 动作计时和异步阶段；
4. hitbox/hurtbox；
5. 真实 collider/contact query；
6. 攻击、受击和物理结果系统。

完成这一层后，当前项目才会从“动作流程演示器”升级为“简单动作玩法控制器”。

> 我们的最终目的是做一个通用智能体驱动的游戏底座,当然现在只能服务于角色扮演游戏,我们会先出一个版本,用于剧本杀类角色扮演游戏的创作,只要按要求生成资产并注入资产和设定,剧本都可以变成对应的游戏,我们需要为创作者提供什么工具和接口? 需要在公司内部做一些什么工具?

这个目标是可行的，但产品形态不应该是“把一份剧本和几个模型文件丢进去”，而应该是：

> 创作者工具把剧本转换成结构化游戏包，运行时再把这个游戏包交给 AI 角色、Backend 世界规则和 Godot 展示层执行。

可以把它理解成“剧本游戏编译器 + 智能体运行时”。

## 一、创作者最终要提供什么

创作者不应该直接编辑 JSON 或代码，而应该使用一个 Creator Studio。

### 1. 项目与 IP 工具

用于填写：

- 世界观；
- 时间、地点、阵营；
- 核心真相；
- 禁止违背的设定；
- 结局条件；
- 作品风格和语言风格。

必须区分：

- `世界客观事实`：凶手是谁、尸体在哪里；
- `角色已知事实`：某个角色知道什么；
- `角色错误认知`：某个角色以为谁是凶手；
- `玩家可见信息`；
- `主持人/导演可见信息`。

剧本杀最重要的不是让 AI 自由发挥，而是不能让 AI 泄露自己不该知道的事实。

### 2. 角色编辑器

每个角色需要配置：

- 人物身份、性格、目标；
- 秘密、动机、恐惧；
- 初始知识和记忆；
- 与其他角色的关系；
- 可以使用的技能；
- 可以观察、拿取、交易或隐藏的对象；
- 允许说出的内容；
- 不知道的内容；
- 角色被质问、威胁、诱导时的反应倾向。

角色设定不能只是一段人物小传，必须能转换成运行时的 `Actor Dossier`、知识边界、目标和行动能力。

### 3. 剧本结构编辑器

把线性剧本拆成结构化节点：

```text
场景
  └── 回合 / 时间段
        └── 剧情节拍
              ├── 进入条件
              ├── 可见事件
              ├── 隐藏事件
              ├── 角色目标
              ├── 可触发线索
              └── 结束条件
```

创作者可以配置：

- 开场；
- 场景切换；
- 时间推进；
- 角色进入和离开；
- 线索出现；
- 对话触发；
- 任务完成；
- 阵营关系变化；
- 多个结局；
- 超时、失败、僵局和提前结束。

### 4. 线索与证据工具

剧本杀的核心工具之一。

每条线索需要有：

- 线索内容；
- 所属场景和物体；
- 谁可以看到；
- 谁可以理解；
- 谁可以隐藏或销毁；
- 是否是真证据、假证据或误导；
- 与哪些事实相关；
- 被发现后的事件；
- 是否可以被其他角色传播。

例如：

> “抽屉里的血迹”是客观证据，角色 A 看见了，但角色 A 不一定知道它意味着谋杀。

### 5. 场景和物体绑定工具

美术资源不能只导入模型，还要给模型添加游戏语义：

- 这是门、桌子、椅子还是证物；
- 是否可以打开、搜索、搬动、破坏；
- 可交互距离；
- 碰撞体；
- 站位点；
- 手部接触点；
- 可播放的动作；
- 交互后的状态；
- 对应的声音、特效和 UI。

也就是说，资产必须有 `affordance` 和 `presentation binding`，否则 AI 不知道它在游戏里能做什么。

### 6. 对话、声音和 UI 工具

需要配置：

- 自由对话和关键台词；
- 角色说话风格；
- 语音绑定；
- 背景音乐和音效；
- 字幕样式；
- 角色状态面板；
- 线索面板；
- 投票和指认界面；
- 主持人/导演控制面板；
- 玩家个人秘密和任务界面。

对于剧本杀，至少要有三种视图：

- 玩家视图：只能看到自己的信息；
- 角色视图：只能看到角色允许知道的信息；
- 主持人视图：可以查看全部事实、事件和角色状态。

## 二、需要稳定定义的接口

建议先建立 typed contract，再决定具体使用 REST、WebSocket 还是 SDK。

核心数据合同至少包括：

- `ProjectManifest`：项目版本、资源、规则和运行配置；
- `WorldFact`：世界客观事实；
- `ActorDossier`：角色设定、目标、知识和能力；
- `PrivateKnowledge`：角色私有知识；
- `SceneDefinition`：场景、物体和可交互点；
- `BeatGraph`：剧本节拍和流程图；
- `ClueDefinition`：线索和证据规则；
- `RelationshipDefinition`：关系和阵营；
- `AffordanceDefinition`：物体可执行动作；
- `ActionDefinition`：动作阶段、成功条件和失败结果；
- `DialoguePolicy`：对话边界和角色表达风格；
- `PresentationBinding`：模型、动画、音频、UI 资源绑定；
- `SessionConfig`：人数、角色分配、时间限制和结局规则。

运行时则需要提供类似这些能力：

```text
创建游戏局
分配角色
进入场景
提交结构化意图
获取角色允许看到的状态
提交对话
执行调查或物体交互
发布世界事件
推进剧情节拍
检查结局
暂停、恢复、回放
```

其中最重要的约束是：

> AI 可以自由生成语言和策略，但不能直接修改核心事实、线索归属、任务状态或胜负结果。

## 三、公司内部必须建设的工具

### 1. 内容编译器

把创作者项目编译成运行时包：

```text
剧本配置
角色配置
线索配置
场景配置
资源清单
        ↓
校验
        ↓
运行时包
        ↓
Backend + Godot
```

它需要检查：

- 引用是否存在；
- 角色是否知道不该知道的内容；
- 线索是否无法获得；
- 结局是否永远无法触发；
- 场景物体是否缺少交互定义；
- 动作是否缺少动画；
- 角色是否没有可执行目标；
- 是否存在循环、死锁和无法结束的剧情。

### 2. 资产导入与绑定工具

公司内部要做统一的：

- 模型导入；
- 材质和贴图规范化；
- 动画命名和动作标签；
- 碰撞体生成；
- socket/站位点标记；
- 音频格式转换；
- TTS voice profile 管理；
- 资源版本和依赖管理。

创作者交付的美术资源必须经过标准化，不能每个项目手工接线。

### 3. AI 剧本模拟器

这是非常重要的内部工具。

它用多个模拟角色自动跑剧本，检查：

- 角色是否会卡住；
- 角色是否泄露秘密；
- 线索是否被错误传播；
- 是否存在无解场景；
- 角色是否长期重复同一句话；
- AI 是否会偏离角色设定；
- 不同玩家行为是否都能得到合理结果；
- 结局是否可以正常触发。

可以把它理解成“没有真人参加的剧本杀排练场”。

### 4. Harness 和回放系统

需要能够记录：

- 每个角色看到了什么；
- 每次模型输出；
- 每次世界事实变化；
- 每次 authority 判定；
- 每条线索传播路径；
- 每个动作成功或失败原因；
- 最终结局。

之后可以按事件回放整局游戏，定位：

> 是模型判断错了、剧本配置错了、权限错了，还是 Godot 展示错了。

当前项目已有 Event Store、authority、replay 和 Observatory，这些可以继续发展成创作者调试工具。

### 5. Prompt、模型和角色运行时管理工具

内部需要集中管理：

- 角色 prompt 模板；
- 世界事实注入模板；
- 私有知识过滤；
- 模型 provider；
- fallback 策略；
- token 和成本限制；
- 超时和降级；
- 模型版本；
- 不同项目的模型配置。

不能让每个剧本作者手工修改 prompt 代码。

### 6. 内容质量与安全检查

需要自动检查：

- 角色信息泄露；
- 不允许的事实写入；
- AI 越权修改世界状态；
- 恶意或不合适内容；
- 版权和语音授权；
- 敏感信息进入日志；
- API key 或私有素材被打包进客户端。

### 7. 发布和版本管理系统

创作者需要能够：

- 创建项目版本；
- 预览和试玩；
- 邀请测试玩家；
- 发布测试版；
- 回滚旧版本；
- 查看运行数据；
- 更新角色、资源和剧本；
- 迁移已有存档；
- 发布正式游戏包。

## 四、第一版最应该做什么

第一版不需要支持所有 RPG，而应该先把“剧本杀游戏包”做完整。

建议 MVP 只支持：

- 3 至 8 个角色；
- 1 至 3 个场景；
- 30 至 90 分钟一局；
- 对话、调查、线索、秘密、关系、投票和多结局；
- 少量物体交互；
- AI 角色自主对话和有限行动；
- 主持人/导演观察面板；
- 自动排练和回放。

第一版的产品链路应该是：

```text
创作者导入 IP 和剧本
        ↓
配置角色、线索、场景和结局
        ↓
绑定美术、动画、音乐和 UI
        ↓
自动校验和 AI 排练
        ↓
生成运行时游戏包
        ↓
玩家进入一局剧本杀
```

当前项目已经具备的，是运行时底层的一部分：

- 角色心智和角色档案；
- Event Store 和 authority；
- affordance/action registry；
- 具身动作流程；
- Godot mirror；
- Observatory 和回放。

当前最缺的不是再添加一个角色模型，而是上面的“内容生产层”：

- 剧本结构化编辑器；
- 角色和私有知识编辑器；
- 线索/证据系统；
- 场景 affordance 标注器；
- 内容编译器；
- AI 自动排练器；
- 创作者调试和发布工具。

最核心的产品判断是：

> 创作者提供“世界、角色、线索、剧情和资源”，平台负责把它们编译成可运行的智能体游戏；AI 负责在作者规定的事实和规则范围内自由发挥，而不是替作者重新发明世界真相。

> 世界模型和世界动作模型,能不能融入我们的项目?我们现在的游戏表现极度依赖3d建模,工作量很大,不知道以后能不能把项目改造成基于世界模型和其他大模型的harness底座,让角色智能体在世界模型生成的世界里交互,同时用底座来实现世界的时空记忆,并且还能让物理引擎正常工作避免世界模型消耗太大? 或者,直接用世界模型生成的可交互全套美术资源来投入底座,做好接入,实现角色智能体在世界模型生成的世界里交互.

可以融入，而且和当前项目的架构方向是兼容的。但不建议让世界模型直接取代 Backend、Godot 物理和世界权威。

更合理的目标是：

> 世界模型负责生成、理解、预测和补全世界；Backend 负责世界真相；Godot 负责近距离实时运动和物理；角色智能体负责目标、决策和行动意图。

## 推荐的整体分工

```text
IP / 剧本
   ↓
世界模型生成场景和资源
   ↓
World Pack Compiler
   ↓
实体 ID、碰撞体、导航、交互点、物理参数、资源绑定
   ↓
Backend 世界状态 + Godot 场景
   ↓
角色智能体提出行动
   ↓
World Action Model 生成行动方案
   ↓
EmbodiedActionController 执行
   ↓
Godot 物理确认结果
   ↓
Backend 写入事件和世界记忆
```

## 世界模型可以做什么

### 1. 离线生成世界和美术资源

这是近期最现实、收益最大的方向。

世界模型可以帮助生成：

- 房间、街道、建筑和地形；
- 家具、道具、服装和装饰；
- 角色外观；
- 动画候选；
- 光照和环境风格；
- 场景变体；
- 剧本对应的视觉氛围。

但生成的模型不能直接当作“可交互游戏对象”。还必须经过编译，补齐：

- 稳定的 `entity_id`；
- 物体语义类型；
- 碰撞代理；
- NavMesh 几何；
- 质量、摩擦、重量等物理参数；
- 站位点、抓取点、手部 socket；
- 可执行 affordance；
- LOD；
- 资源版本和来源。

例如世界模型生成一张桌子，平台还要知道：

```text
它是桌子
可以查看
可以放置物品
抽屉可以打开
抽屉里可以藏线索
不能被角色直接穿过
可以被推倒，但需要足够力量
```

否则它只是漂亮的模型，不是游戏对象。

### 2. 帮助角色理解世界

世界模型可以从场景中推断：

- 房间布局；
- 物体之间的空间关系；
- 哪些地方可能藏有物品；
- 哪些物体适合某种行动；
- 角色当前看到的环境；
- 场景变化后的可能影响。

但它只能生成结构化观察或建议，不能直接修改世界真相。

### 3. 预测行动结果

World Action Model 可以根据：

```text
角色能力
目标物体
当前位置
场景结构
当前状态
```

生成：

```text
行动序列
所需站位
动作阶段
预计结果
失败可能性
```

例如：

> “角色 A 想打开上锁的抽屉。”

模型可以提出：

```text
靠近抽屉
观察锁
尝试使用钥匙
如果钥匙不匹配，停止并返回失败
```

但最终能不能打开，仍然由 Backend 和 Godot 的规则、权限、碰撞及物理结果决定。

## 如何让物理引擎正常工作

不能让世界模型每一帧生成整个世界。成本太高，也容易产生几何和状态漂移。

应该采用分层模拟：

### 近距离活动区域

角色正在交互的房间使用 Godot 实时物理：

- 30/60Hz 物理 tick；
- 真实 CharacterBody；
- 碰撞体；
- hitbox/hurtbox；
- 刚体；
- NavMesh；
- 接触检测；
- 真实动作和动画。

这里的世界真相必须稳定，不能每帧被模型重写。

### 附近区域

使用简化模拟：

- 简化碰撞；
- 低频状态更新；
- 运动学对象；
- 简化 NPC 行为；
- 只保留与当前剧情有关的变化。

### 远处或未加载区域

使用：

- Backend 状态；
- 事件推进；
- 世界模型预测；
- 低成本的抽象模拟。

当角色接近时，再根据事件和快照加载成真实场景。

这样可以做到：

> 眼前的桌子、角色和线索是真实可交互的；远处的城市和 NPC 不需要一直运行完整 3D 物理。

## 世界的时空记忆怎么做

世界模型可以参与记忆，但不能成为唯一记忆源。

推荐分成三层：

### 客观世界记忆

由当前项目已有的 Event Store、world fact、snapshot 保存：

- 谁在什么时候进入房间；
- 哪件物品何时被移动；
- 哪条线索何时被发现；
- 哪个角色是否真的听见某句话；
- 世界状态如何变化。

这是唯一的权威真相。

### 角色私有记忆

每个角色单独保存：

- 自己看到的；
- 自己听到的；
- 自己推断的；
- 自己记错的；
- 对其他角色的判断；
- 尚未解决的目标和怀疑。

不同角色不能共享不该共享的记忆。

### 世界模型记忆

用于：

- 语义检索；
- 场景摘要；
- 长时间事件压缩；
- 空间关系查询；
- 行动结果预测；
- 生成下一步行动候选。

它是“记忆助手”和“预测器”，不是世界真相数据库。

## 能不能直接使用世界模型生成的完整可交互美术资源

可以，但必须经过一层 `World Pack Compiler`。

这个编译器要把世界模型输出转换成项目运行时能够理解的包：

```text
WorldPack
├── entities
├── scenes
├── colliders
├── navigation
├── affordances
├── physics_profiles
├── action_bindings
├── actor_spawn_points
├── clue_bindings
├── audio
├── ui_bindings
└── provenance
```

其中：

- `entities` 定义稳定对象；
- `colliders` 给物体生成简化碰撞；
- `navigation` 生成导航区域；
- `affordances` 定义可执行动作；
- `physics_profiles` 定义重量、摩擦和刚体属性；
- `clue_bindings` 把剧本线索绑定到具体物体；
- `provenance` 记录资源来源和版本。

如果没有这一层，世界模型生成的资源只能作为背景展示，不能可靠地参与剧本、交互、记忆和物理。

## 最适合当前第一版的路线

剧本杀第一版不建议一开始做“运行时无限生成世界”，而应该做：

1. 世界模型离线生成场景和美术资源；
2. 创作者在工具中确认场景、线索和交互；
3. 编译成稳定的 `WorldPack`；
4. Godot 加载生成后的世界；
5. Backend 保存世界真相和剧本进度；
6. World Action Model 辅助角色计划行动；
7. 关键交互由 Godot 物理和 Backend 权威结算；
8. 远处和非关键区域再使用世界模型做低成本模拟。

这样既能大幅降低人工建模工作量，又不会让关键线索、角色行动和物理结果变得不可复现。

最终可以把项目发展成：

> 一个多模型智能体游戏 Harness：角色模型负责思考，世界模型负责理解和生成环境，动作模型负责提出行动，Backend 负责真相和记忆，Godot 负责身体、画面和近场物理。

但要避免一个核心误区：

> 生成式世界模型可以生成“看起来像世界”的内容；只有经过实体化、语义化、碰撞化和权威化之后，它才真正成为游戏世界。

> 如果有一天世界动作模型可以做到低成本实时使用,那项目能不能作为harness去包装它,从而实现AI游戏并且可以作为机器人的大脑沙盒(脑中预演),就像codex对于gpt模型而言.

能，而且这是当前项目很自然的长期方向。

但前提是把项目从“RPG 运行时”进一步抽象成：

> 世界动作模型的执行、记忆、仿真、验证和安全 Harness。

这和 Codex 与 GPT 的关系很像：

| Codex + GPT | 未来本项目 + 世界动作模型 |
|---|---|
| 代码仓库 | 世界状态和环境 |
| 文件、终端、工具 | 感知、查询和行动接口 |
| Git、测试、回放 | 世界记忆、轨迹和仿真回放 |
| 编译器和测试系统 | 物理引擎和世界规则 |
| Codex 执行工具调用 | 动作模型执行角色/机器人行动 |
| 验证器 | 碰撞、权限、安全和结果校验 |

模型本身只负责：

> 看到了什么、想做什么、下一步怎么做。

Harness 负责：

> 它能看到什么、允许做什么、行动是否成功、世界发生了什么、能否回放和验证。

## 未来应该形成的结构

```text
世界动作模型
      ↓

      ↓
统一观察接口 / 统一动作接口
      ↓
World Action Harness
      ├── 世界状态
      ├── 物理模拟
      ├── 时空记忆
      ├── 角色私有视角
      ├── 行动执行器
      ├── 权限和安全约束
      ├── 分支预演
      ├── 回放与评估
      └── Godot / 机器人 / 其他环境适配器
```

对于 AI 游戏：

```text
模型 → 角色意图 → 游戏动作 → Godot 物理 → 世界事件
```

对于机器人脑中预演：

```text
模型 → 机器人动作计划 → 仿真环境预演 → 安全检查
      → 真实机器人执行 → 真实结果反馈
```

两者可以共用同一套：

- 观察协议；
- 动作协议；
- 世界状态；
- 目标和任务；
- 记忆；
- 轨迹记录；
- 分支回放；
- 结果评估；
- 安全约束。

差别只是底层环境不同。

## 当前项目已经具备的基础

当前项目中的这些部分正好可以成为未来 Harness 的核心：

- Backend 世界权威；
- Event Store 和 replay；
- 结构化 action request；
- affordance/action registry；
- InteractionSession；
- EmbodiedActionController；
- Godot 本地高频执行；
- 角色私有感知和记忆；
- Observatory；
- mirror 和运行时状态投影。

因此，未来世界动作模型不应该直接控制 Godot 节点坐标，而应该输出类似：

```text
目标：靠近椅子
行动：踢击
目标对象：chair_01
期望结果：使椅子偏转
置信度：0.86
```

然后由 Harness：

1. 检查角色是否知道椅子存在；
2. 检查角色是否有能力踢击；
3. 规划站位；
4. 运行物理和动作；
5. 判断是否真实接触；
6. 写入世界事件；
7. 把结果反馈给模型。

## “脑中预演”需要什么

真正的机器人脑中预演，不只是让模型生成一段动作，而是要支持：

- 当前世界快照；
- 机器人自身状态；
- 目标状态；
- 传感器噪声；
- 可能的动作序列；
- 多分支 rollout；
- 失败预测；
- 碰撞和安全检查；
- 行动成本估算；
- 选择最优方案；
- 执行后的结果回写。

例如机器人要拿起桌上的杯子：

```text
方案 A：正面靠近，可能撞到桌角
方案 B：从侧面接近，路径更长但安全
方案 C：杯子被遮挡，抓取成功率低
```

动作模型提出这些方案，Harness 在模拟环境中预演，再选择方案 B。真实机器人执行后，结果再写回记忆，修正下一次计划。

## 但 Godot 不能独自承担机器人沙盒

Godot 很适合：

- 角色身体表现；
- 视觉环境；
- 交互演示；
- 剧本游戏；
- 中低精度的动作预演。

机器人需要更强的物理和传感器模拟能力，例如：

- 关节动力学；
- 接触力；
- 摩擦和柔性物体；
- 相机、深度、触觉传感器；
- 控制周期；
- 真实硬件接口；
- sim-to-real 校准。

所以未来最好把物理引擎抽象成适配器：

```text
World Action Harness
  ├── Godot Adapter
  ├── Headless Game Simulator
  ├── Robotics Physics Adapter
  └── Real Robot Adapter
```

Godot 是一个环境适配器，而不是整个机器人模拟底座。

## 需要提前抽象的部分

为了将来支持世界动作模型，当前项目需要逐步避免把核心逻辑绑定在 RPG 名词上：

- `Character` 抽象成 `Agent`；
- `Action` 抽象成通用动作；
- `Scene` 抽象成环境；
- `Affordance` 保留为通用能力；
- `WorldFact` 保留为客观状态；
- `InteractionSession` 抽象为执行会话；
- Godot 角色控制器抽象成 embodiment adapter；
- RPG 任务、线索、装备成为具体插件。

这样，剧本杀只是第一个应用：

```text
Agentic RPG
      ↓
World Action Harness
      ├── 剧本杀
      ├── 开放世界 RPG
      ├── 生存模拟
      ├── 机器人脑中预演
      └── 其他智能体环境
```

## 最大的技术前提

即使未来世界动作模型足够便宜、足够快，也还必须满足：

- 有稳定的观察输入；
- 有明确的动作输出协议；
- 支持角色或机器人私有视角；
- 能处理部分可见信息；
- 能表达不确定性；
- 能被暂停、回放和重演；
- 能在固定时间预算内输出；
- 不能直接越过物理和安全层；
- 结果可以被环境验证。

如果模型只能生成视频或画面，而不能给出稳定的实体、动作和状态接口，那么它只能用来做视觉生成，不能直接作为可靠的游戏或机器人行动模型。

最终可以把项目发展成：

> 一个类似 Codex 的世界行动 Harness：把世界动作模型接入真实或虚拟环境，为它提供世界、记忆、工具、身体、物理、权限、回放和验证，让同一个智能体模型既能驱动 AI 游戏角色，也能在机器人仿真环境中进行脑中预演。

当前最现实的演进顺序是：

1. 剧本杀内容编译器；
2. 世界模型辅助生成场景和资产；
3. World Pack Compiler；
4. World Action Model Adapter；
5. headless 世界模拟和分支预演；
6. 时空记忆与轨迹评估；
7. 独立的机器人物理适配器；
8. 最后再接入真实机器人。

> 有办法让世界模型和多模态模型,推理模型一起在我们的harness包装下合作工作吗?区分ai游戏和机器人沙盒两种情况来说

有，而且这很可能是 Harness 最有价值的方向。

但不能让三个模型每帧互相自由聊天，而应该让它们处在不同层级，由 Harness 统一调度、隔离上下文并验证结果。

## 三种模型的分工

| 模型 | 主要职责 | 不应该直接做什么 |
|---|---|---|
| 多模态模型 | 看图像、视频、音频，识别角色、物体、空间关系和状态 | 直接修改世界真相、直接驱动电机 |
| 世界模型 | 维护或预测环境变化，进行未来状态预演 | 直接宣布物理结果已经发生 |
| 推理模型 | 理解目标、角色动机、任务和长期策略，生成行动计划 | 直接控制每一帧位置或关节 |
| 世界动作模型 | 把状态和计划转换成动作序列或动作策略 | 绕过权限、碰撞和安全层 |

真正的最终裁决仍然由：

- AI 游戏：Backend 世界权威 + Godot 物理；
- 机器人：状态估计器 + 物理仿真 + 安全控制器 + 机器人硬件。

## Harness 中间层

Harness 需要提供一个带版本号的共享状态黑板，而不是让模型之间直接传自然语言。

核心消息可以是：

```text
ObservationFrame
WorldStateSnapshot
PrivateAgentView
ReasoningPlan
WorldActionProposal
PredictedOutcome
ExecutionResult
MemoryWrite
```

每条消息都应包含：

- `world_version`；
- `observation_id`；
- `actor_id`；
- `target_refs`；
- `preconditions`；
- `expected_effects`；
- `confidence`；
- `expires_at`；
- `trace_id`。

如果模型基于旧世界状态做计划，Harness 就拒绝执行并要求重新规划。

## AI 游戏里的协作方式

以剧本杀为例：

```text
Godot画面/声音
      ↓
多模态模型：识别谁在房间、桌上有什么、谁听到了声音
      ↓
Backend：合并客观世界事实和角色私有视角
      ↓
推理模型：判断角色目标、怀疑、对话策略
      ↓
世界动作模型：提出调查、靠近、隐藏、质问等动作
      ↓
Action Controller：转换成结构化动作阶段
      ↓
Godot + Backend：执行、碰撞、结算
      ↓
Event Store：记录事件和记忆
```

例如角色 A 看到角色 B 从抽屉旁离开：

- 多模态模型判断“B 离开了抽屉区域”；
- 世界模型推测“抽屉可能被打开过”；
- 推理模型根据 A 的性格和目标决定是否追问；
- 世界动作模型提出“靠近抽屉并搜索”；
- Backend 判断 A 是否有权限、是否真的能看到线索；
- Godot 执行搜索动作；
- 世界事实更新为“线索已被 A 发现”。

这里：

- 多模态模型负责看见；
- 世界模型负责预测和补全；
- 推理模型负责想；
- 动作模型负责提出怎么做；
- 游戏规则负责确认到底发生了什么。

AI 游戏可以允许推理模型和对话模型较自由地发挥，但核心真相、线索、身份、胜负和物体状态不能由模型直接写入。

## 机器人沙盒里的协作方式

机器人场景需要更严格的分层：

```text
相机 / 深度 / 触觉 / 关节传感器
      ↓
多模态模型和状态估计器：识别环境与机器人姿态
      ↓
世界模型：预测物体运动、遮挡和接触结果
      ↓
推理模型：分解长期任务
      ↓
世界动作模型：生成候选轨迹或动作策略
      ↓
物理仿真：在沙盒中预演
      ↓
安全控制器：检查速度、力、碰撞和工作空间
      ↓
真实机器人执行
      ↓
传感器反馈和事件记忆
```

例如机器人要拿一个杯子：

1. 多模态模型识别杯子、桌面和障碍物。
2. 推理模型决定先清理挡路物，还是从侧面抓取。
3. 世界动作模型生成几个抓取方案。
4. Harness 在仿真中预演这些方案。
5. 物理引擎检查是否会碰撞、滑落或超过关节限制。
6. 安全控制器只允许合格方案发送给机器人。
7. 真实机器人执行。
8. 真实传感器结果回写，修正模型记忆。

机器人场景中，推理模型可以几秒调用一次，动作控制器可能需要几十到几百赫兹运行。绝不能让推理模型直接承担电机控制。

## 两种场景的核心区别

| 项目 | AI 游戏 | 机器人沙盒 |
|---|---|---|
| 主要目标 | 剧情、关系、探索、交互 | 完成真实任务 |
| 多模态输入 | 画面、声音、对话 | 相机、深度、触觉、关节状态 |
| 世界模型 | 场景理解、分支预测、背景模拟 | 动力学、遮挡、接触和未来状态预测 |
| 推理模型 | 角色动机、任务、社交策略 | 长期任务分解和规划 |
| 动作模型 | 语义动作和动作阶段 | 轨迹、控制策略和动作序列 |
| 最终权威 | 游戏规则和 Godot/Backend | 物理仿真、安全控制器和硬件 |
| 容错 | 可以失败、重试、回放 | 必须安全停止，不能撞坏设备 |

## 需要在当前项目上增加什么

当前项目已有：

- Event Store；
- 世界 authority；
- 角色私有视角；
- action/affordance registry；
- EmbodiedActionController；
- Godot 本地执行；
- replay 和 Observatory。

还需要新增一层“多模型编排运行时”：

1. Model Gateway
   统一接入多模态模型、世界模型、推理模型和动作模型。

2. Model Scheduler
   按实时性调度模型，而不是所有模型每帧运行。

3. Typed Blackboard
   保存当前世界快照、角色视角、计划、预测和执行结果。

4. Rollout Engine
   支持从同一个世界快照分叉出多个未来方案。

5. Conflict Resolver
   处理多个模型意见冲突，优先服从权限、物理和安全规则。

6. Memory Layer
   保存客观事件、角色私有记忆和世界模型摘要，但不允许摘要取代客观事实。

7. Evaluation and Replay
   比较不同模型计划，分析失败原因，支持整局游戏或整段机器人行为回放。

8. Environment Adapters
   至少提供 Godot、headless 游戏模拟器、机器人物理模拟器和真实机器人接口。

未来的项目可以变成：

```text
      ↓
```

8. 结果会回写事件、记忆和其他角色的感知。
9. 角色会根据世界反馈继续决策。

这已经不是普通的“AI 对话 NPC”，而是：

> 有身体、有视角、有能力限制、能在 3D 世界中行动，并且行动结果会改变世界的角色智能体运行时。

当前具身链路大致是：

```text

  ↓

  ↓

  ↓
InteractionSession / Authority
  ↓
Godot 本地动作执行
  ↓
世界状态结算
  ↓
事件、记忆和其他角色感知
```

这条链路已经有不少真实实现和 bounded runtime proof。

## 当前真正完成的是什么

当前更准确的定位是：

> 结构化具身智能运行时 + advisory VLA 感知子链。

也就是说，角色已经能在 3D 场景里具身行动，但它当前的行动主要由：

- 角色心智；
- 结构化 world facts；
- affordance；
- action registry；
- interaction orchestration；
- authority settlement；

共同驱动。

VLA 目前主要负责：

- 帮角色理解视觉空间信息；
- 补充不确定的视觉发现；
- 提供候选实体和空间关系；
- 支持 active perception；
- 给后续决策提供 advisory evidence。

它还没有成为：

> 看到画面后直接决定“向左走 2 米、转身、抬脚、踢击”的实时动作模型。

## 这和完整 VLA 还差什么

真正完整的 VLA 具身闭环应该是：

```text
视觉/音频/状态输入
  ↓
VLA 感知
  ↓
目标和动作预测
  ↓
动作轨迹或 action atoms
  ↓
实时身体控制
  ↓
碰撞和物理反馈
  ↓
下一次感知
```

当前缺口主要是：

- VLA 结果还不能生成正式的 action proposal；
- 没有把 VLA 结果稳定桥接到 Action Controller；
- Action Controller 的导航和接触仍有 probe/演示性质；
- 真实动作时序还不是异步、可中断的运行过程；
- 真实 hitbox/hurtbox 和接触检测不完整；
- 真实物理反馈回流不完整；
- VLA 还不是每个动作周期都参与的闭环；
- 当前 live provider 证据仍受配置、样本覆盖和新鲜性限制。

因此，当前还不能说：

> “VLA 已经控制角色在 3D 世界里自主行动。”

更准确的说法是：

> “角色智能体已经具备 3D 具身运行时，VLA 已经作为受约束的视觉空间感知能力接入，当前仍处于 advisory 和 bounded interaction 阶段。”

## 空间方面：有空间身份，但不等于有精确三维位置


这对 grounding 很重要，可以避免模型凭空编造实体 ID。

### 精确空间数据

`RawFactWorld` 模型支持：

```python

```

但当前 [l1_fact_projection.py](/D:/Users/User/Documents/paralls-phase-0-demo/backend/app/world_runtime/l1_fact_projection.py) 的事实投射逻辑主要输出：

- 是否可见；
- 是否被遮挡；
- 是否可达；

- XYZ 坐标；
- 旋转；
- 相对距离；
- 速度；
- bounding box；
- 目标姿态；
- 相机坐标到世界坐标变换；

填入 `RawFactWorld`。

因此当前准确的说法是：

> 系统具备时空身份和空间 grounding，但目前不是每一条 VLA/事实信息都带有可直接用于物理计算的精确三维 pose。

- TTS 和对话协议。

应该下沉到 3D adapter：

- `CharacterMotor`；
- `CharacterBody3D`；
- `NavigationAgent3D`；
- 3D collider；
- Skeleton/IK；
- root motion；
- 3D 物理；
- 3D animation playback。

同时新增：

- `CharacterMotor2D`；
- `TilemapEnvironmentAdapter`；
- `StagePresentationAdapter`；
- `MediaTimelineAdapter`；
- `CanvasAnchorResolver`；
- `HotspotInteractionAdapter`。

## VLA 也可以服务 2D

当前 VLA 输入已经有视觉 artifact、空间引用、场景引用和 grounding catalog。只需要扩展 coordinate space 和 artifact 类型，就可以处理：

- 2D 截图；
- 像素地图；
- Live2D 画面；
- UI 热点；
- 视频帧；
- 图文界面。

不过对于 Live2D 和互动视频，VLA 不一定是主要感知来源。很多状态本来就应该由结构化事实直接提供：

```text
当前对话角色 = char_a
视频时间 = 32.4 秒
可点击热点 = drawer_handle
当前剧情节拍 = reveal_clue_03
```

模型只处理真正需要理解的内容，避免让视觉模型重复读取已经明确的结构化状态。

## 最现实的抽取顺序

建议分四步：

1. 把 Backend 核心合同从 3D 名词中解耦。
2. 先实现一个 Godot 2D adapter。
3. 用同一套角色、剧本、线索和事件做一个 2D 剧本杀版本。
4. 再增加 Live2D、图文和视频舞台适配器。

第一版 2D 目标可以是：

> 3 至 8 个角色、多个场景、角色私有线索、自由对话、点击调查、关系变化、投票和多结局。

这会最大化复用当前已有的角色智能体和世界权威，同时避开 3D 动画、骨骼和物理的大量工作。

最终定位可以是：

> 一个与表现形态无关的智能体游戏核心，加上 3D、2D、Live2D、像素和互动视频等不同的 embodiment/presentation adapter。

所以答案是：**可以抽，而且值得抽；但不是把当前 Godot 3D 工程复制一份改成 2D，而是把 Backend 的智能体、世界、剧本、记忆和权威层提升为通用核心，再让 3D 和 2D 都成为它的表现适配器。**

> Live2D和VRM能不能结合,然后结合玩家的触屏或隔空手势控制和角色动作交互?因为我想在未来能实现VR眼镜+手套的第一视角游戏,尤其是用于AI陪伴.

可以，而且这条路线很适合 AI 陪伴。但要区分：

> Live2D 和 VRM 可以共享同一个“角色智能体”，但不应该强行共用同一个身体渲染系统。

可以把它理解成：

- Live2D：角色在手机、桌面、聊天窗口里的形态；
- VRM：角色进入 3D/VR 世界后的身体；
- Backend：两种形态背后的同一个人格、记忆、关系和状态。

## 推荐架构

```text
共享角色智能体
├── 人格
├── 记忆
├── 情绪和关系
├── 目标
├── 对话
└── 行动意图
        ↓
Embodiment Adapter
├── Live2D Adapter
├── VRM Adapter
├── 2D Adapter
└── XR/Robot Adapter
        ↓
对应的表现和交互
```

例如用户在手机上和 Live2D 角色聊天，角色记住了这段关系。之后用户戴上 VR 眼镜，进入同一个世界，角色以 VRM 形态出现，仍然保留同样的记忆和人格。

## Live2D 和 VRM 怎么结合

有三种方式。

### 1. 同一个角色的不同终端形态

这是最推荐的方式：

- 手机、桌面：Live2D；
- 普通 3D 游戏：VRM；
- VR 眼镜：VRM；
- 聊天界面：头像、表情和语音。

共享：

- `actor_id`；
- 人格；
- 记忆；
- 关系；
- 当前情绪；
- 对话上下文；
- 世界状态。

不共享：

- 骨骼；
- 3D 碰撞；
- IK；
- 3D 动画；
- Live2D 参数本身。

### 2. VRM 角色旁边显示 Live2D 窗口

例如 VR 世界中出现一个悬浮的 Live2D 头像，用于：

- 对话；
- 情绪放大；
- 角色状态；
- 小地图；
- 记忆回顾；
- 非现实化的心理表现。

这时 Live2D 是 UI/叙事表现，VRM 是实际身体。

### 3. Live2D 作为 VR 中的 2D 角色

可以让 Live2D 角色存在于 VR 空间中的一块屏幕、书本、终端或魔法窗口里。但它不是真正的立体角色，不能自然参与：

- 绕行；
- 遮挡；
- 真实抓取；
- 体积碰撞；
- 第一视角近距离身体交互。

## 触屏和隔空手势怎么接入

输入不应该直接送给 AI 模型，而要经过意图转换：

```text
触屏 / 手势 / 语音 / 视线
        ↓
Input Adapter
        ↓
Gesture / Touch Intent
        ↓
Affordance 检查
        ↓
Interaction Session
        ↓
角色动作、对话和情绪反馈
```

例如：

| 用户输入 | 结构化意图 |
|---|---|
| 点击角色 | `focus_actor` |
| 长按角色 | `hold_attention` |
| 拖动物品 | `move_object` |
| 指向角色 | `point_at_actor` |
| 捏合 | `pinch` |
| 握拳 | `grab` |
| 挥手 | `wave` |
| 伸手靠近 | `offer_hand` |
| 抚摸头部 | `touch_head` |
| 推开角色 | `push_away` |

AI 可以根据意图产生人格化反应，但是否真的能触碰、推动或拿取，仍然由交互和物理系统判断。

## 未来 VR 眼镜 + 手套的结构

```text
VR 头显
├── 头部姿态
├── 视线
├── 摄像头
└── 空间定位

手套 / 手部追踪
├── 手掌位置
├── 手指姿态
├── 抓握状态
├── 接触压力
└── 触觉反馈

        ↓
XR Input Adapter
        ↓
HandPose / Gaze / Gesture / Haptic Contract
        ↓
本地 60Hz 以上交互与 IK
        ↓
Backend 权威世界状态
        ↓
AI 角色决策和反馈
```

VR 中最重要的原则是：

> 用户自己的手和身体必须本地实时控制；AI 角色的动作也必须由本地动画、IK 和物理执行；模型只负责较高层的回应和行动意图。

不能让大模型直接控制用户手部的每一帧，也不能让模型直接输出 VRM 骨骼坐标。

## AI 陪伴的具体体验

例如用户伸手去摸角色的头：

1. 手套或手部追踪得到手掌和手指姿态。
2. 本地 XR 系统检测是否接近角色头部。
3. 交互系统判断角色是否允许这类接触。
4. Backend 生成一个结构化事件：

```text
actor: player
action: touch
target: companion
body_region: head
contact: accepted
```

5. 角色智能体根据关系、性格、当前情绪决定反应：
   - 亲近地低头；
   - 抬手挡开；
   - 询问你在做什么；
   - 害羞；
   - 没有反应。
6. VRM 播放对应表情、眼神、身体动作和语音。
7. 事件进入角色记忆和关系状态。

这里最重要的是：

> 玩家动作是现实输入，角色反应是智能体决定，最终表现由 XR/VRM 运行时完成。

## 当前项目可以复用什么

当前项目已经具备可复用的部分：

- 角色智能体和人格；
- 对话、记忆和关系；
- 角色私有视角；
- InteractionSession；
- affordance/action registry；
- authority settlement；
- Godot 本地动作执行；
- VLA 感知 advisory；
- TTS 和 voice profile；
- 事件记录和 replay。

还没有完成的部分包括：

- VRM avatar adapter；
- OpenXR 集成；
- 手部追踪和手套 SDK；
- Gaze adapter；
- 手部和身体 IK；
- VRM 表情、Look-at、Spring Bone；
- 手部碰撞和接触检测；
- 触觉输出；
- VR 中的第一视角移动和舒适性控制；
- 90Hz 左右的稳定本地 XR 渲染；
- XR 断线和模型延迟时的本地 fallback。

VRM 本身只是角色模型和骨骼格式，不包含：

- AI；
- 物理；
- 手势识别；
- 触觉；
- 网络；
- 记忆；
- 世界规则。

这些仍然由项目底座提供。

## 最现实的演进顺序

1. 先抽象共享的 `ActorState`、`EmotionState`、`PresentationState`。
2. 增加 Live2D adapter，让同一个角色能以 2D 形态运行。
3. 增加 VRM adapter，让角色可以进入普通 Godot 3D 场景。
4. 接入 OpenXR 和头显姿态。
5. 接入手部追踪，再接手套和触觉。
6. 实现手部 IK、接触检测和简单物理交互。
7. 把触摸、指向、抓取、拥抱、推开等变成通用 affordance。
8. 最后再做长期记忆、情绪关系和更强的自主陪伴行为。

最终形态可以是：

> Live2D 是角色的桌面和手机身体，VRM 是角色的 3D 身体，XR 和手套是玩家的身体输入，当前项目的智能体运行时则负责让这个角色拥有连续的人格、记忆、关系和行为。

这条路线可行，而且 AI 陪伴会比单纯聊天更有价值，因为角色不只是“会说话”，还会看见你、回应你的动作、记住互动，并在不同终端中保持同一个身份。

> 原来VRM是用于3d的,那能不能直接结合到我们当前的项目里

可以，而且 VRM 很适合直接接入当前项目。

当前项目本身就是 Godot 3D 架构，VRM 可以作为现有角色的“视觉身体”，替换现在的 `KnightRoleSkin` 或其他角色皮肤，而不需要重写角色智能体、Backend 或世界权威系统。

## 当前项目中的对应关系

```text
Character Agent / Backend
        ↓
结构化角色状态、动作和对话
        ↓
CharacterReplica
        ├── CharacterMotor：移动、跳跃、碰撞
        ├── VRMRoleSkin：模型、骨骼、表情、动画
        └── InteractionController：动作阶段和交互
```

VRM 主要替换这一层：

```text
KnightRoleSkin → VRMRoleSkin
```

Backend 仍然只发送：

- 角色状态；
- 角色动作意图；
- 对话和情绪；
- 目标对象；
- 结构化交互结果。

不应该让 Backend 直接处理 VRM 的骨骼坐标。

## 第一阶段可以直接实现

先把一个 VRM 角色放进当前 `CharacterReplica` 场景，支持：

- idle；
- walk；
- run；
- jump；
- speak；
- look-at；
- 基础表情；
- 基础动作；
- 与现有角色智能体绑定；
- 与当前场景和世界交互。

这一步基本不需要改变：

- Character Agent；
- Event Store；
- authority；
- affordance；
- InteractionSession；
- 对话系统；
- Godot mirror。

只需要实现 VRM 的表现适配器，例如：

```text
VRMRoleSkin
├── set_state()
├── set_motion_profile()
├── play_reviewed_action_atom()
├── restore_reviewed_action_playback()
├── apply_presentation_input()
└── set_expression()
```

这些接口对应当前项目已经存在的角色表现合同。

## 需要补充的 VRM 专用部分

VRM 模型本身不自动提供完整游戏功能，还需要：

- VRM 1.0 导入插件或运行时；
- humanoid bone mapping；
- AnimationPlayer/AnimationTree；
- 表情和 blend shape 绑定；
- Look-at；
- Spring Bone；
- 角色胶囊碰撞体；
- 手、脚、身体的交互碰撞代理；
- 站位点和抓取点；
- IK；
- 动画和动作 atom 绑定；
- VRM 模型的材质、光照和性能处理。

需要特别注意：

> VRM 的网格和骨骼是视觉表现，不等于游戏物理碰撞。

通常应该是：

```text
CharacterBody3D
  ├── CapsuleCollision
  ├── NavigationAgent3D
  ├── Interaction Proxies
  └── VRM Visual Root
       ├── Skeleton
       ├── Meshes
       ├── Expressions
       └── Spring Bones
```

也就是由 `CharacterBody3D` 负责世界移动和碰撞，VRM 负责身体表现。

## 当前项目不能直接做到的部分

“把 VRM 文件复制进项目就自动完全接入”目前不行，主要原因是：

- 不同 VRM 模型的骨骼命名和动画质量不同；
- 有些模型没有可用的动作资源；
- 表情参数不一定统一；
- 手部、脚部和物体接触需要额外 IK；
- 当前动作控制器仍然是 reviewed action atom 模式；
- 真实抓取、触碰和物理交互还没有完全闭合。

所以第一阶段应当是：

> VRM 作为现有角色的替换皮肤，先接入对话、移动、基础表情和有限动作。

之后再扩展：

> VRM + 手部 IK + 物体抓取 + 第一视角交互 + VR 设备。

## 最现实的接入顺序

1. 选择一个 VRM 1.0 模型并确认授权。
2. 接入 Godot VRM importer/runtime。
3. 创建 `VRMRoleSkin`。
4. 让它实现现有 `CharacterReplica` 的表现接口。
5. 接入 idle/walk/run/speak/look-at。
6. 给角色补标准胶囊碰撞和交互代理。
7. 运行现有角色、对话和具身交互验证。
8. 再增加表情、手部 IK、抓取和 VR 输入。

结论是：

> VRM 可以直接成为当前项目的 3D 角色表现层，而且是实现 AI 陪伴、3D 角色和未来 VR 交互的合适入口。当前项目的核心智能体和世界系统可以保留，主要工作集中在 VRM 导入、角色表现适配、动画、IK 和交互代理上。

> 用VRM和用3d建模绑骨后导入到godot里,会有什么区别,优劣怎么分析,分别更适合什么情况?

核心区别是：

> VRM 是“标准化的人形角色资产格式”；
> 自定义 3D 建模绑骨是“为某一款游戏定制的角色生产管线”。

两者不是高低关系，而是适用场景不同。

| 维度 | VRM | 自定义建模绑骨 |
|---|---|---|
| 接入速度 | 快，适合批量导入 | 慢，每个角色都要处理 |
| 角色互换 | 强，标准化程度高 | 弱，通常绑定具体项目 |
| 人形骨骼 | 有统一 humanoid 约定 | 可以完全自定义 |
| 表情和 Look-at | 通常已有标准支持 | 可做得更强，但需自行制作 |
| 动画 | 仍需另外提供或重定向 | 可针对角色精确制作 |
| 物理 | 常有 Spring Bone 等基础能力 | 可定制完整物理和交互 |
| 画面质量 | 取决于 VRM 作者，差异大 | 可完全按项目要求控制 |
| 非人形角色 | 不适合 | 更适合 |
| 高强度战斗 | 需要额外动作和 IK | 更适合定制 |
| 创作者资产接入 | 非常适合 | 接入成本高 |
| IP 独占性 | 需要严格检查授权 | 更容易保持独占资产 |
| 运行依赖 | 需要 VRM importer/runtime | 通常依赖普通 Godot 资源流程 |

## VRM 的优势

VRM 很适合当前项目的几个目标：

- 快速把 AI 角色放进 3D 场景；
- 批量接入不同角色；
- AI 陪伴；
- 社交、剧情和轻交互 RPG；
- 用户自定义角色；
- 未来手机、桌面、普通 3D 和 VR 多端复用；
- Creator Studio 让创作者上传角色后快速试玩。

它通常已经包含或约定了：

- 人形骨骼映射；
- 表情；
- Look-at；
- 头发、衣服等 Spring Bone；
- 角色元信息；
- 基础人形结构。

因此非常适合：

> “我有很多角色设定，需要快速让它们在游戏里说话、走动、表达情绪。”

## VRM 的限制

VRM 并不等于“导入后什么都有”。

仍然需要补：

- 行走、攻击、受击等动作；
- 动作重定向；
- IK；
- 手部抓取点；
- 角色碰撞体；
- 武器和装备 socket；
- 物体交互代理；
- LOD 和性能优化；
- 适合游戏的材质；
- 动画阶段和 action atom 绑定。

而且 VRM 角色质量差异很大：

- 有些模型只适合站立聊天；
- 有些没有合适的手指骨骼；
- 有些脸部表情不足；
- 有些拓扑不适合高强度动作；
- 有些模型的材质或授权不能用于商业产品。

所以 VRM 更像：

> 标准化的角色入口，不是完整的游戏角色包。

## 自定义建模绑骨的优势

自定义资产更适合：

- 核心 IP 主角；
- 高质量剧情演出；
- 高强度动作战斗；
- 复杂武器和装备；
- 精确的手部交互；
- 特殊体型；
- 怪物、动物、机械体；
- 复杂服装和身体物理；
- 对面部、肌肉、表情有较高要求的角色。

它的优势是可以完全控制：

- 骨骼结构；
- 动画；
- 面部 rig；
- 碰撞体；
- IK；
- 动作节奏；
- LOD；
- 材质；
- 物理；
- 角色和场景的配合。

缺点是成本高。每一个角色都可能需要单独处理：

- 绑骨；
- 权重；
- 表情；
- 动画；
- 动作重定向；
- 碰撞；
- 装备；
- 性能优化；
- Godot 导入问题。

## 对当前项目最适合的方案

建议采用混合方案：

```text
Shared Actor Runtime
        ↓
        ├── VRMRoleSkin
        ├── CustomRoleSkin
        ├── Live2DRoleSkin
        └── RobotEmbodimentAdapter
```

Backend、角色智能体、记忆、关系、对话、authority、action contract 都共用。

### VRM 适合

- 普通 NPC；
- AI 陪伴角色；
- 创作者快速生成的角色；
- 大量支线角色；
- 社交和剧情 RPG；
- 早期原型；
- VR 中可替换的陪伴角色；
- 需要跨项目、跨平台复用的角色。

### 自定义模型适合

- 核心主角；
- 关键反派；
- 重要剧情角色；
- 战斗 Boss；
- 有复杂装备和动作的角色；
- 需要精确接触和物理反馈的角色；
- 非人形角色。

## 对你们的创作者平台尤其重要

如果目标是“创作者注入 IP 和资产后生成游戏”，VRM 应该作为第一版推荐角色格式之一，但要有自动校验：

- VRM 版本；
- humanoid bone 是否完整；
- 面部表达是否完整；
- 手指和脚部骨骼；
- 身高和比例；
- 朝向和单位；
- 动画能力；
- Spring Bone；
- 商业授权；
- 贴图和材质限制；
- 是否有动作资源；
- 是否需要自动生成碰撞代理。

最终创作者交付的不能只有：

```text
一个 .vrm 文件
```

而应当是：

```text
角色模型
+ 角色设定
+ 表情配置
+ 声音配置
+ 动作资源
+ 交互能力
+ 碰撞和站位配置
+ 授权信息
```

结论是：

> VRM 适合快速、标准化、批量化地把 AI 角色送进当前项目；自定义建模绑骨适合高质量、强动作、强 IP 和复杂交互。当前项目最合理的技术路线不是二选一，而是让 VRM 和自定义角色都实现同一个 `RoleSkin/Embodiment` 接口。

> 所以我们其实需要很多种版本的游戏底座来服务不同呈现类型的游戏,你列举一下我们需要哪些

需要多种“运行形态”，但不建议维护很多套互相分叉的底座。

更合理的结构是：

```text
一个通用 Agent Game Core
        ↓
多个表现 / 物理 / 输入适配器
        ↓
不同类型的游戏运行时 Profile
```

## 最重要的架构原则

不要做成：

```text
Live2D 底座
2D 底座
3D 底座
VR 底座
机器人底座
```

每套各自复制角色、记忆、事件和世界逻辑。

应该做成：

```text
Agentic Game Core
   ├── Stage Adapter
   ├── 2D Adapter
   ├── 2.5D Adapter
   ├── 3D VRM Adapter
   ├── 3D Custom Adapter
   ├── XR Adapter
   └── Headless Simulation Adapter
```

所以真正需要“多版本”的不是多套智能体后端，而是：

- 不同的表现适配器；
- 不同的物理适配器；
- 不同的输入适配器；
- 不同的资产编译器；
- 不同的创作者模板。

这样同一个角色、同一个剧本、同一套记忆和世界规则，才有机会分别以 Live2D、像素、3D、VRM 或 VR 陪伴的形态运行。

> 角色智能体的感知和运动控制现在都是为3d服务的,在2d里就不一样了

对，这个判断是关键。不能把当前 3D 的感知和运动控制直接搬到 2D，只抽 Backend 还不够。

更准确的拆法是：

```text
通用智能体核心
  ├── 3D 具身适配器
  ├── 2D 具身适配器
  ├── Live2D 舞台适配器
  ├── 互动视频适配器
  └── XR 具身适配器
```

## 3D 和 2D 的感知差异

当前 3D 感知主要围绕：

- 3D 世界坐标；
- 相机视锥；
- collider；
- NavMesh；
- world anchor；
- 距离；
- 遮挡；
- 角色姿态；
- 骨骼和身体状态。

2D 需要另外处理：

- 画布坐标；
- Tilemap 或网格；
- sprite 层级；
- z-order；
- 2D 摄像机；
- 热点区域；
- 2D 碰撞；
- 画面遮挡；
- 视线和可见区域；
- 像素或 UI 坐标；
- 角色朝向是左/右还是八方向。

Live2D 和互动视频甚至不一定有真正的连续空间，它们更像：

```text
舞台状态
角色位置槽位
表情参数
对话层
图片热点
视频时间点
```

所以不能要求它们都返回 3D `position`、`collider` 和 `NavMesh`。

## 运动控制也必须分开

当前 3D 角色的控制链是：

```text
CharacterBody3D
  ↓
CharacterMotor
  ↓
move_and_slide
  ↓
3D 碰撞 / 重力 / 跳跃
```

2D 应该是另一套：

```text
CharacterBody2D 或 Grid Actor
  ↓
CharacterMotor2D
  ↓
2D 碰撞 / Tilemap / 网格寻路
```

Live2D 则可能是：

```text
Stage Controller
  ↓
切换角色槽位、表情、动作和对话状态
```

互动视频则可能是：

```text
Media Timeline Controller
  ↓
跳转片段、播放 cue、触发分支
```

它们都可以响应同一个高层意图：

> “调查桌上的线索。”

但具体执行不同：

- 3D：走到桌边并播放调查动作；
- 2D：移动到桌子的热点位置；
- Live2D：切换调查表情并显示线索；
- 视频：跳到调查片段。

## 应该抽象什么

不要抽象成一个“通用 3D CharacterMotor”，而应该抽象成通用的语义接口：

```text
AgentObservation
  ├── 时间信息
  ├── 当前场景
  ├── 可见实体
  ├── 关系和状态
  ├── 可用 affordance
  └── 坐标空间类型

AgentMotionIntent
  ├── 目标
  ├── 动作
  ├── 前置条件
  ├── 约束
  └── 期望结果

AgentExecutionResult
  ├── 成功 / 失败
  ├── 失败原因
  ├── 实际结果
  ├── 观测证据
  └── 时间和空间 lineage
```

然后不同模式扩展自己的数据：

```text
3D:
Pose3D / velocity / collider / stance

2D:
Pose2D / tile / layer / sprite_state

Live2D:
stage_slot / expression / motion / dialogue_state

Video:
timeline_position / hotspot / branch_state
```

## 当前 Action Controller 也要改成两层

当前的：

```text
navigate
align
prepare
execute_contact
recover
```

不能作为所有类型的具体执行步骤。

应该拆成：

```text
通用动作流程
  resolve_target
  check_preconditions
  prepare
  execute
  observe_result
  commit
  recover
```

再由各具身适配器实现：

```text
3D adapter:
navigate / align / contact / physics

2D adapter:
pathfind / face / hotspot / sprite animation

Live2D adapter:
move_to_stage_slot / expression / motion / dialogue

Video adapter:
seek / play / branch / cue
```

这样角色智能体只需要决定：

> “调查目标物体。”

而不需要知道它是怎么走过去的。

## 当前项目应该怎样改

当前 3D 实现应该被明确放到 3D 适配器下：

```text
embodiment/
  core/
  godot_3d/
    CharacterMotor3D
    PerceptionAdapter3D
    ActionRealizer3D
    PhysicsAdapter3D
  godot_2d/
    CharacterMotor2D
    PerceptionAdapter2D
    ActionRealizer2D
    PhysicsAdapter2D
  live2d/
    StageController
    ExpressionAdapter
  video/
    TimelineController
```

其中：

- 角色心智继续复用；
- 世界事实继续复用；
- 任务、线索、关系继续复用；
- authority 继续复用；
- Event Store 继续复用；
- 感知、空间、运动、动画和物理由适配器实现。

所以你的判断是对的：

> 2D 不是“少一个维度的 3D”，而是另一种具身环境。

真正通用的不是运动算法，而是：

- 角色如何观察环境；
- 角色如何形成目标；
- 角色如何提出行动；
- 环境如何执行行动；
- 环境如何返回结果；
- 结果如何进入记忆和世界状态。

当前项目要支持 2D，重点不是复制一套 `CharacterMotor2D`，而是先把 3D 感知和运动从智能体核心中剥离出来，建立清晰的 `Embodiment Adapter` 边界。

> 所以你觉得我们的整套项目架构应该是怎么样的?能够组成多少种底座来服务多少种游戏

我建议不要做很多套互相独立的游戏引擎，而是做：

> 一个通用智能体核心 + 多种玩法包 + 多种具身/表现底座。

- 物理仿真；
- 传感器模拟；
- 动作轨迹验证；
- sim-to-real。

它可以复用智能体、世界、记忆、行动和回放系统，但需要独立的机器人物理和硬件适配器。

## 五、最终能服务多少种游戏

不是固定支持 8 款游戏，而是：

```text
1 个智能体核心
× 4 类玩法包
× 6 类表现底座
```

组合后可以覆盖：

- 剧本杀；
- 视觉小说；
- 互动电影；
- Live2D AI 陪伴；
- 像素 RPG；
- 2D 箱庭；
- 2.5D RPG；
- 3D VRM RPG；
- 3D 社交模拟；
- 3D 探索 RPG；
- 轻动作 RPG；
- VR 陪伴；
- VR 剧情游戏；
- 多角色日常模拟；
- 阵营和关系游戏；
- AI 自动生成的剧情游戏。

不是所有组合都应该立即支持。第一阶段最合理的是：

```text
StoryStage
PixelWorld
AgentWorld3D
HeadlessAgentSim
```

之后再做：

```text
World2.5D
XRCompanion
3DAction
MediaStage
RobotSandbox
```

最终定位应当是：

> 通用智能体游戏核心负责“角色怎么想、世界怎么记、规则怎么判”；玩法包负责“游戏怎么玩”；表现底座负责“角色以什么身体和媒介存在”。

当前项目最需要做的架构工作，就是把现有 3D 感知、运动、骨骼和物理代码收进 `AgentWorld3D`，把角色智能体、世界事实、事件、记忆和 authority 提升为所有底座共用的核心。

> 我希望我提供的底座是可以被codex等智能体直接控制的,降低创作者的创作门槛.你觉得我是否应该提供资产商店和交易市场,还有资产生成网站?做游戏在线一键生成还是做一个可下载(但不开源)的开发底座让codex帮助玩家快速开发?

我的建议不是二选一，而是：

> 统一一套 `Project Pack` 和 CLI/API，让 Codex 等智能体可以直接控制；同时提供云端一键生成作为普通创作者入口。

不要做两套不同产品。在线服务和可下载底座都应该操作同一种项目格式、调用同一套编译器和验证器。

## 最终产品形态

```text
Creator / Codex
      ↓
Project Pack
      ↓
CLI / MCP / HTTP API
      ↓
内容编译器、资产绑定、验证器
      ↓
闭源运行时
      ↓
Godot / Web / VR / Headless
```

## 可下载的闭源开发底座

这是最适合 Codex 直接控制的形态。

核心可以闭源，但必须开放：

- 项目文件格式；
- 角色、场景、剧本、线索等 schema；
- CLI；
- MCP 工具；
- API；
- 日志和验证报告；
- 资产 manifest；
- 插件接口；
- 运行时错误和 replay。

Codex 不需要读核心源代码，它需要能够执行：

```text
创建项目
导入 IP
创建角色
生成场景
绑定资产
配置线索
运行测试
启动游戏
读取错误
修复配置
重新构建
导出游戏
```

例如：

```text
paralls create mystery-game
paralls add-actor char_a
paralls import-asset chair.vrm
paralls bind-affordance chair_01 kick
paralls validate
paralls simulate --runs 20
paralls preview
paralls export
```

这比让 Codex 操作一个纯网页界面可靠得多。

## 在线一键生成

在线服务适合：

- 不懂技术的创作者；
- 快速试玩；
- 协作；
- 云端模型调用；
- 自动部署；
- 手机或网页访问；
- 项目分享和发布。

但它不能只是一个“大 prompt 输入框”。必须有：

- 项目结构；
- 生成过程状态；
- 可回滚版本；
- 资产和设定编辑；
- 错误报告；
- 预览；
- 测试；
- 导出；
- API/MCP 接口。

否则生成出来的游戏不可解释、不可修复，也无法让 Codex 稳定接管。

最好的做法是：

```text
云端 Studio = GUI + 云端构建 + 云端运行
下载版 SDK = CLI + 本地构建 + 本地运行
两者使用同一个 Project Pack
```

## 资产商店和交易市场

长期应该做，但不建议一开始就开放完全自由的市场。

第一阶段先做官方精选资产库：

- VRM 角色；
- 3D 场景；
- 2D 像素资源；
- Live2D 角色；
- 立绘和背景；
- 动画；
- 音效和音乐；
- UI；
- 剧本模板；
- 线索模板；
- 交互模板。

资产不能只有一个模型或图片，还要包含：

```text
资源本体
+ 类型和语义
+ 版本
+ 交互能力
+ 碰撞 / 热点 / 锚点
+ 动画绑定
+ 性能等级
+ 授权信息
+ 依赖
```

例如一个 VRM 角色资产应该说明：

- 是否有完整 humanoid 骨骼；
- 有哪些表情；
- 支持哪些动作；
- 是否有手指骨骼；
- 是否适合 VR；
- 是否允许商业使用；
- 是否需要额外动画包。

否则资产商店会变成“看起来能用，导入后全部坏掉”的素材网站。

第二阶段再开放第三方市场，并加入：

- 授权和版权验证；
- 版本兼容性；
- 质量评分；
- 自动验证；
- 收益分成；
- 资产依赖；
- 撤销和更新机制。

## 资产生成网站

也应该做，但它的输出必须是“可编译资产包”，不能只生成一张图或一个模型。

例如生成一个角色时，最好同时生成：

```text
角色外观
角色设定
表情
动作候选
语音配置
碰撞代理
交互能力
资源预览
授权来源
```

生成一个场景时，最好同时生成：

```text
场景模型
实体 ID
碰撞体
导航区域
可交互物体
热点
站位点
线索绑定点
灯光和音频
```

关键流程应该是：

```text
AI 生成
  ↓
自动结构校验
  ↓
人工确认
  ↓
语义绑定
  ↓
运行时验证
  ↓
进入项目或商店
```

不能让生成模型直接写入世界权威或直接发布。

## 四种产品的建议优先级

| 产品 | 价值 | 风险 | 建议 |
|---|---|---|---|
| Codex 可控制的下载版底座 | 高控制力、适合专业创作者 | 初始安装和学习成本 | 第一优先 |
| 在线一键生成 | 降低普通用户门槛 | 成本、稳定性、锁定 | 第二阶段 |
| 官方资产库 | 快速提高产出质量 | 资产制作成本 | 第一阶段同步做 |
| 开放交易市场 | 网络效应和生态 | 版权、质量、兼容性 | 后期 |
| 资产生成网站 | 降低建模和内容门槛 | 生成质量和版权 | 先内部，再开放 |

## 最终定位

你们可以把产品定位为：

> 面向 Codex 和其他智能体的 Agentic Game Foundry：智能体可以直接读取项目结构、生成内容、绑定资产、运行测试、修复问题并构建游戏；普通创作者则通过网页工具完成同样的流程。

所以我的结论是：

- 不要只做在线一键生成；
- 不要只做一个黑箱下载程序；
- 核心应该是可被智能体直接操作的闭源开发底座；
- 在线 Studio 是它的低门槛外壳；
- 官方资产库是早期必需品；
- 公共交易市场和资产生成网站应该在项目格式、验证器和授权体系稳定后再开放。

> 你觉得Codex 可控制的下载版底座能给开发者省下多少时间和成本?相比之自己用codex或者codex控制游戏开发引擎开发的话

短答：

> 对于剧本杀、AI 陪伴、叙事 RPG 这类游戏，成熟的 Codex 可控制底座大概率能减少 50% 至 80% 的重复工程量；对于高强度动作 RPG，可能只能减少 20% 至 40%。

前提是底座真的提供了完整的项目格式、CLI/MCP、模板、验证器和运行时，而不是只有几个 SDK。

## 大致对比

以下假设是：1 至 3 人团队，使用 Codex，玩法范围受控，美术资源已经存在或可以购买。

| 类型 | 从零用 Codex + Godot | 使用成熟底座 + Codex | 主要节省 |
|---|---:|---:|---:|
| 剧本杀 / Live2D 叙事 | 6 至 12 周 | 1 至 3 周 | 60% 至 80% |
| 2D / 像素 AI RPG | 2 至 4 个月 | 3 至 8 周 | 40% 至 70% |
| VRM 3D 社交 / 剧情 RPG | 4 至 8 个月 | 1.5 至 3 个月 | 50% 至 70% |
| 简单 3D 动作 RPG | 9 至 18 个月 | 6 至 12 个月 | 20% 至 40% |
| 高质量动作 / 复杂物理 | 1 年以上 | 仍可能需要接近同等时间 | 10% 至 30% |

这些是工程和集成时间，不包括核心 IP 创作、精品美术、音乐制作和游戏调优。

## 底座主要节省什么

从零开发时，Codex 仍然要反复完成：

- 角色智能体架构；
- 记忆和私有知识；
- 世界事实；
- 任务和剧本系统；
- affordance；
- authority；
- 事件和存档；
- 模型接入；
- Godot 通信；
- 失败恢复；
- replay；
- 测试和验证；
- 资产绑定；
- 发布流程。

这些工作 Codex 可以写代码，但每个项目都要重新理解和调试。

有底座后，Codex 主要做：

```text
读取剧本
创建角色
导入资产
配置线索
配置场景
绑定交互
运行验证
修复配置
构建游戏
```

也就是说，Codex 从“重新造引擎”变成“编排内容和规则”。

## 资产方面的节省

资产商店和生成工具可以进一步减少成本，但差异很大：

- 通用 NPC、家具、背景、UI：可能减少 30% 至 70%；
- VRM 角色快速接入：可以显著减少绑骨和基础接入时间；
- 核心主角、Boss、特殊生物：节省通常较少；
- 高质量战斗动画、面部表演和物理动作：仍然昂贵。

因此，底座不能承诺“自动消除美术成本”，更现实的是：

> 把“导入资产后还要大量手工接线”的成本消掉。

资产必须带有：

```text
模型 / 图片 / 音频
+ 语义
+ 交互能力
+ 动画绑定
+ 碰撞或热点
+ 性能信息
+ 授权信息
```

## 下载版底座为什么适合 Codex

可下载的闭源底座可以让 Codex 直接操作：

```text
project.yaml
actors/
scenes/
beats/
clues/
assets/
tests/
```

再通过 CLI 或 MCP 执行：

```text
create
import
bind
validate
simulate
preview
export
```

核心闭源不是问题，但不能做成黑箱。必须开放：

- schema；
- 命令；
- MCP/API；
- 错误报告；
- replay；
- 验证结果；
- 插件合同；
- 版本迁移工具。

否则 Codex 遇到问题时只能看到“运行失败”，无法自动修复。

## 在线一键生成和下载版的关系

最优方案是同一个底座提供两种入口：

```text
下载版：
Codex + CLI + 本地运行时 + 本地构建

在线版：
网页 Studio + 云端构建 + 云端预览 + 一键发布
```

两者使用同一个 `Project Pack`。

这样：

- 技术型创作者使用 Codex 和本地底座；
- 非技术创作者使用网页工具；
- 项目可以在本地和云端互相迁移；
- 平台不会被某一种 UI 绑死。

## 什么时候能真正收回底座投入

底座本身会是一项大型产品工程。第一款游戏可能因为学习和适配，节省不明显；真正的收益出现在第二款、第三款开始。

如果一款剧本杀游戏能节省 3 至 8 个人月的重复工程，那么做出成熟底座后，通常需要连续生产几款游戏才能覆盖平台投入。

所以不应该只用第一款游戏判断价值，而应该测量：

- 从空项目到第一个可玩版本的时间；
- 新增一个角色需要多久；
- 新增一个场景需要多久；
- 新增一条线索需要多久；
- 新增一种交互需要多久；
- Codex 自动生成内容的通过率；
- 资产导入后的人工修复时间；
- 回归缺陷数量；
- 第二款游戏是否能复用第一款的内容工具。

结论是：

> 对你们计划中的剧本杀、AI 陪伴和叙事 RPG，Codex 可控制的下载版底座很有可能把开发从“几个月的工程项目”压缩到“几周的内容生产项目”。但它的价值不在于让 Codex 写更多代码，而在于提前把世界、角色、资产、动作、测试和发布流程标准化。

> 我们把底座做到什么程度能给复杂游戏节省更多的成本和时间?

要让复杂游戏也明显省时间，底座不能只做到“有 AI 角色和几个交互 demo”，而要做到：

> 复杂游戏中约 70% 至 80% 的通用工程由底座提供，项目团队只实现剩下的 20% 独特内容和规则。

重点不是支持所有游戏，而是把重复工作彻底产品化。

## 成熟度分层

| 阶段 | 底座能力 | 能节省的范围 |
|---|---|---|
| L1 | 角色智能体、对话、事件、基础交互 | 简单原型 |
| L2 | 剧本、角色、线索、资产可配置生成 | 剧本杀、叙事游戏 |
| L3 | 2D/2.5D/3D 多表现适配器 | 多类型 RPG |
| L4 | 任务、关系、经济、战斗、持久化、网络 | 复杂 RPG |
| L5 | Codex 工具链、资产管线、自动测试、云构建 | 大规模持续生产 |

当前项目大约处于：

> L1 已有较强基础，正在向 L2 和 L3 过渡。

如果要真正为复杂游戏节省大量成本，至少要做到 L4；如果要让不同团队持续使用并批量生产，还要做到 L5。

## 最重要的八个能力

### 1. 完整的通用世界内核

必须稳定支持：

- 世界事实；
- 时间；
- 事件；
- 快照；
- replay；
- 幂等；
- 权威结算；
- 存档；
- 版本迁移；
- 多角色私有视角。

这部分一旦不稳定，每个游戏都要重新维护一套世界状态系统。

### 2. 内容编译器

创作者和 Codex 应该通过项目文件描述：

```text
角色
场景
线索
任务
物品
技能
关系
交互
结局
```

然后一键生成：

- Backend 配置；
- Godot 场景绑定；
- 角色运行时配置；
- action registry；
- UI；
- 测试用例；
- 初始存档。

如果新增一个角色或线索还需要手改多个 Python、Godot 和 JSON 文件，底座还不够成熟。

### 3. 真正可复用的玩法模块

至少要提供可组合模块：

- 对话；
- 剧情和任务；
- 线索和调查；
- 关系和阵营；
- 物品和装备；
- 经济和交易；
- 技能和能力；
- 战斗；
- 潜行；
- 探索；
- 建造和经营；
- 投票和多结局。

复杂游戏的独特部分应该通过插件扩展，而不是复制底座源码。

### 4. 多种具身适配器

至少要支持：

- Live2D/舞台；
- 2D；
- 2.5D；
- 3D VRM；
- 3D 自定义角色；
- XR。

通用核心只处理：

```text
角色意图
目标
动作
前置条件
执行结果
```

运动、感知、动画、碰撞和物理由不同适配器处理。

### 5. 完整的 3D 动作基础

想服务复杂 3D 游戏，必须补齐：

- CharacterMotor；
- NavMesh；
- IK；
- AnimationTree；
- 动作阶段；
- hitbox/hurtbox；
- 受击和打断；
- 物理接触；
- 装备和 socket；
- 动画重定向；
- 网络预测和同步。

否则底座只会显著帮助剧情和社交游戏，对动作 RPG 的帮助有限。

### 6. 资产自动化管线

资产导入不能停留在“模型能加载”。

每个资产要自动检查：

- 资源格式；
- 骨骼；
- 表情；
- 动画；
- 碰撞；
- 导航；
- LOD；
- 交互能力；
- 性能；
- 授权；
- 版本；
- 依赖。

理想状态是：

> 创作者提供资产，Codex 调用导入器和验证器，底座自动完成绑定并报告缺失项。

**要真正实现“创作权和分红权上链”，还缺这些核心层**

1. **IP 权利模型**

必须把以下概念分开：

- IP 根权利；
- 世界观使用权；
- 剧本版权；
- 角色设定权；
- 美术、音乐、声音、模型权利；
- Fork 和衍生权；
- 商业授权权；
- 收益权；
- 治理权。

“买了一个资产”不等于拥有整个 IP，“使用一个角色”也不等于拥有角色版权。

2. **贡献记录与贡献确认**

区块链只能证明“某个贡献记录在某时刻被提交并确认”，不能自动判断这个贡献是否有价值。

因此需要：

- 贡献提交；
- 版本差异；
- 父版本和 Fork 关系；
- 贡献者身份；
- 审核和验收；
- 贡献类型；
- 最终确认人或确认委员会；
- AI 生成内容的人工贡献说明。

例如，AI 生成了一段剧本，不能简单把“AI”作为法律权利人。需要明确由哪个人或实体承担创作责任、持有授权或获得收益。

3. **链上权利注册系统**

至少需要实现：

- IP 根记录；
- 资产内容哈希；
- 版本和 Fork 家谱；
- 贡献者地址；
- 授权范围；
- 收益比例；
- 合约版本；
- 变更历史；
- 撤销、纠正和争议状态。

大文件、模型、音乐、场景等不应直接全部放链上。应使用对象存储或 IPFS 保存内容，链上保存哈希、引用和权利记录。

4. **链上分账系统**

正确的链路应是：

```text
游戏服务器权威事件
    -> 销售/使用收入记录
    -> 收益归因与分账计算
    -> 签名结算批次
    -> 链上智能合约
    -> 钱包或支付账户
```

不能让客户端、玩家或 AI 直接触发分账。

游戏内高频对话、移动、物理、记忆和每帧事件仍然应留在后端事件系统；只有销售、授权、订阅、门票、服务器收入等需要结算的结果进入链上。

5. **收入来源接入**

自动分红的难点不是智能合约，而是收入是否全部经过可验证的渠道。

如果大玩家可以线下收费、私下收款、在外部平台售票，平台就无法自动知道真实收入。因此需要：

- 平台统一支付；
- 服务器经营收入接口；
- 订阅和门票订单；
- 退款和拒付处理；
- 收益归因；
- 防刷量和反作弊；
- 跨平台收入申报或审计。

6. **创作者与大玩家工具**

要开放共创，至少要提供：

- IP/世界创建器；
- 剧本编辑器；
- 角色和智能体设定编辑器；
- 资产导入与语义绑定工具；
- Fork、分支、合并和版本管理；
- 创作贡献确认界面；
- 授权协议配置；
- 收益比例配置；
- 模拟运行和回放；
- 发布审核；
- 服务器部署和经营控制台；
- 收益和贡献查询面板；
- CLI、API、MCP，让 Codex 能直接操作这些能力。

7. **治理、审核和法律体系**

还必须补上：

- 著作权、商标、肖像、声音和模型授权；
- AI 生成内容的责任归属；
- 内容审核和侵权投诉；
- 分账争议处理；
- 退款、撤销和合约纠正；
- 税务、实名、支付和反洗钱；
- 未成年人和消费者保护；
- 合约升级和平台紧急冻结机制。

特别要注意：上链存证不等于法律上的著作权登记，链上收益凭证也不等于可以随意发行和交易的股份或证券。第一阶段不建议直接发行治理代币或公开出售收益 Token，应先做“链上权利登记 + 链上版税分配”的封闭试点，并让实际运营地和用户所在地的法律顾问审核。

**最现实的启动方式**

可以先做一个“许可型 IP 共创计划”：

1. 平台发布一个 IP 根世界和创作章程；
2. 邀请编剧、美术、音乐、角色设计师、服务器经营者加入；
3. 每个人使用钱包身份签署贡献和收益协议；
4. 所有作品进入 Project Pack，生成哈希和版本谱系；
5. 通过审核的贡献写入链上权利登记；
6. 游戏销售、门票、订阅和授权收入由后端权威事件产生；
7. 智能合约按版本化分账规则自动结算；
8. 所有参与者可以查看自己的贡献、授权范围和收入来源。

这样就能先支持一个真实 IP 的共同创作，而不必一开始就做完全开放的 DAO。

我建议分三阶段：

- **阶段一：封闭共创试点**
  一个 IP、有限创作者、人工审核、链上确权和定期自动分账。

- **阶段二：受控开放生态**
  开放 Fork、资产市场、大玩家服务器、自动授权和自动分账。

- **阶段三：完整生态治理**
  跨 IP 授权、IP 议会、社区治理、持续世界和更开放的贡献激励。

所以，答案是：你们的技术方向足以支撑“发起 IP、组织共创、按贡献分红”这个目标，但必须把链上权益系统视为与游戏运行时同等重要的一条产品主线。当前底座是基础，真正决定生态能否成立的是“权利模型、贡献确认、收入归因、智能合约结算、法律协议和运营治理”这六件事。

不要直接复用完整对话和完整结局，而是提炼成：

- 具体因果后果；

**哪些内容适合复用**

| 内容 | 复用方式 |
|---|---|
| 规则、动作、镜头、音乐编排 | 高度复用 |
| NPC 策略、冲突结构、节奏曲线 | 参数化复用 |
| 故事线骨架和反转模式 | 作为候选方案 |
| 完整对话 | 只在获得授权后局部复用 |
| 玩家私密记录、情感信息 | 默认不可复用 |
| 当前局事实、隐藏线索、最终真相 | 必须重新结算 |

最重要的是做“结构复用、表层变化”。同一个冲突骨架可以换角色、地点、证据、动机和结局，否则玩家很快会发现自己只是在重复别人玩过的剧本。

**司命应该怎么做**

司命不能单纯选择最省钱的方案，而应同时优化：

```text
玩家适配度
+ 公平性
+ 故事价值
+ 新鲜度
+ 角色关系连续性
- 算力成本
```

算力成本只是一个约束，不应成为最高优先级。

司命可以读取：

- 玩家已经体验过的故事结构；
- 玩家偏好的节奏和冲突类型；
- 玩家最近是否连续遇到相似反转；
- 玩家与角色的关系状态；
- 当前局有哪些未闭合的叙事义务；
- 哪些内容可以安全复用。

但不能读取其他玩家的私密对话、隐藏事实和个人经历来制造廉价剧情。

**玩家为什么愿意付算力费**

玩家不会因为“算力”本身而长期付费，他们会为以下结果付费：

1. 角色真的记得自己，并且关系会持续发展；
2. 每次进入都能出现新的、适合自己的故事；
3. 可以拥有一个长期陪伴的角色或小世界；
4. 能获得高质量语音、画面、镜头和 WOW 时刻；
5. 自己创造的故事可以继续影响后来的世界；
6. 自己贡献的优质故事被复用时，可以获得署名、算力返还或收益分成；
7. 能把一段特殊经历保存成故事报告、短片、角色记忆或可分享资产。

因此建议采用四层付费：

- **基础层**：平台承担基本角色智能和基础剧情；
- **个人智能层**：玩家购买长期记忆、更复杂关系和更强推理；
- **高光层**：高质量视觉、语音、视频、WOW 时刻按套餐或额度使用；
- **世界/服务器层**：大玩家为高并发 NPC、持续运行世界和高质量房间购买算力。

不要让玩家感觉“不给钱角色就变傻”。基础人格和基础回应应该始终可用，付费买的是更高质量、更长记忆、更强连续性和更多新颖内容。

**可以建立“共享算力池”**

玩家可以明确选择：

- 本局仅自己使用；
- 允许在当前 IP 内匿名提炼；
- 允许公共生态复用；
- 允许商业复用并参与分成。

愿意贡献的人可以获得：

- 未来算力抵扣；
- 角色或世界的优先访问权；
- 贡献署名；
- 被复用次数和影响力统计；
- 商业衍生收益；
- 参与该 IP 共创治理的资格。

这会把玩家从“算力消费者”变成“故事资产共同生产者”。

但必须明确：玩家支付算力，不自动等于拥有全部生成结果。支付之后的权利要在开局前写清楚，包括隐私、授权范围、商业复用、撤回、署名和分成。

所以最终判断是：

> 这条路不仅可行，而且可能是 Paralls 区别于普通 AI 游戏的核心商业飞轮：玩家付费产生体验，体验沉淀为可复用叙事资产，资产降低后续算力成本并提升内容质量，优质贡献者继续获得算力和收益回报。

第一步不应直接做“无限复用”，而应先验证一个小闭环：

> 但算力消耗的大头应该会是什么?司命的全局推演?角色智能体带着长周期记忆去感知,推理,规划,执行? 这些怎么做到让玩家无感的复用资源呢?

大头通常不是物理和动画，而是“模型调用次数 × 上下文长度 × 输出长度”。最主要的成本大致如下：

| 模块 | 主要成本 | 是否适合复用 |
|---|---|---|
| 3D 物理、移动、动画 | CPU/GPU，较稳定 | 不需要模型复用 |
| 感知、检索、Embedding | 中低成本 | 可以缓存 |
| 司命全局推演 | 中高成本，取决于调用频率 | 快照和候选可以复用 |
| 角色深度推理、规划 | 通常是模型成本大头 | 记忆摘要、行为策略可以复用 |
| VLA、多模态理解 | 单次成本高 | 低频调用、缓存视觉事实 |
| TTS、图片、视频、WOW 表现 | 偶发高峰成本 | 生成资源和表现编排可以复用 |

真正危险的情况是：

```text
每个事件
    -> 司命深度推理
    -> 每个角色各自读取长记忆
    -> 每个角色各自调用大模型
    -> 再调用视觉、语音和表现模型
```

这样算力会随着角色数量和事件数量迅速膨胀。

**正确的运行频率**

应该把系统拆成不同时间尺度：

```text
每帧：
本地物理、运动、碰撞、动画

每个事件：
规则判断、状态更新、轻量感知

每个关键行动：
角色短推理、局部规划

每个叙事节点：
司命公平判断、冲突调度、深度规划

每局结束或后台：
长记忆压缩、故事资产提炼、经验复盘
```

这和主项目已经冻结的方向一致：角色采用 Rule / Fast Model / Deep Model 三层路由，快慢链路分开；司命采用 P0-P4 优先级，先保证公平快照、候选、决策和审计，视觉和复杂导演能力可以降级。[角色智能体运行时预算](/D:/Projects/Paralls/docs/phase1/core/01-运行时核心/角色智能体/09-运行时服务拆分、模型路由与性能预算.md:34) [司命高并发策略](/D:/Projects/Paralls/docs/phase1/core/01-运行时核心/司命/14-司命高并发与子智能体运行策略.md:15)

**司命怎么降低成本**

司命不应该每次从头“重新想完整故事”，而应该维护：

- 当前世界公平快照；
- 当前叙事义务；
- 已经出现过的冲突；
- 玩家已经体验过的套路；
- 当前可执行的候选路径；
- 最近使用过的干预冷却状态。

一次全局快照可以服务整个房间，不能让每个角色分别计算一遍。

然后司命只在关键节点使用深度推理：

- 玩家行为改变核心案件；
- 阵营严重失衡；
- 某个角色关系发生重大转折；
- 需要生成新的反转；
- 当前没有可复用的合适方案。

普通情况使用规则、缓存候选和小模型。

**角色智能体怎么让长周期记忆变便宜**

不能把角色几个月的聊天记录全部塞进上下文。主项目的记忆设计已经明确，记忆应拆成事件、观察、知识、社交和高阶认知五个池，而不是一坨聊天历史。[记忆系统与知识状态设计](/D:/Projects/Paralls/docs/phase1/core/01-运行时核心/角色智能体/04-记忆系统与知识状态设计.md:9)

实际调用时只需要：

```text
当前场景状态
+ 最近关键事件
+ 与当前目标相关的记忆
+ 关系状态摘要
+ 少量原始证据
```

例如角色要判断玩家是否撒谎，不需要读取三个月的完整聊天，只需要读取：

- 玩家过去几次相关承诺；
- 已确认或争议中的事实；
- 当前信任值；
- 几条最相关的原始对话；
- 当前场景的新证据。

其余内容留在数据库、图结构和向量索引中，只有检索命中后才进入模型。

**哪些资源可以让多个玩家无感复用**

可以建立独立的“体验资产库”，保存的不是上一局的最终答案，而是结构化经验：

```text
故事资产
- 适用前提
- 参与角色类型
- 需要的世界事实
- 冲突结构
- 行动链
- 预期结果
- 可替换变量
- 新鲜度标签
- 质量评分
- 成本
- 隐私和授权范围
```

举例：

- “销毁证据后引发目击者误判”可以复用；
- “背叛后关系破裂再短暂结盟”可以复用；
- 一段优秀的镜头、音乐、慢动作组合可以复用；
- NPC 发现玩家撒谎时的行为策略可以复用。

但当前玩家的具体身份、秘密、关系、真实结局和私有记忆必须重新计算。

当前司命规格也已经规定：已验证的故事线只能作为候选生成启发，不能覆盖事实、角色自主性和执行可行性。[siming-agent-loop-architecture-design.md](/D:/Users/User/Documents/paralls-phase-0-demo/docs/superpowers/specs/2026-06-17-siming-agent-loop-architecture-design.md:540)

**让玩家感觉不到复用**

技术上可以这样做：

1. 服务器预先生成通用故事骨架和高光编排；
2. 开局时根据玩家和角色状态检索合适方案；
3. 用小模型替换角色、地点、线索和语言表层；
4. 用规则和 ESM 重新验证当前局是否成立；
5. 关键转折才调用大模型；
6. 对话结束后异步提炼新经验，不阻塞当前游戏；
7. 通过新鲜度账本避免连续复用相同套路。

例如上一位玩家贡献了“庄园停电后有人趁乱转移证据”的故事结构。下一位玩家不会看到原故事，而是可能遇到：

- 不同地点；
- 不同角色；
- 不同动机；
- 不同证据；
- 不同结局；
- 但同样紧张的冲突节奏。

玩家感受到的是“司命很懂我”，而不是“系统在套模板”。

**需要特别防止的误区**

“无限体验”不能理解为无限生成。更准确的目标是：

> 用有限的高价值叙事模块、角色策略和表现资源，组合出大量满足当前玩家状态的不同体验。

如果司命只为了省钱不断复用，玩家会感到套路重复。因此需要把“成本、质量、新鲜度、玩家满意度”一起纳入调度，而不是把成本放在最高优先级。

当前项目下一步真正需要增加的模块是：

- `Experience Asset Registry`：体验资产注册表；
- `Narrative Distiller`：把游玩记录提炼为故事资产；
- `Semantic Cache`：按世界状态、角色版本和权限缓存；
- `Novelty/Fairness Manager`：管理新鲜度和公平；
- `Compute Metering`：记录每局和每类智能的算力成本；
- `Cross-player License`：管理玩家记录的匿名化和商业复用授权。

最终的成本控制不是“让所有 AI 都变小”，而是：

```text
规则负责高频确定性问题
小模型负责普通解释和行动
大模型只负责关键不确定性
司命共享全局快照
角色只检索相关记忆
故事和表现资产离线提炼、在线组合
```

这样玩家支付的是持续的角色智能、记忆、关系和高光体验，而不是每次都为同一类推理重复付费。

```text
Narrative Distiller
Semantic Story Cache
Memory Retrieval / Compression
Novelty and Reuse Manager
Compute Metering
Player Consent and License Layer
```

目前的底座已经为这些模块留出了事件、快照、记忆、审计和模型网关接口，但距离“玩家无感地共享前人算力成果”还有一层完整的叙事资产化和成本调度系统。

> 对于单局(30-60分钟)的剧本杀来说,角色深度推理、规划会占很大的成本吗?做好记忆压缩和关键提取(使用知识图谱,应用五池记忆等)做到有用的记忆才会被调用的上下文窗口管理,是否能够大幅降低成本?

会占成本，但不一定是单局 30–60 分钟剧本杀的最大成本。关键取决于是否让每个角色、每个事件都调用大模型。

**两种完全不同的架构**

高成本架构：

```text
每次感知
    -> 每个角色读取完整历史
    -> 每个角色深度推理
    -> 每个角色重新规划
    -> 生成回应
```

这种情况下，角色智能体推理会成为主要成本，而且角色数量一多就会线性膨胀。

合理架构：

```text
普通事件：规则和小模型
关键事件：角色局部推理
重大转折：深度推理和规划
局后/后台：记忆压缩与故事资产提炼
```

这时深度推理只发生在：

- 发现关键线索；
- 事实互相冲突；
- 判断是否撒谎；
- 阵营或关系发生重大变化；
- 角色需要改变长期目标；
- 需要做高价值行动选择；
- 结局或重大 WOW 时刻。

移动、碰撞、普通观察、基础情绪变化、简单对话回应，不应该每次调用深度模型。

**记忆压缩确实能大幅降低成本**

五池记忆、知识图谱和关键提取主要能降低两类成本：

1. 减少每次模型输入的 token；
2. 减少模型需要重新推理的内容。

角色不应携带完整聊天历史，而应生成一个受控的 `Context Pack`：

```text
当前场景事实
+ 当前私有知识
+ 与当前目标相关的记忆
+ 关键关系状态
+ 未解决矛盾
+ 最近事件
+ 必要的原始证据
```

例如角色判断“玩家是否在撒谎”，不需要读取 45 分钟全部对话，只需要读取：

- 玩家过去相关承诺；
- 当前证据；
- 角色对玩家的信任和怀疑；
- 与该事件有关的几条记忆；
- 角色当前目标。

其他内容仍保留在记忆库和知识图谱里，只在相关时检索。

主项目的记忆设计已经确定了事件、观察、知识、社交和高阶认知五池结构。[记忆系统与知识状态设计](/D:/Projects/Paralls/docs/phase1/core/01-运行时核心/角色智能体/04-记忆系统与知识状态设计.md:17)

**但当前代码还没有做到成熟检索**

当前项目已经：

- 按角色隔离五类记忆；
- 记录来源事件、时间和置信度；
- 生成工作记忆状态；
- 对模型上下文做数量和样本摘要；
- 支持本地持久化。

但当前 `recall()` 主要是把该角色已有记录取出来，还没有真正实现：

- 语义 Top-K 检索；
- 知识图谱查询；
- 记忆重要性排序；
- 时间衰减；
- 当前目标相关性评分；
- 自动合并重复记忆；
- 长期记忆压缩版本管理。

所以当前是“结构化记忆 + 初步摘要”，还不是完整的“只调用有用记忆”。[memory_store.py](/D:/Users/User/Documents/paralls-phase-0-demo/backend/app/character_agent/storage/memory_store.py:233)

**单局成本的实际构成**

对于 30–60 分钟、5 个 AI 角色的剧本杀，应该按以下方式规划：

```text
每帧：
本地物理、动画、空间感知，不调用大模型

每次普通事件：
规则判断和结构化状态更新

每次普通对话：
小模型或有限上下文生成

每个角色若干次关键决策：
深度推理和规划

每个叙事节点：
司命做全局公平和候选干预

局后或后台：
压缩记忆、提炼故事资产
```

深度推理的工程目标应该是“每个角色一局只在少数关键节点调用”，而不是每个事件都调用。具体次数必须通过真实剧本回放压测确定。

**司命和角色的成本要分开**

司命的成本来自“全局状态和公平推演”。如果每个事件都启动复杂全局推演，成本会很高。

当前司命已经采用：

- 公平快照；
- 状态树；
- 事件驱动；
- 候选干预；
- P0-P4 优先级；
- 高压时关闭低优先级表现链。

主链优先保证公平快照、候选、决策和审计，复杂视觉和高光能力可以降级。[司命高并发策略](/D:/Projects/Paralls/docs/phase1/core/01-运行时核心/司命/14-司命高并发与子智能体运行策略.md:71)

这意味着司命不应该每秒重新写完整故事，而是：

- 共享一次房间级全局快照；
- 只处理状态变化；
- 只有重大失衡或关键叙事节点才调用深度模型；
- 普通事件使用规则候选和缓存状态。

**能降低多少**

相对于“每个角色每轮调用大模型，并带完整聊天历史”的方案：

- 记忆压缩可以显著降低输入 token；
- 关键事件门控可以显著减少深度调用次数；
- 故事方案和表现资产缓存可以减少重复生成；
- 小模型承担普通感知、解释和对话；
- 大模型只承担真正高价值的不确定问题。

降低数倍是合理的工程目标，但不能只靠记忆压缩实现。因为以下成本不会因此消失：

- TTS；
- 图片和视频生成；
- 高质量视觉高光；
- 大模型输出 token；
- 多人同时在线的并发成本。

因此应重点监控：

```text
每局深度调用次数
每次调用输入 token
每局模型输出 token
记忆检索命中率
故事资产复用率
缓存命中率
每局平均算力成本
玩家满意度和重复感
```

当前项目已经具备 Rule/Fast/Deep 的基础网关和降级路径，但还没有把“记忆相关性、故事资产复用和算力预算”接入统一调度器。[角色模型网关](/D:/Users/User/Documents/paralls-phase-0-demo/backend/app/character_agent/gateway/model_gateway.py:24)

最终判断是：

> 对 30–60 分钟的剧本杀，只要深度推理采用关键节点触发，长期记忆采用知识图谱和五池记忆提取，角色大多数时候使用规则和小模型，单局算力成本是可以控制的；而且记忆压缩与关键提取确实能够带来明显的成本下降。

但这套优化当前还处于“架构已经预留、基础实现已存在、生产级检索和算力调度尚未完成”的状态。
