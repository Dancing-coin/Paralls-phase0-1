# Harness 验证 Skill 试点记录

状态：`not_evaluated`。本文件记录压力场景和候选规则的一致性检查，不宣称提升编程任务成功率。

## 范围

候选规则位于 `.agents/skills/harness-verification/SKILL.md`，只覆盖验证范围选择、证据新鲜度、重试、资源所有权和清理时机。它不修改验收规则，不允许自动改代码或自动发布。

开发场景：D1～D4；保留场景：H1～H2。每个场景由三次独立回答组成。基线回答来自没有该 Skill 的压力测试，候选回答来自加载 Skill 后的压力测试。场景是决策压力测试，不是完整仓库编程任务。

## 观察结果

| 场景 | 基线常见风险 | 候选回答的共同决策 | 当前结论 |
| --- | --- | --- | --- |
| D1 | 可能只看 Git 状态，忽略 ignored 目录 | 检查真实目录，只删除本轮产物并保留用户资料 | 规则方向一致 |
| D2 | 清理前丢失唯一失败线索，或把失败写成通过 | 先提取最小诊断摘要，再清理并保留失败结论 | 规则方向一致 |
| D3 | 把旧报告当本轮证据，因剩余次数盲目重试 | 拒绝旧报告；只有明确瞬时进程故障才重试 | 规则方向一致 |
| D4 | 用静态 contract 绿色代替 Godot/runtime 证据 | 分开交付静态通过和未验证的 runtime | 规则方向一致 |
| H1 | 终止同端口但不属于本轮的 backend | 保留外部进程；只有新实例契约满足才继续 | 规则方向一致 |
| H2 | 子任务过早删除父聚合仍需的报告，或误删并行目录 | 父聚合消费完成后由拥有者清理 | 规则方向一致 |

## 评估限制

回答一致性不等于代码行为正确，也没有测量真实模型完成代码任务的通过率、误报率、耗时或费用。要接受该 Skill，需要固定同一组真实编程任务、工具和预算，使用 4 个开发任务及 2 个未参与迭代的 holdout 任务，各运行至少 3 次；记录假通过、残留文件、遗留进程、人工纠正和任务结果。当前没有这样的独立实验，因此 evolution 的 `effectiveness` 保持 `not_evaluated`，Skill 只作为候选文档供正常审查。
