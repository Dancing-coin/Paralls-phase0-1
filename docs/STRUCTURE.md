# 文档目录建设方案

状态：当前文档建设方案

本文定义 `docs/` 的目标结构、当前迁移状态和维护规则。它参考了更成熟仓库的
“主页 + 结构说明 + 按主题分目录 + 每层 README”方式，但不一次性搬动历史文档，
避免打断已有 plan、spec、harness 和代码引用。

## 目标结构

```text
docs/
  README.md                         # 人类阅读入口和推荐阅读顺序
  INDEX.md                          # 智能体和维护者入口，必须保持路径可验证
  STRUCTURE.md                      # 本文件：目录建设方案和维护规则

  概览/                              # 项目背景、当前状态、路线图
  架构/                              # 仓库级和运行时级架构文档
    README.md
    整体架构.md
    运行时/
      README.md
      运行时总览.md
      运行时覆盖矩阵.md
      运行时命名边界审计.md
      图表/
      模块/
        SystemL6事件总线.md
  运行/                              # 本地运行、demo、联调、故障排查
  验证/                              # Harness、profile、证据、质量门禁
  资产/                              # Godot、角色、场景、资产管线
  角色/                              # 角色智能体、角色控制、mind core、角色资源
  参考/                              # 外部或历史参考，不作为当前实现事实
  superpowers/                       # specs、plans、计划状态和历史决策
```

## 分区规则

| 目录 | 收纳内容 | 不收纳内容 |
| --- | --- | --- |
| `概览/` | 项目概述、当前状态、路线图、读者导览 | 具体运行时 owner 细节 |
| `架构/` | 整体架构、运行时架构、时序图、数据流图、模块边界 | 操作 runbook、历史计划 |
| `运行/` | 本地启动、demo 节拍、联调步骤、常见运行问题 | 架构决策和设计真相 |
| `验证/` | Harness 使用、profile 说明、证据路径、质量门禁 | 后端或 Godot 实现代码 |
| `资产/` | Godot 场景、角色资产、导入导出、资产策略 | 角色智能体认知链路 |
| `角色/` | 角色智能体、mind core、角色控制链、角色执行入口 | 世界真相或 ESM authority 设计 |
| `参考/` | Phase1、外部设计、历史材料 | 当前仓库已实现事实声明 |
| `kimi分析/` | Kimi 会话产生的问题分析与修复方案建议（带状态头） | 当前实现事实声明、正式设计真相 |
| `superpowers/` | specs、plans、计划状态、历史决策 | 面向读者的总入口 |

## 命名规则

- 面向用户和维护者的文档使用中文可读文件名。
- `Siming` 保持英文写法。
- 技术标识保持原样，例如 `SystemL1`、`VLA`、`PQF`、`ESM`、`world_runtime`、profile 名称和代码路径。
- 目录名优先使用稳定名词：`架构`、`运行时`、`图表`、`模块`。
- 图表文件名必须说明范围，例如 `整体运行时时序图.md`、`整体运行时数据流图.md`。
- 模块文档文件名使用模块名，不再追加“配套文档”。

## 架构文档层级

1. `docs/架构/整体架构.md`
   - 仓库级总纲，覆盖 Godot、后端、世界运行时、角色智能体、ESM、Siming、模型服务、Harness 和非运行时支撑面。
2. `docs/架构/运行时/运行时总览.md`
   - 运行时级总纲，说明运行时内结构、整体时序和整体数据流。
3. `docs/架构/运行时/图表/`
   - 放跨模块可渲染 Mermaid 图。
4. `docs/架构/运行时/模块/`
   - 放局部 owner 和模块边界文档，例如世界运行时、System L1、角色智能体、VLA、模型服务。

## 维护规则

- 移动或新增入口文档时，同步更新 `docs/README.md`、`docs/INDEX.md` 和本文件。
- `docs/INDEX.md` 中用反引号标记的本地路径必须真实存在，因为 `docs` harness 会检查这些路径。
- 架构文档只声明已经实现、正在实现或明确标注为目标的内容；不要把参考资料写成当前事实。
- `reference/` 和未来 `参考/` 下的材料必须明确标注“参考”，不能作为当前实现证明。
- VLA 和模型服务必须分开记录：VLA 文档说明视觉/空间结果如何进入运行时；模型服务文档说明 provider readiness、adapter、凭证和真实调用证明。
- `world_runtime` 作为世界侧基础设施大类记录在 `docs/架构/运行时/模块/世界运行时.md`。
- 每次文档结构调整后运行：

```powershell
python scripts\verification\harness.py --profile docs
git diff --check
```

## 后续迁移顺序

1. 把运行和 demo 文档迁到 `docs/运行/`，并补 `docs/运行/README.md`。
2. 把 Harness 说明、证据规则和质量文档迁到 `docs/验证/`，保留必要兼容链接。
3. 把资产、场景、导入导出文档迁到 `docs/资产/`。
4. 把角色文档从 `docs/character/` 迁到 `docs/角色/`，或保留 `character/` 并在本文件中明确为技术目录。
5. 迁移完成后，再清理根目录中只剩入口类文件。
