## 1. 审查结论

本批规格和计划可以作为一套**非授权的实施设计输入**继续审查，但不能据此宣称“全体角色社会生命、完整群体模拟、Laya 持续心智运行时或局部活化已经实现”。现有实现已经提供了人口 cadence、有限 B0 连续状态、owner-bound read-set/receipt、角色 simulation seed、角色私有记忆图、激活生命周期、有限 Laya L3 adapter 和确认后 Godot 人口镜像；缺少的是把这些能力统一成全体角色覆盖的社会生命闭环。

本批当前结论：

## 2. 状态语义

- `[current]`：代码、测试或正式主线文档能够直接证明的边界。
- `[planned]`：十月分析和本批规格有来源依据，但当前实现或验收证据不完整。
- `[blocked]`：存在明确的接口、owner、数据、provider 或证据缺口，不能进入相应实现门禁。
- `[deferred]`：原始范围允许暂缓，且本批明确不进入 active gate。
- `[forbidden]`：本批不允许引入的架构方向。它不是延期事项。

### 3.3 角色私有记忆与图谱边界

[`graph_memory_store.py`](../../../../../backend/app/character_agent/storage/graph_memory_store.py) 已有五类角色私有记忆池（event、observation、knowledge、social、higher-order），并通过 actor scope、story branch、valid time、recorded time、source event 和幂等键读取/写入。它可以作为本批“角色记忆永存但按隐私和感知边界读取”的实现基础。

这段代码**不是**全体角色公共社会图，也没有证明每个角色都拥有一个持续被社会因果传播更新的公共节点。公共派生图必须继续复用 HeavenlyGraph、authority projection 和已有 provenance/privacy/revision 边界；不能把 `CharacterGraphMemoryStore` 变成第二个世界真相 owner。

### 3.4 激活生命周期与表现镜像

[`activation.py`](../../../../../backend/app/population_continuity/activation.py) 已有 profile 注册、active/suspended/requeued/locked 生命周期、region assignment 的受限 project view 和 commit receipt。它能证明“角色可以被激活/暂停并保留可审计身份”，但还没有证明激活就是完整 L1-L4 角色智能体的 admission，也没有统一 Life/Presence/Soul owner。

[`presentation.py`](../../../../../backend/app/population_continuity/presentation.py) 只在 cadence receipt 确认后向 Godot fanout 固定公开字段；位置由 actor id 的稳定 hash 生成，且代码明确说明布局坐标不代表权威空间位置。它适合作为当前人口镜像证据，不可被写成真实空间同步、角色近场行为脚本或物理碰撞结算。

### 3.5 Laya adapter 与角色心智链

[`laya_provider.py`](../../../../../backend/app/character_agent/gateway/laya_provider.py) 已有固定 source/checkpoint revision、`/v1/systemone` endpoint、冻结候选校验、只返回候选选择、延迟和概率证据。它明确禁止 provider 提供执行参数、authority fact 或 fallback decision。

[`l3_planner.py`](../../../../../backend/app/character_agent/planning/l3_planner.py) 在配置 `CHARACTER_LAYA_ENDPOINT` 时把 L3 planning 路由到 Laya，并把角色 profile、记忆、动态状态、能力摘要和冻结候选放入 request context。这证明了**一条有限 L3 provider 路径**，不证明 Laya 已经覆盖全部 ThoughtMode、L1-L4 连续回路、B3 admission、慢/Deep 回落和真实质量门禁。

### 3.6 司命当前 group bridge

[`siming_projection.py`](../../../../../backend/app/services/siming_projection.py) 的 `GroupSimulationBridgePort` 只有 `summarize(room_id)` 协议；默认 `StubGroupSimulationBridge` 返回 `status="unavailable"`、`mode="shape_only"` 和只读摘要。[`siming_runtime.py`](../../../../../backend/app/services/siming_runtime.py) 在没有显式注入 bridge 时使用该 stub。

因此，司命当前可以消费人口 capability、storyline obligation、fairness 和 HeavenlyGraph 相关的受限输入，但默认运行时没有一个能持续推演全体角色的 group simulation bridge。它是本批最直接的实现阻断之一。

## 5. 阻断登记

### B-01：全 roster 的连续生命记录没有闭环证明

**影响规格：** 00、02、03、计划 01。

**现状：** roster 提供稳定 actor id，cadence/B0 和 seed planner 能处理被投影选中的角色候选；但还没有证据证明每个登记角色在每个窗口都有可恢复的生命状态、位置锚点、关系变化、承诺和记忆 cursor。

**解除条件：** 以正式 roster fixture 覆盖全体 actor，证明 B0 cursor、角色 revision、生命/位置/关系字段、缺席窗口追赶和恢复重放；不得用“生成了一个 seed”替代 continuity commit。

### B-02：公共社会生命图与全体节点覆盖缺失

**影响规格：** 02、04、计划 02/03。

**现状：** HeavenlyGraph、authority projection 和角色私有记忆图可复用；默认 group bridge 是 stub，尚无公共社会图的节点/边 allowlist、版本化 projection、影响传播查询和全量 coverage 证据。

**解除条件：** 先定义并验收 `CharacterRecordRef`、关系/地点/组织/事件/义务节点和来源边；由 owner projection 派生，支持 revision、privacy、valid/recorded time、冲突和回放；任何图查询不得直接提交领域事实。

### B-03：B1 轻量行为模块和 B2/B3 handoff owner 未闭合

**影响规格：** 00、03、05、计划 01/03/04。

**现状：** B0 连续推进、激活事件和角色智能体运行时分别存在，但没有一份已验收的 `ParticipationResolution`、B1 module registry、唯一推进权、handoff cursor、冲突处理和回退回执把同一角色串起来。

**解除条件：** 对同一 actor 做 B0→B1→B2/B3→B1/B0 场景回放；明确谁在窗口内拥有推进权、哪些字段可带入 L1、哪些字段必须由 owner 重新结算、失败如何 requeue。

### B-04：Laya provider、admission 和质量门禁不完整

**影响规格：** 01、03、计划 03。

**现状：** 已有 L3 adapter 和冻结候选约束，但没有真实 `laya-serve`/checkpoint 的 fresh evidence、中文心智输入基线、结构化可接受动作集合的覆盖率、选择质量阈值、延迟预算、slow/deep 回落和“实测触发必要微调”的正式门禁。

**解除条件：** 固定 multilingual checkpoint 为 A 阶段 baseline；用独立题集区分输入正确、候选覆盖、Laya 选择正确率、角色差异、校准和闭环执行；本地服务优先，无本地 LLM 时才使用 API；微调只能由预先登记的质量阈值触发，不能用 slow/deep 回退冒充 Laya 完成。

### B-05：Life / Presence / Soul 的 owner 与可见投影未统一

**影响规格：** 00、02、05、计划 01/04。

**现状：** 角色 profile、动态状态、activation region 和私有记忆分别存在；尚未有一个可审计的跨域 owner contract 规定生命状态、世界存在/位置、灵魂规则、角色感知和 Godot 表现之间的读取与写入边界。

**解除条件：** 逐域指定 owner、proposal/preview/commit/receipt 类型、隐私范围和恢复顺序；模型、图谱和表现层只能提交受限 proposal，不能直接写 Life/Presence/Soul truth。

### B-06：时间与空间的 `ClockMapping`/evidence envelope 缺失

**影响规格：** 05、计划 04。

**现状：** `SimulationClock` 和 cadence cursor 能推进逻辑时间，Godot 镜像有确认点和稳定布局坐标；没有后端 tick、区域、位置锚点、物理时间、客户端观测时间、延迟和 revision 的统一映射。

**解除条件：** 先定义单一时空 envelope，再做 far/warm/near/engaged 分层和现场回引后台；物理碰撞只有在结构化 evidence 经过 authority 结算后才能改变世界真相。必须在独立的 B/C 场景中验证延迟、乱序、重连、碰撞和回放。

### B-07：动物/静物原子行为与局部表现组装未接入现有边界

**影响规格：** 05、计划 04。

**现状：** 现有 population presentation 只有固定公开状态和动画 tag；尚未有“有/无自我意志动物”“受高级意志控制的动物”“静物模型脚本状态机”“原子动作”和 Physics-to-authority evidence 的统一合同。

**解除条件：** 行为脚本只能由注册原子模块组成；动物意志与高级控制必须可被显式覆盖并记录来源；静物状态只能由模型脚本和物理/领域 owner 变更；玩家近场观察不能绕过事实结算。

### B-08：非玩家中心的自主焦点覆盖没有规模证据

**影响规格：** 02、04、计划 02/03。

**现状：** 司命已有 fairness、obligation、population capability 和有限随机/候选输入，但尚未证明焦点能来自全体角色 due、关系传播、区域压力和公平 seed，并且在无玩家关注时持续产生可回放社会因果。

**解除条件：** 以无玩家输入的长窗口测试证明至少多个独立角色/区域产生可追溯 due、影响传播和 owner receipt；焦点只决定计算资源和观察窗口，不生成未经来源支持的剧情事实。

## 7. 实施放行顺序

放行顺序以 [计划 00](../../计划/既有中旬计划/00-总实施顺序与门禁计划.md) 为准，审查建议的最小证据顺序是：

1. 解除 B-01，先证明全 roster 的角色连续性和可恢复游标。
2. 解除 B-05/B-06，固定 Life/Presence/Soul owner 和时空 envelope，避免后续图谱与表现层重复建模。
3. 解除 B-02/B-08，证明派生社会图能覆盖全体角色并产生非玩家中心的因果候选。
4. 解除 B-03，固定 B0/B1/B2/B3 唯一推进权和交接回执。
5. 解除 B-04，完成 Laya 本地服务 baseline、质量评估和必要微调触发门禁。
6. 在 1–5 有 fresh evidence 后，再按计划 04 做近场活化、动物/静物脚本和 B/C 场景；该场景不复用 `StreetCombatDemo`，只复用 `StreetCombatActorDemo` 已验证动作底座。

没有解除对应阻断前，计划文件中的任务只能作为设计拆解，不能直接被解释为实施授权。
