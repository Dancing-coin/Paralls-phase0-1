# 时间空间表现与局部活化实施计划

状态：`analysis/planned/non-authorizing`

**Spec：** [规格 05](../../规格/既有中旬规格/05-时间空间表现层与局部活化规格.md)、[规格 03](../../规格/既有中旬规格/03-群体模拟B0-B1与角色智能体B2-B3交接规格.md)。

**Sources：** 十月角色 06/08/09/10/11/16；`docs/架构/运行时/模块/Godot表现与角色入口.md`；AGENTS runtime boundary；用户关于区域局部活化、动物/静物、物理和后台因果同步的讨论。

## 1. 目标和范围

让远场世界以低成本连续运行，玩家附近才创建/激活需要表现的对象；现场 physics/atomic actions/behavior scripts 形成可观测输入，backend owner 接受结构化证据和 intent 并回放确认结果。

不在本计划中实施通用编辑器 control-plane、AD/Blender 正式动作生产线、自走棋/单局运行时或全城高精度 3D 物理。

## 2. 前置条件

- Plan 01: identity/cursor/continuity/recovery Gate 1。
- Plan 02: region/location/actor/relationship projection 与 scoped query Gate 2。
- Plan 03: 角色 handoff、Laya admission、Owner receipt 和 failure paths Gate 3。
- Godot/physics/ESM 真实 message 和 scene admission 接口完成代码映射。

任一前置不满足时只可做静态设计或独立 presentation-only probe；不能声明后台和现场一致。

## 3. 预期责任文件

| 区域 | 责任 |
|---|---|
| `backend/app/world_runtime/` | cadence window、region activation read model 和时间映射接口 |
| `backend/app/character_agent/` / `backend/app/embodied/` | actor ingress、intent/evidence envelope、handoff receipt |
| `backend/app/gameplay/` / ESM owner | physics evidence admission、语义结算和 Owner receipt |
| Godot `scripts/` / `scenes/` | region presentation, local physics, atomic action/behavior script consumption |
| `backend/tests/test_population_presentation_projection.py` 等 | presentation projection, persistence, scope and evidence |
| Godot test/verification profiles | live scene and visible result; static checks are insufficient |

具体 Godot scene、autoload、adapter 和 owner 必须由实施前审计确认；禁止预设新场景自动替换既有 actor。

## 4. 任务序列

### Task 1：现有时钟/场景/物理边界映射

1. 查明 SimulationClock tick、world mode revision、Godot physics frame/time、backend event timestamp 的当前对应关系。
2. 查明 region load/unload、actor instancing、perception ingress、physics evidence 和 owner event 的真实路径。
3. 将已实现与 planned 的 ClockMapping、position anchor 和 transform ownership 分开登记。
4. 评估 cadence 落后、网络延迟和玩家立即碰撞情况下的竞争窗口。

**阻断：** 没有可验证时间映射时，任何精确的“现场反引导后台”都只能是 proposal，不能成为统一真相。

### Task 2：far/warm/near/engaged 策略

1. 使用现有 world mode/cadence 控制远场 B0/B1，不建立第二 scheduler。
2. 区域查询取得稳定 actor/object refs、presentation seeds、source revisions 和 visibility scope。
3. warm 区域只预构建可重建表现输入；不得读取 private memory 或将预测记为事实。
4. near 区域根据参与策略和设备预算选择脚本/Actor/Physics 实例数。
5. engaged 角色按 Plan 03 的唯一锁与 L1-L4/Laya admission 激活。
6. region exit 时释放局部实例，后端状态继续按 Owner/Core cursor 推进。

### Task 3：时空 evidence envelope

定义/复用结构化 envelope，至少可追溯：

```text
world_ref
region_ref
actor_ref/object_ref
physics_frame_id
mapped_world_tick/window
clock_mapping_revision
position_frame_ref
evidence_kind and digest
source_actor/client
visibility/scope
causation/correlation/idempotency
expected owner/character revisions
expiry/late policy
```

物理 evidence 只证明几何/接触/运动事实；其语义后果由 Owner 解释并结算。

### Task 4：原子行为脚本合同

1. 动物脚本组合原子动作与 agency policy；支持 `self_directed/directed/mixed`，并明确控制覆盖和打断条件。
2. 静物脚本采用有限状态机与受限自动行为，不创建角色心智或意志。
3. 每个模块声明版本、状态 schema、输入/输出、随机 seed、预算、物理约束、可见投影和结算所需 owner。
4. 脚本只能提出动作/物体变化候选；道具库存、门锁、损坏、受伤和生命变化由相应 Owner 结算。
5. 购买、消耗、货架补充等表现差异必须由确认 inventory/economy receipt 回投。

### Task 5：现场输入和后台收敛

1. Godot 上传证据采用有界队列，明确 drop/backpressure policy 和 prior-window late message 行为。
2. backend 经 L1/ESM/Gameplay admission 校验 scope、actor binding、time map、revision 和 replay identity。
3. 直接玩家动作与 NPC/animal response 的现场排序以 physics evidence window 为输入；持久顺序以 owner event order 为准。
4. 相同事件不能由 B0 和现场重复结算；取得 actor lock 或建立局部窗口 lease 的方案须复用当前 activation/authority boundary。
5. backend 提交确认 event/receipt 后生成新的 population/graph/presentation projection。
6. 客户端可以先显示可撤销预测，超时/拒绝/冲突时必须回退至最后确认状态。

### Task 6：区域同步和可见验证

以一处区域和有限 Actor/静物为样板：角色、动物、玩家、可购买物体均在后端和现场有稳定引用。完成后台空载推进、玩家进入、观察、近场互动、冲突碰撞、离开再返回、重启恢复和回放。

示例至少包含“马被勒住、回避孩子、碰撞包子笼”和“玩家同时撞入”。验收要区分 player view、physics evidence、world truth、population approximation、character memory 和 presentation view。

## 5. 验证与证据

Backend：已有 `test_population_presentation_projection.py`、`test_population_godot_runner.py`、`test_population_godot_evidence.py`、`test_world_runtime_population_cadence.py`、`test_esm_physical_channel_runtime.py`、`test_embodied_authority_settlement.py` 和相关 websocket tests 先作基线。

Godot：必须有 editor/runtime profile 的 fresh evidence。静态脚本测试不证明物理碰撞、actor admission 或可见结果。证据至少包括：

- scene/build revision 和运行时场景身份；
- backend cadence/tick mapping；
- physics evidence envelope；
- owner event + receipt/replay digest；
- Character Core receipt（角色连续性受影响时）；
- graph/presentation projection revision；
- 截图/录屏中的确认前后可见状态；
- 玩家同时碰撞时的稳定排序和恢复结果。

运行 backend focused tests、`python -m pytest -v` 和通过 `docs/harness.md` 选取的 Godot integration profile；完成宽范围变更后执行 `python scripts/verification/harness.py --profile all`。

## 6. 回滚点

- region activation 可关闭，远场 cadence 保持。
- behavior module 可逐个 disable，回到静态/已确认 presentation projection。
- 物理 evidence adapter 可切换诊断/零写模式；已提交 owner events 不删除。
- Godot prediction 可关闭并等待 owner receipt；不能在失败时保持假成功状态。
- scene actor admission 失败只影响新实例，不替换既有 actor 或 asset binding。

## 7. 阻断

- 缺 ClockMapping/evidence revision：阻断现场持久回写和精确后台同步声明。
- 缺 physics-to-owner admission：现场动作仅作本地表现，不产生持久后果。
- 缺静物/库存 owner operation：可以播放可逆预测，不可持久减少库存。
- 缺 Life/Presence owner：不可宣称死亡/复活/生成/销毁同步。
- 没有 fresh Godot scene evidence：只能报告静态合同和后端测试。
