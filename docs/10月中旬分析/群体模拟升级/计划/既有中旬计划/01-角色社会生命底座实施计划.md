# 角色社会生命底座实施计划

状态：`analysis/planned/non-authorizing`

**Spec：** [规格 00](../../规格/既有中旬规格/00-全体角色社会生命与混合心智总规格.md)、[规格 03](../../规格/既有中旬规格/03-群体模拟B0-B1与角色智能体B2-B3交接规格.md)。

**Sources：** 十月角色 01、06、08、10、13；`2026-08-22-character-simulation-memory-seed-continuity-design.md`；人口连续性主线；[现状审查](../../审查/既有中旬审查/00-实现映射与阻断登记.md)。

## 1. 目标与边界

在既有 Character Core、profile/dossier、roster、population hot state 和 cadence 上形成所有 admitted 角色都可恢复的生命连续性记录。只实现有真实 owner 的字段；Life/Presence/Soul owner 未准入时保留 unavailable/diagnostic，禁止推导 alive/safe。

**不做：** 新角色真相库、新 scheduler、新 event store、新时钟、全部角色 LLM、社会图写入或未授权的静物/动物事实。

## 2. 预期文件责任

执行前按实际代码重映射，不得覆盖用户已有修改。

具体新文件名在实施时由现有目录模式确定，本计划不预设新 truth owner 或 registry。

## 3. 任务序列

### Task 1：Owner 与字段基线

**目标：** 固定角色生命记录字段的唯一来源和 owner。

**操作：**

1. 映射当前 profile/dossier、PopulationRoster、PopulationHotState、Character Core、authority projection 和 activation 状态。
2. 对 `life_state`、presence、位置、日程、需求、资源引用、关系、承诺、模块状态、memory cursor 列出 source owner、read API、write API、revision 和 privacy。
3. 缺 owner 的字段登记为 unavailable/deferred，不用字符串或 mock 产生写权限。
4. 固定哪些字段属于 authored profile、runtime continuity、domain fact、derived projection。

**交付证据：** owner-field matrix、read/write boundary 表、确定的 roster inclusion policy。

**门禁：** 任一关键状态字段没有 owner 时，不得推进其生产性写回，只能把字段标为 unavailable 并继续独立的身份/游标工作。

### Task 2：全 roster identity 与 continuity admission

**目标：** 已注册角色自动有一个稳定 continuity anchor，未激活状态可恢复。

**操作：**

1. 复用 roster 和 profile ref；禁止在 Population 层另造 actor identity。
2. 设计幂等 admission：相同世界、actor、profile revision 不重复建立连续性记录。
3. 记录 admitted/rejected/requeued 原因、profile revision、world ref 和初始 cursor。
4. tombstone、死亡和 despawn 分离；没有 lifecycle owner 时不将缺记录当成死亡或未生成。
5. 在持久化恢复时从当前 authority/continuity checkpoint + tail 重建，不依赖进程内缓存。

**预期验证：** `test_population_roster.py`、`test_population_roster_import.py`、`test_population_persistence_wal.py`、`test_population_durable_cadence_recovery.py`、`test_character_population_continuity.py`。

### Task 3：连续状态和 B0 cursor 合同

**目标：** 让每个 admitted actor 的低精度状态可以准确推进、暂停、恢复。

**操作：**

1. 先保持 `advance_b0_row()` 的 pure deterministic 语义，将现有字段和游标归属明确为当前合同。
2. 扩字段前为每个新增字段说明来源、单位、范围、时间含义、可聚合性和 owner。
3. `simulation_tick_cursor` 只由已确认 cadence/window 推进，不能因候选、planner report 或模型调用推进。
4. batch due 执行采用稳定排序；同一 read set + seed + policy 得到同一 delta。
5. stale cursor/partial write/retry 必须零写或由 receipt-driven recovery 收敛。

**预期验证：** `test_population_b0_continuity.py`、`test_population_continuous_runtime.py`、`test_population_hot_state_equivalence.py`、`test_population_parallel_determinism.py`、`test_population_checkpoint_closure.py`、`test_population_batch_settlement_equivalence.py`。

### Task 4：B1 模块状态与 proposal boundary

**目标：** 在不调用模型的前提下，让角色档案和经历通过受限模块产生差异候选。

**操作：**

1. 只接纳已注册、版本化的纯计算/受限模块；模块不能自行写 Owner。
2. 每个模块定义 schema、输入投影、状态字段、allowed output kind、运行间隔、成本上限和 fail-closed behavior。
3. 从来源设计选择第一批模块，不能根据本方案臆造性格数值或行为事实。
4. 模块输出显式标为 `population_module/approximation`，包含 reason codes、source revisions、expires tick 和 recheck requirement。
5. 候选与 owner-bound intent 分离；有客观效果时仍必须走既有 capability catalog 和 Owner receipt。

**验收：** 两个具备不同 authored profile/模块输入的角色，在同一冻结事件下产生不同、可解释候选；模块确定性和上限能回放；未知模块零写。

### Task 5：角色记忆 seed 和 exposure admission

**目标：** 保证角色被激活前后的 memory cursor、候选和 Character Core 物化连续。

**操作：**

1. 复用 `CharacterSimulationSeedCandidate`、`CharacterMemoryCandidate`、`CharacterContinuityCommand/Receipt`。
2. 增加/消费 exposure basis 时复用角色 10 的定义；world event 不自动意味着 actor exposure。
3. 私人记忆 candidate 只存引用、时间和最小必要摘要，写入由 Character Core admission 决定。
4. 将 Owner receipt、连续性 receipt 和 memory materialization receipt 分开统计。
5. 修复恢复时的重复物化和 owner 已提交但 Core 未接纳的补交路径。

**预期验证：** `test_siming_led_population_seed_continuity.py`、`test_character_agent_seed_continuity.py`、`test_character_agent_memory_writeback.py`、`test_character_memory_consistency_flow.py`、`test_character_graph_memory_store.py`。

### Task 6：角色精度状态与安全退出

**目标：** 记录同一 actor 当前由何种推进方式持有，并提供可恢复降级。

**操作：**

1. 复用 activation lock 和已有状态，不把 `fidelity_state` 当作第二调度器。
2. 定义 B0/B1/B2/B3 状态事件/投影来源和 allowed transitions；只有实现来源已有依据才启用。
3. 超时、模型不可用、权限收紧时执行 continuity floor/requeue。
4. 回退保留 accepted deltas、unresolved obligations、simulation cursor 和 memory cursor。
5. 每 actor 每窗口唯一推进者；持锁角色的 cadence 到期进入队列，不越过锁写入。

**验收：** activation conflict zero-write、stale frame rejection、停机恢复和 lock release 有测试证据。

## 4. Harness 与验证

先跑有针对性的上述 tests 和 `python -m pytest -v`；扩展为 broad change 后运行 `python scripts/verification/harness.py --profile all`。Harness 产物按 `docs/harness.md` 和 `.harness/` 契约保存，仅把 fresh evidence 导出到仓库外要求的位置。

必要指标：roster coverage、unresolved owner fields、cursor lag、B0/B1 cost per actor、replay digest、memory candidate/materialized/rejected counts、activation lock collision、recovery backlog。

## 5. 回滚点

- admission 可停用并继续读历史 continuity。
- B1 注册模块可逐个关闭，角色回到 B0；已确认 Owner/Core 事实不删除。
- 新字段只通过版本化 projection/可重建 checkpoint 引入；迁移保留旧 schema 读取。
- memory 写入失败时留 pending candidate/requeue，不清除来源 owner event。

## 6. 依赖与阻断

- Gate 0 owner matrix 未通过：只允许静态审计和无写 pure calculation。
- Character Core 不存在对应 admitted field：不得把 B0 delta 写入该字段。
- Life/Presence/Soul owner 未准入：维持 unavailable，不影响独立身份/游标测试。
- 规模优化不得先于 determinism/replay/privacy gate。
