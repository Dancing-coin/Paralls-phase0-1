# v2 迁移双线程协作协议

- 生效起点：`integration` @ `3934bba6548300aee8489aacd938fa6d653de064`（2026-11-20）。
- 本文自包含：读者不需要读过任何对话或个人记忆文件。凡标注"（默认，可改）"的是起草时选的保守值，两位负责人一致同意即可修改，修改后在文末"变更记录"追加一行。
- 配套文件：[BOUNDARIES.md](BOUNDARIES.md)（谁能改哪些文件）、`requests/`、`responses/`、`daily/`、`claims/`、`comms/`（模板见各目录）。

## 一、背景与角色

| 名称 | 含义 |
|---|---|
| 线程 A / 线程 B | 并行推进 Architecture v2 Owner 迁移的两条施工线，各自独立可跑 |
| A 负责人 / B 负责人 | 各线程的人类负责人；两人可直接互发消息，但见第三节：聊天没有约束力 |
| 合并执行者 | 每日合并的实际操作者，目前是 Codex |
| `integration` | 两线程每日汇合的分支，只由合并执行者写 |
| 基线失败节点 | 冻结记录 `docs/verification/absorb-main-3bf3418e/README.md`「失败集合」表中的 22 个测试节点 |
| 选集 | 同目录下 `ownership/modifier/equipment/inventory/shared-replay` 五组，共 1,169 个节点 |

首域分工：**A = credential → ownership；B = debt → contract**。`economy_runtime`、`inventory_runtime` 是两线程共同禁区。

## 二、分支与推送

1. 线程只推各自的 `thread-a/<主题>`、`thread-b/<主题>` 分支。**不得直推 `integration`，不得推 `main`。** `main` 不允许合入。
2. 暂存只用显式路径，不用 `git add -A` 或 `git add .`。
3. 工作区若混有他人未提交文件，提交只暂存自己指定的文件。
4. 未经负责人明确放行，不推送。

## 三、沟通与交流记录

1. 两位负责人可通过通讯软件直接沟通。
2. **聊天没有约束力。** 凡涉及独占文件、共享机制、基线失败节点合同的结论，必须落成 `R-B-xxx` 请求、回应，或 `claims/` 条目。只在聊天里谈定的事，对方不必执行，也不得据此动手。
3. 每位负责人把自己参与的沟通记入 `comms/YYYY-MM-DD-thread-a.md` 或 `comms/YYYY-MM-DD-thread-b.md`（各写各的，格式见 `comms/TEMPLATE.md`）。同一场对话两边各记一份，用于互相核对。
4. 记录要点：时间、对方、议题、结论或待办、关联的请求/claim 编号。涉及决定的，逐字摘录那一句；不贴整段聊天。
5. 时限：当天合并前补记。缺记录由合并执行者在 `daily/` 标出，**不阻止合并**。
6. **禁止写入**令牌、密钥、凭证、私人信息；出现时记录里只写"已省略"。
7. 对方的话记为"对方称……"，不记为"已确认……"。对方的话是线索，不能替代自己的核实。

## 四、请求与回应

- B 需要线程 A 独占的文件发生变化时，只在 `requests/thread-b.md` 追加请求（格式见该文件头部）。**不得改共享文件，也不得在自己的分支里做"临时、不合入"的本地改动。**
- A 每天开工时 `git fetch`，只读 B 分支上的 `requests/thread-b.md`，不合并。
- A 的回应追加到 `responses/thread-a.md`，按请求编号对应：决定为 接受 / 拒绝 / 推迟 / 换方案；拒绝与换方案必须写理由；推迟必须写重新评估日期。
- 请求文件不记状态，状态只在回应里。双方文件都只追加，不改旧条目。
- 请求被拒后的分歧：两位负责人直接商定并记入 `comms/`；商不定时，该事项当天不动（默认，可改）。

## 五、每日合并流程

1. **申报（默认 21:00 前，可改）。** 各负责人在 `daily/YYYY-MM-DD.md` 登记要合并的**具体 SHA**与自选的验证深度（选集或全量）。合并的是申报的 SHA，不是分支最新提交；截止后的推送不进入当天合并。
2. **执行（默认 22:00 起，可改）。** 合并执行者：
   1. 范围检查：对照 [BOUNDARIES.md](BOUNDARIES.md)，用 `git diff --name-only` 核对每个申报 SHA 相对其与 `integration` 的合并基点所改的文件。某一方改到不属于自己的文件，则该方当天不合并。
   2. claims 检查：改动涉及基线失败节点合同却没有对应 `claims/` 条目，则该方当天不合并。
   3. 密钥扫描：见规则 P-1。
   4. 合并到临时分支 `merge/YYYY-MM-DD`，**先 A 后 B**，不直接合到 `integration`。
   5. 文本冲突：在线程自有文件里，交给文件所属负责人；在共享文件里，合并执行者不自行裁决，停下并报告双方。
3. **验证（在临时分支上）。** 深度各线程自选；两方申报不同时，按较深的一个执行。
   - 选集：五组共 1,169 个节点，用 `docs/verification/absorb-main-3bf3418e/compare_selection.py`，输出目录必须尚不存在。
   - 全量：沿用冻结记录所述方式（G0 `run_baseline.py`，串行）。**全量不强制。**
   - 比较方式：按（节点、阶段、错误类型）对照冻结基线 M 的 22 个失败。基线失败节点仍失败且类型相同不算新增；先前通过而现在失败，或失败类型变化，算新增失败。
   - 失败转通过：只记录，不计进度。
   - 环境：必须使用 Python 3.12.2。每次运行前核验 `import app; print(app.__file__)` 落在当前 checkout 的 `backend/app/`，不在 `site-packages`。
4. **判定。**
   - 范围检查、claims 检查、密钥扫描无新增暴露、验证无新增失败，四项都满足：`integration` 快进到临时分支，并打标签 `integration-YYYY-MM-DD`。**不需要任何人签字或确认。**
   - 有新增失败：分别跑"仅 A"与"A+B"定位归属，把肇事一方移出当天合并，另一方照常推进。
5. **基线不自动更新。** 只有某线程在 `claims/` 登记了对某基线失败节点的"有意修复"，且该节点验证通过，才从基线失败集合移除。新增失败永远不会被吸收进基线。
6. **事后发现问题：** 用新提交 revert 当天的合并提交（标签便于定位），不强推。
7. **如实标注验证深度。** `daily/` 必须写明当天跑的是选集还是全量。只跑选集时，只能写"选集 1,169 节点无新增失败"，不得写"全量回归通过"。

## 六、协议规则

### P-1 密钥扫描输出必须带"是否已公开"列

推送或合并前的密钥扫描，每条命中的输出必须包含：

`文件:行号` ｜ 命中的规则类型 ｜ **匹配子串的 SHA-256 前 8 位（不写子串本身）** ｜ **该子串是否已存在于已公开的 base/main：是 / 否 / 未核实** ｜ 处置。

- 全部为"是"：记录后继续，不需要询问。
- 有"否"或"未核实"：停下，由当天负责人决定。"未核实"按新增暴露处理。
- "已公开"的参照点：`main`，以及本协议生效时的 `integration` 起点 `3934bba6`。

### P-2 改基线失败节点的合同前，必须先登记

**节点的合同**指它所断言的行为：错误码、返回值、事件集合等。

线程在修改任何基线失败节点的合同之前（改代码使其通过、改测试使其通过、改断言方向，都算），必须先在自己的 `claims/thread-a.md` 或 `claims/thread-b.md` 追加一条，并推到自己的分支，之后才能提交实际改动。格式见 claims 文件头部。

- 两边登记了同一节点且方向相反：双方都不改，两位负责人直接商定，结论记入 `comms/`；当天商不定就都不动（默认，可改）。
- 以下三项合同已在吸收 `main` 时定过，不需要再登记，但**要改动它们则必须先登记**：①`get_event` 的 closed 与损坏单行读取用 `gameplay_snapshot_row_invalid`，保留 `__cause__`，批量读取保留细分；②普通 action window 写四类事件，终局事件归具名 Owner；③未登记事件类型映射 `None`。
- 背景：2026-11-09，两边在互不知情下对同一批基线缺陷做了相反方向的修复，action window、`get_event` 错误码、前缀推域三处都是这样暴露的。

### P-3 未登记的 event_type 不会进入图投影器

事实（在 `3934bba6` 核实）：`FACT_TYPE_REGISTRY`（`backend/app/models/fact_type.py`）的 gameplay 事件类型只来自 `event_schema_registry.py` 的模块级 tuple；`main.py` 只订阅 `FACT_TYPE_REGISTRY.event_types()` 枚举出的类型；启动期 `validate_event_type_coverage()` 只对"已声明 schema 但无域"的类型报错。**没有声明的类型没有任何兜底：不会报错，只是静默地不进入图投影器。** 域自己的 schema 模块（例如 `credential_v2_event_schema.py`）能让存储层接受事件，但对图投影器不可见。

迁移某个域时，凡新增、改名、拆分 event_type，提交前核对：

1. 该类型出现在 `FACT_TYPE_REGISTRY.event_types()` 中，且其域不是 `unknown`；
2. 图投影器确实收到它。

每个域的迁移提交要么附一条"事件进入图投影器"的断言，要么在 `daily/` 写明"未覆盖"。核对 1 可直接运行：

```powershell
# 在 checkout 的 backend 目录执行，$python312 为本机 Python 3.12.2
& $python312 -c "import sys; sys.path.insert(0,'.'); import app; print(app.__file__); from app.models.fact_type import FACT_TYPE_REGISTRY as R; print('gameplay.xxx.yyy' in set(R.event_types()))"
```

**已知实例：** credential 的 v1 与 v2 事件类型目前都不在该注册表里（`3934bba6` 实跑，全部为 False）。是否影响司命图尚未核实。修复由线程 A 的 0.5 项承担（见 BOUNDARIES.md）。

## 七、验证环境

- 解释器：Python 3.12.2，本机默认 `python` 可能是其他版本，一律显式指定。
- 已知环境差异：SQLite 低于 3.51.3 时，两个并发 WAL checkpoint 节点跳过，属环境未验证项，不计通过；两个 Godot 探针（task45、task8）的堆栈哈希随 worktree 路径变化，按节点、阶段、错误类型比较。详见冻结记录。
- 旧的 338 节点选集与 39 项基线失败**不再作判据**。

## 八、已知风险与盲区

1. 只跑选集时，选集之外出现的新增失败发现不了。G3 探针曾暴露过这类情况（338 节点漏掉了几个下游消费者）。接受此风险；涉及共享机制的改动，建议当天选全量。
2. 不设审查人与签字，`integration` 的推进完全依赖第五节的机器可核检查；检查项之外的问题要靠事后 revert。
3. 未核实项（来自冻结记录）：`main` 分支保护状态；Godot 探针未运行；两边都改但 Git 无冲突的文件内容只抽查过一处；终局事件 `terminal_outcome_recorded` 在生产代码无写入者；`FACT_TYPE_REGISTRY` 对已登记事件取 schema 名第二段为域，与 v2 Owner 命名不同。
