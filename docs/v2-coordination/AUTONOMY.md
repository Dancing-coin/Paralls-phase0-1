# 自主推进规则

- 版本 1（2026-11-22）。配套：[PROTOCOL.md](PROTOCOL.md)、[BOUNDARIES.md](BOUNDARIES.md)、[board.md](board.md)。
- 目的：让线程 A、B 不靠逐步请示也能推进，同时不让质量靠人盯。做法是**预先写死决策表 + 机器可查门禁 + 可回退的小提交**，不是"先做再说"。

## 一、三条义务

1. **中间产物写进仓库文件，不只在对话里报。** 负责人读仓库，不读对话，也不转述。没写进文件的结论视为不存在。
2. **一次一个单元。** 单元结束即提交；不攒大改动。提交可独立回退（或写明为何不能）。
3. **门禁没过不合并、不宣称完成。** 可以继续做下一个单元，但该单元标"未通过"，不得写成通过。

## 二、决策表

### 自主继续（不需要请示）

| 情形 | 要求 |
|---|---|
| 改动只落在自己归属的文件（见 BOUNDARIES） | 直接做、提交、推自己的分支 |
| 新增或修改本域测试、本域规则包 | 同上 |
| 新增事件类型、改事件类型名 | 必须过 P-3 断言，断言结果写进证据或 `daily/` |
| 持久事件**新增可选字段** | 单独提交 + 枚举读取方 + 跑全量 + 写兼容说明；不停 |
| 探针零代码通过 | 记结论，继续 |
| 探针失败 | 按 §四 归因表自判；判为"前置未完成"就补前置后重跑，判为"架构限制"则停 |
| 定向测试与选集无新增失败 | 继续 |
| 需要判断"是我的改动还是既有失败" | 自己二分：仅本单元 / 本单元 + 上一单元，结论写进证据 |
| 选择实现方式、文件摆放、提交粒度 | 自己决定，写进提交信息 |
| 下一个做什么（有多个候选） | 按 §五 优先级自行选择，在 `board.md` 更新状态 |

### 必须停下升级（写进 `handoff.md` 或 `board.md` 的"待决"列，然后停）

| 情形 | 为什么不能自决 |
|---|---|
| 需要改存储核心（`event_store.py`、`models.py`） | 影响所有域 |
| 需要改共同禁区（`economy_runtime`、`inventory_runtime`、第 4 波枢纽） | 违反归属 |
| 需要改对方独占文件 | 走 `handoff.md`，不自改 |
| 需要改基线失败节点的合同（未按 P-2 登记） | 11-09 有过反向修复 |
| 持久事件**删除、改类型、改语义** | 破坏历史回放 |
| 探针需要改 Owner 或 runtime 代码 | 这是架构结论，不是实现问题 |
| 新增 Owner、改变 Owner 的 native/stewarded 分类 | D5 权限在负责人 |
| 发现新的第二真相（自建状态、绕过 EventStore 的写路径） | 需架构判断 |
| 归属未定的文件导致测试失败（如 `fixed_offer_purchase.py`） | 不能顺手改别人范围 |
| 连续两次尝试仍不能让某项门禁通过 | 避免反复消耗 |
| 发现令牌、密钥、凭证 | 安全 |

**除上述之外，不要停下来问。** 包括：不确定要不要拆提交、不确定选哪个实现、不确定某文件算不算自己归属（按 BOUNDARIES 的字面判断，有疑问就写进 `handoff.md` 并**继续做自己范围内的部分**）。

## 三、门禁（合并前逐条执行，全部通过才可合并）

| # | 检查 | 命令或方法 | 通过条件 |
|---|---|---|---|
| G1 | 范围 | 对每个申报 SHA：`git diff --name-only <merge-base> <sha>`，对照 BOUNDARIES | 全部在自己归属内 |
| G2 | claims | 改动涉及的基线失败节点，须在 `claims/` 有登记 | 无遗漏 |
| G3 | 事件可见性 | P-3 的注册表断言 | 新事件全部在 `FACT_TYPE_REGISTRY.event_types()` 内，域不是 `unknown` |
| G4 | 单元 DoD | 证据文件含 U1–U10 十项，缺项须标注"未做"及原因 | 缺项已显式标注，未伪装为完成 |
| G5 | 回归 | 冻结五组选集（1,169 节点，`absorb-main-3bf3418e/`）**加全部已登记单元选集**（`docs/verification/selection/*.json`），用 `compare_selection.py` 逐份跑；涉及共享机制或持久事件时加全量 | 无新增失败；`daily/` 如实写跑了哪些选集与深度 |
| G7 | 单元选集登记 | 域迁移类提交须新增或更新 `docs/verification/selection/<unit>.json`（规格 U11） | 缺文件 → **不通过**；文件存在但节点全是正例、无回归价值 → 记录并报告 |
| G6 | 密钥 | 按 P-1，输出带"是否已公开"列 | 无"否"或"未核实" |

门禁失败时，线程自己做二分定位，**把责任归属写进 `daily/`，然后按结果决定：自己的问题就修；对方的问题就写 `handoff.md` 并停**。

## 四、探针失败归因表（自判，不需要请示）

| 失败方式 | 判定 | 动作 |
|---|---|---|
| 需要改 FactType 注册表结构 | 声明能力不足 | 补 schema，记缺口，继续 |
| 需要改校验器（可放宽且不违反 H1–H12） | 校验过严 | 调整并补测试，继续 |
| 需要改校验器但违反 H1–H12 | 架构限制 | **停**，写结论 |
| 需要改冲击管线 / L5 引擎 | 前置没落地 | 记录"L5 未覆盖"，先把引擎做出来再重跑 |
| 需要改 Owner 或 runtime 代码 | 机制没抽出来 | **停**，写具体缺口 |
| 需要新增 Owner | 是新事实域 | **停**，按 Owner 门槛判 |
| Bond/原语不变量无法表达 | 原语切法错误 | **停**，回 L1 |

## 五、下一步选什么（无人指派时）

1. 先看 `board.md` 的"待决"列有没有属于自己、已解除的项。
2. 再看当前波次要迁移的域缺哪项机制——缺什么先做什么（例如域迁移需要 Holdings，就先做 Holdings）。
3. 没有具体依赖时：
   - 线程 A：M3-1 `OwnerCommitBuilder` → M2-2 `read_as` → M1-2 Holdings → M1-3 Pool。
   - 线程 B：按 `board.md` 的波次表选"Owner 明确、非枢纽、导入者 ≤2"的域；满足三条件即可自行开始，不需要再确认。
4. 选定后在 `board.md` 把该行状态改为"进行中"，写明单元名。

## 六、汇报与检查

- **取消逐单元汇报。** 每单元结束写一条记录到 `daily/YYYY-MM-DD.md`：单元名、提交 SHA、U1–U10 状态、验证深度（选集/全量）、未覆盖项。
- 负责人随时读仓库；不需要线程主动转述。
- 只有决策表"必须停"的项需要负责人表态；表态写进 `handoff.md`（"项目负责人决定：……"）。
- 负责人可在里程碑结束时做一次抽查：读 `board.md` + 最近三个提交的 diff + 证据文件。抽查不通过时，按 PROTOCOL 的 revert 流程处理，不重写历史。

## 七、这套规则下的已知风险

1. 无人逐步复核，错误会存活到门禁或抽查。缓解：小提交、可回退、门禁机器查。**接受此风险。**
2. 门禁只覆盖机器能查的部分；U1、U2 的语义质量仍靠抽查。**接受，并在里程碑抽查时重点看这两项。**
3. 线程可能把"未做"写成"未覆盖"来绕过。"未做"与"未覆盖"含义不同，`daily/` 必须用准确措辞；抽查时优先查这一处。
