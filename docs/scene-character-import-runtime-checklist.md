# 场景与角色导入运行时检查清单

这份文档总结本项目在 `Blender -> Godot` 场景导入、角色导入和运行时联调中的经验。

目标不是记录某一次具体修 bug 的过程，而是沉淀成之后可以复用的规则。

适用范围：

- 新场景导入
- 新角色导入
- 角色替换已有占位体
- 运行时穿模、脚陷地、首屏不可见、交互锚点错位等问题排查

不适用范围：

- Phase 1 生产级导航系统设计
- 完整 DCC 自动化流水线
- 多人协作资产平台治理

## 1. 结论先行

最重要的经验只有一句：

> **碰撞模块必须和建模契合。**

如果可见模型、碰撞体、角色控制器、巡逻路线、交互锚点彼此不对齐，就会出现：

- 脚没入地面
- 脚浮空
- 角色穿柱子、穿台阶、穿墙
- 巡逻看起来正常但实际在撞碰撞体
- 首屏构图里看不到 NPC
- 交互发生在错误位置

不要把导入工作理解成“把模型放进项目”。
真正的目标是：

- **可视模型**
- **碰撞**
- **控制器**
- **动作**
- **相机**
- **交互锚点**

六者对齐。

## 2. 核心原则

### 2.1 先定碰撞，再定视觉

新场景导入后，优先验证：

1. 地面碰撞是否连续
2. 台阶/斜坡是否与视觉一致
3. 墙体和柱体是否真的挡得住角色
4. 玩家出生点是否落在有效碰撞面上

不要先花时间调材质、灯光、色调，再回头补碰撞。

### 2.2 角色行为壳和可视壳必须分离

保留行为壳，例如：

- `CharacterReplica`
- `InteractiveObject`
- `EnvironmentStateNode`

可视模型统一挂在：

```text
VisualRoot
  AssetMount
    RotationOffset
      ScaleOffset
        ImportedModel
```

这样可以做到：

- 模型可换
- 朝向可修
- 缩放可修
- 行为逻辑不被打散

### 2.3 不要靠肉眼猜“脚是不是埋地”

必须尽量量化：

- 角色控制器根节点高度
- 模型相对根节点的最低点
- 当前地面碰撞高度
- 应用后的视觉偏移值

如果角色是长袍、披风、裙甲造型，纯看截图非常容易误判。

### 2.4 场景实例值可能覆盖脚本默认值

修改脚本默认参数后，要同时检查：

- 脚本默认值
- `.tscn` 里的实例覆盖值

典型例子：

- `backend_url`
- `player_shell_visual_offset`
- `patrol_points`
- `idle_role_state`

如果只改脚本，不改场景实例，运行时仍可能吃旧值。

### 2.5 旧元素先隐藏，再删除

当新场景或新角色正在替换旧灰盒内容时：

- 先让旧元素不可见
- 保留逻辑壳
- 等新锚点和新交互完全接通，再做彻底删除

这比“一口气删干净再补”更安全。

## 3. 场景导入检查顺序

推荐顺序：

1. 导入场景模型
2. 检查地面/墙体/柱体碰撞
3. 确认玩家出生点
4. 确认相机默认构图
5. 放入角色壳节点
6. 再挂正式角色模型
7. 最后清理旧灰盒可见层

### 场景导入最低检查项

- 场景能打开
- 玩家不会出生在空中或地下
- 玩家不会一走就穿墙
- 柱子、台阶、桌子这类大体量物件的碰撞与视觉基本一致
- 相机默认首屏能看到关键区域

## 4. 角色导入检查顺序

推荐顺序：

1. 导入角色模型
2. 验证骨架是否被识别
3. 验证动作是否能切换
4. 测量模型最低点
5. 调整 `RotationOffset / ScaleOffset / visual offset`
6. 检查移动、跑、跳、说话、检查、警觉等状态
7. 放到真实场景里验证，不只在空白测试场景里验证

### 角色导入最低检查项

- `load()` 成功
- `instantiate()` 成功
- 骨架映射可用
- 至少一组 idle / walk / run / speak / inspect / alert 动作可播放
- 首屏能看到角色
- 角色站在地面上，不明显脚陷/脚浮

## 5. 碰撞与建模对齐的具体经验

### 5.1 玩家控制器壳不等于真实地面

第三人称控制器的 `CharacterBody3D`、胶囊体、地面检测，可能仍基于旧碰撞逻辑。

所以要警惕：

- 可见地面是新场景地砖
- 实际碰撞仍是旧灰盒平面

如果两者高度或形状不一致，就会出现脚部观感异常。

### 5.2 巡逻路线必须按可导航空间设计

不要只给“看起来差不多”的几个点。

巡逻点应当考虑：

- 当前地面碰撞
- 柱子和装饰物位置
- 台阶和斜坡
- 玩家初始相机能否看到

推荐先给短直线往返，再逐渐复杂化。

### 5.3 大体量场景里先解决“能看见”，再解决“更自然”

角色经常不是“不存在”，而是：

- 出生太远
- 被柱子挡住
- 初始相机没带到
- 巡逻线跑到视野外

所以首屏可见性本身是验收项。

## 6. 旧元素清理策略

优先级建议：

### 第一阶段：隐藏旧可见层

例如：

- `GreyboxRoomRoot.visible = false`
- `GreyboxTableRoot.visible = false`
- 旧交互物 `visible = false`
- 旧环境球 `visible = false`
- 调试 HUD `visible = false`

### 第二阶段：替换旧锚点

等新场景中的真实物件锚点接通后，再替换：

- `InteractiveObject`
- `EnvironmentStateNode`
- 旧 Letter / 桌子 / 灯具占位体

### 第三阶段：彻底删除旧壳

只有在新锚点已经承担全部职责后，才删除旧壳。

## 7. 动作映射建议

角色动作集至少分两类：

### 运行时动作

- `idle`
- `walk`
- `run`
- `jump`

### 表现动作

- `guard`
- `observe`
- `speak`
- `inspect`
- `alert`
- `ambient`

建议把“表现动作”先绑成显式键位，方便调试。
等验证稳定后，再决定哪些保留给最终玩家，哪些只作为开发调试动作。

## 8. 验证方式建议

### 8.1 系统抓屏

适合验证：

- 窗口是否真的启动
- 前台是不是目标进程
- 当前是否能看到游戏窗口

### 8.2 引擎内视口导图

适合验证：

- 真实渲染结果
- 角色是否进入画面
- 旧元素是否还在可见层
- HUD 是否遮挡

对于场景与角色联调，**引擎内视口导图通常比系统抓屏更可靠**。

## 9. 通用检查清单

每次做场景或角色导入时，至少检查：

- [ ] 角色/场景资源能正常导入
- [ ] 骨架与动作可用
- [ ] 角色壳与可视壳分离
- [ ] 玩家出生点落在有效碰撞面上
- [ ] 可见地面与实际碰撞基本一致
- [ ] 角色首屏可见
- [ ] NPC 巡逻路径不会直接穿模
- [ ] 旧灰盒可见层已隐藏
- [ ] 旧交互物/环境锚点若还保留，已确认是否仍承担逻辑职责
- [ ] 相机/HUD 没有遮挡主要展示内容

## 10. 本仓库中最值得复用的做法

对于当前仓库，后续继续导入场景和角色时，优先复用这些思路：

- 角色继续走 `CharacterReplica` 外壳
- 模型继续挂到 `VisualRoot/AssetMount/.../ImportedModel`
- 新场景继续优先隐藏旧灰盒可见层，而不是直接删
- 巡逻路线先短线验证，再放大范围
- 遇到脚陷/脚浮，先测最低点和偏移，不靠肉眼猜

## 11. 一句话版

以后做导入时，不要只问：

> “模型进来了吗？”

而要问：

> “模型、碰撞、控制器、动作、相机、交互锚点，是否已经对齐？”

真正会让场景坏掉的，通常不是模型本身，而是这些层之间的错位。
