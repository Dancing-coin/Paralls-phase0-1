# 事实上抛链路与多模态链路

状态：当前仓库专题架构文档

本文专门回答三个问题：

1. 当前仓库里“事实上抛链路”和“多模态链路”分别是什么
2. 两条链在结构上有什么关系
3. 事实上抛链路里是否已经存在融合层，以及它和多模态链的融合层有什么不同

## 一句话结论

当前仓库的两条感知链应明确分成：

- `事实上抛链路`
  - event-first
  - 以结构化事实为主
  - 当前更接近主感知链

- `多模态链路`
  - percept-first
  - 以 provider ref、`PQF` 和 `CanonicalPerceptBundle` 为主
  - 当前更接近增强感知链

两条链不是互相替代，而是在后段汇合到：

- Character runtime
- `Siming` runtime
- `ActorSceneKnowledge`
- `VLA` advisory merge / conflict analysis

## 事实上抛链路

### 主链

```text
Godot fact emitter
-> RawFactEvent
-> fact_router
-> CandidatePerceptEvent
-> per_character_percept_filter
-> CharacterPerceivedEvent
-> Character runtime
```

关键代码：

- `backend/app/services/fact_router.py`
- `backend/app/services/candidate_percept_service.py`
- `backend/app/services/per_character_percept_filter.py`

### 事实类型

当前已进入这条链的主要 family 包括：

- `visual_fact`
- `auditory_fact`
- `spatial_access_fact`
- `role_state_fact`
- `physiology_state_fact`
- `tactile_fact`
- `thermal_fact`
- `olfactory_fact`

### 这条链擅长什么

- 稳定的离散事实
- 已被规则判定过的结果
- 直接进入 authority/public route 或 actor-private percept 的结论
- 验证、回放、审计更直接

## 多模态链路

### 主链

```text
Godot providers
-> SampleInputRef
-> PerceptionQueryFrame
-> CanonicalPerceptBundle
-> Character / Siming runtime consumers
```

可选慢路径：

```text
PerceptionQueryFrame
-> VLAProviderRequest
-> VLAProviderResult
-> VLA percept bridge
-> merge back into CanonicalPerceptBundle
```

关键代码：

- `backend/app/world_runtime/intelligence_upgrade.py`
- `backend/app/world_runtime/l1_perception_frame.py`
- `backend/app/world_runtime/l1_runtime_perception_bridge.py`
- `backend/app/world_runtime/vla_provider.py`
- `backend/app/world_runtime/vla_percept_bridge.py`

### 这条链擅长什么

- 局部 patch / 连续状态 / 不确定材料
- 多模态统一 query
- actor-private / siming-private 上下文隔离
- 视觉/空间 slow-path 增强
- 后续主动感知与重查

## 事实上抛链路是否有融合层

有，但它是“轻量事件语义融合层”，不是 `PQF -> bundle` 这种强融合层。

当前事实上抛链路里的融合主要分三段：

### 1. 路由融合

`fact_router` 把不同 fact family 收进统一后端事实 fabric。

```text
RawFactEvent
-> route_for_family
-> visual / auditory / spatial_access / authority_* path
```

这一步是：

- 路由归一化
- 还不是最终感知融合

### 2. 候选感知融合

`CandidatePerceptEvent` 把不同 fact family 统一翻译成一致的候选感知语义。

```text
visual_fact     -> percept_channel=visual
auditory_fact   -> percept_channel=auditory
spatial_access  -> percept_channel=spatial
tactile/thermal -> corresponding percept_channel
```

这一步已经是第一层真正的感知融合：

- 不同 fact family 被映射成统一 percept event 语义

### 3. 角色私有化融合

`per_character_percept_filter` 把候选感知转成 actor-private `CharacterPerceivedEvent`。

它会结合：

- `actor_id`
- `is_facing_target`
- `distance_m`

把多源 fact 候选收口成“该角色当前实际感知到的东西”。

## 多模态链里的融合层

相比之下，多模态链的融合更强，主要是两层：

### 1. `PerceptionQueryFrame`

不同 provider 的输入先统一到同一个 query object：

- 时间窗
- 空间参考
- 注意力上下文
- 六类 provider 输入 refs

### 2. `CanonicalPerceptBundle`

再统一成：

- `local_spatial_state`
- `target_state`
- `environment_state`
- `embodied_state`
- `attention_state`
- `world_hypotheses`
- `uncertainty`

### 3. `VLA` 的模态增强融合

`VLAProviderResult` 通过 percept bridge 转成：

- `ModalityInterpretationResult`
- `CrossModalUnderstandingResult`

然后再 merge 回 bundle。

## 两条链的关键区别

### 事实上抛链路

- `event-first`
- 先有结构化事实
- 再做候选感知和 actor-private 过滤

它更像：

- 事实语义链
- 轻量感知融合链

### 多模态链路

- `percept-first`
- 先有采样材料和 query
- 再形成统一 percept bundle

它更像：

- 感知材料链
- 强融合输入链

## 两条链在哪里汇合

当前两条链不在事件总线汇合，而是在运行时消费层汇合。

主要汇合点：

- `Character runtime`
- `Siming runtime`
- `ActorSceneKnowledge`
- `VLA advisory` 与 `conflict_refs`

这意味着：

- fact 链给角色的是 `CharacterPerceivedEvent`
- 多模态链给角色的是 `CanonicalPerceptBundle`
- 后续 runtime 必须判断它们是否属于同一拍、同一对象、同一视角上下文

这也是为什么还需要：

- `capture_root_id`
- `capture_id`
- `world_anchor_id`
- actor-private viewpoint reconciliation

## 当前维护判断

当前仓库最合理的心智模型是：

1. 事实上抛链路仍是主感知链
2. 多模态链路是增强感知链
3. 事实上抛链路已经有轻量融合层
4. 多模态链路已经有强融合层
5. 两者当前还缺统一 identity 契约，因此不能把现有“融合层存在”误读成“已经完成完整融合”
