# 事实上抛链路与多模态链路

状态：当前仓库专题架构文档

本文专门回答三个问题：

1. 当前仓库里“事实上抛链路”和“多模态链路”分别是什么
2. 两条链在结构上有什么关系
3. 事实上抛链路里是否已经存在融合层，以及它和多模态链的融合层有什么不同

## 一句话结论

当前仓库的两条感知链已经明确分成：

- `事实上抛链路`
  - event-first
  - 以结构化事实为主
  - 当前仍是主感知链

- `多模态链路`
  - percept-first
  - 以 provider ref、`PerceptionInputFrame`、`PQF` 和 `CanonicalPerceptBundle` 为主
  - 当前是增强感知链

两条链都已经带上统一 identity 契约：

- `capture_root_id / capture_id`
- `clock_domain / monotonic_tick`
- `world_anchor_id`
- `subject_ref / target_ref / source_ref_lineage`

但这不等于完整融合已经全部结束；当前完成的是“共享前置 identity 层”，不是“所有主次和 provider 分级都已完全收口”。

## 事实上抛链路

### 主链

```text
Godot fact emitter
-> RawFactEvent
-> fact_router
-> CandidatePerceptEvent
-> per_character_percept_filter
-> CharacterPerceivedEvent
-> Character runtime
```

关键代码：

- `backend/app/services/fact_router.py`
- `backend/app/services/candidate_percept_service.py`
- `backend/app/services/per_character_percept_filter.py`

### 这条链擅长什么

- 稳定的离散事实
- 已被规则判定过的结果
- 直接进入 authority/public route 或 actor-private percept 的结论
- 验证、回放、审计更直接

## 多模态链路

### 主链

```text
Godot providers
-> SampleInputRef
-> PerceptionInputFrame
-> PerceptionQueryFrame
-> CanonicalPerceptBundle
-> Character / Siming runtime consumers
```

可选慢路径：

```text
PerceptionQueryFrame
-> VLAProviderRequest
-> VLAProviderResult
-> VLA percept bridge
-> merge back into CanonicalPerceptBundle
```

关键代码：

- `backend/app/world_runtime/intelligence_upgrade.py`
- `backend/app/world_runtime/l1_perception_frame.py`
- `backend/app/world_runtime/l1_runtime_perception_bridge.py`
- `backend/app/world_runtime/vla_provider.py`
- `backend/app/world_runtime/vla_percept_bridge.py`

### 这条链擅长什么

- 局部 patch / 连续状态 / 不确定材料
- 多模态统一 query
- actor-private / siming-private 上下文隔离
- 视觉/空间 slow-path 增强
- 后续主动感知与重查

## 事实上抛链路是否有融合层

有，但它是“轻量事件语义融合层”，不是 `PQF -> bundle` 这种强融合层。

当前事实上抛链路里的融合主要分三段：

1. `fact_router`
   - 不同 fact family 的路由归一化
2. `CandidatePerceptEvent`
   - 不同 fact family 的统一候选感知语义
3. `per_character_percept_filter`
   - actor-private 过滤与私有化融合

因此，事实上抛链路应被视为：

- 轻量事件语义融合链

## 多模态链里的融合层

多模态链的融合更强，主要是三层：

1. `PerceptionInputFrame`
   - 统一输入 identity 和时空视角
2. `PerceptionQueryFrame`
   - 统一 query / attention / provider refs
3. `CanonicalPerceptBundle`
   - 统一 local_spatial / target / environment / embodied / uncertainty

并且还叠加：

4. `VLA` 的模态增强融合
   - `VLAProviderResult -> ModalityInterpretationResult -> bundle merge`

因此，多模态链路应被视为：

- 强融合输入链

## 两条链的关系

它们不是替代关系，也不应同时被视为对等主链。

当前最合理的定位仍然是：

1. 事实上抛链路
   - 主感知链
2. 多模态链路
   - 增强感知链

## 两条链在哪里汇合

当前两条链不在事件总线汇合，而是在运行时消费层汇合。

主要汇合点：

- `Character runtime`
- `Siming runtime`
- `ActorSceneKnowledge`
- `VLA advisory` 与 `conflict_refs`

这意味着：

- fact 链给角色的是 `CharacterPerceivedEvent`
- 多模态链给角色的是 `CanonicalPerceptBundle`
- 后续 runtime 必须判断它们是否属于同一拍、同一对象、同一视角上下文

## 当前实现判断

当前仓库最合理的心智模型是：

1. 事实上抛链路仍是主感知链
2. 多模态链路是增强感知链
3. 事实上抛链路已经有轻量融合层
4. 多模态链路已经有强融合层
5. 两条链现在已经共享 `capture_root_id / capture_id / world_anchor_id / source_ref_lineage`
6. 但 provider/fact 主次收敛和更强对象锚点 resolver 仍未完全结束
