# 感知输入对齐层

状态：当前仓库专题架构文档

本文记录当前仓库已经落地的感知输入对齐层，而不是仅记录未来建议。

## 一句话结论

当前仓库已经把显式输入对齐对象落到运行时：

- `PerceptionInputFrame`

并且已经让两条感知链共享这组 identity 语义：

- `capture_root_id`
- `capture_id`
- `clock_domain`
- `monotonic_tick`
- `world_anchor_id`
- `subject_ref`
- `target_ref`
- `source_ref_lineage`

因此，当前事实不是“还需要先发明输入对齐层”，而是：

- 输入对齐层已经存在
- 主感知链和增强感知链都已经开始消费这层 identity
- 剩余问题主要是更严格的对象锚点、provider 分级收敛，以及把对齐层继续收成更强的唯一入口

## 当前两条感知链

当前仓库并行存在两条感知输入链：

1. 上抛器 / 事实上抛器主链
   `RawFactEvent -> fact_router -> CandidatePerceptEvent -> CharacterPerceivedEvent`
2. provider / `PerceptionQueryFrame` / `CanonicalPerceptBundle` 多模态链
   `SampleInputRef -> PerceptionInputFrame -> PQF -> CanonicalPerceptBundle -> Character / Siming runtime`

## 当前实现的输入对齐对象

`PerceptionInputFrame` 当前已经承担：

- 同拍输入身份
- 时空窗口
- actor/camera/listener 视角锚点
- target/focus 对齐
- fact/provider 输入共用 lineage

它不是：

- authority 事件
- 最终 percept bundle
- model output

它是：

- fact 链与 provider 链共享的输入对齐边界

## 当前已实现的行为

当前已经实现：

1. `RawFactEvent` 自动补齐 capture clock 与 object anchor 字段
2. `CandidatePerceptEvent`、`CharacterPerceivedEvent` 沿 fact 链传播 identity
3. `SampleInputRef`、`PerceptionQueryFrame`、`CanonicalPerceptBundle` 沿多模态链传播 identity
4. `VLAProviderRequest / Result` 继承同一 identity
5. `VLA` 慢路径 timeout 明确标记 `capture_relation="late_advisory"`
6. `L1RuntimePerceptionBridge` 已支持 shared-capture multi-actor 分发
7. mixed capture / mixed clock / mixed tick 批次会 fail fast
8. focused verifier 和行为矩阵已覆盖对齐主场景

## 两条链分别意味着什么

### 对事实上抛器链

当前事实上抛器链已经具备：

- `capture_root_id`
- `capture_id`
- `clock_domain`
- `monotonic_tick`
- `sample_ref_id`
- `world_anchor_id`
- `subject_ref / target_ref / source_ref_lineage`

因此它已经不再是“只有离散事实，没有 identity”的旧链。

### 对 provider / PQF 链

当前 provider 链已经具备：

- `PerceptionInputFrame` 作为显式输入对齐对象
- `PQF` 继承同一 capture / object identity
- bundle 继承同一 capture / object identity
- `VLA` 继承同一 capture / object identity

因此它也不再只是“平行的 patch 采样链”，而是与 fact 链共享统一输入身份的增强链。

## 多角色私有视角

当前 `L1RuntimePerceptionBridge` 已同时存在：

- 单 actor `consume_projected_facts(...)`
- multi-actor `consume_multi_actor_projected_facts(...)`

主运行路径当前已经切到 shared-capture multi-actor 分发。

这意味着：

- 同一 `capture_root_id` 下，actor A/B 可以有不同 `capture_id`
- actor A/B 可以保留不同 `actor_frame_ref / camera_frame_ref / listener_frame_ref`
- actor A/B 可以对同一 `world_anchor_id` 形成不同私有属性
- `Siming` 消费 public `multi_actor_patch`，不读 actor-private context

## 当前仍然存在的缺口

虽然输入对齐层已经落地，但还没有彻底收口的部分是：

1. `PerceptionInputFrame` 还没有成为所有上游输入的唯一强制入口
2. 对象锚点 resolver 仍偏向 canonical ref / lineage 推导，不是完整世界对象注册表
3. provider 必要性分级与 fact-first/provider-enhanced 收敛仍主要停在计划和总控层
4. full phase0 broad runtime 还没拿它作为单独 completion gate

## 当前维护判断

当前仓库不应该回到“再扩两条链”的方向，而应该继续守住：

- fact 链和 provider 链共享同一输入 identity
- mixed batch 必须 fail fast
- multi-actor private projection 必须走 shared-capture 路径
- 对象锚点必须继续增强，不允许退回仅靠名称约定的弱实现
