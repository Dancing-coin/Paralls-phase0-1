# 感知输入对齐层

状态：当前仓库专题架构文档

本文回答一个当前主线已经必须面对的问题：

- 仓库同时存在两条感知输入链
  - 上抛器 / 事实上抛器主链
  - provider / `PQF` / `CanonicalPerceptBundle` 多模态链

如果两条链继续并行存在，那么它们必须在输入阶段就完成时空对齐，而不是等到
`CandidatePerceptEvent`、`CharacterPerceivedEvent` 或 `CanonicalPerceptBundle` 阶段再做事后拼接。

## 一句话结论

当前最合理的演进方向不是立刻合并两条链，而是先增加一层统一的
`感知输入对齐层`：

```text
统一 capture / query envelope
-> fact emitter 输入
-> provider 输入
```

让两条链在输入时共享：

- 同一个时间窗
- 同一个空间参考
- 同一个主体视角
- 同一个注意力 / target 上下文

这样可以：

- 暂时允许双链并存
- 避免“不同时间 / 不同视角 / 不同 target”造成的伪冲突
- 为后续裁剪 provider 或裁剪 fact 路线保留真实证据

## 当前问题

当前仓库已经有两条都能工作的感知链：

### 1. 事实上抛器主链

```text
fact emitter
-> RawFactEvent
-> fact_router
-> CandidatePerceptEvent
-> per_character_filter
-> CharacterPerceivedEvent
```

关键代码：

- `backend/app/services/fact_router.py`
- `backend/app/services/candidate_percept_service.py`
- `backend/app/services/per_character_percept_filter.py`

### 2. provider 多模态链

```text
Godot providers
-> SampleInputRef
-> PerceptionQueryFrame
-> CanonicalPerceptBundle
-> Character / Siming runtime consumers
```

关键代码：

- `backend/app/world_runtime/intelligence_upgrade.py`
- `backend/app/world_runtime/l1_perception_frame.py`
- `backend/app/world_runtime/l1_runtime_perception_bridge.py`

这两条链当前并不是完全重复，但已经存在两个显著风险：

1. fact 侧和 provider 侧可能不是同一拍输入
2. fact 侧 target 与 provider 侧 patch scope 可能不是同一主体上下文

如果不先做输入对齐，后续再融合时很容易把“不同时间窗的差异”误判成“同一时刻的感知冲突”。

## 为什么必须在输入阶段对齐

感知冲突有两种：

1. 真冲突
   - 同一时间窗
   - 同一空间参考
   - 同一 target / attention context
   - 但 fact 和 provider / VLA 给出不同结果

2. 伪冲突
   - fact 是 `t0`
   - provider patch 是 `t0 + 300ms`
   - target 已经换了
   - camera / actor frame 已经变化

现在仓库如果直接在后段做融合，最危险的就是把第二种误当成第一种。

因此，当前仓库最应该先补的不是“再多接几个 provider”，而是输入阶段的统一 capture 对齐。

## 目标：统一输入 capture / query envelope

建议增加一层轻量输入对象，暂命名为：

- `PerceptionInputFrame`
  或
- `PerceptionCaptureFrame`

它不是：

- 最终感知结果
- 模型输入结果
- authority 事件

它只负责定义“这一拍感知输入”的共同坐标系。

### 最小字段

建议至少包含：

```text
capture_id
consumer_scope
subject_id
started_at / ended_at
room_id / scene_id / zone_id
actor_frame_ref / camera_frame_ref / listener_frame_ref
target_actor_ids / target_object_ids / target_environment_ids
reason_tags
```

### 作用

它要成为：

- fact emitter 的输入对齐引用
- provider refs 的输入对齐引用
- `PQF` 的上游来源引用
- 后续冲突分析、重查、active perception 的统一入口

## 对两条链分别意味着什么

### 对事实上抛器链

事实上抛器链仍然可以继续作为主感知链。

但需要增加：

- `RawFactEvent` 或其 route metadata 引用 `capture_id`
- `CandidatePerceptEvent` 保留 `capture_id`
- `CharacterPerceivedEvent` 保留来自哪个输入 capture

这不会改变 fact 的主职责，只会让 fact 更容易与 provider 链对齐。

### 对 provider / PQF 链

provider 链不需要重新设计。

只需要：

- `SampleInputRef.runtime_source_refs` 中显式写入 `capture_id`
- `PerceptionQueryFrame` 显式继承 `capture_id`
- 后续 `CanonicalPerceptBundle` 保留这个输入来源

这样一来：

- `PQF` 仍然是统一 query frame
- 但它不再像现在这样更像一条平行主链
- 而是成为“和 fact 链共享同一输入 capture 的增强链”

## 对角色智能体的意义

角色运行时当前同时吃：

- `CharacterPerceivedEvent`
- `CanonicalPerceptBundle`
- `SelfBody`
- `Siming catalyst`

如果没有输入对齐层，角色侧很难判断：

- 这是同一拍的双源信息
还是
- 这是不同拍、不同视角下的材料

加了 `capture_id` 后，角色可以：

- 把同一 `capture_id` 的 fact / bundle 视为同拍补充
- 把不同 `capture_id` 的输入视为时间上前后相继
- 在 `active perception` 时以旧 capture 为 reason 发起重查

## 对 Siming 的意义

`Siming` 当前会同时消费：

- 公开 L1 projected facts
- authority events
- world results
- environment events
- VLA global findings
- multi-actor patch

输入对齐层可以让 `Siming` 更明确地区分：

- 哪些证据属于同一时空片段
- 哪些证据只是后续补充的 advisory

这会直接改善：

- fairness snapshot 的解释
- `conflict_refs`
- `vla_global_advisory` 的可信使用边界

## 这层不解决什么

它不解决：

- 角色最终 `L4 -> CharacterActor` 收敛
- 听觉 actor-private attribution 的完整设计
- VLA live provider proof
- 真实 TTS 接入

它解决的是：

- 双链输入并存时的统一坐标系
- 冲突判断前提
- active perception 重查基础

## 实施建议

建议按下面顺序实施：

1. 定义 `PerceptionInputFrame`
2. 让 fact emitter 输入写入 `capture_id`
3. 让 provider refs 继承同一 `capture_id`
4. 让 `PQF` 和 bundle 保留该输入引用
5. 让角色 / Siming 冲突判断和重查流程读取它

## 当前维护结论

当前仓库不应该急着先删掉哪条链，而应该先做这件事：

- 把两条链的输入时空基准统一

只要输入时空 envelope 没统一：

- 保留两条链会制造伪冲突
- 合并两条链会掩盖问题来源

所以：

- 先做 `感知输入对齐层`
- 再决定哪些 provider 退化为增强链
- 再决定哪些 fact 继续做主链
