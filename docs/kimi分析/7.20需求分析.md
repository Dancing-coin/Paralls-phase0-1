你的总体需求不是“补几个角色属性”，而是：

**先做一个完整的游戏角色与世界玩法底座，再让各种玩法系统通过脚本套件/补丁接入。**

也就是：角色智能体不能只是会对话、会思考，而要成为真正能参与游戏数值、状态、物品、战斗、修炼、经济、关系、司命调度的“游戏角色”。

**1. 角色静态档案与动态状态分离**

你需要角色有清晰的两层：

| 层 | 含义 |
|---|---|
| 静态档案 | 出身、身份、性格、背景、初始关系、初始能力、设定事实 |
| 动态状态 | 当前生命、精力、负伤、背包、装备、财富、修为、关系变化、临时状态 |

目标是：  
档案提供“这个人本来是谁”，动态状态表达“这个人现在怎么样”。

当前 dossier 已经有静态档案基础，但动态游戏状态远远不完整。

**2. 角色游戏状态底盘**

你希望角色智能体的动态状态能直接映射到游戏内角色。

至少要支持：

| 状态组 | 示例 |
|---|---|
| 基础状态条 | 生命、精力、耐力、蓝条、护盾、专注、士气 |
| 身体状态 | 受伤、疼痛、疲劳、饥饿、口渴、睡眠、体温、中毒、流血、姿态、平衡 |
| 状态标签 | 眩晕、沉默、燃烧、冰冻、虚弱、激怒、隐身、束缚 |
| 负重状态 | 当前负重、最大负重、超重惩罚、行动限制 |
| 战斗状态 | 仇恨、架势、硬直、破防、暴击窗口、格挡、闪避 |
| 修炼状态 | 境界、修为、灵力/真气、瓶颈、突破状态、走火入魔 |
| 社交状态 | 信任、敌意、亏欠、关系标签、秘密、误会 |

核心要求：  
**后端和 Godot 都能控制开关，Godot 是镜像和表现，后端是权威。**

**3. 角色拥有物系统**

你明确提出：角色“拥有什么”必须有底层系统。

这不只是背包，而是：

| 类型 | 示例 |
|---|---|
| 具象物品 | 剑、丹药、衣服、钥匙、矿石 |
| 抽象财富 | 金钱、灵石、声望、贡献点 |
| 物权 | 地契、房产、店铺、矿脉、债权 |
| 合约/债务 | 欠款、租约、交易承诺、任务报酬 |
| 资产 | 土地、商铺、储物戒、坐骑、仆从、组织股份 |

这个系统要支撑经济系统、战斗系统、修炼系统、培养系统。

**4. 背包与容器系统**

你需要一个通用容器模型，而不是简单 item list。

需要支持：

| 容器类型 | 规则 |
|---|---|
| 普通背包 | 物品有重量，占容量 |
| 装备栏 | 物品占槽位，影响属性和能力 |
| 仓库 | 大容量，可能不可随身访问 |
| 储物戒指 | 忽略重量，但有容积/格子/禁制限制 |
| 抽象账户 | 存钱、贡献点、积分，不走物理重量 |
| 地产/物权簿 | 记录拥有权，不一定有实体物品 |

关键点：  
**具象物品、抽象财富、物权要能统一进入“角色拥有物”体系，但规则不同。**

**5. 装备系统**

装备不是单独玩法，它是多个系统的连接点。

装备需要影响：

| 连接系统 | 影响 |
|---|---|
| 战斗 | 攻击、防御、暴击、命中、招式可用性 |
| 修炼 | 功法加成、灵气效率、境界限制 |
| 技能 | 授予技能、解锁动作、强化能力 |
| 身体状态 | 负重、耐力消耗、行动速度 |
| 经济 | 价值、耐久、交易、所有权 |
| 表现层 | Godot 外观、武器挂点、特效、音效 |

所以装备系统应该建立在 inventory / ownership / ability / status resolver 之上。

**6. 技能与能力图谱**

你不只要技能列表，而是要角色“能做什么”的结构化图谱。

需要表达：

| 能力图谱内容 | 示例 |
|---|---|
| 技能节点 | 剑术、炼丹、轻功、火球术 |
| 动作节点 | 挥砍、格挡、冲刺、施法、采集 |
| 前置条件 | 需要装备剑、需要 20 点灵力、需要境界筑基 |
| 消耗 | 耐力、蓝条、材料、冷却时间 |
| 授予来源 | 天赋、功法、装备、训练、剧情奖励 |
| 阻断条件 | 眩晕、沉默、断臂、负重过高 |
| 成长证据 | 使用成功、训练记录、师承、突破 |

当前技能系统已经有保守、可审计、policy-gated 的基础，但还没有大型生产 action library、持久化学习晋升、完整能力图谱。

**7. 关系图谱**

角色之间的关系不能只靠文本记忆。

你需要 RelationshipGraph 支撑：

| 关系维度 | 示例 |
|---|---|
| 情感 | 好感、厌恶、恐惧、尊敬 |
| 社会关系 | 师徒、亲属、仇敌、同门、债主 |
| 利益关系 | 欠债、契约、交易、雇佣 |
| 信息关系 | 知道秘密、误会、怀疑、被欺骗 |
| 阵营关系 | 门派、家族、国家、组织 |
| 动态变化 | 事件导致信任下降、亏欠增加、敌意上升 |

关系图谱要接角色记忆、dossier seed、事件系统、经济系统、司命知识图谱。

**8. 司命知识图谱**

你希望司命不只是事件触发器，而是有类知识图谱能力。

司命侧要逐步做到：

| 能力 | 目标 |
|---|---|
| Perspective Graph | 谁看见了什么，谁错过了什么 |
| KnowledgeClaim | 某角色知道/怀疑/误解什么 |
| StoryBeat 关联 | 哪些事实支撑哪个剧情节点 |
| Evidence 链 | 每个判断来自哪里 |
| 冲突识别 | VLA advisory、角色视角、世界事实冲突时能标记 |
| 压缩摘要 | 司命上下文压缩不串记忆、不污染角色私有状态 |

当前司命有证据链、全局态势、状态树、读模型，但还没有真正节点/边式知识图谱。

**9. 玩法脚本/补丁基础设施**

你希望未来支持更多玩法，不是每做一个玩法就硬编码一套。

所以需要底层 patch 系统：

| 基础设施 | 作用 |
|---|---|
| State Group Registry | 注册生命、背包、修为、关系、装备等状态组 |
| Gameplay Patch Registry | 注册战斗、经济、修炼、交易、任务等脚本补丁 |
| Trigger / Condition / Effect | 触发器、条件、效果流水线 |
| Modifier Resolver | 装备、buff、功法、环境对数值的叠加结算 |
| Conflict Resolver | 多个系统同时改状态时决定优先级 |
| Authority Settlement | 后端统一结算成功/失败/约束结果 |
| Godot Mirror Hook | 前端接收状态变更并表现 |

这是你说的“完整基础，再用脚本套件支持更多玩法系统”。

**10. Godot 与后端映射**

你的要求很明确：

| 后端 | Godot |
|---|---|
| 权威状态 | 镜像状态 |
| 结算规则 | 表现、UI、局部预测 |
| 物品/装备/关系/状态真相 | UI、动画、特效、音频、交互反馈 |
| 玩法 patch 执行结果 | 前端可见状态变化 |

Godot 里角色应该支持所有角色智能体动态状态，不管用于 UI、前端交互、数值表现还是引擎计算。

**11. 持久化、迁移、编辑器工具**

长期还需要：

| 需求 | 说明 |
|---|---|
| 动态状态持久化 | 角色状态、背包、关系、技能成长不能只在内存 |
| profile migration | 旧角色档案迁移到 dossier / runtime state |
| authoring tooling | 编辑角色、物品、装备、功法、关系 seed |
| debug workbench | 看状态、图谱、证据链、结算原因 |
| hot reload | 改 dossier / 配置后能安全刷新 |
| verification harness | 每个玩法系统有可重复验证 |

**建议推进顺序**

| 阶段 | 优先内容 |
|---|---|
| P0 | 定义 `CharacterGameRuntimeState` 总 schema、状态组 registry、后端权威/Godot 镜像协议 |
| P1 | 做生命/精力/耐力/蓝条/status tag/body state/effective stats |
| P2 | 做 inventory / container / ownership / wealth ledger |
| P3 | 做 equipment + modifier resolver |
| P4 | 做 ability graph，把技能、装备、身体、资源、功法接起来 |
| P5 | 做 relationship graph |
| P6 | 做 Siming Perspective Graph v0.1 |
| P7 | 做 combat / cultivation / economy 作为第一批玩法 patch |
| P8 | 做持久化、编辑器、迁移、调试工作台 |

一句话收束：

**你的需求是把当前“会思考、会对话、会被司命调度的角色智能体”，升级成“有完整游戏身体、资产、能力、关系、知识、状态结算和玩法扩展接口的游戏角色底盘”。**
