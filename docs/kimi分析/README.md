# Kimi 分析工作区

本目录存放 Kimi（Kimi Code CLI）与后续复核代理在会话中形成的**问题分析、差距判断、路线建议与临时执行计划**。

它是：

- 分析台账
- 历史问题快照
- 待转化 backlog 的中间层

它不是：

- 当前仓库实现事实的最高真相
- 正式主线 spec / plan 的替代物
- 可以直接跳过代码核对就信任的完成声明

## 1. 真值层级

本目录文档必须服从以下真值层级：

1. 当前线程中的明确用户指令
2. `AGENTS.md`
3. `docs/INDEX.md`
4. `docs/架构/`
5. `docs/character/`
6. 活跃 `docs/superpowers/specs/` 与 `docs/superpowers/plans/`
7. `.harness/verification/` 中最新可复核证据
8. 本目录分析文档

结论：

- 本目录可以指出问题、记录差距、给出路线。
- 但只要正式 spec/plan 或代码事实已经覆盖，本目录必须降级为历史/辅助文档。

## 2. 状态词治理

本目录统一使用以下状态词：

- `分析中`
  - 主题仍在探索，代码事实未完成一次系统核对。
- `待评审`
  - 分析已成文，但还没有根据后续代码事实做复核，或还没被纳入正式 spec/plan。
- `已复核更新`
  - 至少做过一次后续代码复核，文档头部状态与 README 台账已同步，但它仍不是正式实施真相。
- `已部分落地`
  - 文档中的部分建议已经实现，但仍保留未完成项；必须明确哪些已做、哪些未做。
- `待转化为正式 spec/plan`
  - 分析仍有价值，但下一步应进入正式规格树或实施计划，不应长期停留在分析层。
- `已被取代`
  - 正式 spec/plan、代码实现或 harness 证据已经覆盖本文主结论；本文保留为历史参考。

禁止使用的含糊状态：

- `完成`
- `差不多`
- `基本没问题`

除非正文明确说明：

- 完成范围
- 未完成范围
- 对应正式文档
- 对应验证证据

## 3. 文档头部规范

每篇文档头部必须包含以下信息：

- 日期
- 状态
- 作者或复核者
- 证据基准
- 性质

推荐格式：

```md
# 标题

- 日期：2026-07-29
- 状态：已复核更新
- 作者：Kimi / Codex
- 证据基准：对照当前工作区代码、相关测试与 harness 报告
- 性质：分析/建议/历史执行计划，不替代正式 spec/plan
- 治理说明：正文保留历史分析快照；当前总状态以本文头部和 README 台账为准
```

## 4. 维护规则

- 只要代码事实发生实质变化，涉及的分析文档必须同步更新头部状态。
- 若某篇文档已被正式 spec/plan 覆盖，应优先更新状态为 `已被取代` 或 `待转化为正式 spec/plan`，而不是继续让它看起来像当前 backlog 真相。
- 若某篇文档仍有开放项，必须在头部或 README 台账中明确“仍开放的问题”。
- 历史正文允许保留原始分析快照，但必须加治理说明，防止读者把旧正文误当当前事实。

## 5. 命名规则

- 文件名统一为：`YYYY-MM-DD-主题.md`
- 同一主题的后续修订直接更新原文档并改状态，不另起新文件
- 历史遗留不合规命名应尽快纠正
