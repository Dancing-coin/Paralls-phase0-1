## 一句话结论

当前项目的角色 `dialogue_generation` 已具备显示文本流式；L2/L3、Siming 和 VLA 仍保持完整结构化结果后提交。TTS 当前是完整 WAV clip/stub 路径，下一步是句子/停顿分段，不是真音频字节流。

当前代码形态是：

- 角色模型：
  - `backend/app/character_agent/gateway/model_provider.py`
  - 使用 `urlopen(...)`
  - 一次性等待完整响应
- 司命模型：
  - `backend/app/services/siming_llm_provider.py`
  - 使用 `httpx.post(...)`
  - 一次性等待完整响应

所以现在的实现是：

- `real provider`
- `non-streaming`

不是：

- `streaming`
- `token-by-token`
- `chunk-by-chunk`

## 2. 流式改造总判断

不是所有智能体大模型链路都应该改成流式。

当前项目里更合理的结论是：

- **必须优先改成流式**
  - 角色 `dialogue_generation`
  - 真实 `TTS` 播放链
- **可以内部支持流式接收，但对 runtime 仍应整包提交**
  - 角色 `L2`
  - 角色 `L3`
  - 司命候选生成
  - VLA advisory 视觉/空间理解
- **当前不建议直接对外流式**
  - `character_agent_execution`
  - `siming_output`
  - `world truth`
  - `ESM authority`

### 2.1 为什么不能一刀切

适合流式的链路直接影响玩家体感：

- 角色说话文本
- 字幕
- 语音播放
- 口型/表情/发声起始时机

它们的核心诉求是：

- 更快首字返回
- 更像“活着的角色正在说话”
- 更自然地驱动语音与表现

不适合直接流式的链路本质上是结构化 runtime 决策：

- `L2` subjective interpretation
- `L3` planning
- `Siming` candidate / decision
- `VLA` advisory findings

这类链路必须先拿到完整结构化结果，经过：

- schema 校验
- policy / feasibility
- validator
- runtime merge

之后才能安全进入下游。  
如果把 partial JSON / partial candidate / partial goal frame 直接放进 runtime，会污染：

- 角色 cognition
- planner selection
- authority boundary
- replay / audit / observatory truth

### 2.2 流式改造矩阵

| 链路 | 是否应改成流式 | 推荐形态 | 原因 |
| --- | --- | --- | --- |
| 角色 dialogue | 是 | 对外流式 | 直接影响玩家体验 |
| 角色 `L2` | 谨慎 | 内部流式接收，整包提交 | 结构化认知结果不能半成品进入 runtime |
| 角色 `L3` | 谨慎 | 内部流式接收，整包提交 | `selected_intent` / `active_goal_frame` 必须完整一致 |
| Siming | 不优先 | 内部流式接收，整包提交 | 候选与决策必须完整校验 |
| VLA | 不优先 | 分析批次 / 整包返回 | advisory spatial findings 更适合完整结果 |
| TTS | 是 | 分段流式或真流式 | 直接影响“角色开口说话”的体感 |

## 3. 各智能体链路的流式建议

## 3.1 角色 dialogue

这是最该改成流式的链路。

建议：

- 先只让 `dialogue_generation` 支持流式
- `CharacterModelGateway` 保留现有整包接口，同时新增流式接口
- websocket 新增一组对话流式消息，而不是污染结构化 runtime 消息：
  - `dialogue_stream_started`
  - `dialogue_stream_delta`
  - `dialogue_stream_finished`
- 最终仍要保留完整 `dialogue_response` 作为落库、记忆、审计、回放的正式结果

## 3.2 角色 `L2`

不建议直接对外流式。

建议：

- provider 可以内部流式接收
- 但只有在完整 JSON 拼完并通过 validator 后，才提交到 `CharacterAgent L2`

也就是：

- **内部可流式接收**
- **运行时边界仍整包提交**

## 3.3 角色 `L3`

默认不应对外流式。

建议：

- provider 可以内部流式接收
- 但只有在完整 planning payload 组装完成后，才交给 validator
- 不允许把半截 `selected_intent`、半截 `candidate_intents`、半截 `active_goal_frame` 暴露给 runtime

## 3.4 Siming

默认不建议优先改成流式。

建议：

- 继续把 `SimingRuntime.tick()` 作为唯一模型调用入口
- 如果未来要支持流式，也只做 provider 内部 streaming gather
- `SimingRuntime` 仍然只接收完整 candidate 列表

## 3.5 VLA

默认不优先做 token 流式。

更合理的是：

- 以一次分析一个 `PQF` / 一批 refs / 一个时间窗为单位
- 完整返回本次 advisory result
- 如果后续确实要做“长视频连续分析”，更像是帧批次流或窗口批次流，而不是普通文本 token stream

## 3.6 TTS

TTS 是应该做成流式优先级较高的链路。

原因：

- 它直接决定角色“开口说话”的自然度
- 如果角色文本已经流式，而 TTS 仍要等全文生成完成，体感会被拖回非实时
- 真正想让智能体显得“活着”，TTS 需要尽量贴近文本增量输出

## 4. VLA 接入方案

## 4.1 VLA 不等于动作控制

在当前项目里，VLA 不应被定义为“直接下发动作”的机器人式 action head。  
它更合适的角色是：

- 视觉/空间 advisory provider
- 对 `PerceptionQueryFrame` 和 artifact refs 做补充理解
- 输出可被角色私有感知或司命全局态势消费的结构化 findings

它不应直接：

- 写 `L1/world truth`
- 写 `ESM authority`
- 直接驱动 Godot 低层角色动作

## 4.2 推荐接入形态

推荐保留现在的总体边界：

```text
Godot sampling / provider refs
-> PerceptionQueryFrame
-> VLA provider backend
-> advisory spatial findings
-> ModalityInterpretationResult
-> CrossModalUnderstandingResult
-> CanonicalPerceptBundle / actor-private or Siming-side consumption
```

推荐模型方向：

- 主力：
  - `qwen3-vl-plus`
- 低延迟档：
  - `qwen3-vl-flash`
- 交叉验证/视频理解补充：
  - `Seed / Doubao` 多模态模型

推荐原因：

- 视觉/多模态模型比纯文本模型更适合处理当前项目的 `image` / `artifact refs` / `space model refs`
- 当前项目已经有 `PerceptionQueryFrame` 与 VLA backend contract，最自然的是补真实 provider，而不是重写 runtime

## 4.3 是否需要流式

默认不优先做 token 流式。

更合理的是：

- 以一次分析一个 `PQF` / 一批 refs / 一个时间窗为单位
- 完整返回本次 advisory result
- 如果后续确实要做“长视频连续分析”，更像是帧批次或窗口批次流，不是普通文本 token stream

## 5. TTS 接入方案

## 5.1 当前状态

当前只有：

- `stub` 路径
- `SpatialVoiceController`
- `voice_stub_played` 验证证据

当前没有：

- 真实 TTS provider
- 真实音频返回链
- voice-by-character 配置
- streaming TTS

## 5.2 推荐接入形态

TTS 在当前项目里应该被定义为：

- 文本智能体输出的听觉表现层
- 可以与角色对话流式链打通
- 可以与 `SpatialVoiceController`、角色口型、音频空间化联动

推荐的工程边界：

```text
dialogue text / dialogue stream
-> TTS service
-> audio chunk or complete clip
-> BackendBridge / LocalPresentationBus
-> SpatialVoiceController / character audio playback
```

推荐形态分两档：

### 第一档：句子级 / 分段流式

适合作为当前项目首个真实 TTS 闭环：

- 文本先按句子或停顿切片
- 每个片段触发一次 TTS
- Godot 逐段播放

优点：

- 比真正 token 级 TTS 简单
- 更容易和字幕、口型、动作节奏对齐
- 失败恢复更清晰

### 第二档：真流式 TTS

适合作为后续增强：

- provider 按 chunk 连续吐音频
- Godot 侧做缓冲和边播边收

优点：

- 更接近实时说话

缺点：

- 后端和 Godot 缓冲链更复杂
- 断流、重传、时钟同步更难

## 5.3 推荐模型 / 服务方向

当前更贴合这条链的不是纯 LLM，而是专门的语音合成服务。

推荐候选方向：

- `Qwen-TTS-Realtime`
- `CosyVoice HTTP / TTS`
- 其他能提供：
  - 实时 TTS
  - chunk 音频输出
  - voice 选择
  - 稳定 HTTP / WebSocket 接口

## 5.4 是否需要流式

TTS 是**应该做成流式优先级较高**的链路。

原因：

- 它直接决定角色“开口说话”的自然度
- 如果角色文本已经流式，而 TTS 仍要等全文生成完成，体感会被拖回非实时
- 真正想让智能体显得“活着”，TTS 需要尽量贴近文本增量输出

## 6. 推荐执行顺序

建议顺序：

1. 先补角色 `dialogue` 流式
2. 再做真实 TTS provider
3. 再决定司命是否真的要流式
4. 最后做 VLA 真实 provider

原因：

- 角色 dialogue streaming 最直接影响“智能体在说话”的体感
- TTS 是把“文本智能体”变成“可听见智能体”的关键一步
- 司命 streaming 的收益未必比角色 streaming 高
- VLA 真实 provider 工程量最大，而且依赖 artifact 输入条件更强
