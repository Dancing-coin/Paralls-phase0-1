## 1. 本文回答的问题

本文覆盖以下问题：

1. 当前项目在接入美术资源后能否实际运行，能够展示什么效果。
2. 角色设定、关系、需求、人格、记忆和秘密能否在运行前注入。
3. 是否能够测试由角色智能体驱动的 3D 角色交互。
4. 美术、动作、声音和物理资源需要准备什么。
5. 动作库不完整时，能否让智能体驱动骨骼和原子动作组合。
6. 角色-角色、角色-物体和角色-世界交互如何避免完全依赖专用动画。
7. 当前感知、真实 LLM 和 VLA 能否支撑“看见椅子后走过去踢中”的连续具身行为。
8. 现有能力、关键缺口、目标架构、实施顺序和验收标准是什么。

## 2. 总结结论

### 2.1 当前项目可以真实运行，但目前是垂直切片

当前 Godot + Python backend 不是仅有静态文件的原型。最近的 Harness 运行记录 `.harness/verification/harness-run-report.md` 表明 `phase0` profile 成功退出；该 profile 覆盖主场景加载、后端连接、结构化对话、成功/失败交互、可见世界状态变化、Siming 反应、语音 stub、root motion 和角色执行计划消费。

当前可观看的效果是：

- 玩家在王座厅 3D 场景中移动并对焦角色或交互物。
- 两名 agent-controlled 角色接收后端的 `character_agent_execution` 表现计划。
- 玩家提交结构化对话，后端返回指定角色的回应并触发表现/调试状态。
- 玩家交互可被 authority 接受，也可因距离等约束返回结构化失败。
- 成功交互可驱动物体或环境状态变化，产生后续视觉、空间、听觉和 Siming 输入。
- 角色与 Siming 的运行态可在 Observatory/trace 中检查。

这已经证明“智能体输出 -> authority -> Godot 角色/世界表现”的链路，但还不等于自然、长期、开放式具身社会模拟已经完成。

### 2.2 角色设定可以提前注入，但真实模型尚未成为默认运行能力

角色 profile 和 dossier 已是项目的一等输入，资源入口包括：

- `assets/characters/profiles/`
- `assets/characters/dossiers/`

dossier 能表达身份、经历、价值观、人格、需求、表达、身体与声音基线、关系种子、技能、权力边界、私密真相及其可见性。运行时可将这些内容投影给角色的私有感知、记忆、needs/affect、规划和执行层。

但 provider readiness 当前仍应被视为阻塞项：角色文本模型缺凭据、Siming LLM 默认 disabled、VLA spatial provider 为 blocked；默认回退可能是 `local_only_stub` 或 continuity fallback。因此，现有成功验证不应被描述为“真实 LLM 已稳定驱动长期角色社会行为”。

### 2.3 目标可达，但必须补齐具身闭环

“角色看见右侧一米的椅子，走过去踢中椅子，椅子倒下，再作出后续反应”需要的不是仅接入 LLM 或 VLA，而是：

```text
可靠感知和场景实体
-> affordance 与动作预条件
-> 本地路径、站位和姿态对齐
-> 动画/IK/物理执行
-> 接触与结果验证
-> authority 结算
-> 记忆、关系和下一步重规划
```

当前仓库具备上述链路的上层心智、authority 和部分感知/物理契约；欠缺的是通用本地动作控制器、可供性注册、动态物理物体、双角色 interaction session 和真实观察回流的整合。

## 4. 美术资源接入评估

### 4.1 当前可用资源与画面状态

现有王座厅和骑士资源已进入运行时场景，能够支持当前 Phase 0 验证。最新运行截图位于：

- `.harness/verification/phase0-strict-main.png`
- `.harness/verification/phase0-focus-main.png`

画面已经能表达空间、角色、焦点和调试信息，但仍不是交付级表现：角色外观复用程度高，焦点/调试色可见，调试文字占据画面，动作、面部和音频表现有限。

### 4.2 `apartment_test` 资源包的当前状态

`apartment_test` 已被隔离为 art pack 源资源和 wrapper/adapter，但尚未成为真实主运行环境。已知风险包括：

- 原始二进制 `.scn` 引用外部 `goblend/scenes/...` 贴图路径，当前项目缺少对应依赖。
- 外部项目的 `project.godot` 不可直接覆盖当前项目的 autoload 和 runtime 边界。
- 当前 `ApartmentEnvironment.tscn` 保留了 `ImportedRoot`、`CollisionRoot` 和 `SceneRuntimeAdapter`，但没有直接实例化有缺失依赖的原场景。

因此，不能将“资源已复制到项目”误称为“公寓环境已接入并可运行”。它需要先被重新导出为依赖自包含的 GLB/TSCE，或修复全部引用后再通过 adapter 进入主场景。

### 4.3 接入新美术的稳定边界

资源替换必须保留 runtime shell 和结构化 ID，不应直接用导入模型根节点替代业务节点：

- 角色：保留 `CharacterReplica` 与 `actor_id`；外部模型作为 role skin 挂载。
- 物体：保留 `InteractiveObject` 与 `object_id`；外部模型作为可视层挂载。
- 环境：保留 `EnvironmentStateNode` 与环境 ID；外部环境通过 `SceneRuntimeAdapter` 暴露碰撞、锚点、出生点和空间信息。
- 跨边界结果：继续由后端结构化 result 驱动 Godot 可见变化。

详见 `docs/art-resource-swap-workflow.md`。

### 4.4 美术资源清单

#### P0：可做首个完整具身场景的最低资源

| 类别 | 最低交付 | 技术要求 |
| --- | --- | --- |
| 环境 | 一个可行走房间、地面、墙、门、桌子、可放置面 | 自包含 GLB/glTF 或可维护 tscn；PBR 贴图；碰撞；NavMesh/导航区域；出生点/锚点 |
| NPC | 至少两套可区分角色外观 | 统一比例和轴向；可映射 Skeleton3D；明确骨骼命名/绑定 profile |
| 原子动画 | idle、walk、run、turn、stop、talk、observe、reach、grip、release、point、generic kick | 可用 AnimationTree 混合；root motion 策略明确；缺失项有安全 fallback |
| 高价值物体 | 椅子、杯子、门、桌子、灯 | 独立 mesh、pivot、collider、interaction anchor、状态变体 |
| 音频 | 临时角色语音或 TTS、脚步、碰撞、交互、环境声 | 优先 mono WAV/OGG，供空间音频播放 |

#### P1：提升角色可信度的资源

- 带 viseme、眨眼、眉眼和情绪 blendshape 的头部/脸部。
- 武器、盾牌等独立装备及手/背/腰 socket。
- 高精度双人交互动画：握手、拥抱、搀扶、扭打等。
- LOD、lightmap UV、透明材质规范、贴图预算和远景代理。

## 5. 动画、骨骼和程序化表现策略

### 5.1 不应让模型逐帧驱动骨骼

后端 LLM 或 VLA 不应输出每根骨骼的高频 transform，也不应直接控制物理引擎。网络延迟、不可重复性、角色模型差异和 authority 越界都会使此方案失效。

正确模式是：角色智能体输出语义执行计划，本地 Godot 在高帧率下实现姿态和运动。

```text
智能体：警惕地接近对方，保持两米，指向信件并说话
-> semantic execution plan
-> locomotion base + posture layer + look-at IK + hand gesture + voice/face layer
-> Skeleton3D final pose
```

### 5.2 三种表现手段并用

| 手段 | 适合的场景 | 例子 |
| --- | --- | --- |
| 物理/程序化 | 结果比姿态更重要 | 推椅子、踢箱子、拉门、物体掉落 |
| 原子动作组合 | 目标与位置经常变化 | 观察、指向、靠近、拿杯子、递交、回避 |
| 专用单人/双人动画 | 情感或接触精度要求高 | 拥抱、握手、舞蹈、急救、扭打 |

原子动作不需要大量资源。约 10-15 个稳定原子，加上 additive posture、look-at、手脚 IK、motion warping 和 attachment，能覆盖大量组合行为。专用动画应只用于关键叙事和高情感交互。

### 5.3 物体操作不等于专用动画

拿杯子可由以下流程完成：接近 -> 计算抓取站位 -> 手部 IK 对准 `grip_anchor` -> 接触检查 -> attach 到手部 socket -> 携带 -> 在放置点 detach -> 恢复刚体物理。

这比为每一种杯子、每一种手型、每一个位置制作动画更可扩展。专用“喝水”动画可以作为表现增强，但不应承担物体所有权或世界状态的唯一真相。

## 6. 角色间交互方案

### 6.1 双人交互需要共享 session

拥抱、握手、递杯子、搀扶不能拆成两个无关联的单人动画。它们需要 `InteractionSession`，至少包含：

- `session_id`、发起者、目标、语义动作和阶段；
- 接受、拒绝、犹豫、取消和中断状态；
- 双方的站位槽、朝向、时间轴和动作所有权；
- 关系、同意、能力、空间、隐私和 authority 预条件；
- 表现策略：原子组合或指定双人动画；
- contact/result observation，以及完成、失败和中断的后端写回。

### 6.2 双人交互的标准路径

```text
发起者提出 hug(target)
-> 目标角色根据关系/需求/设定选择接受、拒绝或回避
-> authority 检查双方位置、同意、空间和场景限制
-> 双方导航至相对站位并完成面向对齐
-> 同步播放双人 clip，使用 IK 微调身高/手部误差
-> 任意一方、第三方碰撞或场景事件可中断
-> 关系、记忆、情绪、目击者感知和世界 trace 写回
```

角色设定对这条路径的作用是实质性的：不同人格、关系、私密边界、疲劳、恐惧、权力关系和当前目标会改变是否发起、是否接受、如何表达和后续关系变化。

## 7. 角色与物体/世界交互方案

### 7.1 必须以 affordance 为中心

模型不应只看到“椅子”字符串。场景对象应提供精确且可执行的 affordance：

```text
chair_01
  transform / bounds / collider
  physical: mass, friction, fixed, dynamic
  anchors: kick_contact, push, sit, grasp
  affordances: kick, push, sit, drag
  states: upright, tipped, blocked, broken
  authority policy: allowed actors, force limits, safety constraints
```

门、杯子、灯和桌子同理。Affordance 数据是开放语义动作与可验证执行之间的关键桥梁。

### 7.2 “踢椅子”不是一句模型指令

正确的闭环应为：

```text
智能体：选择 kick(chair_01)
-> authority：检查距离、能力、权限、椅子状态和风险
-> local controller：计算踢击站位，寻路、转向、准备
-> local pose：generic kick 原子 + 脚 IK 到 kick_contact_anchor
-> contact window：检测真实 collider contact
-> physics：对 RigidBody3D 椅子施加已授权冲量
-> observation：chair_tipped / missed_contact / contact_blocked
-> authority：确认世界状态并写回角色记忆、关系与后续感知
```

这不需要专门的“踢每一把椅子”动画，但需要一个通用踢击原子、足部接触逻辑、物理椅子和结果验证。

### 7.3 物理规律与 authority

Godot 应执行高频的局部碰撞、约束和刚体物理；backend 应保存授权、约束和最终语义世界事实。不能让 LLM 直接把椅子状态改成“倒下”，也不能仅因动画播放完成而宣布交互成功。

## 8. 感知、LLM 与 VLA 的职责

### 8.1 场景真值优先

对于项目自有的 Godot 场景，精确坐标、碰撞、质量、锚点、NavMesh 和当前状态应来自 Godot scene entity / registry。这是角色实现精准走位、抓取、踢击和避障的最可靠来源。

角色动作所需的最小感知帧不应只是“右边一米有椅子”，而应包含：

```json
{
  "self_pose": {"position": [0, 0, 0], "forward": [0, 0, -1]},
  "target": {
    "id": "chair_01",
    "position": [1, 0, 0],
    "bounds": [0.5, 0.9, 0.5],
    "affordances": ["kick", "push"],
    "kick_contact_anchor": [0.8, 0.25, 0]
  }
}
```

### 8.2 VLA 的正确作用

VLA 适合识别未知/未标注资产、视觉状态、潜在可供性和场景异常。例如“画面右侧有一把疑似椅子”“椅子似乎已经倾倒”“桌面上存在可抓取容器”。

VLA 输出必须带置信度，并和 scene entity、collider 和 affordance registry 融合。它是 advisory 慢路径，不应以 30-60Hz 直接控制骨骼、刚体或 authority world state。

### 8.3 LLM 的正确作用

LLM 负责：

- 根据人物设定、记忆、关系、当前感知选择目标和高层意图；
- 生成或理解开放式对话；
- 在失败/中断后选择重试、换策略、寻求帮助或放弃；
- 更新对事件的叙事解释和社会意义。

LLM 不负责：

- 逐帧骨骼控制；
- 路径的精确碰撞规避；
- 直接施加物理冲量；
- 不经验证地宣布物体被拿起、门被打开或椅子倒下。

## 9. 目标架构

```text
                    Character profile / dossier
                                |
                      Character agent / LLM
       goals, dialogue, social strategy, retry/abort decision
                                |
              Structured semantic action request / plan
                                |
             Interaction orchestration + Backend authority
     permissions, constraints, participants, causation, settlement
                                |
                SceneAffordanceRegistry + Perception fusion
      transforms, colliders, anchors, nav, VLA advisory, confidence
                                |
                    EmbodiedActionController (Godot)
    navigation, alignment, animation graph, IK, attachment, contact
                                |
                     Godot physics and visual/audio result
                                |
                  Observations -> authority -> memories/relations
```

其中的关键新增运行时部件是：

1. `SceneAffordanceRegistry`：统一角色、物体、环境的实体、碰撞、状态、锚点和 affordance。
2. `EmbodiedActionController`：将授权动作拆为 `AcquireTarget -> Navigate -> Align -> Prepare -> ExecuteContact -> Verify -> Recover/Abort`。
3. `InteractionSession`：管理多角色动作的协商、同步、中断和结算。
4. `PerceptionFusion`：合并 Godot 精确场景真值与 VLA 低频 advisory，保留置信度和来源。
5. `PhysicalResultBridge`：将接触、刚体最终姿态、attachment 和失败原因转回结构化 authority observation。

## 10. 分阶段实施路线

### 阶段 0：准备可验证的场景和设定数据

- 完成两名 agent-controlled 角色的完整 dossier/profile 数据面。
- 配置真实 character text provider；明确对话、Siming 和 VLA 的运行模式及降级行为。
- 接入一个依赖自包含的环境 art pack，不覆盖现有 `project.godot`。
- 准备椅子、杯子、门、桌子、灯等独立状态化道具。
- 为角色建立 skeleton binding、基础原子动画和 socket。

### 阶段 1：踢椅子闭环

实现 `SceneAffordanceRegistry`、动态 `RigidBody3D` 椅子、`EmbodiedActionController` 的接近/对齐/踢击/验证/恢复，以及 authority 写回。

这不是一个孤立 demo，而是后续所有具身交互的最小骨架。

### 阶段 2：抓取、携带和递交

加入 hand IK、grip/release、attachment、放置面和掉落恢复。以“拿杯子 -> 递给对方 -> 对方接收或拒绝”为验证路径。

### 阶段 3：双角色互动协议

加入 `InteractionSession`，先验证握手的接受/拒绝/中断/关系写回，再接入拥抱等高价值双人同步动画。

### 阶段 4：VLA 与长时自主运行

把 VLA 结果融入实体绑定和置信度治理；在 2-4 名角色、门/椅子/杯子/桌子/私密区域的场景中，运行 30-60 分钟自主社会互动、记忆更新、物理结果和失败恢复测试。

## 11. 验证矩阵

| 场景 | 需要证明的行为 | 成功条件 | 失败条件也必须证明 |
| --- | --- | --- | --- |
| 接近目标 | 角色主动移动到交互站位 | 抵达、转向、保持合理距离 | 路径阻断、目标离开、空间被占用 |
| 踢椅子 | 角色真实接触并改变椅子状态 | 椅子触发物理倒地，authority 写回 `tipped` | 距离不足、椅子固定、脚未接触、被打断 |
| 拿杯子 | 手部与物体所有权一致 | attach 后跟随手部，放下后物理恢复 | 抓取点不可达、杯子被占用、掉落 |
| 递杯子 | 双方协商并转移持有者 | 接收者接受并完成 handoff | 拒绝、目标移动、接收中断 |
| 握手 | 共享 session 和同步 | 双方对齐并完成，关系写回 | 拒绝、超距、第三方干扰 |
| 拥抱 | 专用片段与社会条件统一 | 同意、站位、同步、退出、情绪/关系结果一致 | 拒绝、中断、空间不足 |
| 长时自主 | 多角色持续社会互动 | 对话、记忆、关系、行动和世界结果长期一致 | provider 超时、VLA 不确定、物理失败后可恢复 |

每项均需同时收集：Godot 画面/截图、后端 authority result、角色私有感知、记忆/关系写回、trace/replay artifact。只通过静态测试不足以声称运行时完成。

## 12. 关键风险和约束

1. **LLM/VLA 越界**：直接驱动骨骼、刚体或 world truth 会不可控、不可回放且容易产生幻觉。
2. **动画爆炸**：为每个角色/物体/交互组合制作专用动画不可扩展；必须优先原子动作、IK 与语义动作。
3. **程序化表现僵硬**：拥抱等情感/精确接触要保留专用同步动画。
4. **数据不完整**：裸模型、缺骨骼映射、缺 socket、缺 collider、缺 anchor 的资源无法进入可靠具身交互。
5. **场景语义不可靠**：仅依赖 VLA 估计坐标和碰撞无法保证精准接触；已知场景必须以 engine truth 为准。
6. **provider readiness 不等于产品质量**：在线凭据、延迟、内容安全、失败降级、长时一致性和成本需要独立验证。
7. **权威与物理一致性**：Godot 的实时物理与后端语义状态需要明确的观测、结算和恢复策略，不能各自为真。

## 13. 最终定义

本项目的目标不应是“模型自由生成任何动作并直接改变世界”，而应是：

> 角色依据自己的设定、私有感知、关系、记忆和目标，自主选择开放式语义行动；系统将行动转化为可验证的局部运动、角色协商和物理结果；所有结果受场景、能力、同意、物理和后端 authority 约束，并持续回流为角色的后续感知和社会记忆。

当“踢椅子 -> 走位 -> 接触 -> 倒地/失败 -> 记忆与反应”这条最小闭环稳定后，同一架构才能自然扩展至拿杯子、递交、拒绝、握手、拥抱以及更复杂的多角色社会互动。
