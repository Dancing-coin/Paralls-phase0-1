# 10-司命与事件总线契约

## 1. 文档目标

本文档冻结司命与事件总线之间的正式消息边界：

- 司命收什么
- 司命发什么
- 哪些字段属于总线公共信封
- 哪些字段属于司命确认结果
- 哪些消息必须可 replay / audit

它不重新定义：

- 事件总线底层中间件
- 角色智能体输入链
- `ESM` 物理状态机
- 视觉事实系统本体

它只定义**司命在总线中的身份与契约**。

## 2. 核心定义

司命在总线中的正确身份是：

> **广域订阅者 + 高层催化回写者 + 只读全局裁判**

它不是：

- 世界事实真值的唯一生产者
- 原始事实流的修改者
- 低层动作控制者
- 物理结果写入者

一句话：

> 司命通过总线看见更广的世界，并只通过总线回写高层催化结果。

## 3. 司命接收的消息层级

司命允许正式订阅三类输入：

### 3.1 原始 / 结构化世界事件

例如：

- 角色动作意图、执行、完成
- 物体状态变化
- 环境状态变化
- 空间音频相关事件
- 会话结构变化

这是司命最重要的输入层。

### 3.2 系统状态事件

例如：

- 房间阶段变化
- 世界时钟推进
- 角色状态同步
- 知识状态变化
- 会话确认结果

### 3.3 派生高价值事件

例如：

- `visual_fact_event`
- `visual_evidence_projection`
- 证据链关键摘要事件

它们是司命的高价值判断输入，但不是原始物理真值本身。

## 4. 司命不直接接收什么

司命不直接接收：

1. 原始骨骼/表情高频流
2. `PoseSampleFrame`
3. `SemanticFrame` 原始对象
4. 角色私有内心独白
5. 角色未公开候选行动列表
6. 客户端本地纯表现缓存

原因：

- 这些要么属于 `Godot` 本地表现总线
- 要么属于角色私有主观链
- 不应污染司命的权威输入面

## 5. 司命回写的消息类型

`Phase 1` 司命通过总线只允许回写以下高层对象：

1. `impulse`
2. `opportunity`
3. `fact_reveal`
4. `environment_request`
5. 少量 `system_query / status_request`（内部控制，可选）

### 5.1 `impulse`

作用：

- 给角色一个主观推动倾向

### 5.2 `opportunity`

作用：

- 告诉某角色或局势：一个窗口已经打开

### 5.3 `fact_reveal`

作用：

- 让某角色或某局势终于接触到一条事实性输入

### 5.4 `environment_request`

作用：

- 请求 `L1/ESM` 在规则允许范围内制造环境变化

## 6. 司命不能回写什么

司命不能直接通过总线回写：

1. `go_to_position`
2. `kill_target_now`
3. `set_bone_pose`
4. `open_door_success`
5. `you_now_believe_X`
6. `you_now_choose_Y`

也就是说：

- 不发低层动作控制
- 不发已完成物理结果
- 不发角色认知真值

## 7. 总线公共信封字段

司命相关事件和世界事件一样，必须先落在公共信封里。

当前 canonical 口径统一采用：

- `event_id`
- `event_type`
- `producer_ts`
- `room_id`
- `scene_id`
- `zone_id`
- `source`
- `routing`
- `causation_id`
- `correlation_id`
- `priority`
- `durability`
- `payload`

其中：

- `source.layer`
- `source.system`
- `source.actor_id`
- `source.object_id`（如有）

以及：

- `routing.audience_mode`
- `routing.routing_mode`
- `routing.dialog_group_id`（如有）
- `routing.target_ids`（如有）

不再采用平铺的：

- `producer`
- `source_actor_id`
- `target_actor_ids`

也不再采用：

- `world_ts`

作为事件信封字段。

### 7.1 `source.system` 的司命来源建议

建议固定类似：

- `siming.orchestrator`
- `siming.dispatcher`
- `siming.auditor_information`
- `siming.auditor_participation`

根据来源模块区分。

## 8. 司命确认结果与公共事实的边界

必须严格区分两类东西：

### 8.1 公共事实

例如：

- 谁走近了
- 哪扇门半开了
- 哪个物件从桌上消失了
- 哪个角色后缩了

这些来自：

- `L1`
- `ESM`
- 视觉事实系统

### 8.2 司命确认 / 司命裁决结果

例如：

- 某角色处于 `information_starvation`
- 当前 dominant imbalance 是 `private_channel_lock`
- 推荐干预带是 `opportunity`

这些属于司命自己的运行时判断，不应伪装成原始世界事实。

## 9. 司命与角色输入面的分层

总线中必须保持：

- 司命接收原始/结构化世界事件
- 角色接收 Per-Character 感知事件

这条边界不能被破坏。

司命不能因为“自己知道很多”，就通过总线把自己的全局视角偷偷塞回角色脑中。

## 10. 司命与 `ESM` 的分层

司命可以通过总线发：

- `environment_request`

但最终是否成立，由：

- `L1`
- `ESM`

决定并回写结果。

也就是说：

- 司命请求
- `ESM` 结算
- 结果重新回到总线

不能：

- 司命直接在总线里写“门已经开了”“烟已经起来了”

## 11. 司命与视觉事实系统的分层

司命可以消费：

- `visual_character_fact`
- `visual_object_fact`
- `visual_environment_fact`
- `visual_spatial_relation_fact`
- `visual_evidence_projection`

但不能消费：

- 原始骨骼流
- 原始采样流
- 原始表情权重流

这和双总线结构保持一致。

## 12. replay / audit 必备字段

所有与司命相关的总线事件，至少必须统一携带：

- `event_id`
- `causation_id`
- `correlation_id`
- `producer_ts`
- `room_id`

这样才能把：

`世界事实`
-> `FairnessStateSnapshot`
-> `InterventionCandidate`
-> `InterventionDecision`
-> `Dispatch Event`
-> `Observed Effect`

整条链 replay 出来。

## 13. 推荐 durability

### 必须 `replayable`

- `visual_fact_event`
- `visual_evidence_projection`
- `fact_reveal`
- `opportunity`
- `environment_request`
- 关键 `ESM` 结果
- 关键角色行为回写

### 可 `realtime`

- 一些低价值、短生命周期状态提示

### 可 `reliable`

- 关键干预类消息

## 14. 推荐 priority

### `p0`

- 致命风险 / 临界窗口

### `p1`

- 关键干预
- 关键事实揭示
- 关键环境请求

### `p2`

- 普通催化
- 普通视觉高价值事实

### `p3`

- audit 附加
- 低价值氛围事件

## 15. `Phase 1` 最小协议范围

`Phase 1` 必须保证：

1. 司命能订阅原始/结构化世界事件
2. 司命能订阅视觉事实和证据投影
3. 司命只回写高层消息
4. `environment_request` 必须经 `ESM/L1` 回流
5. 公共事实与司命判断严格分层
6. replay 链完整

## 16. 一句话收束

司命与事件总线的正确关系，不是“司命什么都能发、什么都能收”，而是“司命看得更广，但只说高层催化语言；世界事实仍来自 `L1/ESM/视觉事实系统`，角色真值仍留在角色侧，物理真值仍留在 `ESM` 侧”。\n*** End Patch
