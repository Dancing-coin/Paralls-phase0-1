# 14-司命高并发与子智能体运行策略

## 1. 文档目标

本文档冻结 `Phase 1` 司命在高并发场景下的运行策略：

- 任务如何分级
- 哪些路径必须优先
- 子智能体如何分工
- 何时降级
- 如何避免 `L3` / 视觉 / 环境请求把主链拖死

## 2. 核心定义

司命高并发治理的目标不是“所有事情都实时最优”，而是：

- 关键公平链路不掉线
- 高价值干预不断链
- 可降级路径可解释
- replay / audit 仍成立

一句话：

> 高并发下的司命，首先要像裁判一样稳定，其次才像导演一样精致。

## 3. 任务分级

当前建议固定 5 级：

### `P0`

致命 / 临界链路：

- 关键公平失衡临界点
- 致命环境风险
- 关键会话接入断裂

### `P1`

关键司命主链：

- `FairnessStateSnapshot` 构建
- `InterventionCandidate` 生成
- `InterventionDecision` 选择
- 核心 `environment_request`

### `P2`

高价值支撑链：

- 视觉事实高价值输入聚合
- 证据可见性补充
- 角色承接回流采样

### `P3`

增强与表现链：

- `l3_highlight_path`
- 复杂 `visual_fact_path`
- 次级 narrative surface 刷新

### `P4`

低价值附加链：

- 延迟统计
- 非关键解释增强
- 低优先级运营摘要

## 4. 执行优先级规则

### 4.1 永远先保主裁判链

在任何拥塞时，优先保证：

1. 事件 ingest
2. snapshot 构建
3. candidate 生成
4. decision 输出
5. audit 落地

### 4.2 `L3` 不得挤占主链

无论 `L3` 多复杂，都不能让：

- snapshot 延后
- decision 超时
- audit 丢失

### 4.3 视觉增强可降级

`visual_fact_path`、`l3_highlight_path` 在高压时可以：

- 降强度
- 降频率
- 改走 `character_input_path`
- 或直接 `no_action`

## 5. 子智能体分工

`Phase 1` 建议正式固定 4 个 auditor 子智能体：

1. `information-auditor`
2. `participation-auditor`
3. `suspicion-auditor`
4. `evidence-auditor`

在此基础上，允许 3 类扩展方向：

5. `load-balance-auditor`
6. `l3-coordination-agent`
7. `environment-feasibility-helper`

## 6. 主脑与子智能体关系

### `Siming Orchestrator`

主脑负责编排：

- ingest
- fan-out
- snapshot merge
- candidate merge
- decision selection
- dispatch
- audit

### 子智能体

子智能体只负责各自局部问题，不得：

- 越权直接 dispatch
- 直接写物理结果
- 直接写角色信念真值

## 7. 推荐运行模式

### 7.1 标准模式

适用于普通负载：

- 4 auditor 全开
- 完整 snapshot
- 正常 decision 选择

### 7.2 压力模式

适用于高并发峰值：

- 保留 `information / participation / evidence`
- `suspicion` 降采样
- `L3` 路径降频

### 7.3 生存模式

适用于极限拥塞：

- 只保 `P0/P1`
- 停掉大部分 `P3/P4`
- 强制 audit 简写但不断链

## 8. 降级策略

### 8.1 候选数量过多

策略：

- 先按 `imbalance severity`
- 再按 `target urgency`
- 再按 `path feasibility`

截断到可处理上限。

### 8.2 路径不可执行

优先降级：

`environment_change_path`
-> `visual_fact_path`
-> `character_input_path`
-> `no_action`

### 8.3 预算不足

优先关闭：

- `l3_highlight_path`
- 次级 narrative surface
- 复杂解释增强

### 8.4 replay 压力过大

可降级：

- 降低附加解释细度

不可降级：

- `snapshot_id`
- `candidate_id`
- `decision_id`
- `audit_id`
- `causation_id`
- `correlation_id`

## 9. 性能预算建议

`Phase 1` 建议只冻结相对预算，不先写死机器级 SLA：

- `P0/P1` 必须始终优先于 `P3/P4`
- 每个 tick 必须能完成最少一次公平快照更新
- decision 不能依赖 `L3` 完成后才返回
- audit 必须异步可落地但不可丢

## 10. 失败与恢复

### 10.1 auditor 失败

单 auditor 失败时：

- 标记局部维度不完整
- 继续构建降级 snapshot

### 10.2 decision 路径失败

- 允许 fallback path
- 无可行 fallback 时输出 `no_action`

### 10.3 缓存失效

- 从持久层恢复最近 snapshot / cooldown / readmodel

### 10.4 房间恢复

- `Siming Orchestrator` 重启后应先恢复：
  - 最近 snapshot
  - 最近 cooldown
  - 最近 readmodel

## 11. `Phase 1` 最小实现要求

必做：

1. `P0-P4` 分级
2. 4 auditor 固定分工
3. orchestrator 统一编排
4. 路径降级规则
5. `L3` 不挤占主链
6. audit 不断链

后补：

- 更复杂的动态 worker 池
- 自适应权重学习
- 跨房间全局调度

## 12. 一句话收束

司命的高并发治理，不是把所有子智能体都堆上去一起跑，而是先保住“公平快照 -> 候选 -> 决策 -> 审计”这条主裁判链，再让视觉、`L3` 和复杂导演能力在不拖死主链的前提下逐步发挥作用。
