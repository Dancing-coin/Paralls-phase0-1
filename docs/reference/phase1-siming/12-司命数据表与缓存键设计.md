# 12-司命数据表与缓存键设计

## 1. 文档目标

本文档冻结 `Phase 1` 司命在工程实现上的最小数据层：

- 哪些对象必须持久化
- 哪些对象适合缓存
- 表怎么拆
- 缓存键怎么命名

它不负责：

- 最终数据库 ORM 代码
- 中间件品牌绑定
- 大规模分片策略

它只提供**可实现的最小数据层骨架**。

## 2. 核心原则

### 2.1 快照与真值分离

司命的数据层保存的是：

- 公平快照
- 干预候选
- 干预决策
- 审计记录
- 工作台读模型

不是：

- 全局世界真值库
- 角色长期记忆库
- `ESM` 全量状态机内部态

### 2.2 写模型与读模型分离

- PostgreSQL 持久化写模型与审计真源
- Redis 承担热缓存与运行中状态

### 2.3 room 级隔离

所有主键、索引和缓存键都必须显式带：

- `room_id`

避免不同房间互相污染。

## 3. 持久化对象总表

`Phase 1` 建议正式落库 6 类对象：

1. `siming_fairness_snapshots`
2. `siming_intervention_candidates`
3. `siming_intervention_decisions`
4. `siming_intervention_audits`
5. `siming_checkpoints`
6. `siming_narrative_read_models`

## 5. Redis 缓存对象

`Phase 1` 建议缓存 5 类热对象：

1. 当前房间最新 `FairnessStateSnapshot`
2. 当前房间 cooldown / suppression 状态
3. 当前房间最新 `NarrativeReadModel`
4. 最近 `N` 条 `InterventionDecision`
5. orchestrator 周期性运行中的临时聚合态

## 6. 缓存键命名规范

统一命名前缀建议固定为：

`paralls:siming:`

### 6.1 最新公平快照

`paralls:siming:room:{room_id}:fairness:latest`

### 6.2 指定公平快照

`paralls:siming:room:{room_id}:fairness:snapshot:{snapshot_id}`

### 6.3 干预冷却态

`paralls:siming:room:{room_id}:cooldown:state`

### 6.4 最新读模型

`paralls:siming:room:{room_id}:readmodel:latest`

### 6.5 最近决策列表

`paralls:siming:room:{room_id}:decision:recent`

### 6.6 orchestrator 临时聚合态

`paralls:siming:room:{room_id}:orchestrator:working_set`

### 6.7 auditor 局部结果

`paralls:siming:room:{room_id}:auditor:{auditor_name}:latest`

## 7. TTL 建议

### 持久真源

以下对象不依赖 TTL：

- PostgreSQL 全量持久表

### Redis 热缓存

建议：

- `fairness:latest`：`30-120s`
- `readmodel:latest`：`30-120s`
- `cooldown:state`：按冷却周期写 TTL
- `decision:recent`：`5-15min`
- `working_set`：`30-60s`

## 8. 读写路径建议

### 写路径

```text
Event Ingest
-> Auditor Results
-> FairnessStateSnapshot
-> InterventionCandidate
-> InterventionDecision
-> Checkpoint / Audit
-> NarrativeReadModel
```

### 读路径

```text
Workbench / Replay / QA
-> Redis latest
-> miss 时回 PostgreSQL
```

## 9. 不该缓存什么

不建议在 Redis 中长期缓存：

1. 全量历史快照
2. 全量 audit 明细
3. 原始世界事件全量副本
4. 角色私有信念真值

这些应分别留在：

- 持久库
- 专项系统
- 事件总线回放体系

## 10. `Phase 1` 最小实现要求

必做：

1. 6 张持久化主表
2. 5 类 Redis 热键
3. `room_id + world_ts` 主查询路径
4. decision / audit / readmodel 可回查

后补：

- 历史归档分区
- 多房间聚合报表
- 更复杂的冷热分层

## 11. 一句话收束

司命的数据层不是再造一套世界数据库，而是围绕 `FairnessStateSnapshot`、`InterventionCandidate`、`InterventionDecision`、`InterventionAuditRecord` 和 `NarrativeReadModel` 建立一套 room 级可持久、可缓存、可回放的最小运行时骨架。
