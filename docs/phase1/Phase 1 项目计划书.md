# Phase 1 项目计划书

## 状态

- 状态：第二轮收敛稿
- 主来源轮次：`208-209`、`380`、`398-400`
- 补充来源轮次：`203`、`207`、`267`、`307`、`310`、`379`、`406-450`（当前已产出 `406-437`）

## 当前冻结结论

- Phase 1 的目标是验证“智能体驱动的 3D 动态剧本杀”核心体验，而不是提前完成整个平台生态。
- Phase 1 必须包含轻量版小世界与带走机制，但只做最小情感闭环，不做完整持续陪伴与跨剧本资产化。
- Phase 1 的司命不是被动守护器，而是受边界约束的完整单局导演。
- Phase 1 的核心系统必须目标中立，虽然首个闭环是推理剧本，但底层应同时支撑追凶、逃脱、生存、复仇等目标。
- Phase 1 的 ESM 只做基础交互级能力，不把完整天气 / 生物成长 / 长周期环境推演提前纳入。
- 若本期纳入建造线，当前只做“建筑蓝图建造 / 交易 / 导入生成”闭环，不扩展到完整体素沙盒与世界级编辑。
- 硬件与算力策略采用“先评估再分配”：根据终端硬件能力决定本地、云端或混合执行，不把“本地优先”当绝对规则。
- 深度硬件优化后置到后续阶段；Phase 1 只做必要基础优化并冻结扩展接口。

## 1. 文档目标

本文档用于定义《开本》Phase 1 的正式项目边界、交付清单、成功标准、主要议题与执行顺序。

本文档以 `filtered_conversation_split` 的后期修正版为准，不等同于仓库里的旧 `Phase 1.md` 草稿，也不继承任何已被时间线后段推翻的缩窄或扩张口径。

## 2. 时间线覆盖说明

与 `Phase 1` 相关的规划存在明显迭代，当前采用以下覆盖关系：

- `207`：较早版三阶段开发清单，尚未吸收小世界前置，也未完全消化后续角色层与玩法中立修订。
- `208-209`：明确把个人空间与带走机制前置到 `Phase 1`，形成“MVP + 轻量陪伴”口径。
- `267`：修正“Phase 1 司命过于保守”的切法，明确司命应是完整单局导演。
- `307`：补上证据销毁不应成为信息黑洞的闭环原则。
- `310`、`379`：补上“底层系统必须目标中立”的玩法收束。
- `380`：从基础设施角度收束为“最小闭环优先”，明确先做什么、后不做什么。
- `406-430`：补上建造线、世界引擎交付形态、L3 双链路与司命高并发调度边界。
- `431-437`：补上硬件自适应算力路由、主流准入线、云游戏供给归属，以及“深度优化后置、接口前置”的实施节奏。
- `398`：形成较完整的 `Phase 1` 计划书骨架。
- `399`：补充项目议题与验证口径。
- `400`：作为当前主版本，吸收玩法中立、证据链、小世界、离线补全与三阶段能力表的后期修订。

当前采用规则：

- `398 + 400` 作为项目主版本
- `208-209` 用于冻结“小世界 / 带走进入 Phase 1”
- `267` 用于冻结“司命是完整单局导演”
- `380` 用于约束基础设施与启动顺序
- `310 / 379 / 400` 用于冻结“目标中立”
- `203 / 207` 只用于理解演进，不直接继承其旧范围

## 3. 核心目标

Phase 1 只回答一个核心问题：

玩家是否愿意为一款“智能体驱动、3D 沉浸、同剧本可重复游玩的动态剧本杀”付费，并认可其中的 AI 博弈与轻量陪伴价值。

因此，Phase 1 的目标不是做完整平台，而是验证以下四件事：

1. 动态剧本杀闭环是否成立。
2. AI 角色是否具备可信的人格差异、信息博弈与冲突反应。
3. 司命单局导演是否能在不破坏公平和逻辑的前提下催化戏剧性。
4. 轻量版带走与小世界是否具备初步情感价值。

## 5. 关键修订点

### 5.1 小世界前置，但只做轻量版

采用 `208-209 / 398 / 400`：

- `Phase 1` 包含轻量版个人空间 / 小世界
- 只做基础场景、基础对话、轻量角色快照
- 不做完整陪伴生态和持续世界

### 5.2 司命按“完整单局导演”冻结

采用 `267 / 398 / 400`：

- `Phase 1` 的司命应覆盖事实核心、天平评估、基础冲突催化、单局节奏控制与暗杀机会催化
- 但不进入跨局种子库、世界持续推演和系列导演能力

### 5.3 系统按目标中立设计

采用 `310 / 379 / 400`：

- 核心系统不能只围绕追凶设计
- 搜证、信息共享、威胁感知、暗杀、庇护、环境交互等底座都应服务多目标
- 首个剧本是侦探推理，不等于底层系统只能支撑侦探推理

### 5.4 证据链闭环进入主要议题

采用 `307 / 400`：

- 证据应形成完整闭环
- 销毁证据本身也必须产生新的痕迹、目击或矛盾
- `Phase 1` 不必把所有证据子系统做满，但必须把闭环原则做进首个闭环

### 5.5 基础设施收缩

采用 `380`：

- `Phase 1` 的基础设施围绕“首个可玩闭环”建设
- 不提前实现远期大而全生态底座
- `Phase 0` 先验证链路，再进入完整 MVP

### 5.6 建造线范围收束

采用 `406-437` 的后期收束口径（位于 `406-450` 目录当前产出段）：

- 若建造线进入本期，只做建筑蓝图闭环
- 世界引擎按 `Godot` 运行时 + 规则封装形态交付
- 不把完整体素沙盒、世界级编辑器和世界生态全量推演写成当前交付
- 同步冻结蓝图导入校验链路与最小权限矩阵，不把“先跑后补权限”作为可接受路径

### 5.7 硬件与算力策略修订

采用 `431-437` 的后期收束口径：

- 先评估终端硬件能力，再分配任务到本地/云端
- 不兼容全部硬件，低于主流准入线设备走云游戏兜底
- Phase 1 不做重资产深度优化，但必须前置冻结扩展接口（模型切换、画质分级、物理精度分级）
- 云地调度策略不改变既有消息边界与职责矩阵

## 6. 首个可玩闭环

Phase 1 的最小可玩闭环如下：

```text
选择剧本
  -> 选择角色
  -> 进入 3D 场景
  -> 探索 / 对话 / 观察 / 搜证
  -> 信息共享与博弈
  -> 冲突涌现 / 风险升级
  -> 投票 / 对决 / 结局
  -> 可选带走 AI 角色
  -> 进入轻量版小世界查看结果
```

如果这条闭环不能稳定跑通，`Phase 1` 不算完成。

## 8. 成功指标

Phase 1 成功不只看“功能是否存在”，还要看“体验是否成立”。

建议按四组指标组织：

1. 技术指标
2. 玩法指标
3. 情感指标
4. 商业验证指标

至少应覆盖：

- 剧本闭环能稳定完成
- 玩家能感知到 AI 的人格差异和博弈感
- 司命催化不破坏公平与逻辑
- 结局具备差异化
- 玩家愿意继续玩 / 愿意付费
- 带走机制具备初步吸引力
- 蓝图导入成功率与冲突拦截率达到可运营阈值（权限越权与非法依赖可被稳定拦截）

建造链路量化阈值（V1）：

- 非法导入拦截率：`100%`
- 合法导入成功率：`>= 95%`
- 实例化回写成功率：`>= 99%`
- 自动合并成功率：`>= 90%`（同层且无权限冲突）
- `P1/P2` 冲突工单闭环时间：`P95 <= 30 分钟`
- 审计记录完整率：`100%`

商业验证指标只验证最小闭环：

- 首个剧本是否存在付费意愿
- AI 带走与轻量版小世界是否具备情感价值
- 后续剧本买断 / 门票 / 智能体相关付费接口是否值得保留

不在本阶段验证完整创作者市场、大玩家经营体系、链上确权或智能合约分账。

## 9. 主要风险

### 9.1 AI 实时性与成本

风险：

- 角色响应太慢
- 调用成本太高

控制：

- 模型路由
- 小模型优先
- 规则程序兜底

### 9.2 玩法范围膨胀

风险：

- 将远期愿景和多玩法完整版塞进 `Phase 1`

控制：

- 以 `398 / 400` 的“不在范围内”清单为准
- 所有新增模块先问“是否首个闭环必需”

### 9.3 架构边界混乱

风险：

- 司命、`ESM`、事件总线、证据链系统职责重叠

控制：

- 先以 `技术架构总纲` 为边界
- 每个专题文档必须单列职责与非职责

### 9.4 首个剧本体量失控

风险：

- 过早把首个剧本做成大型内容包

控制：

- 锁定《血字的研究·变奏》
- 锁定 `5` 角色、`2` 主场景
- 锁定“可重玩闭环优先于内容膨胀”

### 9.5 目标中立被实现回追凶专用

风险：

- 底层系统名字和接口虽然写成通用，实际实现却只围绕“找真凶”一条路

控制：

- 所有核心系统文档都显式写明“追凶之外的目标适配”
- 首个剧本之外，至少用目标系统反向校验一次可扩展性

### 9.6 硬件覆盖与云成本风险

风险：

- 按绝对本地优先设计导致低配设备不可玩
- 反向全云化导致推理与渲染成本失控
- 将云游戏基础设施错误下放给大玩家，导致服务不可持续

控制：

- 硬件评估驱动任务分配
- 主流准入线 + 云游戏兜底
- 云游戏由平台统一供给，常规经营成本按“谁经营谁承担”拆账

### 9.7 建造权限与映射冲突风险

风险：

- 创作者/大玩家/玩家权限边界未落地，导致越权改写模板或世界规则
- 场景级与世界级更新冲突未收敛，出现状态回写污染

控制：

- 固化最小权限矩阵并接入导入校验链路
- 固化冲突优先级（世界规则 > 授权 > 场景改动 > 临时状态）
- 自动合并失败进入人工审核队列，不做静默覆盖

## 10. 开发顺序

建议顺序：

1. `Phase 0` 原型通过
2. 搭双场景与客户端骨架
3. 打通房间、事件和 AI 基础链路
4. 跑通首个剧本完整闭环
5. 接入轻量版小世界与带走机制
6. 做外部测试

## 11. 与后续阶段的接口

Phase 1 必须为后续预留但不提前实现：

- 跨剧本记忆接口
- 剧本结构化配置接口
- 大玩家规则微调接口
- 目标中立玩法扩展接口
- 证据链扩展接口
- 商业化接口预留
- 创造系统能力族接口预留（蓝图版本、映射同步、冲突审核、云地路由扩展）

这类预留只能做“接口和边界预留”，不能做“完整系统提前落地”。
