# 剧本创作模板

## 状态

- 状态：第一版初稿
- 主来源轮次：`271`、`275`
- 补充来源轮次：`044`、`272-274`

## 当前冻结结论

- Phase 1 剧本采用结构化文件集，而不是单一长文案
- 创作者负责写“锚点”，系统负责在锚点约束下生成本局事实与过程
- 结局数量是有限的，过程和细节体验是高变且可反复涌现的
- Phase 1 冻结内部结构化配置规范，不要求同时交付对外编辑器

## 1. 文档目标

本文档用于定义《开本》Phase 1 剧本资产的标准组织方式，供内容、后端、客户端和 AI 系统共同使用。

本文档回答四个问题：

- 一份剧本到底由哪些文件组成
- 哪些内容必须由创作者固定，哪些内容交给系统运行时决定
- 每类字段服务哪个运行时模块
- Phase 1 先冻结什么，哪些工具化能力后移

本文档不展开：

- 对外创作者编辑器 UI
- 多剧本连续承接规则的完整设计
- Phase 2/3 的开放创作生态

## 2. 时间线覆盖说明

剧本模板相关讨论经历了三次重要收束，不能把早期示例直接当成最终规范。

- `044`：第一次清晰区分“固定骨架”和“动态生成”边界
- `271`：给出完整模板雏形，明确剧本不是传统文案，而是多模块结构化数据
- `272`：补足“开局前固定剧情”与“开局后多条故事线”的连接方式
- `273`：补足涌现增强开关，说明剧本还要配置角色自主冲突、临时秘密、动态阵营等可变空间
- `274`：明确“结局有限，过程无限”，修正了容易把动态叙事理解成“无限结局”的倾向
- `275`：把前述内容落成“全套文件”视图，形成当前最适合 Phase 1 执行的组织形态

当前采用规则：

- 文件组织形态以 `275` 为主
- 固定 / 随机 / 涌现边界以 `044 + 272 + 274` 为准
- 涌现增强字段以 `273` 为补充
- 若后续案例与本模板不一致，以本模板为准回改案例，不反向用案例覆盖模板

## 3. 剧本的本质与边界

### 3.1 剧本不是传统长文案

Phase 1 的剧本不是一篇“从头写到尾”的线性文本，而是一组可被系统读取、校验、组合和执行的结构化资产。

它至少同时承担四种职责：

- 内容资产：世界、角色、场景、案件、结局
- 运行时约束：哪些事实固定，哪些变量可抽样，哪些机制启用
- AI 驱动依据：角色心智、司命干预、信息分布、涌现增强
- 测试依据：可模拟、可校验、可回放、可做逻辑检查

### 3.2 创作者写“锚”，系统写“这一次”

采用当前冻结口径：

- 创作者写死：世界背景、角色真实档案、案发前历史、场景布局、随机池规则、结局框架
- 系统决定：本局凶手、动机、凶器、线索子集、不在场证明具体形态、本局冲突与过程
- 玩家与 AI 共创：对话、结盟、背叛、误导、坦白、销毁、暗杀链与结局抵达路径

### 3.3 结局有限，过程高变

剧本模板必须同时支持：

- 有限数量的终局收束条件
- 高变数量的过程变量、事件顺序、关系变化和信息路径

因此，模板中必须显式拆分：

- `ending_conditions`
- `process_variables`
- `emergence_config`

不能只写结局，也不能只写开放过程而不给收束条件。

## 4. Phase 1 采用的文件组织规范

### 4.1 目录结构

Phase 1 推荐冻结如下目录形态：

```text
script_<script_id>/
  script.json
  world_setting.json
  characters/
    <role_id>.json
  scenes/
    <scene_id>.json
  prologue/
    world_background.md
    character_biographies/
      <role_id>.md
    historical_timeline.json
  case_pools/
    death_cause_pool.json
    motive_pool.json
    weapon_pool.json
    clue_pool.json
    alibi_config.json
  endings.json
  disguise_config.json
  mechanism_switches.json
  siming_config.json
  emergence_config.json
  visual_audio.json
  test_config.json
```

### 4.2 为什么采用“结构化文件集”

采用这一形态的原因不是为了文档好看，而是为了运行时和团队协作。

- 不同子系统读取不同文件，避免把所有逻辑塞进单一大文件
- 内容修改可局部进行，减少全文件冲突
- 便于做字段校验、逻辑检查、随机仿真和版本管理
- 便于后续接入编辑器，而不必先推翻存储格式

### 4.3 Phase 1 的格式冻结口径

当前建议：

- 结构化主体优先采用 JSON
- 纯叙事长文本采用 Markdown
- 暂不在 Phase 1 引入更复杂的 DSL 或可视化节点图作为标准底层格式

这不是说 JSON 永远最佳，而是它最适合当前阶段的“先做出内部稳定规范”目标。

## 5. 固定、随机与涌现的分层

### 5.1 固定层

固定层是在创作时锁定、运行时不改写的内容，包括：

- 世界观与社会规则
- 角色真实档案
- 场景布局与交互点定义
- 历史事件时间线
- 死者与案件初始框架
- 随机池与约束规则
- 结局条件定义

### 5.2 随机层

随机层是在开局阶段按规则抽样、然后在本局内冻结的内容，包括：

- 凶手身份
- 动机变体
- 凶器选择
- 核心线索子集
- 证词与不在场证明的具体形态
- 某些角色的初始隐性状态

### 5.3 涌现层

涌现层是在本局进行中由角色、司命和玩家共同推进的内容，包括：

- 对话内容
- 私下交易与共谋
- 临时秘密
- 动态阵营
- 误导与伪造
- 冲突升级
- 暗杀链与次生事件
- 抵达结局的具体路径

### 5.4 与 T0-T3 的对应关系

剧本模板必须兼容事实锁定时间线：

- T0：剧本资产文件完成并冻结基础内容
- T1：房间创建时抽取案件框架变量
- T2：玩家入局或角色分配完成后锁定本局完整事实
- T3：事实不再改写，只允许叙事过程继续涌现

因此，模板设计不能允许“过程变量”在 T3 之后反向改写“基础事实”。

## 6. 各文件职责与字段要求

### 6.1 `script.json`

职责：

- 剧本入口文件
- 汇总全局元信息
- 声明其他文件路径
- 声明本剧本的能力边界

至少包含：

- `script_id`
- `script_name`
- `version`
- `description`
- `tags`
- `difficulty`
- `estimated_duration_min`
- `player_count`
- `phase`
- `supports_series`
- `files`

约束：

- 不要把详细角色、场景、案件内容全部堆进入口文件
- `files` 必须能唯一定位所有子资源

### 6.2 `world_setting.json`

职责：

- 定义世界锚点与全局规则
- 为角色理解、司命判断、视觉表现提供共同上下文

至少包含：

- `universe_id`
- `world_name`
- `era`
- `year` 或等价时间锚
- `location`
- `social_context`
- `technology_level`
- `special_rules`

约束：

- 特殊规则要能被运行时使用，而不是纯文学描述
- 若世界存在超自然、特殊科技、宗教禁忌等，必须明确写入可执行规则

### 6.3 `characters/<role_id>.json`

职责：

- 定义角色真实档案
- 驱动角色智能体初始化
- 提供玩家可扮演或 AI 扮演的统一底座

至少包含：

- 角色基础信息
- 是否允许人类 / AI 扮演
- 人格生成链所需字段
- 目标与恐惧
- 能力与知识域
- 伪装信息

建议至少拆成以下逻辑块：

- `personality_profile`
- `capabilities`
- `disguise`
- `public_identity`

约束：

- 不能退回扁平 NPC 资料卡写法
- 人格字段应与角色智能体文档一致，遵循“基因种子 -> 人生记忆 -> 品格层 -> 五维人格 / 行为层 -> 目标系统”
- 玩家可扮演角色与 AI 角色共用同一底层资产，不应维护两套割裂模板

### 6.4 `scenes/<scene_id>.json`

职责：

- 定义空间节点
- 提供交互物、连接关系、线索绑定和环境状态入口

至少包含：

- `scene_id`
- `name`
- `description`
- `connections`
- `interactables`

建议补充：

- 声音传播属性
- 光照 / 可见度属性
- 特殊区域规则
- 是否支持独处、埋伏、偷听、封锁等玩法

约束：

- 场景文件应以可执行空间逻辑为主，不只写美术文案
- 可交互物必须考虑与证据链、线索、物品流转的绑定关系

### 6.5 `prologue/`

职责：

- 定义开局前固定剧情
- 作为司命和角色记忆初始化的重要来源

其中：

- `world_background.md`：面向世界级叙事背景
- `character_biographies/<role_id>.md`：角色长传记与叙事细节
- `historical_timeline.json`：结构化历史事件线

约束：

- 长文本不是运行时唯一依据，必须与结构化时间线配套
- 历史时间线应包含事件、时间、参与者、影响结果

### 6.6 `case_pools/`

职责：

- 定义案件生成空间
- 在固定事实与随机事实之间建立桥梁

至少包含：

- `death_cause_pool.json`
- `motive_pool.json`
- `weapon_pool.json`
- `clue_pool.json`
- `alibi_config.json`

#### `death_cause_pool.json`

- 定义可接受死因集合
- 应支持物理后果与痕迹类型挂接

#### `motive_pool.json`

- 定义动机母题与角色变体
- 可按角色或关系写差分版本

#### `weapon_pool.json`

- 定义凶器候选、默认位置、可移动性、痕迹类型、是否可清洗

#### `clue_pool.json`

- 必须区分核心线索与干扰线索
- 每条线索至少应包含：
  - 类型
  - 位置
  - 指向
  - 是否可销毁
  - 销毁方式或销毁难度

#### `alibi_config.json`

- 定义初始不在场证明框架
- 明确哪些部分固定，哪些部分可随机

约束：

- 线索池不是传统剧本里的“阅读段落集合”，而是运行时可抽样、可隐藏、可销毁、可转移的结构化对象库
- 销毁逻辑要遵守“销毁本身会产生新信息”的上位规则

### 6.7 `endings.json`

职责：

- 定义有限终局集合
- 给过程提供收束框架

至少包含：

- `ending_id`
- `name`
- `condition`

建议补充：

- `description`
- `epilogue_narrative`
- 与带走 / 轻量小世界衔接的后果标记

约束：

- Phase 1 必须避免“无限结局”表述
- 结局条件应可被系统判断，不应只有文学描述

### 6.8 `disguise_config.json`

职责：

- 定义身份伪装、公开档案与真实档案之间的差异

至少包含：

- 全局伪装开关
- 适用角色
- 伪装深度
- 可搜查的伪装载体

约束：

- 外貌伪装、身份伪装、证件型伪装可分别开关
- Phase 1 可从简，但模板需预留这些差分

### 6.9 `mechanism_switches.json`

职责：

- 冻结本剧本启用哪些玩法模块

至少应能覆盖：

- 暗杀
- 动态阵营
- 迷宫 / 时间循环 / 多时间线等特殊玩法开关
- 信息共享规则
- 特定道具或摄影留证规则

约束：

- 不要把“这是侦探本”当成默认解释一切的开关，必须逐项显式声明

### 6.10 `siming_config.json`

职责：

- 定义本剧本允许司命以什么强度、什么方式参与单局导演

至少包含：

- 干预强度
- 节奏偏好
- 暗杀催化开关
- 干预约束

约束：

- 不能把司命配置写成“直接控制角色”
- 必须与司命四原则兼容

### 6.11 `emergence_config.json`

职责：

- 定义本剧本允许的涌现增强空间

建议覆盖：

- 角色自主冲突
- 压力崩溃
- 感知偏差
- AI 主动误导
- 临时秘密
- 动态阵营
- 节拍点
- 时间压力
- 环境漂移

约束：

- 这些不是“锦上添花配置”，而是决定同剧本重复游玩差异度的重要参数
- 但它们也不能越权改写已锁定事实

### 6.12 `visual_audio.json`

职责：

- 为 L3 视觉增强和沉浸表现提供统一约束

至少包含：

- 美术风格
- 光照与色板
- 环境音
- 音乐动态规则
- L3 触发点

约束：

- 视觉音频文件是表现层规范，不承担玩法逻辑判定

### 6.13 `test_config.json`

职责：

- 让剧本具备可模拟、可验收、可回归的测试入口

至少包含：

- 模拟运行次数
- 测试玩家画像
- 逻辑矛盾率阈值
- 结局多样性要求
- 卡死率阈值
- 平均时长范围

约束：

- 测试配置不是可选附属品，而是 Phase 1 内部剧本生产必须具备的组成部分
- 没有测试配置，就无法稳定迭代动态剧本

## 7. 推荐的最小字段样例

以下样例只用于冻结结构，不是完整内容上限。

```json
{
  "script_id": "blood_letter_variation",
  "script_name": "血字的研究·变奏",
  "phase": 1,
  "player_count": {
    "min_human": 2,
    "max_human": 5,
    "total_roles": 5
  },
  "files": {
    "world_setting": "world_setting.json",
    "characters": "characters/",
    "scenes": "scenes/",
    "case_pools": "case_pools/",
    "endings": "endings.json",
    "siming": "siming_config.json",
    "emergence": "emergence_config.json",
    "test": "test_config.json"
  }
}
```

## 8. Phase 1 的范围边界

### 8.1 Phase 1 必须冻结

- 结构化文件集形态
- 固定 / 随机 / 涌现三层划分
- 有限结局 + 高变过程的设计口径
- 角色、场景、案件池、司命配置、测试配置的基础规范

### 8.2 Phase 1 暂不要求

- 对外可视化编辑器
- 剧本作者图形化流程编排工具
- 多剧本连续承接自动生成器
- 对外资产市场与创作者发布链路

### 8.3 Phase 2/3 预留

后续应在不破坏当前结构的前提下扩展：

- 连续单局的跨局变量继承
- 系列剧变量映射
- 对外编辑器与校验器
- 更复杂的世界级脚本与小世界衔接

## 9. 编写与校验要求

每次新增剧本时，至少应通过以下检查：

- 是否包含完整目录结构
- 是否明确哪些内容固定、哪些内容随机、哪些内容涌现
- 是否为关键机制提供开关与约束
- 是否存在无法被系统读取的纯文学字段
- 是否为核心逻辑提供测试配置
- 是否把“无限过程”误写成“无限结局”

## 10. 当前采用规则

后续剧本整理与实现统一采用以下口径：

- 剧本是结构化文件集，不是单一长文案
- 创作者负责写世界、角色、历史、规则池与结局框架
- 系统负责在规则池内生成本局事实与过程
- 结局有限，过程和细节高变
- Phase 1 冻结的是内部标准格式，不是对外编辑器产品
