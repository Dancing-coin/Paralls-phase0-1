## 当前冻结结论

- `ESM` 是 `L1` 的独立环境状态管理器，不属于司命，也不依赖 `LLM`
- `ESM` 管理的是所有可交互实体的物理状态，不只是“环境”，也不只是“物体”
- `ESM` 负责毫秒级确定性物理计算、状态机执行、环境参数更新和状态变化上报
- `ESM` 不生成物证解释，不管理物品归属，不管理接触痕迹和生物痕迹
- `ESM` 与司命、角色智能体、事件总线是平行协作关系，不存在谁吞并谁
- `302-308` 冻结的是系统最终职责版图，不能直接等同于 Phase 1 全量交付范围
- Phase 1 的 `ESM` 只采用“基础交互”口径：支撑关键物体状态变化、基础燃烧 / 潮湿 / 破坏和最小环境参数闭环

## 3. 核心定位

`ESM` 是《开本》`L1` 确定性空间层的物理法则执行者。

它负责回答的不是：

- 这是不是证据
- 角色怎么看待这件事
- 这件事戏不戏剧化

而是：

- 这个实体现在是什么状态
- 在当前规则下会不会发生变化
- 变化多久发生、如何发生、如何传播
- 变化后应上报什么确定性结果

## 4. 系统身份

### 4.1 所属层级

- 所属层级：`L1`
- 系统角色：环境状态管理器
- 核心特征：确定性、毫秒级、可复现、无 `LLM`

### 4.2 不是什麽

`ESM` 不是：

- 司命的下属脚本
- 角色智能体的感知解释层
- 事件总线
- 物品归属系统
- 指纹 / 血迹 / 纤维等痕迹管理器
- 证据推理器

## 5. 管理对象

### 5.1 当前统一口径

`ESM` 管理的是所有可交互实体的物理状态。

### 5.2 实体类型

#### 独立物体

例如：

- 窗帘
- 地毯
- 窗户
- 门
- 烛台
- 锁
- 信件

`ESM` 管理它们的：

- 燃烧
- 潮湿
- 破碎
- 开关
- 锁定
- 受力后变化

#### 区域环境

例如：

- 餐车
- 车厢尾部
- 实验室
- 室外雪地

`ESM` 管理它们的：

- 温度
- 湿度
- 烟雾浓度
- 风力
- 区域联动边界

#### 天气与结构

例如：

- 暴风雪
- 降雨
- 大雾
- 墙壁 / 地板 / 天花板等结构边界

### 5.3 明确不管理的内容

`ESM` 不管理：

- 谁持有什么物品
- 物体上是谁的指纹
- 物体上有哪些血迹 / 毛发 / 皮屑
- 某个状态变化在侦探意义上算不算证据

这些分别属于：

- 物品流转追踪器
- 接触痕迹管理器
- 生物痕迹管理器
- 司命事实核心 / 角色 `L2`

## 6. 核心职责

### 6.1 状态机执行

对所有挂载交互组件的实体执行状态转化，例如：

- 默认 → 燃烧 → 烧毁
- 默认 → 潮湿 → 干燥
- 默认 → 裂纹 → 破碎
- 解锁 → 锁定 → 破坏

### 6.2 物理规则计算

包括但不限于：

- 火焰蔓延
- 流体扩散
- 受力破坏
- 温度传导
- 湿度影响
- 结构边界阻隔

### 6.3 全局环境参数更新

例如：

- 区域温度
- 湿度
- 风力
- 烟雾浓度
- 天气状态

### 6.4 状态变化上报

把确定性状态变化写成结构化事件，发回事件总线。

### 6.5 视觉 / 表现驱动信号

`ESM` 不直接“做美术”，但会驱动：

- 粒子特效触发
- 贴图 / 材质变种切换
- 模型残骸替换
- 音效触发

## 7. 内部模块

### 7.1 物理规则引擎

职责：

- 计算火焰、流体、破坏、温度、湿度等规则
- 保证结果确定性和可复现

### 7.2 状态机库

职责：

- 保存各类实体状态转化图
- 定义触发条件、阈值、持续时间和不可逆边界

最常用状态机包括：

- 燃烧状态机
- 潮湿状态机
- 破碎状态机
- 结冰状态机
- 开关状态机
- 锁定状态机

### 7.3 实体参数 / 材料模板库

职责：

- 以材料模板复用可燃性、导热性、透水性、坚固度等属性
- 避免为每个物体单独编码一套物理逻辑

典型材料模板：

- 木材
- 布料 / 织物
- 金属
- 玻璃 / 陶瓷
- 石料 / 砖块
- 有机物

### 7.4 全局环境参数管理器

职责：

- 管理区域级物理参数
- 让天气、区域、实体状态产生联动

### 7.5 表现同步接口

职责：

- 把状态变化同步给渲染与表现层
- 不直接承载推理或业务逻辑

### 7.6 状态变化事件生成器

职责：

- 将状态变化转成可广播的结构化环境事件
- 供司命、感知过滤器、日志和证据相关子系统消费

### 7.7 动作结算接口层

职责：

- 承接来自角色、玩家输入链或司命环境请求的高层动作
- 在不越过物理边界的前提下，判定动作是否成立
- 产出 `ActionResolutionResult`、`ConstraintStateResult` 与相关状态变化事件

这一层不负责：

- 角色为什么要做这件事
- 这件事叙事上值不值得推动
- 某个结果是不是证据

### 7.8 区域环境场层

职责：

- 维护区域级环境参数
- 让同一区域内的温度、湿度、烟雾、噪音、光照、可见度产生联动
- 给感知链与视觉事实上抛提供“可观察前提”

这一层是 `ESM` 从“物体状态机集合”升级为“环境执行内核”的关键。

## 8. 与 Godot 底层组件的对齐设计

本节基于项目内已拉取的 `/.tmp/godot/` 源码，冻结 `ESM` 在 Godot 侧最适合依赖的底层组件。

### 8.1 `World3D` + `PhysicsDirectSpaceState3D`

关键事实：

- `World3D::get_direct_space_state()`
- `PhysicsDirectSpaceState3D::intersect_ray()`
- `PhysicsDirectSpaceState3D::intersect_shape()`
- `PhysicsDirectSpaceState3D::cast_motion()`
- `PhysicsDirectSpaceState3D::get_rest_info()`

设计含义：

- `ESM` 的“动作可行性检查”和“接触 / 遮挡 / 传播前置判断”不需要自己发明空间求交系统
- 最小动作结算层可直接建立在 Godot 已有的空间查询能力之上

推荐用途：

- 视线可达性
- 接触点确认
- 道具使用落点判定
- 门 / 遮挡 / 物体之间的阻隔关系确认
- 环境请求落地前的可行性预检

### 8.2 `Area3D`

关键事实：

- `Area3D` 支持 `monitoring`
- 可查询 `get_overlapping_bodies()`
- 可查询 `get_overlapping_areas()`

设计含义：

- `ESM` 的区域触发器、危险区域、声音 / 烟雾 / 热区等不必全靠自定义逻辑
- `Area3D` 很适合承载“进入区域即触发某种环境态”的低成本原型能力

推荐用途：

- 烟雾区
- 高温区
- 潮湿区
- 私密环境区
- 声音衰减 / 扩散辅助区

### 8.3 `RayCast3D` 与 `ShapeCast3D`

关键事实：

- `RayCast3D` 可直接提供 `is_colliding()`、`get_collider()`、`get_collision_point()`
- `ShapeCast3D` 可提供 `get_collision_count()`、`force_shapecast_update()`

设计含义：

- `ESM` 不必把所有前置查询都放到后端逻辑抽象里
- 客户端 / Godot 侧可以先完成局部碰撞前检和近距离交互候选收束，再交给 `ESM` 做结构化结果确认

推荐用途：

- 玩家点击交互前的目标确认
- 近距离物体使用候选
- 大体积交互体的接触预估

### 8.4 `PhysicsBody3D`

关键事实：

- `PhysicsBody3D::move_and_collide()`
- `PhysicsBody3D::test_move()`

设计含义：

- 角色、推动物体、阻挡、受力导致的动作失败等都已有底层结算入口
- `ESM` 应重用这些入口做“动作是否成立”的判定，而不是自行复制一套位移物理

推荐用途：

- 推门 / 撞门 / 受阻
- 简单推动物体
- 角色身体碰撞约束

### 8.5 `SceneTree` / `MessageQueue`

关键事实：

- Godot 有 `SceneTree`
- `MessageQueue` 提供 deferred queue

设计含义：

- `ESM` 的状态应用、场景树修改和表现同步，必须遵守 Godot 主线程安全约束
- 这意味着：
  - 规则判断、状态准备可在线程外做
  - 真正修改场景节点、材质、粒子、声音时必须回主线程安全时机

这条约束必须写死，否则 `ESM` 后续实现会天然不稳定。

## 9. 设计建议：`ESM` 的工程分层

基于上面的 Godot 底层组件，`ESM` 在工程上更适合拆成 5 层：

### 9.1 `Entity Registry`

- 管理所有可交互实体的注册信息
- 统一维护 `entity_id -> Node3D / Area3D / PhysicsBody3D / state machine profile`

### 9.2 `Material / Constraint Layer`

- 管材料模板
- 管是否可燃、可湿、可破、可锁、可遮挡

### 9.3 `Action Resolution Layer`

- 收 `ActionRequest`
- 调用 `PhysicsDirectSpaceState3D` / `PhysicsBody3D` 做前置结算
- 产出 `ActionResolutionResult`

### 9.4 `State Machine / World Field Layer`

- 执行物体状态机
- 执行区域环境参数推进

### 9.5 `Fact Emission Layer`

- 只上抛结构化结果
- 不做证据意义解释

这 5 层和 Godot 底层的适配关系比“把 `ESM` 写成抽象环境大脑”更可落地。

## 10. 与司命的边界

### 8.1 司命负责什么

司命负责：

- 叙事催化
- 事实记录
- 知识传播判断
- 冲突机会评估
- 高层干预

### 8.2 ESM 负责什么

`ESM` 负责：

- 物理可行性检查
- 状态机执行
- 环境变化结算
- 变化结果上报

### 8.3 协作关系

当前最稳的口径是：

- 司命定调
- `ESM` 执行
- 角色响应

但这不是主从关系，而是平行协作。

### 8.4 司命不能替代 ESM

司命不能：

- 直接令门无规则地烧毁
- 跳过 `ESM` 令火焰瞬间蔓延到不可能区域
- 直接写出违背材料属性和空间边界的结果

它只能：

- 提出高层催化意图
- 由 `ESM` 在规则允许范围内执行
- 接收执行后的状态变化并做叙事解释

## 11. 与角色智能体的边界

### 9.1 ESM 给角色的是什么

`ESM` 不直接给角色“结论”，而是给事件总线上报状态变化。

例如：

- 窗帘进入燃烧态
- 水缸温度上升
- 门锁被破坏
- 棉花团由燃烧转为潮湿

### 9.2 角色如何接收

角色不会直接消费全部 `ESM` 状态变化。

流程是：

`ESM` 状态变化事件
→ 事件总线
→ Per-Character 感知过滤器
→ 角色 `L1` 感知
→ 角色 `L2` 理解

### 9.3 角色不能替代 ESM

角色智能体不能：

- 自己结算火焰蔓延
- 自己判定门是否被烧坏
- 自己决定水流如何扩散

它只解释、感知和响应。

## 12. 与证据链的边界

### 10.1 ESM 上报的是状态变化，不是物证解释

例如：

- `curtain_dining_01` 从默认态变为燃烧态
- 19:48 被 `char_colonel` 使用打火机接触引燃

这仍然只是物理事实。

### 10.2 谁把它变成“证据”

- 司命事实核心：把状态变化写入事实、比对时间线和说法矛盾
- 角色智能体 `L2`：基于自身感知和认知能力解释其推理意义

### 10.3 与其他证据子系统拆分

当前统一拆分为：

- `ESM`：物体和环境物理状态变化
- 物品流转追踪器：归属与位置变化
- 接触痕迹管理器：指纹 / 纤维 / 唾液等接触痕迹
- 生物痕迹管理器：血迹 / 毛发 / 皮屑等生物痕迹
- 司命事实核心：矛盾、事实链、时间线比对

## 13. 输入与输出

### 11.1 输入

`ESM` 主要接收：

- 精确世界事件
- 高层催化请求
- 环境参数更新
- 系统时钟

### 11.2 输出

`ESM` 主要输出：

- 环境状态变化事件
- 实体状态稳定事件
- 区域参数变化事件
- 表现同步信号

更推荐在工程上正式固定为：

- `ActionResolutionResult`
- `ObjectStateResult`
- `EnvironmentStateResult`
- `BodyStateResult`
- `ConstraintStateResult`

### 11.3 示例

以“点燃棉花再投入水缸”为例，`ESM` 负责：

- 判定棉花材质可燃
- 开始燃烧状态机
- 递增燃烧进度
- 落水后触发潮湿状态优先
- 停止燃烧逻辑
- 更新为潮湿 + 部分烧毁稳定态
- 上报完整状态变化链

## 14. 运行时主循环

当前可抽象为：

```text
接收来自 L1 / 事件总线的精确世界事件
  -> 可选：调用 World3D / PhysicsDirectSpaceState3D 做空间查询
  -> 检查目标实体组件与材料属性
  -> 执行状态机与物理规则计算
  -> 更新局部 / 全局环境参数
  -> 通过 SceneTree / MessageQueue 安全触发表现同步
  -> 生成结构化状态变化事件
  -> 回写事件总线
```

时间特征：

- 毫秒级物理结算
- 可复现
- 不依赖 `LLM`

## 15. Phase 1 边界

### 13.1 系统最终版图

从系统最终职责看，`ESM` 理论上可以覆盖：

- 更完整材质规则
- 更复杂天气联动
- 更细流体与温度传播
- 更复杂区域环境演化
- 更长时间尺度生态变化

这些来自 `302-308` 的完整版图。

### 13.2 当前 Phase 1 采用范围

但 Phase 1 不按完整版图全量实现。

当前采用：

- 关键物体的基础状态机
- 基础燃烧 / 潮湿 / 破坏 / 开关 / 锁定
- 关键区域基础参数
- 最小动作结算接口
- 最小区域触发能力
- 支撑叙事所需的最小物理闭环
- 与事件总线、司命、感知过滤器打通

### 13.3 Phase 1 不做什么

Phase 1 不要求：

- 完整天气系统
- 生物成长系统
- 全面点云过渡体系
- 超复杂材料反应库
- 大范围持续环境演化
- 完整连续流体 / 火焰传播仿真
- 复杂多实体链式破坏系统

### 13.4 三阶段收束

- Phase 1：基础交互版 `ESM`
- Phase 2：完整物理规则版 `ESM`
- Phase 3：`ESM + 天气 / 生物成长 / 更大世界尺度`

## 16. 当前统一口径

后续所有文档提到 `ESM` 时，应统一采用以下口径：

- `ESM` 是 `L1` 独立环境状态管理器，不属于司命
- `ESM` 管理的是所有可交互实体的物理状态
- `ESM` 负责状态机和确定性物理执行，不负责证据解释
- `ESM` 上报的是状态变化事件，不是物证结论
- `ESM` 与司命、角色、事件总线是平行协作关系
- `ESM` 在 Godot 侧应优先复用 `World3D`、`PhysicsDirectSpaceState3D`、`Area3D`、`RayCast3D`、`ShapeCast3D`、`PhysicsBody3D`、`SceneTree`、`MessageQueue`
- `302-308` 是系统职责蓝图，`400` 才是当前阶段范围边界
- Phase 1 的 `ESM` 采用基础交互口径，不等于完整环境物理系统

## 17. 延后项

当前不在本版冻结范围内：

- 天气系统完整版
- 生物成长与生态变化
- 全面点云过渡与复杂视觉形变体系
- 大世界尺度环境持续推演
