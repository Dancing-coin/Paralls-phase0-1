# 02-角色驱动方案A-B裁决与双总线架构

## 1. 文档目标

本文档基于 `/.tmp/godot/` 源码审查，对“方案 A / 方案 B”的取舍做明确裁决，并冻结《开本》在角色驱动与事件传播上的双总线架构。

## 2. 方案定义

### 方案 A

高层语义/参数驱动：

- 外部后端或 Python 智能体发送高层状态、意图、`FACS/SACS` 激活集合与表达核
- Godot 本地使用 `AnimationTree + SkeletonModifier3D + face runtime` 执行

### 方案 B

底层关节/骨骼直接驱动：

- 外部智能体高频发送每个骨骼、每个关节、甚至每个局部姿态的直接控制流
- Godot 侧更多像木偶执行器

## 3. 裁决

主方案必须选 **A**。

但不是“纯 A”，而是：

> **A 做跨边界主协议，B 只作为 Godot 本地具身后处理子层。**

也就是：

- 跨边界：只传高层语义和 canonical 控制结果
- 本地：允许骨骼级精修，但这一步必须留在 Godot 内部

## 4. 为什么不是主选 B

从 Godot 源码和本项目需求共同看，B 做主方案会带来：

1. 主线程安全压力更大
2. 网络 jitter 直接映射到骨骼 jitter
3. 很难复用 `AnimationTree` 主动作混合能力
4. 回放与可解释性差
5. 多角色并发扩展成本爆炸

## 5. 双总线架构

《开本》应明确采用双总线：

### A. 后端权威叙事/事实总线

负责：

- 原始世界事实
- 可感知信息编译
- 角色私有感知事件
- 司命高层消息
- `ESM` 结果
- 角色行为回写
- replay / audit

### B. Godot 本地表现总线

负责：

- 角色副本更新
- 表达计划 revision
- `AnimationTree` 参数更新
- `SkeletonModifier3D` 精修触发
- UI 提示推送
- 本地安全 deferred 执行

## 6. 正确的本地执行结构

建议固定采用：

- `AnimationTree` 主轨：locomotion / base gesture / state transition
- `SkeletonModifier3D` 精修轨：gaze、torso tension、injury compensation、hand intention 等
- 面部独立轨：`FACS -> face runtime`

## 7. 角色智能体设计的直接优化点

1. 把 `Embodiment Binder` 拆成：
   - 服务端 canonical compiler
   - Godot 本地 runtime binder
2. 给角色智能体设计补一个 `Godot Local Expression Runtime` 层
3. 事件总线设计里新增“Godot 本地表现总线”边界
4. 玩家输入桥接只发意图，不发世界修改结果
5. `SACS` 高频执行从后端拉到 Godot 本地
6. 做角色副本分级更新策略

## 8. 一句话收束

Godot 源码底层明确支持骨骼级精确控制，但《开本》的正确主架构不是“外部智能体逐骨骼遥控木偶”，而是“后端权威高层语义驱动 + Godot 本地高频具身执行”的双总线结构。
