# 受约束社会模型编译器设计（中文版）

状态：`已确认设计；尚未授权实现`

日期：`2026-09-17`

关联基线：[角色与群体模拟增量设计](2026-09-16-角色与群体模拟增量设计-中文版.md)

英文主文档：[Constrained Social Model Compiler Design](2026-09-17-constrained-social-model-compiler-design.md)

## 一、决策摘要

本设计在《角色与群体模拟增量设计》定义的“社会模型层”中增加一个
**受约束社会模型编译器**。它不是第二套世界运行时、人口真相 owner、事件库、
时钟、调度器、结算 router，也不是跨域社会读库。

编译器把一个获准的结构化请求，编译为针对 owner 签发的冻结输入向量的临时模型。
它可以计算预测、行动候选、冲突、风险、展开请求和协议调用请求。所有结果始终是
提议：既有推进主体决定是否采纳；既有事实 owner 与已登记协议才决定是否提交世界
事实。

```text
既有提议者 + 有效 ModelRunGrant
  -> SocialModelDraft
  -> 静态模板与权限准入
  -> 图谱候选发现 + owner FactCard/Proof 读取
  -> 冻结 InputVersionVector
  -> 临时声明式 IR 执行
  -> CandidateEnvelope[] + ModelRunReceipt
  -> 既有 B0/B1/B2/B3 推进主体可选择采纳
  -> 既有 ModuleProposal / ActionIntent / 协议请求
  -> 既有 owner 重验、结算、receipt 与投影
```

它从属于既有的分层方向：

```text
原子事实与原子操作
  -> 已登记的预编译协议
  -> 社会模型
  -> 派生投影
```

它不改变原子事实归属、Character Core 连续性、`ParticipationResolution`、
activation/handoff lock，也不改变 `SimingRuntime.tick(...)` 作为司命决策与派发
入口的地位。

## 二、范围与硬边界

### 2.1 范围内

- 在冻结快照上运行、无副作用、有限分类的声明式社会分析。
- 不可变受信玩法包模板与参数 profile。
- owner 签发的最小读取输入、图谱辅助发现、确定性或固定种子情景分析、候选输出、
  读侧投影与回放凭据。
- B0 群体/有限分片分析，B1/B2 批量或局部分析，B3 最小获准个人上下文分析。
- 司命治理的计算授权，以及从 shadow 到 active advisory 使用的分阶段启用。

### 2.2 范围外

本设计不授权：

- 通用社会、人口、市场、组织或战争事实 owner；
- 组织、市场、家庭、军队或编译器的独立意志、目标或人格；
- 模型、图谱、LLM、司命或表现层直接写库存、账户、权利、关系、人口、空间、
  法律、记忆、流程或其他世界事实；
- 动态 Python、包内脚本、公式 DSL、动态 schema 或任意可执行插件；
- 编译器自己的队列、重试循环、时钟、调度器、事件库、锁或结算协调器；
- 影子 NPC 数据库、B0 的逐人分配表或全局社会快照库；
- 声称完整人口模拟、战争贸易、外交或尚未准入的 owner capability 已经实现。

## 三、封闭的八类模型

V1 固定为八类。每个模板必须声明自己使用的类别；受信玩法包只可在类别内组合
已登记节点、算子和数据 profile。第九类、新 IR 节点或算子语义变更均需要独立的
架构准入与回放合同。

| 类别 | 解决的典型问题 | 典型对象 | 编译职责与输出上限 |
| --- | --- | --- | --- |
| 实体—关系图 | 谁和谁、谁属于谁、谁有权做什么 | 家庭、组织成员、职位、敌对、盟约、债务 | 发现可行参与者、关系冲突、授权缺口、展开请求；不授予、撤销或创建关系 |
| 资源保管与流量网 | 什么资源在哪、归谁、能否移动、何时耗尽 | 粮食、钱、武器、药品、仓库、车队 | 计算短缺、流量候选、保管/容量冲突；不消耗、预留、转移或创建资源事实 |
| 空间—可达性图 | 人与物能否经过、运多久、风险多大 | 道路、港口、关卡、火区、积雪、战线 | 计算路线候选、时间与风险；未确认物理信号只能提高风险 |
| 流程/状态机 | 一件社会事务处在哪一步 | 报价→订货→装载→运输→验收→付款；征兵→集结→补给→作战→休整 | 报告合法下一步候选与阻塞点；不推进流程 |
| 承诺与时间表 | 谁答应什么、何时到期、违约会怎样 | 合同、工资、配给、债务、条约、任务 | 报告到期/违约风险、履约候选；不创建、履行、豁免或违约承诺 |
| 约束与分配模型 | 有限资源如何竞争、分给谁、哪里冲突 | 避难床位、粮食配给、工坊产能、军需、预算 | 比较群体/分片可行方案与冲突集；B0 不输出逐人分配表 |
| 风险与传播模型 | 压力怎样沿关系和空间传播 | 饥荒、谣言、疾病、逃兵、火灾、市场恐慌 | 输出区间、情景分支、预警与复核建议；预测不是事件 |
| 聚合与分摊模型 | 群体现象如何压缩并安全重新关联个人 | B0 士气、疲劳、食物压力、迁徙风险、伤亡候选 | 输出群体/分片指标、曲线与升级请求；不覆盖保护字段或 `individual_only` 字段 |

家庭、组织、市场、迁徙、灾害和战争后勤都是八类的组合模板名称，不是新增类别、
runtime host 或独立行动主体。

## 四、权限与主体

### 4.1 既有主体继续拥有原有职责

| 主体 | 可以做什么 | 不可以做什么 |
| --- | --- | --- |
| 司命 | 在既有 tick 中签发限定 scope 的 `ModelRunGrant`，选择全局 cadence 与 catalyst，消费红脱敏摘要 | 读取角色私有记忆、直接结算事实、把写权限交给模型 |
| B0/B1/B2/B3 推进主体 | 提交草案、接收候选、在既有路径中决定是否采纳 | 把候选当事实，绕过 activation/handoff lock |
| Character Agent / LLM | 选择已激活模板、填写受限参数、说明目标/异常、解释结果 | 发明类型、事实、规则、代码、schema 或结算路径 |
| 编译器 | 验证、装配、计算、发现冲突、记录运行凭据 | 提交协议、选择赢家、获得锁、预留资源或提交事实 |
| 事实/协议 owner | 签发过滤后的 FactCard、重验已选择请求、结算自身事实、签发 receipt | 信任过期模型输入，或把事实归属让给编译器 |
| Heavenly Graph | 发现已索引的候选与带来源的派生上下文 | 变成事实 owner 或替代 owner 读取 |
| Godot/表现层 | 发射具身观察，展示确认结果或可重建预测 | 因动画、碰撞、声音或 UI 看似成功而修改持久真相 |

### 4.2 候选采纳

只能由原有推进主体采纳编译器候选：

- B0 由司命已批准的群体策略采纳；
- B1/B2 由既有脚本推进规则采纳；
- B3 由角色智能体在自己的合法私有上下文内采纳。

编译器、组织、市场和事实 owner 不会因收到候选而获得一般决策权。采纳只会把候选
转换为既有 `ModuleProposal`、`ActionIntent` 或类型化协议请求；目标 owner 仍必须
检查当前事实与预期 revision。

## 五、数据合同

下列名称描述目标合同，不表示已经实现。

### 5.1 `SocialModelTemplate`

由已准入玩法包提供的不可变声明，至少包含：

```text
package_ref, package_digest, template_ref, template_version, active_set_digest
八类标签、IR 节点声明、固定算子/profile 引用
必需与可选 FactCard kinds
允许提议者类别、消费 scope、privacy ceiling 与 purpose
允许输出类别与目标 capability/protocol 引用
B0/B1/B2/B3 适用范围和聚合限制
最大 analysis_window、频率、情景数、计算/上下文预算
声明的降级表和红脱敏策略
```

模板不含可执行代码、动态查询、自由 schema、事实坐标或写权限。

### 5.2 `ModelRunGrant`

司命在既有 tick 中签发临时、不可变的计算许可。它只能收紧模板上限，不能扩大：

```text
grant_ref、签发者与 Siming tick/correlation 引用
template/package/active-set pins
请求主体和允许的提议者类别
purpose、scope、privacy ceiling 与 reader roles
有效时间区间、analysis_window 上限与运行频率上限
context、节点/边、情景、候选和执行预算
运行模式：off | shadow | advisory | active
grant revision 与 digest
```

它不是协议授权，也不是资源预留。

### 5.3 `SocialModelDraft`

既有提议者创建的受限请求：

```text
template_ref 与预期 package/active-set pins
提议者身份与 purpose
参与者、情境和上下文引用
受限、类型化参数与请求情景数
请求的输出类别和 correlation/idempotency identity
```

草案不能携带自由 IR、事实值、可执行文本、owner command、调度指令或无边界上下文。

### 5.4 `FactCard` 与 `Proof`

只有来源 owner 可以为硬约束签发读取输入。每张卡或证明至少包括：

```text
card_ref、事实族与 source owner
被授权的 purpose、scope、privacy class 与 consumer/reader 约束
revision、digest、valid_at、recorded_at、expiry 与 source event refs
provenance，以及所需 rule/package/policy pins
```

具身和环境证据还需带来源身份、对象/空间版本、confidence、有效区间与确认状态。
编译器读取经过过滤的卡，不读取 owner 私有数据库或内部投影。

### 5.5 `InputVersionVector`

运行前，编译器固定所有输入：

```text
template、package、active-set、operator-profile 与 grant pins
FactCard/Proof 引用及其 owner、revision、digest
密码本 expansion receipts
图谱候选引用与成功的 owner back-check proofs
时间锚、analysis_window、类型化参数、确定性排序与 seed
```

所有必需卡必须存在且有效。可选卡缺失只能走模板声明的保守降级，不能用旧缓存或猜测补洞。

### 5.6 `CandidateEnvelope`

全部输出使用一个受限信封：

```text
candidate_ref、correlation/idempotency identity、输出类型
由固定模板 schema 验证的语义负载
目标已登记 capability/protocol 引用（适用时）
input vector digest、预期 owner revisions、支撑 proof refs
风险/confidence 边界、情景 seed/reference、expiry
受影响 scope、privacy/redaction 标签、预算消耗
```

唯一合法输出类型：

```text
prediction
action_candidate
continuity_or_state_delta_candidate
conflict
risk
expansion_request
protocol_call_request
```

任何 envelope 都不是 command 或事实。连续性候选必须复用既有版本化
`ModuleProposal`/continuity 合同，只能命名 active module 与
`ParticipationResolution` 允许的字段。

### 5.7 `ModelRunReceipt` 与 `ModelProjection`

每次已准入运行——包括空结果、降级、拒绝、截断与错误——都生成最小红脱敏 receipt：

```text
run_ref、status、correlation、template/grant/input-vector/seed digests
codebook read receipts、graph back-check outcome
operator/profile versions、确定性排序、预算结果
candidate/output digest、cache reuse 引用、时间与红脱敏 metadata
```

`ModelProjection` 是从 receipt 派生的、会过期、按 scope 过滤的读投影。它可为以后获权
消费者提供预测、风险、短缺区间或冲突摘要；但它不成为事实、不成为 Heavenly Graph
事实节点，并在输入、权限、隐私或时间窗口失效时作废。

## 六、编译流程与沙箱

### 6.1 静态准入与预编译

不可变玩法包激活时，系统验证模板类别、固定节点、算子/profile pins、声明 read-set、
输出许可、预算、LOD 限制与降级表。验证通过的模板骨架可预编译为静态 IR 执行图；
骨架不含实时世界数据。

固定算子目录中只有纯函数、可版本化实现。玩法包提供阈值、路线成本权重、传播衰减、
分配目标选择、状态转移条件和聚合曲线等数据 profile。profile 不能改变算子语义、
加载代码、创建新输出类别或指向新的 owner operation。

### 6.2 运行时编译

```text
验证 grant、提议者、模板 pins、purpose、scope、privacy 与预算
-> 验证受限草案参数
-> 在获权 scope 内发现图谱候选
-> 回查每一个会成为硬约束的候选 owner
-> 请求必需/可选 FactCards 与密码本展开
-> 冻结 InputVersionVector
-> 把引用和参数绑定到静态 IR 骨架
-> 执行无副作用的硬约束裁剪
-> 执行资源、空间、流程、承诺与分配计算
-> 最后运行有限数量的风险/情景分支
-> 产出 envelopes、projection candidates 与 ModelRunReceipt
```

编译器拒绝未声明节点、未声明合法无环求值顺序的循环、动态派发、未 pin 算子、
非法数值域，以及任何试图获取世界资源或写句柄的操作。

### 6.3 不确定性

编译器使用两条不同通道：

1. 认识不足绝不随机化。缺失、过期、无权或互相矛盾的信息必须返回明确降级状态。
2. 合法模板可计算确定性边界，也可用冻结 seed 计算有限情景分支。情景只用于比较，
   不是已提交的未来世界结果；真实随机结果仍由相应 owner 的协议和证据链决定。

## 七、输入、图谱、隐私与上下文

### 7.1 Heavenly Graph

Heavenly Graph 继续是带 scope、时间、revision、privacy、consistency audit、source event
与 provenance metadata 的派生索引。它可发现候选参与者、关系、路径、依赖和因果上下文。

图边只有在以下步骤全部成功后，才可变为硬模型约束：

1. 检查可见性、新鲜度、revision、audit 状态和 provenance；
2. 取得图边的 source-event 与 source-owner 引用；
3. 获得 owner 签发、在兼容冻结 revision 上确认关系的 FactCard/Proof。

任一步失败都不能用图谱猜测补位。模板返回 `graph_degraded`、
`context_insufficient` 或声明的条件性风险。保管、权利、余额、容量、成员资格和流程状态
等可操作事实始终需要 owner 卡。

### 7.2 隐私与密码本

每次运行绑定 requester identity、purpose、scope 与 privacy ceiling。跨域模型只交换
owner 签发的最小卡、聚合值或证明。密码本沿用现有 L0/L1/L2 权限路径，并记录
expansion receipt；编译器只保存引用和 digest，不保存万能明文副本。

司命只收到公开或明确可见的摘要；B0 通常只读 L0 安全摘要；B3 仅为相关 actor/purpose
读取获准私有卡。输出对每位消费者再次过滤。

## 八、真相更新与具身证据

### 8.1 真相更新原则

| 表面变化 | 模型可输出 | 唯一可确认事实与确认者 | 必需依据；未知时如何处理 |
| --- | --- | --- | --- |
| 库存减少 | 消耗/配给候选、短缺预测 | Inventory 保管/容量 owner | 保管、可用量、purpose、协议 receipt；没有证据不扣减 |
| 人口迁徙或死亡 | 风险、迁徙/救援 intent、B2/B3 请求 | Character Core 连续性加适用的生命/空间/环境 owner | 身份、位置、确认的证据和规则；群体伤亡统计不能断言个人死亡 |
| 财富/价值变化 | 供需/价格区间 | 市场价格是投影；账户余额是 Economy ledger 事实 | 真实报价/订单/交易/规则；预测不能创造价值或 posting |
| 账户余额 | 付款/hold 候选 | Economy/account ledger owner | 权限、对手方、余额、合同和原子 receipt |
| 角色权利 | 授权缺口或申请候选 | 既有 Rule/Organization/Government owner | 有效程序、资格、代表权与 receipt |
| 组织成员 | 资格/冲突候选 | Organization owner | 身份、章程/程序/表决/任命证据 |
| 道路/建筑损毁 | 路线/维修候选和风险升高 | Space/Construction/environment owner | 确认的对象/空间版本化证据；纯表现不够 |
| 市场价格 | 风险/价格 projection | 由事实事件推导的 Economy/market projection | 已提交交易/订单/规则数据；预测不写正式价格 |
| 军队士气 | 群体压力和连续性候选 | 允许的 Character Core receipt 或已准入领域 owner | 确认事件和允许 module rule；B0 不逐兵写状态 |

候选被采纳时，目标 owner 比对请求的 expected revision 与当前源版本。不匹配必须是
`stale_input` 或 `conflict` 的硬拒绝与零写入，不能局部修补旧模型的数量、路线或参与者。

### 8.2 证据分类

| 证据类型 | owner 确认前在模型中的身份 | 进入硬约束的路径 |
| --- | --- | --- |
| 纯语义事件 | intent、proposal、catalyst 或 candidate，永远不是事实 | 已登记协议/规则与 owner receipt |
| 具身行动事件 | 带来源/confidence 的短时风险输入 | 事实上抛器证据 -> 对象/空间/权限/因果验证 -> confirmed FactCard |
| 持续环境事件 | 带区域/版本/confidence 的短时风险输入 | 环境/空间 owner 确认 -> confirmed FactCard |
| 纯表现事件 | 永远不是模型事实或硬约束 | 无；它只保留为可重建本地表现 |

例如门接触与动画完成可使模型请求复核或绕开危险路径；在相应对象/空间/权限 owner
确认前，不能断言门已打开。

## 九、LOD、调度与性能

### 9.1 上下文 LOD

| 上下文层级 | 合法输入与计算 | 可提出什么 | 必须升级条件 |
| --- | --- | --- | --- |
| 玩家局部 | 已确认局部投影、获权对象/角色状态、可重建预测 | 玩家输入与交互 intent | 玩家交互进入既有 handoff 判断 |
| B3 关键角色 | 最小私有 FactCards、获权密码本展开、共享 module state、局部模型结果 | ModuleProposal、ActionIntent、草案、解释 | 对话、谈判、长期冲突、保护字段、不可脚本裁决 |
| B2 局部事件 | 事件局部空间/流程/关系/资源卡与有限角色 | 局部候选、草案、升级请求 | 玩家交集、个人权利/合同/家庭冲突、范围溢出 |
| B1 普通日常 | archetype/profile/situation、B1 modules、常规局部/分片摘要 | 批量普通 proposals/intents | 无法裁决规则冲突、保护字段、局部异常 |
| B0 群体压缩 | L0 摘要、群体/有限分片卡、ParticipationResolution 摘要、聚合模型投影 | 群体指标、曲线、风险、总量候选、升级请求 | `individual_only`、家庭分离、关键财产、合同/权利、玩家关系、死亡/伤害、不安全物化 |
| 司命全局摘要 | 公开/司命可见 owner 摘要、红脱敏投影、图谱发现、grant 状态 | grant、catalyst、例外选择、cadence 提议 | 私有/个人裁决只能请求权限展开 |

编译器只能提出 `required_fidelity` 或 `expansion_request`。既有
`ParticipationResolution` 和 activation/handoff lock 才能裁定并完成交接。
Character Core 仍是唯一连续性/物化接纳者。

### 9.2 B0 聚合规则

B0 必须保持粗粒度：

```text
B0 成员账本
  = 身份锚点、分片、入组 revision、策略摘要、保护引用和 cursor
  != 逐人分配、资源、伤亡或位置表

B0 模型
  = cohort/shard/resource-pool/route/process-batch 分析
  -> 总量、比例/曲线、短缺区间、风险区间、seed 与 expiry
  != 逐 actor 状态变更、保管归属或交易
```

owner 可以确认消耗粮食、占用床位、使用车队容量等群体/分片总量，以及统计分布描述符。
角色退出 B0 时，既有交接路径根据该角色锚点、保护约束、已确认 aggregate receipt 与
模板规则构造最小安全上下文；它要么形成允许的连续性候选，要么返回 `unknown`/要求
B1/B2/B3，绝不把平均值写成未经验证的个人事实。

### 9.3 Cadence 与 analysis window

编译器不逐帧运行，也不推进世界时间。模板声明有界最大 `analysis_window`；grant 只能
缩短，不能扩大。超过窗口必须在新的世界时间和输入向量上重新读取、重新编译。

| 频率 | 归属 |
| --- | --- |
| 每帧/实时 | 仅 Godot 本地表现与物理采样 |
| 局部物理/流程事件 | 相应 owner 证据确认；确认事件可使相关模型 scope 失效 |
| B2 分钟级/局部事件 | grant 下的既有局部推进路径 |
| B1 小时级 | grant 下的既有脚本推进路径 |
| B0 游戏日级/获权灾害 cadence | 司命治理的群体路径 |
| 周级 | 只产生宏观 `ModelProjection` |
| 已确认重大事件 | 使受影响模型失效；既有路径决定是否重编译 |

### 9.4 性能与缓存

目标是预编译一次、批量执行、按需展开：

1. 以 package/template/active-set/IR/operator digest 缓存静态模板骨架。
2. 首期仅对完整 input-vector、参数、grant、seed 完全相同的模型结果缓存。
3. 只有独立证明后，才增加 owner-card fragment 级失效；绝不近似复用旧世界结果。
4. B0 操作 cohort、shard、pool、route 和 process batch，而非每个 NPC 节点；先做硬约束，
   再做昂贵情景计算。
5. 不相交 scope 的纯推演可并行，但它们不共享可变世界状态；owner 结算仍独立做版本检查。

缓存命中须在 receipt 中记录 `reused_from`。任何缓存都不能变成 NPC 真相副本或
“最新社会状态”数据库。

## 十、失败、降级与运行模式

编译器没有自动重试队列。它返回状态和 receipt；既有 grant/cadence/event 路径决定后续
授权窗是否重试。

| 状态 | 必须行为 |
| --- | --- |
| `ok` | 生成了合法候选，但候选仍不可信 |
| `unknown` | 没有合法结论；保留未决状态 |
| `context_insufficient` | 缺必需卡或展开；在既有策略下等待、请求展开或升级 |
| `proposal_only` | 分析有用但没有已准入目标 capability/protocol |
| `graph_unavailable` | 跳过图谱发现；只有 direct owner read 足够时才继续 |
| `graph_degraded` | 图谱候选 audit/freshness/provenance/back-check 失败；不得作硬约束 |
| `owner_unavailable` | 必需 owner 无法签卡；零写入并 defer |
| `stale_input` | 输入或采纳 revision 已变；硬拒绝，在新向量上重编译 |
| `budget_exhausted` | 仅返回已完成安全摘要或 proposal-only；不得自旋或悄悄放宽策略 |
| `policy_denied` | grant/template/proposer/privacy/LOD 不允许；零写入 |
| `conflict_detected` | 报告冲突集与依据；不选择赢家 |
| `zero_write` / `error` | 保留红脱敏诊断 receipt，不产生持久效果 |

运行模式：

```text
off       不编译、不读模型输入
shadow    编译并对比；候选/投影不送达推进主体
advisory  获权消费者看到候选/投影，但策略禁止采纳
active    既有推进主体可通过既有路径采纳候选
```

## 十一、回放、审计与投影验证

每个已准入运行必须支持 full replay 与 checkpoint-plus-tail replay。回放固定
template/package/active-set、operator profile、grant、input cards、codebook read receipts、
graph back-check、确定性参数排序、时间锚、analysis window、预算与 seed。

回放必须得到相同 status、output digest、降级理由和 cache 解释；但不会强制世界 owner
将未来随机结果等同于某条预测情景。后续每次采纳与 owner receipt 均保存源
`ModelRunReceipt` correlation，以区分：

- 模型提出了候选；
- 推进主体采纳或忽略候选；
- owner 接受或硬拒绝候选；
- 投影过期且未产生世界效果。

receipt 与 projection 是读侧/审计产物，可进入既有获权观测面，但不能 append 世界事实，
也不能被重分类为图谱事实。

## 十二、样板 A：洪灾下的村庄粮食分配

这是首个预期验证垂直，不是实现宣称。司命为村庄、南北两个非敏感分片以及有界当日窗口
签发游戏日级洪灾 grant。`flood_village_rationing@v1` 模板组合家庭/授权关系、粮食保管、
车队和避难容量、损坏道路、配给流程状态、既有配给承诺、聚合分配、风险和 B0 压缩。

图谱可发现村庄/家庭/道路/避难所候选；Organization、Character Core、Inventory、
Space/Environment 与 Rule owners 提供对应卡。一条“南路可能被碎石堵住”的未确认报告
仅是短时风险输入；owner 确认道路关闭后才变为硬约束。

模型可以报告：

```text
北片：日需求 82% 覆盖率候选
南片：因路线风险，48-62% 覆盖率区间
避难所：剩余 16 个已确认 aggregate 床位
输出：总量配给/运输协议请求、道路复核请求，
      以及面向受保护家庭和玩家附近角色的精度升级请求
```

它不能断言老王获得某个具体粮食量，也不能断言某个指名角色已入住。

| 视角 | 职责 |
| --- | --- |
| 玩家 | 看到确认的道路、存储和避难结果及可重建评估反馈；可提交护送、清障、运送 intent |
| 司命 | 看到群体风险/例外摘要和 grant 预算；选择 cadence/catalyst，而非逐人分粮 |
| 角色智能体 | 合法 B2/B3 交接后读取最小获权家庭约束，提出家庭安全 intent |
| 编译器 | 比较总需求、路线、容量、承诺和风险，输出候选与升级请求 |
| 事实 owners | 重验仓储、车辆、道路、授权和容量；结算已登记协议事实或拒绝 |
| 表现/物理层 | 观察装卸、接触、路线和门状态，提交证据，但不宣布送达、收容或粮食转移 |

成功路径是 owner 确认的 aggregate 库存/容量 receipt 与允许的连续性反馈。若容量或
revision 冲突，owner 硬拒绝、零写入；老王保留已确认疲劳、恐惧、义务和未决请求，不能
被错误展示为安全。

## 十三、样板 B：冬季战争贸易

这是完整设计示例，不是现有 owner capabilities 齐全的声明。
`winter_embargo_supply_risk@v1` 在有界冬季窗口中组合全部八类：

- 公开代表、商会、车队、军队后勤、盟约、敌对与确认的授权关系；
- 粮食、燃料、药品、武器、仓储、车队和补给池卡；
- 港口、道路、关卡、积雪、战线和确认的限制；
- 报价/订单/装载/运输/验收/付款及征兵/集结/补给/作战/休整流程；
- 禁运、合同、交付期限、债务和条约义务；
- 民用市场、医疗、军队、战略库存之间的竞争；
- 恐慌、走私、逃兵、疾病与路线中断风险；
- 非关键车队劳力、军需压力和民用需求的有限聚合分片。

它可预测军需覆盖区间、报告车辆/时间窗冲突、提出既有运输/配给/外交审查协议请求、
请求复核港口状态，或要求关键谈判者升 B3；还可比较“港口持续关闭/部分复开”的冻结
seed 情景。它不能实施禁运、移动车队、记账、认定间谍、授予走私权、发动战争或签订条约。

| 视角 | 职责 |
| --- | --- |
| 玩家 | 只见获权公开市场、路线与禁运影响；可护送、谈判、侦察或提交类型化 intent |
| 司命 | 治理 grants 与全局风险/catalyst 摘要；不决定国家意图或修改外交 |
| 角色智能体 | 商人、军官、外交官、平民用各自获权承诺/约束提出行动 |
| 编译器 | 比较冻结的关系、保管、路线、流程、期限、分配与风险约束 |
| 事实 owners | Inventory/transport、Economy、Organization、Government/Rule、Contract、Space/Environment 分别重验并结算自身事实 |
| 表现/物理层 | 展示确认的关卡、积雪、车队、装卸与到达；提供证据但不确认产权、验收或付款 |

若禁运、条约、运输或账户所需 capability 没有已准入 owner-bound protocol，输出必须是
`proposal_only` 或 `owner_unavailable`。编译器不得用通用战争贸易 authority 填补缺口。

## 十四、实施顺序与验收证据

每个阶段均可独立评审，且只证明既有链路上的有界扩展：

1. **基础分类与合同。** 固定 taxonomy、合同、红脱敏、状态与非目标。证明未知类别、
   动态代码、自由字段和禁止 authority 路径 fail-closed。
2. **静态模板准入与 shadow 编译器。** 加入不可变模板骨架、固定纯算子目录、grant 与
   `off`/`shadow` 运行。证明零事实写入和确定性 output digest。
3. **FactCard 与版本向量读取。** 为洪灾垂直提供最小卡与图谱回查。证明 expiry、
   owner 不可用、privacy denial、图谱降级和 checkpoint-tail replay。
4. **洪灾 B0 advisory。** 构建总量/分片粮食、路线、仓储、避难、风险与精度候选。
   证明无逐人 B0 分配或隐藏人口真相。
5. **既有路径采纳。** 仅允许原推进主体生成既有 intent/proposal；证明一个 aggregate
   receipt 成功与一个 stale/capacity 硬拒绝。
6. **读投影与精确缓存。** 加入过期 `ModelProjection`、红脱敏审计 receipt、静态骨架
   缓存和精确向量结果缓存。证明不保存私有明文或 NPC 镜像。
7. **经证明的扩展。** 只有独立证据后才加 fragment invalidation；再只在相应 owner
   capability 单独准入后扩展迁徙、组织、市场与战争贸易模板。

跨阶段验证至少覆盖：合同准入/拒绝、privacy 与 codebook receipts、预算耗尽、封闭分类、
图谱回查、具身证据分级、B0 聚合限制、LOD handoff、候选冲突报告、过期输入硬拒绝、
全部降级状态、full/checkpoint-tail replay、owner receipt correlation，以及 Godot
表现层永不把预测提升为真相。
