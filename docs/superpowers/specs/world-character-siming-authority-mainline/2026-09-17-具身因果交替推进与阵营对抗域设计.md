## 一、目的与前提

本设计解决一个在 2026-09-16 基线中尚未收口的因果问题：玩家和 Character Core 的行动会先在 Godot 具身层经历移动、接触、受力、遮挡、燃烧、建造等过程；一旦过程改变了真实可达性、资源保管、设施能力或环境风险，群体模拟不能继续把旧世界当作上下文，也不能等到下一次全局大周期才避免错误写入。

目标不是让 Godot 成为世界 owner，也不是让后端精确复演所有刚体、粒子或骨骼。目标是让具身层为世界提供可核验的证据，让确认后的变化以最小、可回放的影响摘要进入同一条事实链，并让玩家、角色、群体、司命和 UI 在各自权限范围内交替推进。

本设计是 2026-09-16 设计的后继，不改变其十五条核心原则：同一角色跨 B0–B3 连续、模块只产生提议、Character Core 只结算角色连续性、领域 Owner 只结算其原子事实、Godot 无世界事实写权、一个角色同一时刻仅一个推进器、失败必须是正式结果。

### 1.1 实施门禁

本设计可以先评审和冻结，但不得抢跑实施。只有以下前置完成并有独立证据后，才可进入本设计的代码计划：

1. 2026-09-16 设计的阶段 0–7 完成；
2. `CharacterSimulationFrame`、`ParticipationResolution`、模块建议、B0 成员账本、B0–B3 交接与通用密码本的基线合同已可用；
3. 该基线的 replay、隐私、zero-write rejection、handoff lock 和 Godot 事实投影门禁均通过；
4. 后继实现仍只扩展既有 `world_runtime`、L1、ESM、Gameplay Foundation、Character Core、Siming 与 Godot 通道。

不得借此新建第二个 runtime、clock、scheduler、event store、空间真相库、万能 router、万能 settlement owner、Population Truth Owner 或 Situation Truth Owner。

## 二、白话总览

世界有三种不同速度，但只有一个确认边界：

```text
Godot 帧/物理过程：快，局部，可预测，可失败
        ↓ 结构化具身证据
Owner 提交世界 revision：慢一些，原子，可回放，是唯一真相
        ↓ 确认影响摘要
角色/群体/司命反应 tick：按影响范围与预算推进，可局部加速
```

因此“表现层变化快于群体模拟”不会靠强迫所有 NPC 立刻全量重算来解决，而靠两步：

1. 一条具身结果确认后，立刻令依赖旧世界版本的候选不可执行；
2. 仅让受影响角色、cohort、组织压力和司命态势进入事件触发的局部微 tick。

这形成真正的双向因果交替：玩家和角色的具身行动能改变群体推演的前提；群体/司命产生的、经 Owner 确认的项目、调度和限制又投影回 Godot，改变下一轮具身行动的可行性。

```text
确认世界 Rn
  -> 多主体候选与具身过程
  -> Owner 结算 Rn+1
  -> 失效旧候选 + 局部信念更新
  -> 群体/司命/角色新候选
  -> Owner 结算 Rn+2
```

这里的 tick 是可原子提交、可回放的因果窗口，不是 Godot 的渲染帧或物理帧。

| --- | --- | --- | --- | --- | --- |
| 语义意图、规则与协议层 | 玩家、Character Core、B0–B2、司命提出候选；Owner 校验权利、规则、资源、版本、冲突；协议结算并回放 | 已确认的所有权/保管、设施阶段、通行能力、伤害/状态、项目状态、资源/组织结果、战区状态 | 行动授权、reservation、读取版本、能力检查、被拒原因 | 按钮反馈、候选提示、司命建议文本 | 将模型判断、角色意图、群体计划直接写成世界事实 |
| 几何、物理与空间证据层 | Godot 采样碰撞、接触、位置、遮挡、材质、承重、导航、热/火、可见/可闻；L1 归一化事实、空间锚点与 occupancy 输入 | 只在 Owner 采纳后，改变可达性、容量、占用、危险级别、构件完整性、物体位置/保管、环境字段 | 接触摘要、支撑/碰撞判定、路径阻断样本、热量阈值、施工对位、视觉/声音观察、资产版本 | 原始刚体轨迹、粒子、逐骨骼姿态、镜头抖动、局部碎片、未确认水花 | Godot 或 L1 自行宣布门已打开、桥已建成、对象已损坏、角色已受伤或道路已通 |
| 表现、感知与信息编排层 | Godot 展示后端投影；Character Core 接收角色可知输入；司命按权限排序与表达；UI 标注来源和不确定性 | 无直接写入权；只能消费确认投影 | 玩家亲见、角色听闻、报告与传感器记录可作为后续感知证据 | 动画、音效、镜头、预测残影、UI 过渡、ragdoll、表情 | 将预测显示为确认、泄露敌方私有情报、让司命篡改事实或延迟关键动作回执 |

### 3.1 什么必须成为真相

以下结果如果会影响其他主体后续行动的合法性、可达性、结算或回放，必须经 Owner 确认后进入真相：

- 路、门、桥、城墙、船坞、建筑等的通行能力、承重能力、占用、损坏阶段和可用阶段；
- 人物/物体的确认位置、保管、附着、受伤/失能、死亡、上船/下船与运输完成；
- 火灾、烟雾、洪水、塌方等持续环境状态的阈值跨越、区域扩展、稳定、熄灭或解除；
- 项目 `planned / in_progress / partially_operational / operational / suspended / failed` 及其确认能力；
- 会影响库存、容量、领地、组织义务、军队补给、任务完成或战区结算的空间结果。

### 3.2 什么只作物理证据

接触法线、瞬时冲量、路径探测、局部遮挡、材质采样、构件对位、受力余量、热/烟采样、视觉捕获、听觉定位与原始传感器引用，通常只证明某个候选结果是否可被采纳。它们不自动成为长期世界字段。

### 3.3 什么永远停留在表现层

逐帧位置曲线、骨骼姿态、ragdoll 形态、粒子、碎片、镜头、音量包络、临时脚步、动画进度和预测的门/桥状态不得进入群体或司命的事实输入。低层数据只允许在本地调试回放或受控证据保留中存在。

### 3.4 美术资产是受控空间输入，不是事实 writer

可交互资产应发布版本化 `EmbodimentManifest`，它绑定：

```text
asset_ref / manifest_digest / visual resources
collision and support volumes / nav slices / material and flammability profile
destructible segments / interaction anchors / semantic class
allowed evidence probes / supported project phases
```

内容作者可以改变“该资产作为空间输入是什么”，但不能宣告“该资产已建成、已损坏或可通行”。世界事件只引用经审核的 `asset_ref + manifest_digest + placement anchor + transform`；Godot 据其生成视觉、碰撞、导航和探针。资产版本变化与空间/项目版本不匹配时，证据必须拒绝或重投影。

## 四、统一证据—确认—回流链

### 4.1 标准时序

```text
1. Rn 已提交
   -> 玩家 UI、Character Core、cohort、司命各取授权视图

2. 人类玩家 / Character Core / PopulationPlanner 并发提出候选
   -> 每项固定 read revision、dependency read-set、knowledge basis、causation 与幂等键

3. Owner 预检
   -> 规则、权限、资源 reservation、空间/资产版本、能力与冲突窗口
   -> 返回 grant、拒绝或待核验；grant 不是成功事实

4. Godot 具身执行
   -> 本地动画、碰撞、移动、施工、燃烧、攻击等
   -> 上抛结构化 EmbodiedEvidencePacket；本地预测可见但不可写事实

5. Owner 确认
   -> 证据可信度、交叉来源、版本、领域规则、冲突窗口和幂等校验
   -> 原子 append_batch，产生 OwnerReceipt 和 Rn+1；失败零写入

6. 确认影响传播
   -> 从 Rn+1 派生 ConfirmedImpactSummary
   -> L1/occupancy dirty scope、Godot 投影、角色可见事实、阵营情报、群体失效索引、司命态势输入

7. 事件触发局部微 tick
   -> 立即阻断旧 dependency；只挑选受影响 B2/B1 与相关 B0 摘要
   -> 角色、群体、司命各自在权限范围更新信念，提出新候选

8. 再次 Owner 结算
   -> 接受、拒绝、延迟或 conflict_lost
   -> 写入 Rn+2，并开始下一因果窗口
```

### 4.2 参与者职责

| 参与者 | 提出什么 | 读取什么 | 不得做什么 |
| --- | --- | --- | --- |
| 人类玩家 | 结构化输入与具身行动尝试 | 自己可知事实、观察、报告、动作回执 | 以客户端 payload 宣称世界成功或扩大视野 |
| Character Core | 角色私有行动意图、连续性建议、升级请求 | 角色感知、记忆、授权知识、确认结果 | 直接写空间、库存、项目或阵营事实 |
| B0–B2 群体 | 压力增量、局部行为/工程/运输/避险候选 | 已确认公共或阵营授权摘要 | 把预测或展示种子写成世界结果 |
| 司命 | 微 tick 调度、催化、优先级、受治理 owner-bound candidate、UI 排序建议 | 确认态势、授权情报、聚合压力和 receipt | 读取成员私有内心、直接修改世界或角色记忆 |
| Godot/L1 | 具身过程、采样、锚点、证据、确认投影 | grant、后端 result、批准资产/空间版本 | 成为真实性 owner 或向群体广播未确认画面 |
| 领域 Owner | 规则、版本、冲突、原子结算与 receipt | 准入候选、确认证据、所属领域事实 | 充当跨域万能 router、读取无关私有状态 |

## 五、通用数据合同草案

下列为逻辑合同。后续代码计划必须将其拆到既有窄模块中，不得一次性创建万能 DTO 或万能写入口。

### 5.1 `EmbodiedEvidencePacket`

```text
evidence_id / schema_version
attempt_ref / grant_ref / source_session_ref
actor_ref / source_kind / optional faction_ref / optional domain_ref
target_refs / world_anchor_refs / asset_manifest_digest
expected_revision_vector / observed_tick / capture_root_id / capture_id
observation_kind / normalized_observation_summary / artifact_refs
trust_class: presentation_only | admissible_session | corroborated | server_verified
independence_group_refs / confidence_band / retention_policy
causation_id / correlation_id / idempotency_key / source_ref_lineage
```

规则：`presentation_only` 不能作为世界确认依据；`admissible_session` 只能用于低/中影响结果；高影响、不可逆或跨战区结果必须达到 `corroborated` 或 `server_verified`。同一独立组的重复采样不算交叉证据。

### 5.2 `ConfirmedImpactSummary`

```text
impact_ref / owner_receipt_ref / committed_event_refs
world_revision_vector / effective_sim_tick
affected_anchor_refs / affected_capability_refs / affected_scope_refs
invalidated_dependency_refs / superseded_candidate_refs
reaction_class: ordinary | urgent_local | emergency_domain
public_visibility / faction_visibility / actor_visibility rules
projection_refs / replay_digest / causation_id / correlation_id
```

它只能由已提交 Owner 事实派生；可随投影重建。它不是“第二份世界状态”，也不能脱离 receipt 单独宣布变化。

### 5.3 `CausalCandidateEnvelope`

```text
candidate_id / source_kind: player | character | population | siming_catalyst
actor_ref / cohort_ref? / faction_ref? / contest_domain_ref?
read_world_revision_vector / dependency_read_set
knowledge_basis: confirmed | observed | reported | inferred
belief_refs / requested_effect / required_evidence_class
conflict_window_ref / policy_revision / capability_ref
causation_id / correlation_id / idempotency_key
```

Owner 在任何写入前必须检查 read set；受影响依赖已变更时返回 `stale_world_context`，不得静默按旧事实继续执行。

### 5.4 `SituationBeliefProjection`

```text
belief_ref / scope: actor_private | faction_scoped | siming_scoped
proposition_key / subject_scope / prior_band / posterior_band / direction
evidence_refs / contradicting_refs / confidence_interval_or_band
expiry_or_review_tick / invalidation_conditions / policy_revision
```

事实、信念、假设必须分别标记。LLM 可提出“信念更新建议”或“调查建议”，但不能修改确认事实，也不能抹除来源更强的结构化事实。

### 5.5 通用回执

所有来源共用语义：

```text
accepted                 已确认或已进入受控执行
rejected                 规则、权限、资源或证据不足；零写入
stale_world_context      read set/依赖已变化；必须重算
conflict_lost            冲突窗口中未获胜；引用可见的裁决原因
pending_verification     可继续观察，但未改变长期事实
visibility_restricted    结果存在，但该主体无权知道细节
```

## 六、群体与司命：证据式更新而非全量重算

### 6.1 B0–B3 的输入边界

| 层级 | 读取 | 输出 | 不能读取 |
| --- | --- | --- | --- |
| B3 | 角色私有感知、确认回执、近场空间与授权上下文 | 复杂意图、对话、具身行动 | 敌方私有计划、全局原始物理流 |
| B2 | 确认局部空间、任务、风险、阵营情报摘要 | 局部工程、运输、侦察、救援、战术候选 | ragdoll、粒子、未确认画面 |
| B1 | 确认组织、区域资源、路线能力、压力 | 排班、补给、动员、区域调度候选 | 个人私有记忆与敌方隐秘计划 |
| B0 | 确认的粗粒度能力、人口状态与到期事项 | 连续压力、需求、风险和升级摘要 | 细物理、未确认候选、角色内心 |
| 司命 | 确认态势、授权阵营情报、B0–B2 聚合压力、拒绝/延迟回执 | 催化、预算、微 tick 排序、UI 表达建议 | 未传播私人信念、跨阵营秘密 |

### 6.2 事件触发局部微 tick

`ConfirmedImpactSummary` 进入一个已有 cadence 之上的受限优先队列，不新建 scheduler owner。它只：

1. 查询依赖受影响的候选、任务、reservation、角色与 cohort；
2. 先标记不可落地项，保证旧方案不能在群体来得及重算前写回；
3. 在 mode policy 的固定预算内按 `reaction_class`、生命安全、不可逆风险、玩家邻近度和到期义务选择对象；
4. 调用既有 `SimingRuntime.tick(...)` 和 PopulationPlanner 入口生成新候选；
5. 预算不足时产生 `requeue` 与可见的滞后指标，绝不伪造已反应。

未受影响 B0 对象继续常规 cadence。局部微 tick 只改变调度频率和 read-set，不改变同一事实链、同一规则或 Owner。

## 七、阵营隔离与对抗域

### 7.1 默认与触发条件

世界默认只有 `world:cooperative`。职业、地区、家庭、组织、资产归属、LOD、普通意见分歧、野兽或一次遭遇不得自动创建阵营。

只有玩家或独立 Character Core 经 authority 确认具备持续的独立决策、资源/动员权、目标和需要保护的情报边界时，才建立或加入阵营。阵营关系和参与方变化必须是可回放的组织/关系/授权事实；`FactionContext` 只组合它们。

### 7.2 `FactionContext` 与 `ContestDomain`

```text
FactionContext
  faction_ref / controller_refs / representation refs
  objective refs / resource scope refs / membership and cohort refs
  knowledge scope / belief scope / diplomacy relation refs
  policy revision / active contest domain refs

ContestDomain
  domain_ref / mode policy / participant faction refs
  geographic and object scope / objective refs
  start revision / conflict-window policy / end conditions
  visibility and projection policy
```

它们不拥有成员、库存、领地、伤亡、建筑或战果的直接写入权。所有事实继续由对应 Owner 持有。阵营内可以协作；阵营间可以竞争；双方仍共用一个时间、一个世界 revision、一套空间事实和一组领域 Owner。

### 7.3 信息与 UI 边界

阵营上下文只能包含公共确认事实、己方资源/命令、显式报告、受权指挥链、共享传感器或符合 visibility policy 的观察结果。成员的私有记忆、未报告观察、推理草稿与隐藏关系不能自动上交。

同一个确认战场事实可以投影为不同信息卡：蓝方看到“己方闸门已开启”，红方可能只看到“峡谷道路已阻断”；两者都不能改变“道路是否阻断”的确认事实。司命只为各方已知上下文排序与措辞，不泄露另一方私有计划。

## 八、七个领域案例

| 案例 | 具身证据 | Owner 确认真相 | 群体/角色反应 |
| --- | --- | --- | --- |
| 开门 | 锁、把手、门洞碰撞与授权探针 | 门状态、访问权、门洞通行能力 | 旧路径候选失效/恢复；角色重新寻路 |
| 搬运 | 抓取、附着、载重、容器容量、到达锚点 | 保管、位置、运输阶段、容量占用 | 物流 cohort 更新；旧交接按版本拒绝 |
| 攻击命中/受伤 | 授权攻击、接触、部位/防护摘要、交叉观察 | 伤害/失能/死亡或未命中 | 医疗、撤退、士气、战术候选更新 |
| 登船 | 登乘锚点、容量、附着、船体状态 | 乘员名单、运输关系、航行资格 | 路线、补给和下船计划按船状态重算 |
| 持续火灾 | 热/烟阈值、可燃材质、跨区采样 | 危险等级、区域封锁、设施停用、熄灭 | B2 疏散/救火，B1 资源调度，B0 风险摘要 |
| 塌方/城墙破坏 | 支撑/断裂摘要、碰撞阻断、资产构件版本 | 完整性阶段、通行/遮挡/承重能力变化 | 路线和攻守候选立即失效；清障/修复项目生成 |
| 粮车倾覆与建造修复 | 载荷、倾覆、散落/保管探针；施工对位与承重证据 | 货物状态、道路阻断；项目阶段和可用能力 | 抢救、转运、修桥/清障候选；未验收脚手架不可当正式设施 |

## 九、两个验收样板

### 9.1 协作洪灾：具身变化进入社会反应

人类玩家开启上游闸门，Character Core 同时带领运输/救援。Godot 先呈现闸门、水流、道路积水和桥梁受压；Owner 仅在资产、权限、水位和交叉证据满足后提交道路/桥梁/避难能力变化。

确认后，旧运输候选立即 `stale_world_context`；受影响 B2 处理清障、救援和分流，B1 调整粮食/床位，B0 更新压力摘要；Character Core 只在自己可知范围更新路线和承诺；UI 区分已确认淹没、正在救援和北路是否可走的推测。

### 9.2 双阵营战区：四位高层主体与兵群

蓝、红双方各有一名人类玩家和一名扮演玩家的 Character Core，各自拥有守军/工兵/后勤 cohort。双方争夺同一峡谷、桥梁、城门与补给线。

同阵营的两名高层主体可协作开闸、架桥、运粮、加固或突袭；两阵营的候选进入同一领域冲突窗口。确认战场事实对双方一致，但可见原因、情报、信念、计划和 UI 互相隔离。桥梁、城墙、粮车、伤害和道路的所有结果仍经同一空间、设施、库存、战斗或组织 Owner 写入。

## 十、实施分期、验证与风险

### 10.1 分期

1. **后继合同门禁**：完成本规格的 owner/operation conflict matrix；逐项证明新字段归入既有 RawFact、world result、candidate、projection 或 receipt，而非新 store。
2. **具身证据与影响摘要**：为一个低/中影响交互和一个高影响环境变化建立证据分级、确认、outbox、replay 与 Godot 回流。
3. **依赖失效与局部微 tick**：为候选读集、影响索引、`stale_world_context` 和有界 requeue 建立 deterministic replay。
4. **信念与 UI 投影**：接通角色私有、阵营 scoped、司命 scoped 的派生信念；验证 UI 只排序/表达。
5. **阵营与对抗域**：以既有组织/关系/资源事实组合 FactionContext，验证私有情报隔离和共享 Owner 仲裁。
6. **样板闭环**：先协作洪灾，后四高层主体战区；每个样板必须有成功、拒绝、过期、冲突、断线重投影与 replay 用例。

### 10.2 验收标准

- 不新增 runtime、事实库、clock、event bus、万能 router 或 truth owner；
- 同一事实前缀、规则版本、冲突窗口和证据包重演得到相同 receipt、impact、失效集合和投影摘要；
- 过期候选不能写入；重复证据不重复写入；不同证据载荷复用幂等键必须拒绝；
- 单一客户端画面不能作为高影响结果的唯一确认依据；
- 群体、司命、敌方 UI 与 B0 永不消费未确认的低层表现；
- 阵营私有计划和未报告观察不泄露；
- 四主体并发改变同一战区时，领域规则窗口裁决确定，失败理由可审计；
- Godot 结论必须有真实运行时证据：后端在运行、真实边界消息、场景中可见的确认/拒绝效果。缺 Godot 时只能报告静态或后端验证。

### 10.3 主要风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 本地表现抢跑造成群体幻觉 | 未确认状态不得发布 impact；Owner 先阻断旧候选再允许局部重推 |
| 证据合同变成万能物理系统 | 只采纳领域需要的归一化摘要；资产/协议逐项声明允许的证据 |
| 微 tick 变成全局重算 | 以 impact scope、预算和 requeue 限制；B0 只消费摘要 |
| 阵营变成第二套世界 | 阵营仅隔离上下文；世界、空间、时钟、EventStore 和 Owner 永远单一 |
| 司命成为作弊裁判 | 司命只能读授权态势、产出催化/排序；双方真相均由 Owner 确认 |
| UI 把建议变成事实 | 信息卡强制来源与状态标签；关键回执由确定性投影直接交付 |
| 9 月 16 日基线被提前打断 | 实施门禁要求完整阶段证据；本设计在此前仅供评审 |

## 十二、最终原则

> 具身层参与世界真相生产的方式，不是成为真相 owner，而是提供带版本、因果、可信等级和可复核来源的证据；只有 Owner 确认的结果才改变世界。确认结果立刻使旧推演失效，并以受限局部微 tick 让角色、群体、司命与 UI 各自在自己的知识边界内更新。阵营只隔离高层对抗主体的目标、资源和情报，绝不隔离或复制世界真相本身。
