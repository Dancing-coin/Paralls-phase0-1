# Siming-Led Population Simulation Design

Status: `proposed; design artifact only; no runtime authorization`

Date: `2026-08-29`

This document defines how the project implements population simulation with
Siming as the governing subject. It narrows the implementation direction; it
does not create a second runtime, clock, scheduler, event store, truth owner,
or generic writer.

The governing continuity contract is
[Character Simulation Memory Seed And Continuity Design](2026-08-22-character-simulation-memory-seed-continuity-design.md).
The Chinese rationale and external-reference analysis are in
`docs/8月分析/司命与群体世界补充设计/`.

## 1. Decision Summary

Siming is the population simulation's governance and intent subject:

- it decides what world pressure or story objective the next batch addresses;
- it authorizes scope, cadence, policy, selector and budget;
- it invokes the internal `PopulationPlanner`;
- it reviews reports and candidates;
- it decides `no-op`, `requeue`, activation priority or governed submission;
- it turns approved simulation outcomes into character simulation seeds;
- it receives owner receipts and drives the next projection cycle.

Siming is not the batch calculator, the world truth owner, the character memory
store or the low-level action controller.

The population simulation is therefore a Siming-owned capability domain, not a
peer authority:

```text
Siming authority
  -> authorized cadence and scoped read-set
  -> internal PopulationPlanner
  -> BatchReport and candidates
  -> Siming policy, feasibility and capability admission
  -> owner-bound intent / CharacterContinuityCommand
  -> domain owner or Character Core receipt
  -> scoped projection and CharacterSimulationSeed projection
```

The game starts with population simulation available. This means that the
existing world-mode, activation and schedule projections provide the first
structured cadence input after session start. It does not mean that Siming
starts an unbounded background thread or that every actor runs a full LLM loop.

## 2. Ownership and Terminology

| Term | Canonical meaning | Does not mean |
| --- | --- | --- |
| Siming | global policy, admission, narrative governance and governed submission | world truth owner or per-frame controller |
| Population Simulation | Siming's controlled capability for advancing offline world/actor continuity | second world, second truth source or peer authority |
| `PopulationPlanner` | pure cohort and batch calculator invoked by Siming | independent executor or writer |
| `CharacterSimulationSeed` | revisioned, provenance-bearing continuity input for one actor | prompt text, five-pool record or second actor |
| Agent activation | high-fidelity local cognition for the same `CharacterRecord` | transfer of world authority |
| Owner receipt | proof that a domain owner settled an intent | proof that every actor knows or remembers it |

The word `control` has two meanings and they must remain separate:

1. Siming controls the simulation policy, batch selection, seed content and
   activation priority.
2. An active character agent controls its local interpretation and high-level
   intent within the received seed, private evidence, capability and scene
   constraints.

## 3. Runtime Shape

`SimingRuntime.tick(...)` remains the only Siming decision and dispatch path.
The population capability is an internal deep module behind that interface.
It must not become a new external runtime.

```text
existing world runtime
  -> population_cadence_input
  -> SimingRuntime.tick(...)
       -> public observation
       -> immutable PopulationReadSet
       -> population capability authorization
       -> PopulationPlanner.plan(...)
       -> report/candidate review
       -> governed execution or no-op/requeue
       -> owner receipt / continuity receipt
       -> bounded audit and read model
```

The internal seam is intentionally narrow:

```text
PopulationSimulationCapability.run_cycle(
    cadence_input,
    scoped_read_set,
) -> PopulationCycleResult
```

The caller must not supply an arbitrary destination stream or event family.
The result contains candidates and receipts, not an assertion that the world
has changed.

The existing `GroupSimulationBridgePort` read summary can remain a read-model
surface. It must not be mistaken for the production population executor. The
current default `StubGroupSimulationBridge` therefore remains a truthful
unavailable adapter until the formal vertical below is implemented.

## 4. Game-Start and Cadence Flow

At session start, the existing world runtime publishes or hands off a
structured cadence projection. The cadence is an input owned by the world
runtime; it is not generated by Siming, Godot or a wall-clock loop inside the
planner.

```text
session started
  -> world-mode projection is active
  -> cadence window is admitted
  -> Siming receives population_cadence_input
  -> Siming freezes the read-set and starts one batch
```

Each batch pins:

```text
world_mode_ref / world_mode_revision
cadence_source_ref / cadence_source_revision
window_start / window_end
base_checkpoint_ref / base_revision_vector
source_revision_vector
policy_revision / selector_revision / ruleset_revision
deterministic_seed
catch_up_limit / budget
report_scope
```

Missing, revoked, stale or scope-incompatible cadence input produces an
auditable `no-op` or `requeue` with zero production write.

## 5. Population Behavior Contract

Population behavior uses a closed action taxonomy and registered owner
behavior rows. The first production row is:

```text
schedule_gated_supply
  -> OrganizationAuthority
  -> owner settlement
  -> owner receipt
```

Every calculated outcome is classified before it leaves the planner:

```text
presentation_seed
  -> rebuildable behavior/presentation input; no world write

activation_candidate
  -> changes actor activation priority; no actor memory write

owner_bound_intent
  -> static capability admission and domain-owner settlement
```

Routine movement, waiting, work and similar behavior can remain
`presentation_seed` until a registered owner contract exists. Inventory,
production, employment, contracts, relationships or other objective changes
must be `owner_bound_intent` and must identify a statically admitted capability
through the catalog. A candidate is never a fact.

When the story requires a behavior not yet registered, the behavior follows a
governed innovation path:

```text
story/world pressure
  -> behavior type proposal
  -> closed schema and precondition review
  -> target owner and event family mapping
  -> privacy/replay/idempotency review
  -> signed catalog revision
  -> next population batch may use the behavior
```

The new behavior cannot execute in the same tick that invents it. Until its
revision is admitted, it is limited to `branch`, `preview`, `report` or
`requeue`. If the behavior conflicts with current world truth, expected
revision, permissions or owner rules, the entire intent is rejected with zero
production write; no partial settlement or owner switching is allowed.

## 6. Seed-Centered Character Control

The main control channel from population simulation to characters is the
`CharacterSimulationSeed`, not a low-level action and not `siming_output`.

The seed flow is:

```text
PopulationPlanner
  -> seed candidate for actor
  -> Siming policy/provenance/scope review
  -> owner-bound world intent when an objective effect exists
  -> owner receipt
  -> CharacterContinuityCommand
  -> Character Core validation and settlement
  -> SeedDelta and continuity checkpoint
  -> character_simulation_seed_projection
  -> CharacterAgentRuntime.ingest_seed_projection(...)
```

The seed is a closed, revisioned logical contract. Its fields are governed by
the mother spec and include:

```text
actor_ref / world_ref
from_tick / to_tick
base_checkpoint_ref / base_revision_vector
source_event_refs / source_owner_receipt_refs
ruleset_revision / selector_revision / deterministic_seed
state_deltas
memory_candidates
drift_candidates
activation_hints
presentation_seed
visibility_scope / privacy_disposition
cursor_vector / apply_status / idempotency_key
```

The seed is parsed into three different kinds of actor input:

| Seed content | Character effect | Direct five-pool append |
| --- | --- | --- |
| `state_deltas` | task, pressure, fatigue and continuity state | no |
| `presentation_seed` | remote/prewarm behavior continuity | no |
| `activation_hints` | priority for prewarm/active | no |
| `memory_candidates` | possible subjective experience | no; Character Core decides at materialization |
| `drift_candidates` | possible long-term tendency change | no; existing promotion gate required |

Character Core performs revision, exposure, privacy, temporal, deduplication
and idempotency validation. Only Character Core may append `SeedDelta`, update
actor continuity state or materialize a candidate into one of the five memory
pools.

The seed is never injected as raw text into an LLM prompt. The character
runtime turns it into a scoped private snapshot and mind frame:

```text
seed projection
  -> exposure/privacy filter
  -> CharacterPrivateWorldSnapshot
  -> CharacterMindFrame
  -> L2 interpretation and needs/affect
  -> L3 intent selection
  -> L4 structured execution plan
```

`siming_output` remains a high-level catalyst/presentation message. It must
not carry private continuity data or impersonate a Character Core seed.

## 7. Agent Activation and Takeover

The same `CharacterRecord` moves through fidelity states:

```text
dormant
  -> batch_planned
  -> seeded
  -> prewarm
  -> active
  -> pending_merge
  -> dormant / requeue
```

Player interaction changes the fidelity state, not the owner of world truth:

```text
player_nearby
  -> prewarm

player_focus / structured interaction
  -> activation candidate

dialogue / conflict / consequential action
  -> activation lock
  -> active CharacterAgentRuntime
```

“Agent activation” means that CharacterAgentRuntime temporarily owns the
actor's local high-fidelity cognition:

- interpreting the current private perceptual frame;
- retrieving allowed memory cards;
- updating needs, affect, belief and social interpretation;
- selecting a high-level response or goal;
- producing dialogue and a structured execution plan.

It does not mean that the agent can:

- append world facts;
- directly write five-pool memory;
- override Siming guardrails or domain constraints;
- control Godot's low-level motor outside the existing execution ingress.

After interaction, the result follows the existing settlement/writeback path:

```text
character intent
  -> domain owner or ESM settlement
  -> world result / owner receipt
  -> Character Core continuity writeback
  -> next simulation seed
```

## 8. First Production Vertical

The first vertical is `schedule_gated_supply` in the bakery district. It proves
the subject relationship without claiming a general population engine:

```text
game start
  -> Siming receives cadence
  -> planner reads organization/household/social projections
  -> planner computes supply candidate and actor seed candidate
  -> Siming admits the fixed Organization capability
  -> OrganizationAuthority settles or rejects the supply intent
  -> owner receipt returns
  -> Character Core accepts continuity command
  -> affected actor receives state/behavior/memory candidates
  -> player approaches and activates the same actor
  -> CharacterAgentRuntime consumes the parsed seed
  -> character produces a local structured intent
```

The supply candidate is not committed if the organization schedule, inventory,
expected revision, privacy scope or capability admission is invalid. The actor
seed does not become a memory merely because the owner settled the supply; the
actor still needs the applicable participation, observation, disclosure or
consequence evidence.

## 9. Proposed Module Mapping

This mapping keeps the implementation local to existing owners:

| Proposed responsibility | Existing seam or target location |
| --- | --- |
| population cadence input | existing world-mode/activation/schedule projection |
| Siming decision path | `backend/app/services/siming_runtime.py` |
| pure batch calculation | `backend/app/population_continuity/batch.py` |
| population contracts | `backend/app/population_continuity/models.py` |
| owner settlement | existing `GameplayCommandEnvelope`, `SettlementPlan`, `GameplayEventStore` and domain authorities |
| activation lock/pending/requeue | `backend/app/population_continuity/activation.py` |
| actor seed parsing | Character Core continuity owner and existing character-agent runtime ingress |
| actor private context | existing CharacterAgent L1-L4 and memory projectors |
| frontend presentation | existing `character_agent_execution`, `world_result` and `siming_output` projection paths |

No Godot seed writer, generic population writer, second event store or
independent population scheduler is part of this design.

## 10. Failure and Replay Rules

The following outcomes are first-class results:

| Condition | Required result |
| --- | --- |
| missing/stale cadence | `no-op` or `requeue`, zero production write |
| stale source or target revision | `stale_read_set`, discard/requeue batch |
| unknown action/capability | `capability_not_admitted`, zero production write |
| owner business rejection | owner receipt/refusal, auditable requeue policy |
| missing actor exposure | memory materialization denied, no pool write |
| private or branch-only source | privacy/branch denial, no production write |
| duplicate seed or command | idempotent replay, no duplicate state or memory |
| Character Core conflict | continuity receipt with no partial actor write |
| LLM schema/policy failure | untrusted proposal discarded, structured candidate retained |

Each accepted batch and seed must preserve source refs, source revision vector,
policy/ruleset/selector revisions, deterministic seed, scope digest, result
digest, receipts and cursor movement. Full replay and checkpoint-tail replay
must produce equivalent projections. A failed memory materialization cannot
advance the memory cursor while state and experience cursors may advance only
according to their own receipts.

## 11. Verification Gate

Before runtime authorization, a focused implementation plan and Harness profile
must prove:

1. game-start cadence creates a bounded population input without a new clock;
2. `SimingRuntime.tick()` remains the sole decision/dispatch path;
3. `PopulationPlanner` has no independent append or owner-selection authority;
4. a registered owner behavior reaches the exact domain Owner and receipt path;
5. an unregistered behavior cannot execute in the same tick that proposes it;
6. an invalid or stale behavior produces zero production write;
7. an owner receipt is required before an objective world effect advances;
8. Character Core, not Siming or the planner, admits the continuity command;
9. seed parsing produces actor-local structured context, not raw prompt injection;
10. actor activation changes only local cognition fidelity and preserves identity;
11. player proximity/focus/interaction follow prewarm -> activation policy;
12. active character output remains a proposal until the existing settlement path;
13. exposure and privacy prevent global Siming knowledge becoming actor memory;
14. state, experience and memory cursor rules remain separate;
15. duplicate, stale, branch-only and rejected outcomes are replayable and audited;
16. `schedule_gated_supply` closes the planner -> Siming -> Organization Owner
    -> Character Core -> activation handoff vertical.

Suggested Harness profile:

```text
siming-led-population-seed-continuity
```

## 12. Non-Goals

- no per-actor, per-tick full LLM population loop;
- no generic population truth owner;
- no second runtime, scheduler, clock or event store;
- no direct Siming access to actor-private five-pool memory;
- no direct PopulationPlanner write to world facts, runtime state or memory;
- no automatic authored-dossier overwrite;
- no branch result promotion without owner/capability and Character Core gates;
- no claim of complete civilization or large-scale population simulation from
  the first vertical.
