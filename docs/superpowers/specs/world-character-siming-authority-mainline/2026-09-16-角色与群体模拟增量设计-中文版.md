## 一、先用白话说清楚

我们要做的不是“给世界增加一个人口系统”，也不是“让所有 NPC 永远运行大模型”。我们要做的是让同一个 NPC 可以在不同成本的推进方式之间自然切换：远处时用很便宜的统计或脚本推进，玩家靠近或剧情命中时，再把这个 NPC 展开成一个有连续记忆、关系和行动能力的角色。

这个 NPC 在任何模式下都应该还是同一个人。

```text
远处、普通、低风险
    -> B0 群体压缩，或 B1 简易脚本

玩家附近、局部事件
    -> B2 增强简易模型

对话、谈判、剧情冲突、长期计划
    -> B3 角色智能体
```

切换的是“怎么推进”，不是“换一个 NPC”。

群体模拟也不是一个有独立意志的社会。村庄、组织、商店、政府、市场和经济都不应该像角色一样自己产生愿望。真正提出愿望的是角色；组织和制度负责按照章程、权限、合同和法律检查这些愿望；通用事实底座负责记账；表现层负责展示已经确认的结果。

```text
角色产生动机与行动意图
    -> 预编译社会协议检查条件
    -> 通用事实底座原子结算
    -> 事件、回执、投影
    -> 角色、群体和表现层获得结果
```

司命的作用是治理和调度：决定什么时候适合群体化，挑出哪些人需要特殊安排，施加哪些高层情境催化，以及在规则不足或叙事交集出现时要求展开。司命不是人口真相 owner，也不是每个 NPC 的逐帧控制器。

## 二、为什么要这样设计

### 2.1 我们真正要解决的问题

前面的讨论暴露出几个容易混淆的问题：

1. 群体模拟、角色智能体、世界真相和表现层容易各自保存一份状态，最终出现“同一个 NPC 有几种版本”。
2. 组织、库存、经济、政府被叫作 owner，但它们的层级不同：库存可能接近原子事实，经济却包含账本、交易、金融、宏观投影多个层次。
3. 玩法包如果只能写一套专用 NPC 类，就无法覆盖不同游戏；如果所有逻辑都塞给司命，司命上下文会被大量可预计算细节占满。
4. 简易 NPC 与角色智能体如果各自使用不同数据，就无法丝滑切换：脚本 NPC 不知道自己的过去，角色智能体也接不上脚本留下的行为和承诺。
5. B0 如果只保存一个群体总数，角色离开群体时无法解释“这个人这段时间发生了什么”。
6. 密码本如果只是角色或司命专用工具，就会继续产生许多重复的上下文查询系统。

### 2.2 设计目标

本设计同时追求以下目标：

```text
角色有持续身份，不因精度切换而换人
群体计算足够便宜，可以长时间推进
重要角色可以由玩法包预设进入、停留和退出规则
没有预设的特殊情况可以交给司命判断
简易模型覆盖心智和行为，而不只是情绪数值
角色智能体可以直接复用简易模型的状态和模块
组织、库存、经济和政府由角色与制度驱动，不产生独立人格
INF 逐步发展成通用分层系统，而不是不断增加窄域 owner
能预填和确定性计算的内容移出司命常驻上下文
群体、角色、司命和领域事实始终可以回放、审计和恢复
```

### 2.3 非目标

本设计不授权：

- 新建 Population Truth Owner、Situation Truth Owner 或文明真相库；
- 为群体模拟增加第二套 runtime、clock、scheduler、event store 或 event bus；
- 让组织、政府、经济或市场获得像角色一样的独立意志；
- 让群体模拟直接写库存、账户、法律、组织职位、剧情事实或角色私有记忆；
- 让每个 NPC 永远运行完整 LLM；
- 用一条新的通用 router 或万能 settlement coordinator 代替现有能力目录、协议和 owner receipt；
- 现在就宣称 INF-4 或 P6/P7 完整群体／文明模拟已经完成。

## 三、总架构：四种推进方式，一套角色状态

### 3.1 四个精度层

| 层级 | 白话名称 | 主要用途 | 典型输出 |
| --- | --- | --- | --- |
| B0 | 群体压缩 | 战争、灾害、迁徙、远处日常等共同压力 | 群体趋势、可分摊增量、升级候选 |
| B1 | 简易心智与行为 | 普通 NPC 的日常生活 | 日常行动候选、状态增量 |
| B2 | 增强简易模型 | 玩家附近、局部环境、短互动 | 具体局部意图、升级信号 |
| B3 | 角色智能体 | 对话、谈判、复杂冲突、长期计划 | 结构化行动意图、复杂计划 |

B0 不等于“没有角色”，B3 也不等于“获得世界写权限”。四层都使用同一个角色身份和连续性；四层提出的结果都要经过相同的事实结算边界。

### 3.2 统一推进链

```text
Character Core / 已确认领域投影
    -> CharacterSimulationFrame
    -> B0/B1/B2 模块，或 B3 角色智能体
    -> ModuleProposal / ActionIntent / CharacterContinuityCommand
    -> 已登记 capability 与预编译协议
    -> 原子事实 owner + GameplayEventStore.append_batch()
    -> OwnerReceipt / CharacterContinuityReceipt
    -> projection / replay / codebook 摘要
    -> 角色、群体、司命和 Godot 表现层
```

其中：

- `Character Core` 负责角色连续性，不负责替角色完成交易；
- Siming 负责人口模拟的治理、筛选、预算和催化，不负责逐人记账；
- `PopulationPlanner` 负责纯计算，不直接写事实；
- `ActionIntent` 是提议，不是事实；
- 领域协议和事实底座决定行动是否真的成功；
- Godot 只拥有本地具身、输入和表现，不拥有世界真相。

## 四、INF 的最终层级：不是窄域堆，也不是超级 owner

用户特别指出：INF 还没有完成，最终状态应是通用系统；当前窄域 owner 的层次参差不齐。这个判断是本设计的基础。

### 4.1 第一层：原子事实

只有这一层拥有某类事实的最终记账权：

```text
角色连续性
资源、物品、容器、保管和容量
账户、余额、冻结、债务和账本
所有权、成员关系、职位和授权
承诺、合同、义务和履约状态
法律、章程、许可和程序规则
位置、占用、道路、设施和环境
事件、outbox、projection 和 replay
```

原子事实 owner 的问题是“某个事实现在是什么”，不是“社会应该想做什么”。

例如：

- Inventory 记录粮食由谁保管，不自动决定谁应该买粮；
- Ledger 记录账户冻结了多少钱，不自动决定角色是否要付款；
- Organization 记录谁是成员、谁有代表权，不自动产生组织目标；
- Character Core 记录老王的照护压力，不自动替他完成避难；
- Environment 记录水位和道路状态，不自动把老王送进避难所。

### 4.2 第二层：通用原子操作

原子事实 owner 提供少量稳定操作：

```text
资源：reserve / transfer / consume / produce
账本：hold / post / obligate / clear
关系：relate / assign / grant / revoke
承诺：propose / approve / fulfill / breach
规则：evaluate / authorize / reject / expire
空间：move / occupy / release / restrict
连续性：apply_delta / advance_cursor / materialize
```

这些操作不应该知道“农民”“商会”“政府救灾”等具体社会语义。

### 4.3 第三层：预编译社会协议

复杂社会行为由多个原子操作组合而成。协议不是一个新真相 owner，而是一个有版本、来源、权限和回执的流程定义。

协议至少声明：

```text
参与方
输入事实和来源版本
适用规则与权限
原子操作顺序
成功事件和失败事件
补偿、重试或延期方式
隐私范围
幂等键和回执格式
```

典型协议包括：

```text
交易、雇佣、租赁、贷款、保险
征税、配给、避难申请、组织表决
公共项目、军队补给、物资运输
```

角色只提出意图，协议才把意图转换成一组受控原子操作。

### 4.4 第四层：社会模型

经济、组织、政府、家庭、军队、市场和灾害是高层社会模型。它们把角色行为、协议、制度和投影组合成玩法可理解的社会语义。

```text
经济 = 账本事实 + 交易/雇佣/金融协议 + 市场投影
组织 = 成员关系 + 职位授权 + 决策程序 + 资源引用
政府 = 组织模型 + 公共授权 + 法律程序
家庭 = 关系事实 + 承诺 + 照护协议 + 私有投影
军队 = 成员/编制 + 命令授权 + 后勤协议 + 战况投影
```

这些模型不能被解释成有自己的心智。所谓“组织决定”，必须能追溯到成员、代表、表决程序或已经生效的机械规则。

### 4.5 第五层：派生投影

以下内容通常是从已确认事件计算出来的观察值：

```text
价格、供需、就业、通胀、短缺风险
组织压力、公共服务压力、社会声望
灾害风险、区域粮食风险、迁移趋势
```

投影可以进入角色模拟帧，影响角色下一步行动，但不能直接反向改写事实。

### 4.6 经济为什么必须多层

经济尤其不能被当成一个 owner。它至少有：

```text
L0：资源保管、账户余额、冻结额、债务和权利
L1：付款、转移、预留、报价、订单、雇佣、履约
L2：市场撮合、工资周期、信贷、保险、税务、破产
L3：农业经济、战争经济、城镇经济、灾害配给等社会模型
L4：价格、供需、就业、流动性、短缺和宏观风险投影
```

当前 `EconomyPlatformAuthority`、`EconomyMarketAuthority`、`EconomyFinancialPlatformAuthority`、`EconomyMacroPlatformAuthority` 等已经表现出这些层次；旧 facade 和历史垂直入口仍然混合多个层级，因此后续工作的重点是标记层次和收束调用面，而不是继续把所有功能塞进一个“经济 owner”。

## 五、角色到底是什么：原型、档案、连续状态、模块和智能体

一个 NPC 不应由一段巨大的 JSON 或一个大模型 prompt 定义。角色由五种互补数据组成。

### 5.1 角色原型默认值

玩法包定义一类角色的常态：

```text
普通农民
默认身份：农民、村民、家庭成员
默认需求：饥饿、休息、安全、收入
默认日程：耕作、吃饭、采购、回家
默认供给：粮食生产、劳务
默认情绪：疲劳、恐惧、满足
默认推进：B1
```

原型是可复用的预设，不是角色的完整个人经历。

### 5.2 单个角色档案覆盖

档案说明“这个角色与原型哪里不同”：

```text
老王有病妻
老王持有祖传种子
老王与玩家有旧识
老王默认不能接受家庭分离
老王洪灾时需要优先处理家庭共同安全
```

档案覆盖默认只能收紧或细化原型。若玩法包要放宽原型限制，必须显式写出理由、版本和迁移方式，不能因为字段缺失而默认放宽。

### 5.3 Character Core 连续状态

Character Core 保存角色在运行中的变化：

```text
需求强度
疲劳、情绪和压力摘要
日程阶段
承诺和未决事项
模块运行状态
模拟 tick 游标
来源版本向量
角色连续性 revision
```

完整私有记忆、推理草稿和隐私内容不直接进入群体共享热状态。

### 5.4 简易模型模块

模块把心智和行为放在一起：

```text
身份：我是谁
需求：我现在缺什么
日程：我通常什么时候做什么
家庭：我对谁负有什么责任
供给：我能生产、提供或交换什么
情境：环境变化怎样影响我
情绪：压力和体验怎样改变优先级
行为：在脚本条件下提出什么行动
```

### 5.5 角色智能体

角色智能体不是另一种 NPC，也不是模块的替代物。它读取同一份身份、模块状态、承诺、情境和已确认事实，在需要语言、记忆、长期计划或复杂权衡时增加更细的判断。

它仍然只能提出 `ActionIntent` 或连续性建议，不能跳过事实协议。

## 六、参与策略：角色什么时候进入群体模拟

### 6.1 不是一个布尔开关

角色参与策略不是 `in_population = true/false`，而是一份“这个角色在哪些情况下允许被怎样推进”的合同。

```text
角色原型默认
    + 单个角色档案覆盖
    + 当前情境预设
    + 当前承诺、锁和已确认状态
    = ParticipationResolution
```

`ParticipationResolution` 至少包含：

```text
允许的精度层
本轮推荐精度层
允许运行的模块和维度
禁止被群体化的维度
必须升级的触发条件
是否可进入/退出 B0
最大 B0 持续时间和复核时间
策略版本
```

### 6.2 情境预设

玩法包可以预设“战争、洪灾、迁徙、瘟疫、军队行军”等特殊情境：

```text
适用成员条件
群体形成规则
允许聚合的字段
禁止聚合的字段
强制展开条件
进入与退出条件
最大持续时间
复核频率
```

情境预设只改变当前窗口内的允许范围，不覆盖角色的原始身份和连续性。

### 6.3 没有预设时司命怎么做

如果重要角色没有预设，程序不直接猜，也不默认把它送入 B0。它把以下摘要交给司命：

```text
角色是否满足群体基本条件
可被压缩的维度
保护维度
风险和剧情压力
建议的进入/退出窗口
需要展开的密码本引用
```

司命可以决定“是否暂时参与、什么时候展开、是否把角色变成剧情交点”，但不能越过档案中的硬禁止，也不能直接写角色内心或社会事实。

### 6.4 司命和角色智能体必须同时消费

两者读取同一份 `ParticipationResolution`：

| 消费者 | 能提出的意见 |
| --- | --- |
| 司命 | 是否进入群体、挑出谁、何时展开、施加什么催化 |
| 角色智能体 | 哪些承诺不能被压缩、是否请求升级、能否接受降级 |
| 简易模型 | 哪些模块能运行、哪些行为需要升级 |
| 程序 | 计算硬边界、锁定唯一推进器、执行交接 |

这不是两方投票。程序先计算硬边界；任一方提出硬限制时取更严格结果；最终由 activation/handoff lock 确保同一角色同一时刻只有一个推进器。

### 6.5 示例

```text
司命：洪灾下老王可以暂时进入灾民群体
角色智能体：病妻照护承诺禁止自动家庭分离
程序：允许老王接收疲劳、道路风险和食物压力；
      禁止自动转移、家庭分离和关键物品处理；
      玩家接触或病情恶化时立即升 B2/B3
```

## 七、共享数据介质：同一张角色模拟帧

### 7.1 为什么要统一数据介质

如果 B0、B1、B2、B3 各自有不同的数据格式，切换时必然要做“翻译”：脚本模型不知道智能体的上下文，智能体不知道群体期间发生的状态，司命也无法判断双方是否基于同一版本。

因此，所有推进器都围绕同一个只读 `CharacterSimulationFrame` 工作。

### 7.2 角色模拟帧的字段区

```text
A. 身份与原型
   actor_ref、archetype_ref、profile_revision、身份标签、模块绑定

B. 角色连续性
   needs_summary、affect_summary、schedule_state、commitment_refs、cursor、revision

C. 模块状态
   module_ref、definition_version、state_values、state_revision、last_delta_ref

D. 领域事实引用
   fact_ref、fact_kind、owner_ref、source_revision、visibility_scope、digest

E. 当前情境
   world_ref、situation_ref、天气、危险、道路、时间窗口、玩家距离

F. 参与策略结果
   allowed_tiers、forbidden_dimensions、upgrade_triggers、B0 期限和策略版本

G. 密码本引用
   code_ref、safe_summary、source_revision、可展开等级、过期时间

H. 一致性字段
   source_revision_vector、cursor_vector、lock_ref、owner_receipt_refs、frame_digest
```

共享帧是工作输入，不是新的真相库。完整记忆、秘密、模型推理草稿和不应公开的社会资料只通过受控引用按需展开。

### 7.3 三种交换对象

```text
CharacterSimulationFrame：当前只读输入
ModuleProposal：模块提出的状态、行动、升级建议
SimulationCommitPacket：准备提交的意图、预期版本、幂等键和来源摘要
```

任何交换对象都不能直接声明“世界已经发生变化”。

---

## 八、简易心智与行为模块

### 8.1 模块的职责

一个模块应回答：

```text
我读到什么条件？
这些条件怎样影响角色？
我能提出什么日常行为？
什么情况需要更高精度？
哪些字段允许进入 B0？
```

例如 `agriculture.work` 模块可以：

```text
读取季节、天气、体力、工具、土地授权和日程
产生工作压力、进度和收入预期
提出耕作、收获、搬运、出售候选
在 B0 只输出劳作压力或产出候选
在 B1/B2 提出具体工作意图
遇到玩家、工具冲突或长期计划时请求升级
```

它不能直接调用库存写入，也不能直接宣布“粮食已经卖出”。

### 8.2 模块合同

玩法包模块定义至少声明：

```text
module_ref / definition_version
category
input_selectors
state_schema
supported_tiers
proposal_kinds
aggregation_policy
distribution_policy
capability/protocol refs
upgrade_triggers
codebook refs
```

角色原型绑定模块，角色档案覆盖模块参数，Character Core 保存模块状态，由既有角色连续性和调度链路生成模块建议。

### 8.3 字段聚合策略

每个模块字段必须明确：

```text
aggregatable：允许统计
distributable：允许按确定性规则回填个人
individual_only：不可进入群体平均
group_summary_only：只保留群体背景摘要
```

未声明时默认 `individual_only`。秘密、关键关系、重要物品、个人合同、玩家关系和家庭承诺通常属于个人专有维度。

### 8.4 模块建议的合并

多个模块的建议先经过硬约束，再进行偏好排序：

```text
法律与安全
  -> 已有承诺
  -> 生存与健康
  -> 家庭责任
  -> 组织职责
  -> 工作和生产
  -> 习惯与偏好
```

不同字段使用不同合并方式：

| 类型 | 处理方式 |
| --- | --- |
| 疲劳、压力 | 相加并封顶 |
| 当前主要目标 | 按优先级选择 |
| 风险标签 | 合并去重 |
| 去工作/去避难 | 互斥选择 |
| 已经买到药 | 必须等待事实确认 |
| 私人记忆 | 只保留候选或引用 |

如果脚本无法合理裁决，输出 `decision_conflict` 和 `required_fidelity = B3`，而不是随机选一个结果。

### 8.5 B0-B3 复用同一模块

```text
B0：只执行可聚合、可分摊的摘要规则
B1：批量运行脚本，选择普通日常行为
B2：加入局部空间、玩家距离和短事件
B3：读取同一模块建议、硬约束和状态，增加语言、记忆和长期计划
```

因此 B3 接手老王时不会从空白 prompt 开始，而是接手“农民身份、照护病妻、洪灾压力、保留种子、与玩家有旧识”等已有模块状态。

## 九、B0 成员账本：临时压缩但不丢人

### 9.1 为什么不能只记一个人数

“村里有 183 名灾民”无法回答：老王为什么疲劳增加？为什么他不能自动撤离？为什么玩家靠近时能找到同一个人？

因此 B0 需要轻量成员账本，但它不是人口真相库。

### 9.2 群体头信息

```text
群体 ID 和类型
成员来源查询及版本
情境和规则版本
聚合/分摊算法版本
确定性种子
当前 tick 和 checkpoint
群体生命周期
```

### 9.3 成员条目

```text
actor_ref
入组时 Character Core revision
ParticipationResolution 摘要和版本
可聚合字段
不可聚合字段引用
群体分片
最后消费的结果游标
active / handoff / excluded / exited 状态
```

完整档案、私有记忆和领域真相仍留在原 owner；成员账本只保存定位、保护边界和回放所需索引。

### 9.4 群体 tick 凭据

```text
输入来源版本
群体统计摘要
分片规则和确定性种子
成员游标变化
owner receipts
Character Core receipts
规则、选择器和投影 digest
```

同样的输入、版本和种子，完整重放和 checkpoint+tail 重放必须得到同样结果。

### 9.5 先统计，再分片，再回填

例如洪灾群体计算：

```text
整体疲劳 +12
食物压力上升
37 人适合撤离
```

程序再按距离、身体状况、照护责任、玩家交互和当前承诺分片：

```text
远距离/体弱成员：疲劳增量更大
普通成员：中等增量
已被玩家接触者：排除自动迁移
照护病人的成员：只接收环境压力，不接收家庭分离结果
```

“37 人适合撤离”只是候选，不代表床位、车辆、药品和接收事实已经发生。

### 9.6 进入和退出

入组：

```text
解析原型、档案、情境和当前承诺
-> 形成 ParticipationResolution
-> 记录入组锚点和保护字段
-> 开始 B0
```

退出：

```text
最后确认的个人状态
  + 允许回填的群体结果
  + 已确认的 owner 结果
  + 未消费游标
  + 个人保护字段
  = 下一推进器起点
```

群体结束不是清空成员历史。未解决成员必须继续由 B1/B2/B3 推进、进入另一个合法群体，或由司命特殊安排。

## 十、群体模拟与角色智能体怎样通信和对齐

### 10.1 不直接聊天，不复制状态

两者不应通过自由自然语言互相同步，也不应各自维护一份 NPC 状态。通信通过统一对象和既有事件链完成：

```text
CharacterSimulationFrame
ModuleProposal
ActionIntent
CharacterContinuityCommand
OwnerReceipt
PopulationSummary
```

### 10.2 群体模拟可以发送什么

```text
状态增量
行为候选
升级信号
群体摘要
需要展开的 code_ref
```

它不能发送：

```text
老王已经获救
老王已经买到药
老王已经入住避难所
```

### 10.3 角色智能体可以发送什么

```text
个人状态建议
结构化 ActionIntent
context_insufficient 请求
冲突摘要
请求升级或保持高精度
```

角色智能体也不能直接确认交易、入住、付款、加入组织或死亡。

### 10.4 交集卡和交接包

出现玩家互动、剧情命中、法律/组织事件、群体结果必须落到个人、模块无法裁决等情况时，程序生成交集卡：

```text
intersection_ref
actor_ref
trigger_kind
group_ref
last_confirmed_tick
continuity_revision
source_revision_vector
hard_constraints
unresolved_proposals
required_code_refs
target_fidelity
```

标准交接顺序：

```text
发现交集
-> 获取 activation lock
-> 固化 B0 游标
-> 应用已确认、允许回填的结果
-> 生成最小交接包
-> 密码本按权限展开
-> 启动 B1/B2/B3
-> 角色提出意图
-> 协议和事实底座结算
-> Character Core 接纳变化
-> 向群体回传安全摘要
```

同一角色在同一时段只能有一个推进器持有活动锁。外部世界仍可以产生事件，但事件只能进入角色下一次受版本控制的模拟帧，不能偷偷改写当前推进器的内部状态。

### 10.5 交集优先级

推进权优先级建议为：

```text
已确认的安全/法律结算
-> 当前玩家互动
-> 已持有的角色智能体交互
-> 司命特殊安排
-> B2 局部事件
-> B1 日常推进
-> B0 背景推进
```

这只是“谁先得到角色局部推进权”，不是谁能抹除已经确认的世界事实。

## 十一、通用密码本：INF 的上下文定位基础设施

### 11.1 设计意图

司命和角色智能体都需要在上下文不足时快速找到原内容，但不能把全部世界资料常驻在模型上下文，也不能让模型持有万能密钥。

因此密码本是整个 INF 的通用基础设施：

```text
短引用
+ 压缩索引
+ 来源版本
 + 权限策略
 + 受控展开
 + 读取回执
```

密码本对业务语义保持中立，既可以指向角色记忆，也可以指向经济合同、库存投影、组织章程、法律条文、环境状态、玩法包规则或司命上下文。

### 11.2 条目字段

```text
code_ref
source_ref
source_type
source_revision
content_digest
scope / visibility
reader_roles
codec_version
encryption_key_ref
safe_summary
expansion_levels
expiry
```

`source_type` 可以是：

```text
character_state
event_slice
relationship_graph
organization_rule
economy_contract
inventory_projection
law_text
situation_snapshot
gameplay_package
siming_context
```

密码本只负责定位、验证、解压、解密和过滤；来源 owner 仍负责解释和写入事实。

### 11.3 分级展开

```text
L0：安全摘要
L1：过滤后的事实卡
L2：授权的精确内容或投影
```

同一个 `code_ref` 对不同读者可以有不同投影：

| 读者 | 可能看到的内容 |
| --- | --- |
| B0 | 该成员有家庭限制，不能自动分离 |
| 司命 | 这是一个高风险例外候选，建议优先展开 |
| 角色智能体 | 获授权的家庭承诺和个人行动约束 |
| 避难协议 | 需要两张床位，其中一人有医疗照护需求 |
| 表现层 | 正在等待家庭安置 |

同一来源没有被伪造为不同事实，只是按主体、目的、范围和隐私等级返回不同的合法投影。

### 11.4 自动展开

模型不能用自然语言要求“给我全部背景”，而应提交结构化缺口：

```text
context_insufficient
reason: household_constraint_unclear
required_decision: can_household_evacuate
code_refs: [household-care:wang:commitment-01]
requested_level: L1
```

程序执行：

```text
检查请求者身份
-> 检查用途和范围
-> 检查版本与 digest
-> 解压/解密
-> 按任务过滤
-> 返回最小充分内容
```

L1 不够才升级到 L2。权限不足返回 `expansion_denied`，不能用猜测替代事实。

### 11.5 读取回执

每次展开记录：

```text
reader_ref
code_ref
source_revision
requested_level
purpose
granted_fields
policy_revision
issued_at / expiry
```

回执能解释“司命为什么挑中老王”“角色为什么知道这项承诺”，但回执本身不包含原文。

### 11.6 上下文预算原则

正式原则是：

> 能由程序预填、参数映射、查询、确定性计算或密码本按需展开的信息，不进入司命和角色智能体的常驻上下文。常驻上下文只保留当前决策所需的摘要、硬约束、冲突、候选和回执。

## 十二、世界真相层和表现层

### 12.1 世界真相层只认已结算事实

群体模拟、简易模型、角色智能体和司命都只能提出建议或意图。世界真相层的工作是：

```text
接收意图
-> 检查规则、权限、资源和版本
-> 组合并结算协议
-> 写入事件
-> 更新投影
-> 返回回执
```

世界真相层不是一个超级数据库，而是多个明确事实 owner、协议和事件回放的联合边界。

### 12.2 Character Core 的位置

Character Core 负责：

```text
角色身份连续性
模块运行状态
需求/情绪/日程等角色连续状态
simulation cursor
SeedDelta 和 CharacterContinuityCommand
私有记忆候选的准入和物化
```

它不负责：

```text
替角色买东西
替组织表决
替经济撮合交易
直接写库存、账户、许可证或空间事实
```

### 12.3 Godot 表现层的位置

Godot 负责：

```text
输入、具身、动画、声音、镜头和可见展示
```

它可以在等待确认时播放短暂、可重建的预测，但不能把预测当成事实：

```text
可以播放：老王请求避难
不能直接显示：老王已入住避难所
```

只有后端确认事件才能成为持久世界展示。

## 十三、组织、库存和经济怎样由角色驱动

### 13.1 组织没有自我意志

组织由以下事实和程序组成：

```text
成员、职位、授权、章程、提案、表决、承诺、资产引用和工作队列
```

例如避难所是否接收老王夫妇：

```text
工作人员或负责人提出接收提案
-> 组织程序确定谁有决定权
-> 相关角色给出意见或执行已生效授权
-> 组织事实记录有效决定
-> 资源协议检查床位和药品
-> 事件回执返回角色和投影
```

如果章程规定负责人可以单独批准，这是已经存在的授权，不是避难所产生了人格。

### 13.2 库存没有意志

库存记录：

```text
物品、批次、容器、保管、预留、运输、质量、耐久和过期
```

它不会自己决定交易。角色提出购买、出售、领取、转移或生产意图，库存协议检查可用性并记录结果。

### 13.3 经济由角色行为和协议组合产生

老王卖粮的链路是：

```text
老王提出卖粮意图
-> 检查保管权和出售权限
-> 买方提出购买意图
-> 报价/订单协议匹配
-> 资源预留与资金冻结
-> 规则检查税费、许可和合同条件
-> 原子事件一次提交
-> 资源和账本事实更新
-> 价格、供需等投影更新
```

价格和供需可以由确定性规则计算，但不能凭空产生“市场想买”或“市场想涨价”。没有角色行为或已生效规则，就不应有对应交易事实。

### 13.4 自动执行的边界

组织、经济和政府可以自动执行已经生效的规则：

```text
租约到期
工资结算
利息累计
预留过期
许可失效
已授权的物资配给
```

这叫规则后果，不叫组织产生了新意志。新的政策目标、新交易、新合同和重大例外仍需要角色、代表、程序或玩法包明确提出。

## 十四、既有链路上的完整推进流程

### 14.1 远处 NPC 的普通生活

```text
世界时间推进
-> 既有世界运行时提供情境输入
-> 司命接收群体摘要和待决策事项
-> 程序计算 ParticipationResolution
-> 司命和角色智能体读取同一策略
-> 程序取得唯一推进锁
-> B0/B1 批量运行模块
-> 生成状态增量、行动候选、升级信号
-> 有世界效果时提交已登记协议
-> 事实底座结算并返回回执
-> Character Core、群体摘要和投影更新
-> Godot 展示已确认结果
```

### 14.2 玩家接近群体中的 NPC

```text
玩家接近
-> 激活策略判断
-> 获取 actor lock
-> 停止该角色 B0 推进
-> 固化群体游标
-> 生成交集包
-> 展开最小必要上下文
-> 启动 B2/B3
-> 角色提出 ActionIntent
-> 协议和事实底座结算
-> Character Core 接受结果
-> 群体收到安全摘要
-> Godot 展示后端事实
```

### 14.3 失败流程

```text
没有床位 -> 不写“已入住”
药品不足 -> 不写“已获得药品”
资金不足 -> 不写“交易完成”
授权失效 -> 不写“组织决定生效”
版本过期 -> 重读、重排队或零写入
交接冲突 -> 暂停该角色，禁止双重推进
```

失败、延期和部分成功都是正式结果，不是异常到可以被忽略的情况。

## 十五、参考样板：农民、村庄与洪灾

### 15.1 样板目标

洪灾不是一个特殊系统，而是验证以下通用能力的第一条组合样板：

```text
角色原型和档案覆盖
情境预设和 B0 群体账本
简易心智/行为模块
B0 -> B2/B3 交接
角色意图进入社会协议
资源、账本、关系、规则和空间协作
表现层只展示确认事实
```

### 15.2 角色与世界

```text
村庄、农田、河流、道路、避难所、粮食组织、地方行政、市场和账户
```

它们是空间、关系、资源、规则和协议的组合，不是有自我意志的角色。

农民原型绑定：

```text
身份、需求、日程、家庭照护、供给、情绪、耕作、交易和避险行为
```

老王的档案覆盖：

```text
病妻、祖传种子、玩家旧识、不可自动家庭分离
```

### 15.3 洪灾预设

允许 B0：

```text
疲劳、恐惧、道路风险、基础迁移压力、基础食物消耗
```

禁止 B0：

```text
家庭分离、重要物品、个人合同、玩家关系、关键任务
```

强制展开：

```text
生命危险、亲属失联、玩家接触、避难冲突、重大法律事件
```

### 15.4 群体阶段

```text
普通村民由 B1 推进
-> 司命批准洪灾群体窗口
-> 程序筛选可入组成员
-> B0 计算共同压力
-> 按成员账本确定性分摊
-> 老王保留家庭和种子保护字段
```

此时群体可以得到“老王疲劳增加、道路风险上升、避难需求上升”，但不能得到“老王已经撤离或入住”。

### 15.5 玩家交集阶段

```text
玩家遇到老王
-> 锁住老王
-> 停止 B0
-> 展开家庭承诺摘要
-> 启动 B2
-> 若路线、床位和家庭冲突无法脚本裁决，升 B3
```

老王的角色智能体读取同一套身份、模块、洪灾状态、家庭承诺、物品和玩家关系，提出：

```text
带妻子去避难所
途中寻找药品
请玩家协助取回种子
```

### 15.6 协议结算

```text
家庭关系确认
-> 资格确认
-> 避难所容量确认
-> 医疗需求确认
-> 路线和交通确认
-> 药品/物资预留
-> 组织接收程序
-> SettlementPlan
-> append_batch
-> 回执和投影
```

成功才记录：

```text
老王和妻子进入避难所
床位减少
药品减少
老王退出洪灾群体
```

失败则保留疲劳、恐惧和未完成承诺，下一轮继续选择。

### 15.7 洪灾结束

情境预设失效后，老王不会被重置：

```text
避难经历、照护责任、损失的种子、债务/收入、玩家关系变化
```

这些结果仍由 Character Core 和相应事实 owner 保存。只有策略允许、没有未决个人事实时，老王才可以回到较低精度。

## 十六、当前项目实现与目标的对应关系

### 16.1 可以直接复用的底座

当前已经存在、应继续复用的能力包括：

```text
GameplayEventStore
SettlementPlan 和 append_batch
schema / contract catalog
replay / projection
Character Core continuity
CharacterSimulationSeed
CharacterContinuityCommand / Receipt
ActionIntent
activation / handoff lock
Siming cadence、read-set、预算和 capability catalog
Inventory、Economy、Organization、Government、Social 的通用平台雏形
```

### 16.2 需要上提或拆层的地方

这些能力可以保留，但要明确层级：

```text
EconomyAuthorityService：旧兼容 facade，不能继续承载所有经济语义
econ1 EconomyAuthority：早期垂直协议和兼容入口
OrganizationAuthority：成员/授权/组织程序与历史垂直混合
GovernmentAuthority：规则/许可/行政流程与历史垂直混合
Population owner adapters：有界切片适配，不是社会主入口
SocialFactAuthority：固定社会垂直可以保留，不能扩成万能社交 writer
```

迁移策略是：保留事件和回放兼容，先为每个方法标记“事实、协议、投影或适配”，新功能优先调用底层原语和已登记协议，禁止继续从兼容 facade 膨胀出新的社会语义。

### 16.3 当前 INF-4 的准确定位

当前 INF-4 可以准确称为：

> Siming 治理的、有版本和回放边界的有界群体连续性与少数 owner 适配切片。

它尚不能称为：

> 由角色意图驱动整个社会运行的通用群体模拟系统。

原因是完整目标还缺：

```text
三层参与策略的正式合同
B0 成员账本和确定性分摊
玩法包可组合的简易心智/行为模块
B0-B3 交集包和安全交接
通用密码本基础设施
角色意图进入多层社会协议的完整闭环
组织决策来源与角色成员行为的完整连接
```

## 十七、实施分期

不建议一次性重写。每期都只在既有连续性、调度、意图、协议、事件、回放和投影链路上增加小能力、合同或纯计算 helper；不构建并行的群体模拟运行时。每期都必须有独立的回放、隐私、零写入和交接证据。

### 阶段 0：层级标记

不改变行为，先把当前类和入口标记为：

```text
原子事实
协议
投影
兼容适配
```

特别审查经济、组织、政府和群体 adapter 的混层方法。

### 阶段 1：共享模拟帧

固定并接通：

```text
CharacterSimulationFrame
ParticipationResolution
ModuleProposal
SimulationCommitPacket
```

目标是让 B0-B3 和司命读取同一个版本化介质。

### 阶段 2：简易模型模块

从农民样板开始，提供：

```text
身份、需求、日程、家庭、供给、情境、情绪、行为
```

证明玩法包新增参数和模块时，不需要新建底层运行时。

### 阶段 3：B0 成员账本

实现：

```text
入组锚点、保护字段、分片、确定性分摊、游标、退出和恢复
```

先覆盖洪灾居民、行军军队和迁徙者等共同压力情境。

### 阶段 4：交接

实现玩家接近、司命挑选、剧情命中、模块冲突到 B1/B2/B3 的统一交接包。

### 阶段 5：通用社会协议接入

优先闭环：

```text
粮食生产 -> 库存保管 -> 交易 -> 账户结算 -> 组织承诺 -> 经济投影
```

随后扩展雇佣、租赁、配给、组织表决、公共项目和军事补给。

### 阶段 6：通用密码本

让角色、司命、群体、协议、调试和回放使用同一套定位、权限、版本、展开和回执接口。

### 阶段 7：DOD 批量优化

正确性闭环后，再在既有热状态、投影和调度链上做列式布局、按群体分桶、批量模块执行和预算优化。不能以性能为理由提前复制一套 NPC 真相或第二 runtime。

## 十八、正式设计原则

下面这些原则是本方案最重要的沉淀。后续代码、玩法包和 INF 新能力都应逐条对照。

### 原则 1：同一个角色，不因精度切换而换人

B0、B1、B2、B3 只切换推进方式，不重建角色身份、连续性和历史。

### 原则 2：群体是压缩方式，不是真相 owner

群体可以统计共同压力、生成候选和分摊允许字段，但没有人口真相、社会意志或通用结算权。

### 原则 3：默认保护个人，未声明不得聚合

任何字段没有明确聚合和分摊规则时，默认 `individual_only`。

### 原则 4：个人覆盖默认只能收紧，放宽必须显式声明

角色档案不能因为字段缺失而悄悄降低保护等级。任何放宽都必须有玩法包理由、版本和迁移路径。

### 原则 5：司命和角色智能体消费同一策略合同

两者可以提出不同路由意见，但不能各自解释一套参与规则；硬限制取更严格结果，推进权由程序锁定。

### 原则 6：模块提出建议，既有角色推进链统一裁决

模块不能相互直接写状态，不能直接调用领域 owner，不能因为执行顺序不同而产生不同事实。

### 原则 7：角色智能体提出意图，不能直接宣布结果

模型输出、脚本输出和司命输出都属于提议；世界事实必须经过协议、规则、权限、资源、版本和 owner receipt。

### 原则 8：组织、制度和经济没有角色式自我意志

它们可以自动执行已生效规则，但新的目标、合同、政策和重大例外必须追溯到角色、代表、表决、玩法脚本或有效授权。

### 原则 9：INF 用分层组合成长，不靠窄 owner 堆叠

新社会行为优先增加通用原子操作、预编译协议、玩法参数和投影，而不是新增一个 `FarmOwner`、`TradeOwner` 或 `WarEconomyOwner`。

### 原则 10：兼容入口不等于最终架构

旧 `supply`、`inspection`、`work` 和旧 Economy facade 可以保留验证和回放，但只能作为兼容适配，不能继续承担新社会语义。

### 原则 11：能由程序处理的信息不占司命常驻上下文

预填、参数映射、查询、确定性计算和密码本展开都应由程序完成。司命只看摘要、冲突、候选、风险和待决策事项。

### 原则 12：密码本通用，但不拥有事实

密码本对业务语义中立，统一处理索引、版本、权限、压缩、加密、展开和回执；来源 owner 仍掌握事实和写入权。

### 原则 13：一个角色同一时间只有一个推进器

B0、B1、B2、B3 通过 activation/handoff lock 串行推进；外部事实只能按版本进入下一次角色帧。

### 原则 14：失败是正式结果，不能用表现层掩盖

没有床位就是申请失败，没有资金就是交易失败，版本过期就是重读或零写入。表现层不能把预测渲染成确认事实。

### 原则 15：状态、记忆和世界事实分开

世界事实不自动等于角色知道，角色知道不自动等于角色记住，群体趋势不自动等于个人经历。每一步都需要来源、权限、暴露和 Character Core 准入。

### 原则 16：回放是设计的一部分，不是上线后的补丁

每个群体 tick、模块版本、分摊结果、交接包、协议结算和密码本展开都必须保留足够的版本、游标、来源和 digest，保证完整回放和 checkpoint+tail 回放一致。

### 原则 17：先做一条真实闭环，再扩展社会规模

农民—村庄—洪灾样板优先证明“角色生活、群体压缩、社会协议和玩家交接”能够连起来，再扩展军队、迁徙、瘟疫、战争经济和文明模拟。

## 十九、验收标准

从本设计派生实施计划时，至少需要证明：

1. `SimingRuntime.tick()` 仍是司命决策和调度的唯一入口。
2. 没有新增 Population Truth Owner、第二 runtime、clock、event store 或万能 router。
3. Character Core 是角色连续性、模块状态和角色游标的唯一接纳者。
4. 司命和角色智能体消费同一份 `ParticipationResolution`。
5. 同一角色同一时刻最多一个激活推进锁。
6. B0 成员账本支持完整 replay 和 checkpoint+tail replay 等价。
7. `individual_only` 字段永远不会进入群体聚合。
8. 客观世界效果必须经过已登记协议和 owner receipt。
9. 模块、模型和司命输出在结算前都保持不可信提议状态。
10. 密码本展开经过权限、版本、digest 和用途校验，并留下回执。
11. Godot 只展示已确认事实或可重建的短暂预测。
12. 老王从 B0 进入 B2/B3 后仍是同一个人，退出后保留已确认经历和未完成承诺。
13. 洪灾样板至少证明一个成功的社会协议和一个 fail-closed 失败路径。
14. 新增玩法包模块只需声明模块、参数、协议和版本，不需要复制一套角色 runtime。
15. 经济、组织、政府新能力能够说明自己属于原子事实、协议、模型或投影哪一层。

## 二十、最终定位

当前实现不是“什么都没有”，也不是“完整社会模拟已经完成”。更准确的定位是：

```text
已有：
  事件与回放底座
  Character Core 连续性
  Siming cadence 和候选决策
  B0 有界状态增量
  owner-bound capability 和 receipt
  Inventory/Economy/Organization/Government/Social 平台雏形

仍需补齐：
  三层参与策略正式合同
  可组合简易心智/行为模块
  B0 成员账本和确定性分摊
  B0-B3 交接包
  通用密码本
  角色意图到通用社会协议的完整闭环
```

最终目标不是“让司命替整个世界做决定”，也不是“让所有 NPC 都变成大模型”。最终目标是：

> 用数据化、模块化、可回放的简单心智和行为模型，让大多数 NPC 在群体和脚本推进下真实生活；当玩家、剧情或社会冲突需要时，让同一个 NPC 平滑切换到角色智能体；所有角色行为都在通用社会规则和法律框架内，通过多层 INF 原子事实与协议推动组织、库存和经济运转。
