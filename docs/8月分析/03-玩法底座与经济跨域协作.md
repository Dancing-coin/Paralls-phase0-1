# 玩法底座与经济跨域协作

状态：`incremental gameplay guidance; grounded in current Gameplay Foundation implementation and evidence`

本文件以现有玩法 owner 为起点，指导后续跨域经济设计。当前实现边界以
`docs/superpowers/specs/world-character-siming-authority-mainline/character-gameplay-foundation/`
及其 matching plan tree 为准。

## 1. 当前玩法底座

当前 Gameplay foundation 的强项是权威结算和跨域一致性，而不是内容数量。已有基础包括：

- Gameplay command、前置条件、revision、幂等和原子事件批次；
- event store、projection、replay、checkpoint、outbox；
- resources、body、status tags、effective stats；
- ability、skill path、grant、restriction、affordance；
- item、container、inventory、encumbrance；
- equipment、slot、modifier、container access；
- ownership、account、fixed offer、gift、debt、simple contract；
- embodied interaction、grab/carry/place 和 Godot mirror。

后续领域必须在这些 owner 上增量扩展，而不是重建平行状态：

| 现有职责 | 当前代码 owner | 增量约束 |
| --- | --- | --- |
| 提交、幂等、replay、outbox | `backend/app/gameplay/event_store.py` | 所有新事实仍通过既有 batch 脊柱提交 |
| 账户与余额投影 | `backend/app/gameplay/economy_runtime.py` | 市场、税费和组织资金不能另建余额真相 |
| 物品、容器与负重 | `backend/app/gameplay/inventory_runtime.py` | 生产、物流和仓储扩展现有 item/container projection |
| 装备、产权与身体资源 | `equipment_runtime.py`、`ownership_runtime.py`、`resource_body_runtime.py` | 新领域只请求各自 Authority 写入其业务事实 |
| 状态、属性与行动 gate | `status_tags.py`、`effective_stats.py`、`skill_action_gate.py` | 生存、岗位和生产规则不复制角色状态或技能所有权 |

## 3. 经济系统的正确定位

当前只能称为：

> 产权与经济基础原语 / 跨领域经济结算基础。

这不把经济排除在玩法之外。经济从 L3 的生产与交换延伸到 L4 的组织、监管和制度选择；
“玩家经营”与“NPC 按日程经营”共享同一 authority 约束，只是 intent 的来源和推进频率不同。
对应玩法层级与领域入口见 [社会与制度玩法](玩法系统/社会与制度玩法/README.md)。

当前已有：

- 账户余额和原子扣款/入账；
- 固定报价购买；
- 物品赠与；
- 独立产权和凭证；
- 简单债务与偿还；
- 注册型简单合同；
- 交易记录、幂等、回放和隐私投影。

这些“当前已有”的证据边界以
[`.harness/verification/gameplay-economy-authority-report.json`](../../.harness/verification/gameplay-economy-authority-report.json)
和 [`.harness/verification/adventure-basic-report.json`](../../.harness/verification/adventure-basic-report.json)
为准；前者证明经济 authority 原语与失败闭环，后者只把其中一部分组合进五个受治理
跨域 reference scenario。

当前没有：

- 供需、动态价格、订单簿和拍卖；
- 生产、消费、库存周转和供应链；
- 劳动力市场、工资和岗位；
- 税收、许可证、货币发行、通胀和政府财政；
- 企业经营、成本、利润、信用、违约和破产；
- 租赁、股份、质押、许可和复杂权利；
- 跨区域、跨世界和持续经济模拟。

## 4. 经济必须和其他系统协作

| 系统 | 经济协作内容 |
| --- | --- |
| 技能 | 决定生产效率、岗位资格、服务质量、劳动力价格和学习成本 |
| 背包 | 管理原料、商品、工具、仓储、运输和容量 |
| 建造 | 提供建筑、工坊、商店、农田、道路和生产能力 |
| 生存 | 产生食物、住房、医疗、能源等持续需求和消费 |
| 商业组织 | 管理员工、岗位、账户、库存、订单、成本和利润 |
| 政府组织 | 管理税费、许可、监管、禁运、补贴、处罚和公共建设 |
| 产权 | 管理土地、建筑、企业、设备和资产权利 |
| 经济域 | 管理市场、价格、订单、工资、税费、债务和结算 |

## 5. 目标经济循环

```text
技能/劳动力
  -> 生产或服务
  -> 背包/库存/物流
  -> 市场交易
  -> 商业组织经营
  -> 生存需求消费
  -> 政府征税与监管
  -> 反过来改变技能、价格、组织和生产
```

例如，一家面包店不应只是一个“购买面包”的固定报价：

```text
员工技能 -> 面粉消耗 -> 工作台/建筑占用 -> 面包产出
-> 库存变化 -> 工资与成本结算 -> 市场价格
-> 居民食物需求 -> 销售收入 -> 税费 -> 企业利润
```

## 6. 跨域结算原则

经济不能直接修改技能、背包、建筑或生存状态。下列是后续跨域领域在既有 Authority 服务之上收口的目标流程；当前已批准的窄场景仍由各 Authority 直接构造并提交事件批次：

```text
生产/交易命令
-> 读取多个领域的 pinned revision
-> 语义/规则求值得到预提交 SettlementPlan
-> authority 统一校验并映射领域事件
-> GameplayEventStore.append_batch
-> projection、账目和镜像更新
```

例如“完成生产订单”需要由技能域确认能力，由背包域扣原料和生成商品，由建筑域确认工作站，再由经济域结算工资和成本。

## 7. 增量收口顺序

本顺序服务于后续立项，并与主线 plan tree 同步。经济系统不应先做动态价格，更不能跳过它依赖的既有 `world_runtime`、ESM 与 Gameplay authority 路径；每一步均须先形成独立 spec、plan 和验证：

1. 在既有事件/权威脊柱上，先验证实体、语义、effect/resistance、规则、待收口的
   `SettlementPlan -> append_batch` 边界与调度的 V0 垂直样板；
2. 生产/制作/服务订单；
3. 工作站、建筑能力和资源消耗；
4. 劳动力、岗位和工资；
5. 基础需求与周期消费；
6. 商业组织账户、库存、利润和权限；
7. 政府监管、税费和许可；
8. 市场价格、供需和区域经济；
9. 信用、违约、跨区域和链上收益结算。
