## 当前实现边界

本文件定义的是基于现有边界的 Creator Control Plane 增量约束，不是现有 API 清单。当前可复用的实现边界仅包括：

- Gameplay Patch runtime 的内部/受信任 manifest、Rule IR 和受限 capability；它不是对创作者开放的通用代码执行、发布或注册中心；
- 后端签发的 trusted-local WebSocket 镜像读取 scope；它不是生产账号、组织成员、项目 grant 或创作者写权限系统；
- 事件、revision、replay 和受过滤投影脊柱；它们不是 `CreatorControlPlane`、`ActiveWorldRevision` 或发布流水线的已实现替代品。

因此，以下命令名、三层运行环境和 revision 模型都必须先迁入正式 spec、matching plan 并获得验证，才可作为外部 UI、CLI 或 MCP 的实现授权。

## 文档责任边界

本文件只拥有创作者的身份/项目范围、数据分级、query/command contract、草案到 revision
生命周期，以及 Workbench/Preview/Production 的操作语义。它不拥有角色心智、世界事实、
玩法结算或部署保护本身。

- 哪些 runtime、authority、密钥和私密数据必须保留在闭源核心，以及如何做模块/进程/
  内容包隔离，见 [11-全面闭源核心保护与创作者控制面方案.md](11-全面闭源核心保护与创作者控制面方案.md)；
- 各领域的 canonical owner 见 [全域架构责任矩阵](全域架构/00-系统边界与责任矩阵.md)；
- 创作者流程不能反向决定 world mode、`SettlementPlan` 或 event-store 的内部实现。

## 1. 目标

让创作者能够在自己的项目内读取资料、制作内容、配置允许的玩法规则，
并由项目管理员发布和运营；同时保持角色心智、世界实体/语义/规则/调度、
感知与知识投影、状态写回、Gameplay/ESM authority 和事件账本为闭源核心。

这不是“禁止创作者读取档案”的设计。可信项目管理员可以读取其项目的
完整 authored content，包括创作者定义的私密剧情信息。需要保护的是：

- 未获授权主体不应读取不属于其范围的内容；
- 任何创作者角色都不能直接改写运行时真相或核心算法；
- 内容编辑、发布和启用必须可归因、可回放、可撤销；
- UI、CLI 和 MCP 的权限结果必须一致。

## 2. 决策模型

每一个请求都按下列五元组作出 allow/deny 决策：

```text
principal + project scope + resource + capability + data classification
```

角色不是唯一判断条件。`admin` 也只在其被授予的项目或组织范围内生效，
不能天然读取其他项目，不能获得平台核心源码或任意 runtime 写权限。

所有未明确允许的请求 fail closed。客户端传递的角色名、project ID 或
principal ID 只能被视为待验证声明；控制面必须从已认证 session/token
解析主体和有效范围。

## 3. 三档创作者权限

| 角色 | 读取 | 修改 | 发布与管理 | 明确禁止 |
| --- | --- | --- | --- | --- |
| `reader` | 已发布内容、允许的草案视图、规则 schema、裁剪调试视图 | 无 | 无 | 编辑内容、读取其他项目、读取 runtime-private 数据、执行状态命令 |
| `editor` | `reader` 内容及项目内可编辑 authored content、验证/模拟结果 | 创建和修改草案；上传受治理内容包；调整白名单规则参数 | 可提交发布申请 | 直接发布/启用/回滚；管理成员；写 Gameplay 事件；调用核心内部函数 |
| `admin` | 项目内完整 authored content 与完整审计视图；按独立 debug capability 读取裁剪 runtime 诊断 | `editor` 的全部能力 | 成员管理、审批、发布、启用、停用、迁移、回滚和密钥轮换 | 跨项目访问、事件删除、任意状态迁移、修改 L1-L4 或 authority 内部实现 |

高风险 `admin` 操作可要求二次确认、审批人分离或短时 step-up grant，
但这不是第四种常驻角色。

## 4. 数据分级

权限角色和数据分级必须独立。建议初始分级如下：

| 分类 | 例子 | 可见性 |
| --- | --- | --- |
| `platform_core` | L1-L4 算法、记忆语义、实体/语义/规则/调度实现、隐私策略、authority 实现 | 仅闭源核心服务 |
| `project_authored` | 世界设定、公开角色档案、规则包、资产绑定 | 项目范围内按角色可读 |
| `project_private` | 创作者定义的角色秘密、剧情反转、未发布草案 | 项目 admin 默认可读；reader/editor 由显式 grant 决定 |
| `runtime_private` | 原始五池记忆、推理工作区、模型上下文、内部风险信号 | 不经 raw API 暴露；只返回受限调试投影 |
| `security_audit` | 审计记录、密钥 ID、授权失败原因 | admin 按项目可读；敏感字段裁剪 |

例如，编剧可被授予读取 `project_private` 的“商人是走私者”设定；
这不等于他可读取商人本轮 L2 工作区、另一个项目的秘密或平台 prompt。

## 5. 统一控制面

外部 UI、CLI 和 MCP 都只能调用同一个 `CreatorControlPlane`。它是唯一的
产品级读写入口；CLI/MCP 不是获得 Python import 权限的别名。

```text
UI list/checkboxes ─┐
CLI command         ├-> CreatorControlPlane -> policy decision -> audit
MCP structured tool ┘                         -> draft/revision lifecycle
                                                    -> closed core activation
```

初始命令面：

```text
project.inspect
dossier.get_view
ruleset.describe_schema
world_revision.get_view
semantic.describe_schema
semantic_definition.draft.create / patch / validate
rule_definition.draft.create / patch / validate
draft.create
draft.patch
draft.validate
draft.simulate
draft.diff
draft.submit_for_review
revision.publish
revision.activate
revision.retire
revision.rollback
audit.list
```

每个写命令必须包括 `command_id`、idempotency key、expected revision 和
目标 scope。`principal`、项目成员资格和角色由服务端解析，不接受客户端
自报。所有响应应给出稳定的拒绝码，但不得借拒绝码泄漏隐藏资源的存在。

控制面查询一律返回按项目范围与数据分级裁剪的 `creator_debug_view`。它与角色
或玩家所见的 `actor_perception_view`、以及闭源结算器内部使用的
`authority_evaluation_view` 是三种不同的投影；`reader` 的读取 grant 绝不扩大
规则求值可见面，也不能让 UI、CLI 或 MCP 复用 authority query。

## 6. 档案与规则的生命周期

```text
content input
-> draft revision
-> schema/dependency/privacy validation
-> sandbox simulation and impact report
-> editor review request
-> admin publish (immutable content digest)
-> scheduled activation
-> session pins revision
-> retire / forward migration / rollback
```

规则与 dossier 都只能创建新 revision，不能原地覆盖已发布真相。已运行的
session 必须固定所使用的 dossier/ruleset/patch revision，并记录包含语义、
政策、文明、schema 和 core compatibility 的 `ActiveWorldRevision`；新 revision
的启用时间由世界时钟或显式运维窗口决定。

对角色 dossier 的编辑必须拆为 layer-aware proposal。控制面允许的 layer、
字段级 capability、影响投影和迁移策略都来自核心注册表，不能由内容包
自由声明。`replace_dossier_layer()` 可以继续作为核心内部纯函数，但不能
成为 CLI、MCP、插件或内容包的公开写接口。

## 7. 内容包、签名与闭源边界

草案内容包可由 editor 创建，但已发布包必须包含：

```text
project_id
package_kind
revision_id
parent_revision_id
content_digest
declared_capabilities
schema_versions
required_core_version
compatibility_range
migration_ref
author_principal_ref
publisher_principal_ref
created_at / published_at
signature_key_id / signature
```

闭源核心验证 manifest、签名、scope、capability 和兼容性后才加载内容。激活时
由核心把已发布包、world config、semantic registry、policy/civilization、schema
与 core version 组合成新的 `ActiveWorldRevision`，并将其 digest 写入 session、
settlement receipt、checkpoint 与 replay。`migration_ref` 只能引用闭源核心已注册、
签名且可测试的 migrator；内容包无权附带任意 Python/GDScript、事件删除指令、
可执行 migrator 或 authority handler。需要扩展行为时，内容包只能引用核心注册
且被授权的 declarative rule/capability。

离线下载版只能提供完整性和授权控制，不能承诺在创作者完全控制的机器上
绝对保密。真正需要保护的 core、私密运行态与发布签名应运行在远程服务或
受保护进程中；本地 CLI 仅持有短期、范围受限的控制面凭据。

## 8. 创作、预览与正式运行的区别

“本地创作”和“远程正式运行”不是同一运行时上的两套参数，也不是把
本地改动同步到远程后继续编辑。完整产品应明确区分三个环境：

```text
Creator Workbench
  内容/规则草案、验证、模拟和版本 diff
        ↓
Preview/Test Runtime
  临时世界、合成玩家、可重置事件和 replay
        ↓
Production Runtime
  真实玩家、正式状态、权威结算、持久事件和闭源核心
```

### 8.1 Creator Workbench

这是 UI、CLI 和 MCP 所在的创作工作台。它处理：

- 角色、世界、任务、资产和规则草案；
- schema、依赖、隐私和 capability 校验；
- 差异查看、影响分析和本地 replay；
- 内容包、规则包和 dossier revision 的生成。

工作台中的内容尚未成为世界真相。编辑者可以不断修改和重置草案，
但不能从这里直接写入正式账户、库存、产权、角色运行态或历史事件。

### 8.2 Preview/Test Runtime

预览运行时用于回答“这个项目设计能不能正常运行”。它可以在本地，
也可以部署到隔离的临时远程环境。它可以真实执行：

- NPC 对话、技能判定和结构化行动；
- 物品移动、建造、生产和生存消耗；
- 商店交易、组织预算和任务/证据链。

但它只使用临时世界、测试账户、合成玩家、临时事件存储和受限模型。
预览世界可以完整重置，任何预览事件都不能成为正式产权、余额或玩家
历史的来源。

预览结果必须记录：

```text
core compatibility version
ActiveWorldRevision digest
semantic registry / policy / civilization revisions
ruleset and package revisions
world snapshot
asset versions
simulation seed
validation and replay report
```

### 8.3 Production Runtime

正式运行时才是玩家正在经历的游戏世界。它负责：

- 真实玩家 session 和持久角色状态；
- 正式账户、库存、产权、合同、税务和事件账本；
- 闭源角色心智、私密档案和正式模型服务；
- Gameplay/ESM authority、回放、审计、迁移和回滚。

客户端、本地工作台、插件或 MCP 不能直接改写生产结果。玩家购买物品时，
必须由生产 authority 验证资金、库存、产权、容量和税则，并以一个正式
原子结算提交账户、库存、交易和税务事件。

### 8.4 线上更新不是直接改变量

正式运行时之上的数值调整和内容更新属于 live operation：

```text
本地创建 revision
-> 预览与模拟
-> admin 审核
-> 签名发布
-> staging/canary
-> 按指定 world tick 激活
```

例如把 `hunger_decay` 从 `12` 改为 `9`，必须生成新的 ruleset revision；
线上服务器在指定 tick 启用它。旧事件不被改写，已有 session 是否切换
由 revision pinning 和迁移策略决定。直接修改生产内存中的 hunger 数值，
不属于合法的内容更新流程。

### 8.5 本地正式运行的例外

单机、私有部署或离线企业版可以把 Production Runtime 放在创作者本地，
但仍需使用签名内容包、受保护 runtime、受控权限和可恢复事件记录。这样
可以提供离线能力，却不能承诺创作者完全控制机器时仍能绝对防止反编译或
篡改。需要强闭源保护的角色心智、私密运行态、生产签名和模型密钥仍应
放在远程核心服务或受保护进程中。

三种环境的核心区别是：

| 环境 | 解决的问题 | 数据性质 | 是否能成为正式世界真相 |
| --- | --- | --- | --- |
| Creator Workbench | 游戏应该是什么 | 草案和 revision | 否 |
| Preview/Test Runtime | 设计能否运行 | 可重置模拟状态 | 否 |
| Production Runtime | 玩家正在经历什么 | 正式持久状态 | 是 |

## 9. 控制面对玩法的约束

控制面只允许创作者修改“规则定义和内容”，从不允许修改“已发生的游戏真相”。例如：

- 生存调参是 `SurvivalRuleset` 草案经发布后在指定 tick 生效，不是改当前 hunger/stamina；
- 经济调参是已注册的货币、税则、报价和组织规则草案，不是写余额、库存、产权或历史交易；
- 角色编辑是允许 dossier layer 的 proposal，不是写记忆、目标、动态状态或有效能力投影；
- 调试是按 scope 返回脱敏 snapshot、trace 与 replay，不是导出 raw L2/L3 workspace 或跨项目事件。

保护对象和领域级开放/禁止矩阵不在这里重复，统一见 [11](11-全面闭源核心保护与创作者控制面方案.md)。
Gameplay authority 仍是所有现实状态变化的唯一写入者；创作者 revision 只影响之后的
authority settlement。

## 10. 审计、并发与恢复

控制面需要单独的 append-only audit stream。至少记录：

- principal、project、角色、命令、输入摘要、授权判定和 policy revision；
- 草案/revision 的 parent、content digest、签名和发布/启用结果；
- 模拟所用 world snapshot、规则版本和影响摘要；
- 拒绝、失败、回滚、停用和迁移的原因与关联事件。

编辑冲突依赖 expected revision：同一草案的竞争修改返回冲突或显式 merge
任务，绝不静默覆盖。激活、回滚和迁移与既有 event sourcing/patch lifecycle
保持 append-only；“删除旧版本”不是恢复手段。

## 11. 分阶段落地

### Phase A：边界冻结

- 写出 command、resource、classification、capability 和拒绝码 schema；
- 将外部调用收敛到一处 control-plane port；
- 标记 loader 与 dossier layer replacement 为核心内部实现；
- 为现有 UI/CLI/MCP 预留只读与草案接口，但不承诺完整产品化。

### Phase B：受治理创作

- 实现项目成员与 `reader/editor/admin` grants；
- 实现 dossier/ruleset draft、validation、simulation、immutable revision 与 audit；
- 将生存、经济、建造等配置接入声明式 ruleset，而非直接状态写入；
- 为 UI、CLI 和 MCP 使用同一 command/query contract。

### Phase C：安全发布与运行

- 实现签名内容包、发布审批、计划启用、session revision pinning；
- 扩展 scope 至世界、场景、组织和角色；
- 添加 package compatibility、受批准 migrator 与回滚策略。

### Phase D：平台化

- 将核心控制面、私密运行态和签名服务隔离到远程闭源服务；
- 增加多租户隔离、密钥轮换、配额、协作审阅和安全监控；
- 根据生态需求追加资产、贡献归因和收益系统，但不把它们混入游戏经济账本。

## 12. 首批验证不变量

1. `reader` 不能创建草案、写状态或读取未授予的 `project_private` 数据。
2. `editor` 能修改获准内容，但不能 publish、activate、rollback 或写 Gameplay 事件。
3. `admin` 的权限被 project scope 限制，项目 A 的 admin 不能读取项目 B。
4. 外部 UI、CLI、MCP 不存在可直达的 dossier loader、layer replacement 或 event-store 写入口。
5. 任何 published/active revision 都可由 digest、签名、审批和 audit 记录追溯。
6. 已运行 session 在完成前持续使用 pinned revision；新版本不静默改变其角色行为。
7. 所有拒绝 fail closed，错误详情不泄露隐藏 dossier、项目或 runtime-private 数据。

## 13. 后续扩展点

- 自定义项目角色与 capability bundles；
- 组织级授权、多人审核和委托发布；
- 字段级/对象级 dossier grants；
- 安全的规则 DSL 与受限 capability 市场；
- 离线授权、断网草案和重新联机签名；
- 资产、剧情、规则包之间的依赖图与贡献归因。

这些扩展不得改变本方案的核心约束：外部主体只通过控制面发起受权限约束的
命令；闭源核心才拥有最终加载、投影、状态写回和 authority settlement 权限。
