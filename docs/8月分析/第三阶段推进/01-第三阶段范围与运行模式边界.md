# 第三阶段范围与运行模式边界

状态：`incremental design; P3A/P3B formal spec required before implementation`

## 1. 阶段目标

P3 解决的是“角色如何持续存在并被不同精度的世界模式推进”，而不是“角色数量越多越好”。
同一个角色在近场交互、日级批量经营和推演分支中必须保持 identity、资产、关系和事件连续。

## 2. 三种模式复用同一事实链

| 模式 | 触发粒度 | 角色策略 | 允许的差异 | 不变量 |
| --- | --- | --- | --- | --- |
| `game` | 近场即时、窗口级 | 玩家/高精度 CharacterAgent | 更高观察与反馈频率 | authority、revision、事件顺序不变 |
| `simulation` | 小时/日级批量 | planner/规则/低成本 agent | 批量规划和负载预算 | 同一 typed intent 与同一结算规则 |
| `replay` | 固定 seed、固定输入 | 不新增意图 | 只读、可分支 | 输入、ruleset、结论可复现 |

mode profile 只能改变调度精度、激活策略和报告视图，不能改变经济、库存、生存或组织
规则的 canonical owner。暂停恢复必须携带 active revision、最后已提交 sequence 和
未完成 obligation refs。

## 3. owner 责任

| Owner | P3 中新增责任 | 不拥有 |
| --- | --- | --- |
| World runtime | mode profile、activation lock、批次选择、catch-up budget、requeue | 角色本体、经济结算、生产结果 |
| Population planner | 从已授权 projection 生成候选 intent 和优先级 | 角色身份、家庭事实、Gameplay events |
| Character Core | profile-backed identity、心智连续性、memory writeback | 人口计数、组织资产、账户 |
| Social projection | 家庭/职业/关系/知识的受限投影 | 事实写入和经济结果 |
| Gameplay authorities | 组织、库存、生产、经济、Survival 的验证和提交 | 模式调度和批量 planner |
| Mirror/Projection | mode-specific scoped view、trace 和恢复报告 | canonical world truth |

P3 新增的调度能力必须扩展现有 `world_runtime` 和 obligation/settlement contract；不能
把 Population planner 变成第二条事实链。

## 4. 激活生命周期

```text
registered profile
-> eligibility checked
-> activation requested
-> activation locked at revision
-> active snapshot
-> pending changes
-> revision-checked merge
-> suspended / requeued / active
```

未知 profile、冲突的 activation lock、过期 snapshot 和不允许的 world mode 都必须拒绝，
不得创建部分角色状态。merge 失败时保留 pending changes 与原因，等待下一次有界重试。

## 5. 阶段门禁

- 同一 actor 在 game/simulation/replay 中的 identity 和资产引用一致；
- pause/resume/catch-up 不跳过或重复提交 obligation；
- batch planner 只能发 envelope，所有结果仍有 committed event、receipt 和 replay evidence；
- actor、household、organization 和 public view 的隐私边界可独立验证；
- P3 不产生 dynamic market、civilization 或第二个 scheduler owner。
