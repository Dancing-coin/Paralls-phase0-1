# 角色智能体工作意图与经营窗口

状态：`incremental design; P2A/P2C formal spec required before implementation`

本文件定义 CharacterAgent 如何参与面包店工作，以及它能看到什么、能提交什么。角色
智能体是意图来源和本地连续性持有者，不是 Gameplay 事实 writer。经营窗口是显式传入的
有界上下文，不是新的世界时钟或隐式后台调度器。

## 1. 适配边界

当前 L1-L4 与 `CharacterAgentL4Adapter` 已能产生角色动作/表现命令，但这些命令还不应
直接成为组织、生产或经济事实。P2 增加的是一个受限的 **actor-to-gameplay adapter**：

```text
CharacterAgent L1-L4
-> actor-scoped gameplay projection
-> local decision / selected intent
-> adapter validates capability + package allowlist
-> GameplayCommandEnvelope (typed work intent)
-> owning authority / pure SettlementPlan
-> GameplayEventStore.append_batch
-> committed result -> memory writeback + scoped mirror
```

适配器只能返回 envelope 或 structured rejection，不能持有 store、调用
`append_batch`、修改 CharacterProfile、写账户/库存/生产/Survival state，亦不能把模型的
自然语言或 `role_state_hint` 当成完成证据。

## 2. P2 允许的意图

第一阶段默认由 Harness 或玩家触发；自动自治需单独的 policy 开关，默认关闭。

| typed intent（逻辑名） | 必要输入 | authority 结果 |
| --- | --- | --- |
| `respond_shift` | actor ref、assignment/offer ref、accept/decline、expected revision | Organization 更新 shift 生命周期 |
| `start_work` | accepted work order、window、facility/target、actor capability snapshot | Skill/Survival/Inventory/Production 校验并建立 work/run 事实 |
| `finish_work` | work order/run、completion evidence、window close/finish tick、expected refs | Production/Organization 记录完成或失败 |
| `report_absence` | shift/work order、absence reason、source/correlation | Organization 记录 absence，不假设角色身体原因 |
| `request_break` | active work ref、requested duration/window | 只创建待批准请求，不直接改变 need 或出勤 |

以下暂不开放：自动招聘、改工资、改组织权限、直接采购付款、直接销售入账、修改他人
状态、创建角色或把顾客/供应商变成 NPC。

## 3. envelope 最小约束

最终字段必须复用 `GameplayCommandEnvelope`，以下是 P2 额外的逻辑约束：

```text
principal_ref       = actor adapter / approved player principal
actor_ref           = character:<profile_id>
source_ref          = character-agent:<profile_id> 或 player:<session_ref>
command_type        = versioned work intent
transaction_id      = one attempted participation
idempotency_key     = stable for one intent retry
expected_revisions  = assignment, shift/work order, facility/inventory projections
pinned_revisions    = package, policy, recipe, survival profile, wage policy
payload             = only refs and actor-declared request; no canonical balance/state
```

adapter 必须先用 profile registry 和内容包 allowlist 解析 `actor_ref`。不存在的 profile、
不允许在该内容包工作的 profile、跨项目 actor ref 和合成 `character:npc:*` 都在 envelope
生成前拒绝。现有 `char_a`、`char_b`、`char_c` 只能作为 harness 引用，不能由这份设计
改写其 authored identity/occupation。

## 4. actor-scoped projection

### 4.1 角色自身可见

- 自身 actor/profile ref 与已经授权的岗位；
- 自己的 shift offer、work order、窗口、状态和待办义务；
- 自己提交的 attendance/work evidence 及结果 receipt；
- 自己工资应计、已付/逾期状态，不默认暴露组织完整余额；
- 自己的 Skill qualification、Body/Survival labor-availability band 和必要失败原因；
- 面包店公开信息：设施是否可用、公开 quote、公开营业状态和公开需求摘要。

### 4.2 经营者/组织管理可见

- 组织岗位、班次和工作订单状态；
- 每项工作的 evidence refs、总工资应计/预算占用和窗口结果；
- 组织自身账户/库存/设施的授权投影；
- 员工是否接受、缺勤、完成或失败的结构化状态。

不得把其他角色的 need 数值、私有记忆、情绪、未公开报价、工资细目、家庭或社会关系
放进管理面板或角色 prompt。管理者若需介入，只能通过已授权的组织命令。

### 4.3 Godot mirror

Godot 仍只消费 committed、scope-filtered mirror。单观察者参考包可以收到组织管理投影；
角色客户端只收到自己的 actor projection。mirror delivery 失败不得反写 canonical state，
恢复需要重新申请 backend grant 并从 committed snapshot 重建。

## 5. 经营窗口和到期义务

P2 只接受显式 `operating_window` 上下文：

```text
window_ref, organization_ref, opens_at_tick, closes_at_tick,
policy_revision, source_revision, status=open|closed|cancelled
```

这里的 tick 是命令携带的可审计时间坐标，不代表新增 `SimulationClock`。窗口由玩家、
Harness 或未来已授权的调度入口显式打开/关闭；当前阶段不自动唤醒角色，也不在停服后
隐式补算。

窗口内允许：接受班次、开始工作、提交完成证据、报告缺勤、申请受限休息。关闭时只做
一次明确的 due-obligation evaluation：未开始的 accepted work 可转 `absent`，未完成的
started work 按 ruleset 转 `failed`/`recovery_due`，已完成证据进入工资计算。每个转换都
是新 command 和新事件，可重试且带 idempotency。

### 5.1 窗口状态规则

| 状态 | 可接受命令 | 关闭后的结果 |
| --- | --- | --- |
| `planned` | open/cancel | 未 open 不得开始工作 |
| `open` | accept、start、finish、absence、break request | 由显式 close 触发到期评估 |
| `closed` | 仅补偿/支付/恢复命令 | 不得写入原窗口工作事实 |
| `cancelled` | 仅审计/重排 | 既有接受不转为完成 |

重复 close、过期 window、stale revision 和跨组织 window 都必须零写入拒绝。

## 6. 身体与生存系统的协作

Survival 通过既有 state/need projection 给出 `labor-availability` 判断。P2 采用：

- `DISABLED`：不读取或不阻断工作；
- `NARRATIVE`：可生成叙事提示，但不自动写 need tick；
- `LIGHTWEIGHT`/`SIMULATION`：在同一 pinned policy 下，状态可阻断开始/完成或产生
  明确的消费/恢复义务。

CharacterAgent 可以据此选择休息、拒绝班次或报告缺勤，但不能从 prompt 中直接写入
`NeedState`、body resource 或 skill value。阻断原因必须回到结构化 result，供角色记忆和
Godot 表现消费。

## 7. 自动化策略与安全阀

P2 默认策略是 `harness_triggered_intent`：每次工作意图由测试或玩家明确触发。只有在
正式 spec 证明命令幂等、权限过滤、窗口关闭、重放和失败恢复后，内容包才可开启
`agent_auto_intent`。自动化仍只能产生 typed intent，不能提升权限或绕过组织/经济 owner。

## 8. 后置边界

Population Simulation 接入后，批量计划器可以提出同样的 intent；它不创建第二个角色记录、
账户或 settlement path。顾客、供应商、竞争对手和监管人员在本阶段仍是 aggregate/public
profile，直到 Population authority 完成 materialization、continuity、budget 和 batch
revision 门禁。
