# 第二阶段范围与正式收口路径

状态：`incremental design; formal spec required before implementation`

## 1. 要解决的问题

第一阶段证明了一个经营者可以在固定报价、聚合需求和 authority settlement 下经营面包店。
它没有证明以下问题：

- 一个真实角色能否接受或拒绝组织工作，而不是被组织脚本当作数值使用；
- 多人是否会因烤炉、材料、班次或资金约束产生确定的协作与冲突结果；
- 完成工作后工资、疲劳/需求约束和组织期末事实能否保持各自 owner；
- 角色智能体输出是否能以受控 typed intent 到达 Gameplay authority，而不会变成直接 writer；
- 每个参与者是否只看到其被授予的组织和薪酬投影。

第二阶段只收口这些问题。它不以“更多角色数量”作为完成标准，而以 **不同 actor source 的
同一结算规则、同一事实链和可解释失败** 为完成标准。

## 2. 目标状态与阶段边界

| 运行形态 | 允许的 actor 来源 | 需求/报价来源 | 可以声称的能力 | 不可声称的能力 |
| --- | --- | --- | --- | --- |
| `bakery-single-owner` | 一个经营者 | 聚合需求、固定 quote | 单店经营闭环 | 多智能体或商业生态 |
| `bakery-authored-agents` | 2-4 个已存在 CharacterProfile/CharacterAgent | 聚合需求、固定 quote、公开竞争 profile | 受控多角色组织协作 | NPC 生态、人口模拟、动态市场 |
| `bakery-population-ecosystem` | Population Simulation 激活的角色 | 真实角色 intent 与公开规则 | 商业生态 | 本阶段明确不进入 |

第二阶段结束后，项目可以声称“已有角色的多智能体组织协作已通过 authority/replay/mirror
门禁”，但仍不能声称“员工、顾客、供应商和竞争对手由社会模拟驱动”。

## 3. 设计原则

1. **角色先于岗位**：`character:<profile_id>` 必须在角色档案 registry 中已经存在；岗位
   assignment 不创建角色、不覆盖人设，也不创建影子 employee state。
2. **组织安排，角色决定参与**：Organization 只能创建 shift/work offer、预算和权限边界；
   accept/decline、work intent 与可见工作证据经过角色和 domain authority 校验。
3. **工作不是工资事实**：工资只引用已提交的出勤/生产/服务/交付 evidence；角色计划或
   OrganizationOperatingPlan 都不能直接写账户分录。
4. **局部窗口，不造世界时钟**：P2 使用外部明确提交的 `operating_window`/due obligation
   command；不把 `world_runtime` 的角色唤醒器误用为经济 scheduler。
5. **同一 command 入口**：玩家 UI、CharacterAgent adapter 和 Harness 都构造同一版本化
   Gameplay command envelope；authority 仍是唯一 canonical writer。
6. **先 scoped read，后高自治**：角色只能读到自己的班次、授权工作、薪酬状态与必要的
   公开组织信息。私有记忆、其他角色需求/情绪和组织秘密默认不进入 prompt 或 Godot mirror。

## 4. 正式 spec 拆分建议

进入 SDD 时，不应创建一个“多智能体经营总 spec”。最小拆分如下：

| P2 spec | 责任 | 前置证据 | 不拥有 |
| --- | --- | --- | --- |
| P2A Actor-to-Gameplay participation | profile-backed actor ref、授权、typed work intent adapter、拒绝/审计 | Character Core、P1 shared contract | 角色档案、组织/经济事实 |
| P2B Organization work lifecycle | role、shift、work order、attendance/completion evidence 和设施冲突引用 | P1D construction/inventory/organization | 账户、库存、身体/技能真相 |
| P2C Payroll and operating window | evidence-driven wage accrual、支付/逾期 obligation、明确 window close | P1D economy/debt/government | 新市场、通用时钟、角色需求写入 |
| P2D Authored-agents vertical slice | 三角色 bakery composition、scoped mirror、replay/Harness | P2A-P2C | Population Simulation 或真实顾客 NPC |

P2A-P2C 是可并行设计、但实现上需按依赖顺序推进的子 spec；P2D 只能在前三项有 focused
green evidence 后开始。

## 5. 实现前决策清单

正式 P2 spec 需要由用户确认以下内容，而不是由实现者默认决定：

- 受控 reference package 使用哪些已授权的角色档案，及其在该内容包中的岗位许可；
- `accept/decline/absence` 是玩家命令、角色智能体命令，还是两者均可提交；
- 工资按班次、按产出还是混合计算，以及逾期支付的最小游戏后果；
- 哪些 worker body/survival 结果可阻断工作，哪些仅影响质量；
- P2 Godot 演示是单观察者管理面板，还是多个角色分别登录的 scoped mirror；
- 角色智能体是否在此阶段启用自动工作 intent，还是仅接受由 Harness/玩家触发的受控 intent。

未决定时，P2 应采用最保守的 reference policy：显式班次接受、按已完成工作证据计件、
单观察者 Godot mirror、Harness 触发 actor intent，避免把自动自治和内容叙事选择写死。

## 6. 完成门

P2 spec 只有同时满足下列条件才可标记 `implemented-and-verified`：

- 所有 actor ref 可回查到既有 profile registry，未知/合成 ref 零写入拒绝；
- 至少两名角色可在不同岗位完成一次协作经营窗口，并有独立 work evidence；
- 同一 facility/物料争用只允许一个 commit，失败者得到结构化结果；
- 工资 payment 或 overdue obligation 只由已提交 evidence 触发；
- 角色可见 projection 不泄露其他角色私有运行态或组织私有预算；
- success、decline、absence、insufficient skill/body、funds、stale revision、duplicate、
  facility conflict、payment overdue 均可 replay，且被拒绝命令无部分写入；
- full 与 checkpoint-tail replay 一致；Godot 仅消费 committed scope-filtered mirror；
- 没有 `NpcState`、Population authority、动态 order book 或第二条 settlement path。
