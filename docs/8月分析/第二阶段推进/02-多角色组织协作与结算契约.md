# 多角色组织协作与结算契约

状态：`incremental design; P2B/P2C formal spec required before implementation`

本文件把第二阶段的多角色协作落到现有 `OrganizationAuthority`、
`ConstructionProductionAuthority`、`InventoryAuthorityService`、`EconomyAuthority`、
`SurvivalAuthority` 和 `GameplayEventStore` 的 owner 边界上。它不是新的组织运行时、工资
运行时或跨域 coordinator；它只规定这些 owner 之间传递什么引用、证据和 revision。

## 1. 前置条件与已知事实

正式 P2 设计前必须重新运行 P1D 的 focused tests 和 Harness，确认产出入库、销售扣减、
`run_ref -> reservation_ref -> output` 顺序、full/checkpoint-tail replay 一致。P2 不能
用一个新的员工流程掩盖 P1D 的事实链缺口。

当前代码可直接确认的基础：

| 现状 | 含义 |
| --- | --- |
| `RoleAssignment(organization_ref, character_ref, role)` | 只证明一个已存在角色可以被组织引用；不代表雇佣、排班或出勤 |
| `ProductionRun(... reservation_refs)` | 可携带材料预留引用；尚未表达 worker contribution 的业务语义 |
| `BusinessPeriod`、`EconomicObligation` | 可表达经营期和一般义务；尚未形成工资应计/支付/逾期生命周期 |
| `GameplayCommandEnvelope`、`SettlementPlan`、多 stream `expected_stream_revisions` | 可作为 typed intent 与原子提交的共享适配基础；具体跨域映射仍需正式 spec |
| profile registry、L4 adapter、actor-scoped mirror | 可读取和呈现既有角色；L4 adapter 目前不是 Gameplay canonical writer |

## 2. owner 矩阵

| Owner | 持有的 canonical fact | 只读输入 | 明确不得写入 |
| --- | --- | --- | --- |
| Character Profile/Core | `character:<profile_id>`、身份、人设、心智和自身状态 | 角色授权、组织 projection、Skill/Survival capability band | 组织岗位、库存、生产结果、账户 |
| Organization | 组织注册、`RoleAssignment` 生命周期、shift offer、work order、出勤/完成证据引用、经营窗口与期末摘要 | profile existence、技能资格摘要、设施/库存/账户/政府 projection | 角色档案和身体真相、库存数量、生产 run、账户分录 |
| Skill/Ability | 资格判断、技能路径、质量/动作成本证据 | role/work order、角色技能状态 | 岗位、工资、库存和生产结果 |
| Survival/Body/State | need、身体后果和劳动可用性投影 | work window、角色状态组、消费计划 | 出勤、账户、库存转移、组织事实 |
| Construction/Production | facility、slot、recipe、`ProductionRun`、完成/失败和产出证据 | accepted work order、skill evidence、inventory reservations、permit | 工资、账户、角色需求 |
| Inventory | item/lot/custody、reservation、consume/receive | production/sale typed proposal | 生产完成、销售收入、工资 |
| Economy | account、journal、sale/purchase、工资应计、支付和逾期义务 | completed work evidence、组织预算、政府政策 | 角色技能、出勤、库存/设施事实 |
| Government | permit、inspection、tax policy/assessment | organization period evidence | 角色私有状态、组织余额和库存 |
| Projection/Mirror | scoped read model、delivery receipt、trace | committed events/outbox | 任何 canonical fact |

角色在多个岗位出现时仍只有一个 CharacterRecord、背包、身体和账户投影。岗位不是新的
角色类型，也不能创建 `EmployeeState`、`NpcState` 或影子账户。

## 3. 逻辑记录扩展

下表是 P2 的逻辑记录，不是可直接提交的 Python schema。正式 spec 必须决定是扩展现有
记录、增加事件 payload，还是通过稳定引用组合；不得为同一事实建立平行记录。

| 记录/引用 | 最小语义 | owner | 生命周期/约束 |
| --- | --- | --- | --- |
| `RoleAssignment` 扩展 | assignment ref、角色许可、工资政策引用、状态 | Organization | 只能指向已注册 profile；撤销不删除历史 |
| `ShiftOffer` | 组织给某 assignment 的 work kind、facility/资源范围、`operating_window_ref`、预期 revision | Organization | `offered -> accepted/declined/expired`; 不等于出勤 |
| `WorkOrder` | 在一个窗口内的有界工作目标、输入/输出 target refs、所需能力与 evidence kind | Organization | `issued -> accepted -> started -> completed/failed/absent/cancelled`；不可跳过证据 |
| `AttendanceEvidence` | actor、shift/work order、开始/结束或 absence reason、来源和 revision | Organization | 只记录出勤事实和外部 evidence ref，不复制身体数值 |
| `WorkerContributionRef` | 生产/交付事实指向的 assignment/work order/actor evidence | 生产或交付 owner | 以引用附加到自身事实；不得由 Organization 伪造生产结果 |
| `ProductionRun` 扩展 | `worker_contribution_refs`、work order ref、slot reservation ref | Construction/Production | start 与 finish 都重新校验 actor、facility、recipe、reservation revision |
| `WageAccrual` | payee、organization、依据 evidence refs、工资策略 revision、amount | Economy | 只能由已完成 evidence 计算；计划/接受班次不能直接应计 |
| `EconomicObligation` 扩展 | obligation kind=`wage`、accrual ref、payee、due tick、status | Economy | `accrued -> paid/overdue/waived`; 逾期是新事实，不改写应计 |
| `SettlementReceipt` | transaction、committed event ids、stream revisions、projection digest、rejections/audit | 共享契约/Store | 只描述一次提交，不拥有任何域状态 |

工资金额、产出质量和劳动能力都必须可追溯到 evidence 与 pinned revision。不要把
`wage_policy`、`skill_level` 或 `need.value` 的副本写入工资事实。

## 4. 命令与跨域提交顺序

所有来源（玩家 UI、角色智能体适配器、Harness）使用同一版本化
`GameplayCommandEnvelope`。每个命令先读取 pinned projections，再由 owning authority
构造纯 `SettlementPlan`，最后将各 owner 的事件放入一个带完整
`expected_stream_revisions` 的 `AtomicEventBatch`。`SettlementPlan` 不存状态、不 append；
提交失败时所有 stream 都不写入。

### 4.1 接受工作

```text
shift offer
-> actor/profile + assignment authorization
-> character adapter emits accept/decline intent
-> Organization validates offer/window/revision
-> append organization event
```

accept 只改变组织工作生命周期，不预扣材料、不锁定烤炉、不产生工资。

### 4.2 开始和完成生产

```text
accepted work order
-> Skill qualification read
-> Survival/Body labor-availability read (disabled mode = no blocker)
-> Inventory reservation + facility slot proposal
-> Production run start with work/evidence refs
-> due-window finish revalidation
-> inventory reservation consume + authoritative output receipt
-> Production completion evidence
```

若需要同时改变组织、库存和生产 stream，P2 formal spec 必须使用现有多 stream batch
能力，或明确一个可回滚的两阶段协议；不能让三个 authority 先后独立 append 后再声称
原子。任何资格、资源、slot、permit 或 revision 失败都返回结构化失败并保证零写入。

### 4.3 工资与期末

```text
completed work evidence
-> Economy calculates wage from pinned wage policy
-> wage accrual
-> account transfer, or wage obligation remains due
-> explicit operating-window close
-> Organization period summary
```

付款失败不能把工资标记为已付；只能提交 `overdue` 或策略允许的待处理义务。期末摘要
引用收入、成本、工资、税和义务事实，不复制各域余额。

## 5. 冲突和失败语义

| 情况 | owner 判断 | 结果 |
| --- | --- | --- |
| 未知/合成 character ref | Profile/Core bridge | `character_record_required`，零写入 |
| 未被 assignment 授权 | Organization | `work_authorization_denied` |
| offer 已过期或 revision stale | Organization/window | `shift_offer_stale` |
| 能力不足 | Skill | `insufficient_skill`，不创建 run |
| Survival/Body 阻断劳动 | Survival/State | `labor_unavailable`；disabled/narrative 按 policy 不阻断 |
| 烤炉 slot 或材料预留冲突 | Production/Inventory | `facility_slot_conflict` 或 `reservation_conflict` |
| 完成时证据/窗口失效 | Production/Organization | `work_evidence_invalid`，释放或补偿由 ruleset 指定 |
| 资金不足 | Economy | 工资保持 due/overdue，不伪造 transfer |
| 重复命令 | EventStore | `duplicate_replayed`，不得增加第二份事实 |

所有失败应包含 blocked owner scope、source refs、pinned revisions、是否可重试和
`zero_write_guarantee=true`。失败不是删除或回滚历史；恢复通过新命令产生新事实。

## 6. 第二阶段不负责的内容

- 雇佣市场、自动招聘、员工离线生活和家庭预算；
- 动态工资竞价、绩效宏观模型、金融信用和公司破产；
- 全局 `SimulationClock`、隐式 tick 或后台唤醒器；
- 顾客/供应商/竞争对手的 CharacterRecord 与私有经济状态；
- 让 CharacterAgent 直接调用 `GameplayEventStore` 或 authority 私有方法。

这些边界留给 Population Simulation、动态市场或后续组织 spec。
