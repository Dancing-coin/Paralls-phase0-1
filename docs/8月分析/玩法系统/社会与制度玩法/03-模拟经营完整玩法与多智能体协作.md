# 模拟经营完整玩法与多智能体协作

状态：`bounded bakery reference-game and authored-agent slices implemented; full population simulation remains gated`

本文把经济、技能、背包、建造、生存、组织和政府监管组合成一款可以从开始玩到
结束的完整小型模拟经营游戏。第一参考游戏是“面包店经营”，不是完整市场或文明
模拟；完整指相关系统形成可重复的经营闭环，而不是内容规模无限扩大。

本文是 8 月分析下的增量设计指导，不单独授权实现。实现前必须进入正式 spec/plan，
并沿用现有 `GameplayEventStore`、领域 authority、replay、outbox 和 projection 边界。

## 0. 当前实现事实

当前仓库已有受限 `population_continuity` authorities、人口连续性合并器和 P3D 面包店
街区样板；它们只激活已有 CharacterProfile，不创建 NPC 生成器、影子账户或第二条经济
真相路径。完整 `population_simulation`、家庭/职业生活和社会批量经济 planner 仍是
后置设计，不能被当前切片扩大解释。

## 1. 产品目标

玩家接管一家小面包店，在有限资金、材料、设施、劳动能力和监管约束下经营多个
营业日。玩家可以亲自工作、安排生产、采购材料、定价、雇佣、借款和申请许可；
经营结果由订单、库存、账户、技能、身体状态、组织预算和政策结算共同决定。

第一版必须是一个“能玩完”的小游戏：玩家可以开店、生产、卖出商品、支付经营
成本、进入下一日，并在达到目标、资金耗尽、许可证失效或债务违约时得到明确结果。

## 2. 运行配置

同一套玩法使用不同的 actor/调度配置，不复制世界事实：

| 配置 | 可运行内容 | NPC 规则 |
| --- | --- | --- |
| `reference_single_actor` | 玩家角色经营；抽象顾客需求曲线；完整采购、生产、销售、工资/税费和生存闭环 | 不创建员工/顾客 NPC，不注入 NPC 状态 |
| `reference_multi_agent` | 目标配置：玩家与多个已经存在的真实 `CharacterAgent` 角色协作经营 | 必须先有正式 CharacterRecord；不等同于群体模拟 |
| `population_simulation` | 后置配置：员工、顾客、供应商、监管人员由群体模拟批量推进 | Population Simulation Authority 生成/唤醒角色，随后仍使用同一 CharacterRecord 和 Gameplay authority |
| `high_fidelity_activation` | 后置配置：对重大谈判、冲突、投诉、检查等已存在角色提升到高精度交互 | 激活同一角色，不复制角色状态或创建影子 NPC |

完整 `population_simulation` 尚未实现前，P1/P2 仍只能使用
`reference_single_actor`。顾客不是隐藏 NPC，而是带版本和来源的聚合需求输入；员工
岗位、顾客角色和供应商角色只作为后续接入点保留。不得使用初始化脚本把 NPC 的
余额、库存、关系或需求直接写入正式世界。

### 2.1 第一阶段角色数量

- **实际必须存在：1 个经营者角色**。它是正式 `CharacterRecord`，可以由玩家直接
  控制；如果采用智能体经营，则由 1 个 `CharacterAgent` 代表该角色提交意图。
- **实际 NPC 数量：0 个**。顾客由聚合需求曲线表示，供应商由固定 quote 表示，
  监管由政府 policy/authority 表示。
- **可选的多智能体验证：2 至 3 个已有角色**。例如经营者、烘焙师和采购员，
  但这些角色必须先有正式 `CharacterRecord`，不能由面包店脚本临时注入。
- **群体模拟接入后：数量由人口配置决定**。员工、顾客、供应商和监管人员的数量
  不写死在面包店玩法中，也不作为第一阶段完成条件。

## 3. 参与主体与角色

### 3.1 玩家经营者

玩家经营者是普通 `CharacterRecord`，可以同时拥有个人账户、背包、技能、身体状态
和面包店组织的经营授权。玩家只能提交 typed intent，例如：

- `bakery.open_shop`
- `procurement.request_materials`
- `production.start_run`
- `shop.set_quote`
- `organization.assign_shift`
- `government.apply_permit`
- `survival.consume_food`

玩家意图不直接改变库存、账户、设施或生存状态。

### 3.2 多智能体角色

多个智能体角色仍然是多个独立 `CharacterRecord`，每个角色有自己的技能、身体、
背包、账户、知识和关系投影。它们可以分别担任店主、烘焙师、采购员、收银员或
监管联络人，但职位是 `RoleAssignment`，不是新的角色类型。

每个角色都经过同一条路径：

```text
CharacterAgent 观察/计划
-> typed intent
-> 读取角色可见 projection
-> owning authority 验证
-> GameplayEventStore.append_batch
-> committed result / memory writeback / mirror
```

智能体不能因为“计划成功”就视为工作完成；工作完成必须有生产、交付、销售或
检查等 authority evidence。

### 3.3 NPC 角色

员工、顾客、供应商和监管人员在目标设计上都是真实角色，而不是直接嵌入经营状态
的 `EmployeeNpc`、`CustomerNpc` 或 `SupplierNpc` 结构。

它们的正确来源是：

```text
Population Simulation planner
-> Character/World owner validates materialization or activation proposal
-> same CharacterRecord
-> household / occupation / budget / knowledge projection
-> batch planner or CharacterAgent
-> same typed intent and same domain authority settlement
```

群体模拟尚未实现时：

- 不生成这些 NPC 的正式账户、库存、关系或生存状态；
- 不用 fixture、seed script 或隐藏 writer 伪造 NPC 行为；
- 只允许使用聚合顾客需求、固定供应商报价和测试用的非角色约束；
- NPC 相关验收标记为 `blocked-by-population-simulation`，不伪装成已完成。

### 3.4 经营角色与可提交意图

| 世界角色 | 可承担者 | 典型 typed intent | 群体模拟前的处理 |
| --- | --- | --- | --- |
| 店主/经营者 | 玩家或真实 CharacterAgent | 开店、定价、采购、排班、借款、申请许可、停业 | `reference_single_actor` 必须存在 |
| 烘焙师/店员 | 真实 CharacterAgent 或未来人口角色 | 接受班次、预留工具、开始/完成生产、补货 | 没有真实角色时不创建；店主可亲自完成工作 |
| 顾客 | 未来人口角色 | 浏览报价、购买、消费、投诉 | 使用聚合需求，不创建顾客角色 |
| 供应商 | 未来人口角色或组织授权角色 | 发布报价、交付材料、催收付款 | 使用固定供应商 quote，不创建供应商角色 |
| 监管人员 | 未来人口角色或政府组织授权角色 | 检查、签发/续期/吊销许可、开具罚单 | 使用版本化政府政策和规则检查，不创建人员角色 |
| 房东/债权人 | 真实 CharacterAgent、组织或未来人口角色 | 收租、催收、协商续约、发起合同动作 | 第一版可由 organization/government/contract 的非角色主体持有权利 |

同一角色可以同时是店主、烘焙师和债务人；职位和社会身份只是关系/授权投影，
不会复制角色、账户、库存或身体状态。Organization 的 `OperatingPlan` 只能提出
建议和预算边界，不能替员工、顾客或监管人员提交结果。

## 5. 面包店核心数据模型

以下是领域模型边界，不是要求把所有对象塞进一个 `BakeryState` god object。

```text
BakeryOrganization
  organization_id, owner_ref, jurisdiction_ref, account_refs
  facility_refs, role_assignment_refs, operating_plan_ref, status

Facility
  facility_id, plot_ref, ownership_right_ref, capability_refs
  condition, throughput, maintenance_due_tick, permit_ref

Recipe
  recipe_ref, revision, input_lots, tool_refs, skill_requirements
  duration_ticks, output_lots, byproduct_lots, quality_rules

ProductionRun
  run_id, organization_ref, facility_ref, recipe_ref, worker_refs
  reservation_refs, start_tick, finish_tick, status, evidence_refs

InventoryLot
  lot_id, item_ref, quantity, quality, provenance_refs, expiry_tick
  custody_ref, reservation_state

MarketQuote
  quote_ref, item_ref, side, unit_price, quantity_limit
  valid_from_tick, valid_until_tick, policy_revision, demand_digest

RoleAssignment
  assignment_id, organization_ref, character_ref, role_ref
  wage_policy_ref, authority_scope, schedule_ref, status

OperatingPeriod
  period_id, organization_ref, opening_tick, closing_tick
  revenue, costs, payroll, taxes, debt_due, result, close_evidence_ref
```

角色、设施、商品和组织的 canonical fact 分属各自 authority；上述模型之间只保存
稳定引用、revision 和 evidence，不复制另一领域的事实。

## 6. 一日经营流程

### 6.1 开日

1. `SimulationClock` 产生新的 `operating_period.opened`；
2. 读取固定的 ruleset、政策、配方、报价和组织预算 revision；
3. 计算设施可用性、员工可用性和生存需求；
4. 经营者提交采购、排班、生产和报价 intent。

### 6.2 采购与准备

1. Economy Authority 创建采购 quote 或使用固定供应商 quote；
2. Inventory Authority 检查容量、lot 和 custody；
3. 经济域提交付款，库存域转移材料；
4. 任一域失败时整批零提交，保留结构化拒绝。

### 6.3 生产

1. Construction/Production Authority 检查设施状态、工具、材料预留和角色技能；
2. 创建 `ProductionRun` 与完成 obligation；
3. 到期 tick 时重新验证 facility、worker、recipe 和 reservation revision；
4. 成功则消耗输入、生成产出和质量证据；失败则释放、损耗或返工，策略由 ruleset 决定。

### 6.4 营业与销售

1. Economy Authority 读取聚合顾客需求，或在未来读取 Population Simulation 提交的顾客 intent；
2. Economy Authority 生成有有效期的 `MarketQuote`；
3. 销售结算同时验证报价、库存、买方支付能力、税费和营业许可；
4. 成功后写入库存减少、账户分录、税务负债、销售记录和声誉 evidence。

### 6.5 关日

1. 结算工资、租金、许可证费用、税费和债务到期项；
2. Survival Authority 处理角色需求、消费计划、疲劳和劳动能力反馈；
3. Organization Authority 汇总营业收入、成本、现金流、库存和经营目标；
4. 产生 `period.closed`，生成下一日预算和待办义务；
5. 检查成功、继续经营、暂停营业、破产或许可证吊销条件。

每一步都可以重试和回放；不能依靠内存中的“当前营业日状态”恢复。

## 7. 多智能体协作

### 7.1 玩家与智能体角色

玩家、店主智能体、烘焙师智能体和采购智能体都提交相同的 typed intent。区别只在
意图来源、可见 projection 和授权范围，不在结算规则。

冲突示例：两名员工同时预留同一烤炉。设施 stream revision 或 slot reservation
只允许一方提交成功，另一方获得 `facility_slot_conflict`，不能出现双重生产。

### 7.2 NPC 接入后的协作

群体模拟为角色生成工作、消费、求职、采购、投诉和检查计划。计划器只生成 intent，
不直接写入结果：

```text
population batch plan
-> actor/household/org projection
-> typed intent batch
-> authority validation
-> append_batch
-> result back to population continuity / character memory
```

高精度智能体只用于谈判、投诉、检查争议、重大雇佣和经营危机；日常搬运、采购、
消费和排班可以批量规划，但仍需同一 authority。

### 7.3 群体模拟未实现前

- 不创建员工、顾客、供应商或监管 NPC 的正式角色状态；
- 不用隐藏的 `NpcState`、脚本 seed 或测试 fixture 伪造 NPC 已经生活在世界中；
- 第一版面包店使用单玩家经营者 + 聚合顾客需求 + 固定供应商 quote；
- 多角色和 NPC 的接口、事件和 projection 先写入正式 spec/plan，待 Population
  Simulation Authority 通过门禁后接入。

## 8. 第一版成功/失败条件

成功条件示例：连续三个经营日保持正现金流、完成指定订单、许可证有效、至少一次
技能升级或设施升级。

失败条件示例：现金流耗尽、工资或税费违约、生产设施停摆、许可证吊销、关键生存
需求失败导致经营者无法工作。

失败是可回放的领域结果，不删除历史；恢复可以通过新贷款、降低产量、暂停营业、
重新申请许可或重新开始经营周期实现。

## 10. 门禁

只有同时满足以下条件，才可把 Econ-1 标记为 `implemented`：

- 新店启动后能连续运行至少三个经营日；
- 采购、生产、销售、工资、税费、许可、生存和失败恢复都有 canonical event；
- 成功、材料不足、技能不足、库存不足、资金不足、报价过期、许可证过期、
  revision 冲突、重复 tick 和权限拒绝均可测试、回放和解释；
- full replay 与 checkpoint + tail replay 一致；
- Godot 只显示 committed、scope-filtered 经营结果；
- `reference_single_actor` 不产生 NPC 状态；
- 完整 Population Simulation 未实现时，NPC 生活状态门禁保持 `blocked-by-population-simulation`；
- 新增领域只扩展现有 owner，不新增 event store、bus、runtime 或影子角色。
