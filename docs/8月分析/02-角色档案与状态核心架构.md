# 角色档案与状态核心架构

## 1. 核心分层

角色不是一个可以被任意覆盖的大 JSON，而是多种真相和投影的组合：

```text
CharacterDossier / CharacterProfile
        ↓
Effective Profile
        ↓
L1 私有感知
        ↓
五池记忆 + 需求/情绪/目标运行态
        ↓
CharacterMindFrame
        ↓
L2 理解 -> L3 规划 -> L4 执行
        ↓
ESM / Gameplay Authority
        ↓
事件、玩法投影、记忆回写、Godot 镜像
```

## 2. 档案真相层

`CharacterDossier` 是档案外壳，当前包住原有 `CharacterProfile`，主要包含：

- 身份：姓名、别名、身份、职业、组织、社会等级；
- 具身基线：身体类型、感官、运动能力、声音和外观标记；
- 起源与人生经历；
- 价值观、红线和禁止行为；
- 人格：Big Five、facets、气质、冲突风格、防御模式、信任动力；
- 需求层级：生理、安全、归属、尊重、自我实现的权重和满足/挫败通道；
- 表达与对话风格；
- 权限、职责、允许动作和禁止动作；
- 私密真相、秘密的知道者和投影策略；
- 关系种子和能力种子；
- runtime 默认控制模式。

档案真相的原则是：

- 长期 baseline 不等于短期状态；
- 运行时情绪不能直接覆盖人格档案；
- 角色学习证据不能自动改写 authored skill truth；
- 长期 drift 需要证据和晋升闸门；
- 同一档案按 author、self、player、L2、L3、L4 产生不同投影。

## 3. 运行时状态层

### 心智运行态

- L1 角色私有世界快照；
- Working Memory；
- Event Memory；
- Observation Memory；
- Knowledge Memory；
- Social Memory；
- Higher-Order Memory；
- NeedTensionState；
- CharacterDynamicState：affect、tension、motivation；
- 当前目标、目标组合、目标历史；
- 未解决张力、监督状态和 background agenda。

### 玩法运行态

`CharacterGameRuntimeState` 是对已启用玩法状态组的只读组合 facade，包含：

- identity、mental；
- resources、status_tags、body_runtime；
- inventory、ownership、equipment；
- skills、ability_affordances；
- relationships、effective_stats；
- enabled state groups 和 revision vector。

玩法状态不应被心智模型直接写入；L2/L3/L4 只能提交结构化意图和 proposal，最终由 ESM/Gameplay authority 结算。

## 4. `CharacterMindFrame` 的位置

`CharacterMindFrame` 是分层只读视图，当前按以下桶组织：

- `enduring_truth`：档案、人格、权限、秘密和具身基线；
- `memory_evidence`：记忆、关系和信念证据；
- `runtime_state`：感知、需求、情绪、目标和张力；
- `affordances`：技能、行动、环境、装备和物理可行性；
- `cognition_workspace`：当前驱动、冲突、硬约束和候选问题；
- `provenance`：来源和构建版本。

它不是新的心智中枢，也不能替代 L2/L3；它是用于安全投影、调试、模型上下文和观察台的统一视图。

## 5. 当前闭源边界的判断

### 已有基础

- 严格 schema 和未知字段拒绝；
- dossier visibility projection；
- raw secret 不直接进入 L2/L3/L4；
- authored truth、runtime state、memory evidence 和 gameplay state 分离；
- dossier layer 更新只返回 projection invalidation，不直接覆盖记忆、目标、技能或身体运行态。

### 当前仍不够安全

目前 `CharacterDossierLoader` 仍可直接读取 YAML，`replace_dossier_layer()` 仍是可导入的 Python 函数。也就是说，当前是内部架构边界，不是产品发行后的闭源保护边界。

## 6. 建议的闭源产品结构

```text
Closed Character Core
  心智循环、人格投影、记忆写回、目标仲裁、隐私策略、状态迁移

Creator Control Plane
  CLI / SDK / MCP
  档案导入、版本发布、规则包启停、调试回放、资源绑定

Creator Content Package
  档案内容、剧本、资产、音频、UI、受治理规则和扩展配置
```

创作者可以修改内容和允许的配置，但不应获得：

- L1-L4 实现代码；
- 五池记忆语义；
- 人格和目标仲裁算法；
- 状态写回协议；
- 隐私投影和权限校验；
- Gameplay/ESM authority；
- 事件删除、任意迁移和核心状态域卸载权限。

## 7. 保护手段

- 核心运行在闭源服务、私有包或受保护的编译运行时；
- dossier、patch、asset pack 使用版本化签名 manifest；
- CLI 是唯一对外写入口，CLI 不能绕过 backend control plane；
- 只允许白名单 layer 和 capability；
- 修改生成新版本，不原地覆盖真相；
- 运行时事件 append-only，停用使用 `disable/retire`，不使用物理删除；
- 旧版本 session pinning，迁移只能使用核心批准的 migrator；
- 所有安装、启用、停用、迁移和调试操作写审计记录。

如果核心完整下发到创作者自有机器，就无法绝对阻止反编译和二进制篡改；真正强的闭源保护应采用“本地 CLI/内容包 + 远程闭源核心服务”的组合。
