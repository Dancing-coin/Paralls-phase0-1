# 角色档案与状态核心架构

状态：`incremental character-core boundary guidance; creator control plane is specified separately and remains planned`

## 1. 核心分层

角色不是一个可以被任意覆盖的大 JSON，而是多种真相和投影的组合：

```text
CharacterDossier / CharacterProfile
        ↓
Effective Profile
        ↓
L1 私有感知
        ↓
五池记忆 + 需求/情绪/目标运行态
        ↓
CharacterMindFrame
        ↓
L2 理解 -> L3 规划 -> L4 执行
        ↓
ESM / Gameplay Authority
        ↓
事件、玩法投影、记忆回写、Godot 镜像
```

## 2. 档案真相层

`CharacterDossier` 是档案外壳，当前包住原有 `CharacterProfile`，主要包含：

- 身份：姓名、别名、身份、职业、组织、社会等级；
- 具身基线：身体类型、感官、运动能力、声音和外观标记；
- 起源与人生经历；
- 价值观、红线和禁止行为；
- 人格：Big Five、facets、气质、冲突风格、防御模式、信任动力；
- 需求层级：生理、安全、归属、尊重、自我实现的权重和满足/挫败通道；
- 表达与对话风格；
- 权限、职责、允许动作和禁止动作；
- 私密真相、秘密的知道者和投影策略；
- 关系种子和能力种子；
- runtime 默认控制模式。

档案真相的原则是：

- 长期 baseline 不等于短期状态；
- 运行时情绪不能直接覆盖人格档案；
- 角色学习证据不能自动改写 authored skill truth；
- 长期 drift 需要证据和晋升闸门；
- 同一档案按 author、self、player、L2、L3、L4 产生不同投影。

## 3. 运行时状态层

### 心智运行态

- L1 角色私有世界快照；
- Working Memory；
- Event Memory；
- Observation Memory；
- Knowledge Memory；
- Social Memory；
- Higher-Order Memory；
- NeedTensionState；
- CharacterDynamicState：affect、tension、motivation；
- 当前目标、目标组合、目标历史；
- 未解决张力、监督状态和 background agenda。

### 玩法运行态

`CharacterGameRuntimeState` 是对已启用玩法状态组的只读组合 facade，包含：

- identity、mental；
- resources、status_tags、body_runtime；
- inventory、ownership、equipment；
- skills、ability_affordances；
- relationships、effective_stats；
- enabled state groups 和 revision vector。

玩法状态不应被心智模型直接写入；L2/L3/L4 只能提交结构化意图和 proposal，最终由 ESM/Gameplay authority 结算。

## 4. `CharacterMindFrame` 的位置

`CharacterMindFrame` 是分层只读视图，当前按以下桶组织：

- `enduring_truth`：档案、人格、权限、秘密和具身基线；
- `memory_evidence`：记忆、关系和信念证据；
- `runtime_state`：感知、需求、情绪、目标和张力；
- `affordances`：技能、行动、环境、装备和物理可行性；
- `cognition_workspace`：当前驱动、冲突、硬约束和候选问题；
- `provenance`：来源和构建版本。

它不是新的心智中枢，也不能替代 L2/L3；它是用于安全投影、调试、模型上下文和观察台的统一视图。

## 5. 当前实现与内部边界

### 已有基础

- 严格 schema 和未知字段拒绝；
- dossier visibility projection；
- raw secret 不直接进入 L2/L3/L4；
- authored truth、runtime state、memory evidence 和 gameplay state 分离；
- dossier layer 更新只返回 projection invalidation，不直接覆盖记忆、目标、技能或身体运行态。

### 当前仍不是产品级保护

目前 `CharacterDossierLoader` 仍可直接读取 YAML，`replace_dossier_layer()` 仍是可导入的 Python 函数。也就是说，当前是内部架构边界，不是产品发行后的闭源保护边界。两者可以继续作为 core 内部纯实现，但不能被导出为 CLI、MCP、插件或内容包的写接口。

## 6. 与创作者控制面的交接

本文件只定义角色档案、心智状态和玩法状态的 owner 边界；它不定义 project grant、
命令 API、签名发布或部署形态。后续控制面只能提交 layer-aware proposal，由 Character
Core 依据注册的字段 capability、隐私投影和迁移策略接受或拒绝。

- `reader/editor/admin`、数据分级、UI/CLI/MCP 一致性和 revision 生命周期见
  [10-创作者权限与闭源控制面方案.md](10-创作者权限与闭源控制面方案.md)；
- Character Core 与其他 runtime/authority 的保护矩阵、部署隔离和 threat model 见
  [11-全面闭源核心保护与创作者控制面方案.md](11-全面闭源核心保护与创作者控制面方案.md)。

任何外部写入口都不能直接替换 `CharacterMindFrame`、五池记忆、目标运行态、有效能力
投影或既有事件历史。是否将闭源 core 部署在远程服务、私有包或受保护进程，是控制面
与产品交付的后续决策，不改变本文件中的角色 truth 分层。
