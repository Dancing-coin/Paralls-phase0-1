# 增量设计工作台与覆盖矩阵

状态：`navigation and evidence guide; does not authorize implementation independently of formal spec/plan`

## 1. 用途

本文件把 [对话5—13主题重组](../上下文不够用/对话5-13-主题重组.md) 中的长期设计意图，
落回本仓库当前已经存在的代码、正式 spec/plan 和 Harness 证据。它不是新架构总纲，也
不把对话中的概念名称直接提升为新的 runtime 模块。

阅读本目录时先回答三个问题：

1. 这个能力当前是已实现、可复用，还是仍需新增？
2. 它应扩展哪个既有 owner，而不是由谁另起 store、loop 或 authority？
3. 它进入实现前对应的正式 spec、plan 与验收证据是什么？

回答以 [全域架构责任矩阵](全域架构/00-系统边界与责任矩阵.md)、
[运行时覆盖矩阵](../架构/运行时/运行时覆盖矩阵.md)、正式 mainline spec/plan 和
`.harness/verification/` 为准；本目录只提供增量设计判断。

## 4. 两组不可混淆的运行形态

**世界消费模式**由世界调度 profile 决定，服务游戏、社会模拟和反事实推演；它们共享
canonical fact、revision 和结算语义，详见 [14](世界基础设施增量指导/14-群体模拟世界模式与文明演进.md)。

**创作者运行环境**由权限与发布生命周期决定，分别是本地 Workbench、隔离 Preview/Test
和正式 Production；它们决定谁能写 draft、何时激活 revision、事件落在哪个隔离范围，
详见 [10](10-创作者权限与闭源控制面方案.md)。两者可正交组合，例如 editor 可在
Preview 中运行推演 profile，但不能因此获得 Production 的写入权。

## 5. 第一条增量路径

第一阶段的具体推进工作区见
[第一阶段推进](第一阶段推进/README.md)。它把通用契约、V0 内部测试、Econ-1 完整参考游戏、第二个异质样板和证据门禁拆成
独立文档，但仍不替代正式 spec/plan。

对话中的大图不能直接拆成并行子项目。当前建议的依赖顺序是：

```text
现有 event/authority/replay 基础
  -> Phase 1A/1B 通用 identity + semantic/effect + causal + settlement + time + replay contract
  -> V0 霜冻农田或火焰橡木门：第一领域样板
  -> V1 Econ-1 面包店：技能 + 库存 + 设施 + 需求 + 报价 + 税费
  -> 第二个异质样板：冲突/调查、合同/债务或权限型物理交互
  -> 后续受治理的创新与文明能力
```

V0-V3 的边界和验收面统一记录在
[垂直样板与验收矩阵](创作与运营/17-垂直样板与验收矩阵.md)。
现有 `adventure-basic` 仅证明一个受限的五场景参考闭环，不替代这些未来样板；其
证据见 [adventure-basic report](../../.harness/verification/adventure-basic-report.md) 与
[live mirror report](../../.harness/verification/live-adventure-basic-mirror-report.md)。

## 6. 把分析变为实现的固定门槛

1. 在正式 spec 中明确 owner、事实边界、兼容性和非目标；
2. 在 matching plan 中指定改动路径、迁移、回滚和验收；
3. 实现必须复用已有 `GameplayEventStore.append_batch`、revision、outbox/replay 和各领域 authority；
4. 增加成功、拒绝、幂等、revision 冲突、回放和过滤投影证据；
5. Harness 通过后，才将本目录相应条目从 `planned` 更新为 `implemented` 或 `reusable`。

这避免“分析文件先宣布完成、代码和 Harness 之后再补”的倒置。
