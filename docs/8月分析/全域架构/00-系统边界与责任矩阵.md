# 系统边界与责任矩阵

状态：`incremental architecture guidance; non-authorizing analysis synchronized with current spec/plan`

## 1. 目的

Paralls 不是“所有东西都由同一个玩法模块拥有”。世界实体、语义规则、角色心智、
创作者发布和客户端表现各自有不同的真相、权限和演进节奏；但经济、组织、政府、
金融、政治和文明仍是分层玩法的一部分。本文件从既有实现出发定义 canonical owner，
不以 owner 取代玩家体验层级。现有文件若有冲突，必须以正式 mainline spec、matching plan、
代码和 Harness 证据为准。尚无代码 owner 的条目只能作为收口目标，不能被当作并列 runtime。

当前实现基线见 [架构总纲](../../架构/整体架构.md)、
[运行时覆盖矩阵](../../架构/运行时/运行时覆盖矩阵.md) 和
[Gameplay Foundation 与领域结算](../../架构/运行时/模块/GameplayFoundation与领域结算.md)。
后者已提供 gameplay 领域的原子事件提交、replay、outbox、受限镜像和有界参考闭环；
本文件不重新命名或替换那些 owner。

## 2. 分层

```text
Platform and Control Plane
  identity, project scope, grants, drafts, revisions, audit, release
        ↓
Existing World Runtime Paths + Incremental Guidance
  entity records, semantics, rules, facts, scheduling, environment/ecology, event/replay
        ↓
Character Core + Social Projections
  dossier/mind, perception, knowledge, relations, household continuity
        ↓
Layered Gameplay
  L1 action/perception/conflict
  L2 skills/items/survival/quests
  L3 construction/production/trade
  L4 organizations/governance/finance/public order
  L5 civilization and long-horizon world choices
        ↓
Presentation and External Adapters
  Godot/2D/VR, VLA advisory, audio, UI, analytics and reports
```

一项能力可以读取相邻层的已授权 projection，但不得跳过 owning authority 修改
其 canonical fact。L4/L5 社会制度玩法与 L1 战斗/任务玩法具有同等的产品地位，只是
反馈周期、参与主体和事实 owner 不同；既有世界基础设施中的环境/生态路径为它们提供共同环境基础。

## 3. Canonical-owner 矩阵

| 逻辑域 | Canonical owner | 状态 / 当前入口 | 事实与事件 | 创作者可编辑 | 外部只能提交 |
| --- | --- | --- | --- | --- | --- |
| 身份、项目、权限、审计 | Creator Control Plane | `planned`；当前只存在后端认证 session、`/ws` scope、Patch/runtime 生命周期和受限镜像读路径 | grants、draft/revision、发布、audit | authored content、发布配置 | scoped query/draft/release command |
| 实体与因果档案 | World Record Authority | `planned`；当前入口是 `backend/app/world_runtime/*`、ESM、`raw_fact_event` 与现有 projection | entity/thing/environment/relation/causal event | entity schema、内容种子、引用 | entity/relationship proposal |
| 语义、effect 注册 | Semantic/Effect Registry Authority | `planned`；当前入口是 status/resource/body/tag、Patch Rule IR 与各领域 authority 的既有 schema | tag/property 与 effect/resistance definition、active semantic set | 声明式 definition/rule draft | semantic/effect proposal |
| 规则求值 | Closed Rule Engine | `planned`；当前入口是各 Gameplay Authority 的显式验证逻辑与受信任 Patch capability | evaluation trace、typed settlement plan | 参数化 Rule IR | fact/effect proposal |
| 时钟与协调 | Settlement/Scheduler Authority | `planned`；当前入口是 `world_runtime` scheduling/continuity、既有 revision pinning、idempotency 与领域结算协调 | tick、obligation、transaction receipt | calendar/policy revision | scheduled/workflow proposal |
| 事件、回放、投影 | Event Store/Projection Authority | `implemented/reusable`；当前入口是 `GameplayEventStore.append_batch`、outbox、checkpoint、replay | committed events、checkpoint、outbox | projection subscription scope | query/filtered subscription |
| 角色心智 | Character Core | `implemented/reusable`；当前入口是角色档案、L1-L4、五池记忆与目标运行态 | dossier、L1-L4、memory、goals、affect | authored dossier layers、目标模板 | structured intent/goal hint |
| 感知、知识与社会连续性 | Perception/Social Authority | `planned`；当前入口是 actor-local perception、private percept、relationship seed 与有限 social/contact runtime | perception、knowledge、belief、relation、household | relationship/knowledge content policy | evidence/disclosure/social proposal |
| 具体玩法域 | 对应 Gameplay Authority | `implemented/reusable`；当前入口是现有 inventory/equipment/economy/body/interaction 等 authority slice | skill/inventory/construction/survival/quest/conflict state | definitions、assets、ruleset params | typed gameplay command |
| 自然环境与生态 | Environment/Ecology Authority | `planned`；当前入口是 ESM 环境/对象状态、world runtime field/projection 与环境事实链 | region、weather、resource、hazard、ecology facts | climate/resource/hazard configuration | environment/hazard proposal |
| 社会与制度玩法 | Economy/Organization/Governance/Polity Authorities | `planned`；当前入口是 economy primitives、ownership/contract、关系/证据与后续规则扩展点 | market、organization、policy、civilization facts | world policy、scenario configuration | policy/operating proposal |
| 呈现与外部模型 | Presentation Adapter | `implemented/reusable`；当前入口是 Godot mirror、受限 `/ws` 读模型、VLA advisory 和报告链 | 无 canonical world fact | scenes、UI、audio、model binding | structured input/advisory/ack |

`World Record Authority`、`Semantic Registry Authority`、`Closed Rule Engine` 与
`Settlement/Scheduler Authority` 是待收口的逻辑 owner，不是当前独立模块。当前入口仍是
`backend/app/world_runtime/*`、ESM、各 Gameplay Authority 和 `GameplayEventStore`；未来
扩展必须接入这些路径，而不是让 ESM 或 System L6 承担所有领域写入。Event Store 仍是提交后的历史来源。

其中 `GameplayEventStore` 与 System L6 的职责必须分开：前者是 Gameplay domain 的
committed-event/replay source，后者是跨层 `AuthorityEvent` 的公共通知、路由和投影路径。
Gameplay outbox 只能在 batch commit 后派发；L6 不拥有余额、库存、产权、债务、合同或
其 replay。

## 4. 跨域提交的增量收口链

现有跨域写入已经通过各领域 Authority 构造事件并调用 `GameplayEventStore.append_batch`。`SettlementPlan`（早期讨论中称 `StateChangeBatch`）只是为“新增语义/因果/跨域 adapter 还未固化到单一领域 authority”的场景补齐的预提交边界，不是第二个 event store，也不是任何领域可直接写入的事务，更不替换已经存在的 inventory/economy/body/interaction 等 authority slice。引入后，每个 change 必须映射到明确的 domain authority event schema，随后仍调用既有原子提交脊柱：

```text
ActionIntent / external fact / scheduled obligation
-> validated PhysicalFact or LogicalFact
-> authority semantic snapshot and Rule IR evaluation
-> SettlementPlan (formerly StateChangeBatch; no persistence yet)
-> domain validation and event mapping
-> GameplayEventStore.append_batch
-> committed events + outbox + projections + filtered receipts
```

`GameplaySettlementCoordinator` 是后续收口时可能引入的内部协调角色，不是当前模块。它若被实现，也只负责“planned 的多领域 adapter”复用现有 revision pinning、domain validation 和 event mapping；已经落地的领域 authority 仍保持各自直接构造事件并 `append_batch` 的路径。它不能绕过 event store，也不拥有账户、库存、身体或产权的业务事实。任何一个 domain 拒绝，整批零提交。

## 5. Revision、语义和迁移

现有结算已固定各自使用的 stream/patch/schema revision。`ActiveWorldRevision` 是 `planned` 的汇总模型，用于把这些既有 revision 固定成正式运行会话快照；在其真正进入正式 spec/plan 和代码前，当前入口仍是各领域自己的 stream revision、patch/schema revision、session scope 和镜像 source revision metadata，不能把它表述成现成运行时对象：

```text
ActiveWorldRevision
  world_config_revision
  active_content_packages
  semantic_registry_revision
  active_rule_revisions
  policy_and_civilization_revisions
  schema_registry_revision
  core_compatibility_version
```

`ActiveSemanticSet` 是它的语义子集，不独立漂移。事件、checkpoint、simulation
report、settlement receipt 和 session pin 都引用这份 revision/digest。内容包只
能声明 `migration_ref`、目标 schema 与兼容范围；实际 migrator 必须是闭源核心
注册、签名、可测试的 capability，不能随包提供可执行代码。

## 6. 三种读取视图

同一世界数据至少有三种不可混用的读取视图：

| 视图 | 读者 | 能看什么 | 能否决定结算 |
| --- | --- | --- | --- |
| `authority_evaluation_view` | authority/rule engine | 规则所需的完整受政策约束事实 | 是，内部仅限规则计算 |
| `actor_perception_view` | 角色/玩家/模型 | 该角色已感知、可知或被授权的投影 | 否，只能产生意图 |
| `creator_debug_view` | reader/editor/admin | 按 project/data classification 裁剪的内容、trace、replay | 否，只能草案/查询 |

外部权限不得改变确定性世界规则的输入；它只决定谁可以读取何种 projection。

## 7. 状态证据规则

在本分析目录中统一使用：

- `implemented`：可由明确代码路径和 Harness/测试证明；
- `reusable`：现有实现可复用，但不声称目标业务能力已完成；
- `planned`：需要新增 schema、authority、projection、调度或控制面；
- `discussion`：尚未冻结的产品或内容方向。

禁止把权限设计、目标数据模型或尚未存在的 authority 标为 `current`。如证据
不明确，应使用 `planned`，并链接到现有测试或 Harness profile。

## 8. 增量扩展顺序

本节是待回写 `docs/superpowers/plans/world-character-siming-authority-mainline/` 的增量 backlog，不构成新的执行授权。任何 V0 都必须扩展现有 `world_runtime`、ESM、`raw_fact_event` 和 Gameplay authority 链，而不能另起 L1 loop、event bus、scheduler 或 authority。

1. 补齐既有 World Runtime 路径所需的实体、语义、规则、因果和事务 adapter；
2. 用 V0 “霜冻农田”或“火焰橡木门”验证完整提交链；
3. 建立创作者规则/语义内容的 draft-to-activation 闭环；
4. 再推进 Econ-1 与调查/冲突垂直闭环；
5. 最后扩展群体模拟、文明、金融、政治和跨区域世界。
