# 语义注册与规则扩展指导

状态：`INF-1 semantic/entity/causal 窄纵切、四条 Survival effect/state lifecycle 及其闭源 dispel/fixed-transform action、一条 Construction facility-state owner row 及其唯一 dispel/cancel action、两条闭源 weather-front -> Survival source edge，以及闭源多条件 guard 已验证；通用 owner matrix、未注册 lifecycle 与更广 selector 仍未完成`

本文件只定义语义 registry、selector、effect/resistance contract、规则相位和
effect lifecycle 的增量边界。现有 `StatusTagDefinition`、Patch Rule IR、effective
stats 和受信 capability 生命周期已经有受限实现。INF-1 现已实现
`TagDefinition`、`TagAssignment`、immutable semantic snapshot、受限 selector 和
继承/参数冲突拒绝；并已具备 effect/resistance 的纯计算、phase/conflict/chain-budget
meta-rule trace 与 authority settlement bridge。纯 semantic evaluator 的
`expiry_obligation` 仍仅被序列化到 effect payload，尚非通用 event-derived
`ScheduledObligation` lifecycle。唯一例外是已验证的 `SurvivalAuthority` closed matrix：
`state:cold@1` / `effect:cold_exposure`、`state:overheated@1` /
`effect:heat_exposure`、`state:dehydrated@1` / `effect:dehydration_exposure` 与
`state:fatigued@1` / `effect:fatigue_exposure`；其 add/replace/refresh/reject、stack limit、expiry、
dispel/transform 都通过该 owner 的事件行结算；fixed snapshot guard 仅允许
tag/status/数值参数 predicate，以及已验证的单层 `all(...)` / `any(...)` 闭源组合，禁止自由表达式。其他 state/effect owner、通用规则语言
和全部领域 lifecycle 覆盖仍须按独立 spec/plan 扩展。

`INF-1B/1D` 仅补上两条闭源 proposal-to-owner handoff：
`authority:semantic -> effect:cold_exposure -> state:cold@1 -> SurvivalAuthority` 与
`authority:semantic -> effect:heat_exposure -> state:overheated@1 -> SurvivalAuthority`。
它把已验证的 immutable snapshot 转为既有 Survival envelope，由 Survival 通过既有
`append_batch()` 写 state/open-obligation 事件；semantic evaluator 本身仍仅输出 proposal。
未映射 effect/state/owner、非 project privacy 和任意 caller-selected stream 均必须零写拒绝。

`INF-1AC/1AD` 在此 owner matrix 之外分别固定两条 Ecology 证据输入：project-visible
`weather:frost -> effect:cold_exposure -> state:cold` 与 `weather:heat -> effect:heat_exposure -> state:overheated`。
两者都必须消费既有 activation-owned、
project-scoped region assignment，锁定 Ecology/activation/Survival revision，并由既有
`SurvivalAuthority` 单独 append；它们不是通用 weather selector、owner router 或状态矩阵。

`INF-1O` 将三条既有 Survival action 的语义补回其 `StateDefinition`：
`dispel_allowed` 与唯一 `transform_targets=("state:recovering",)` 由闭源
owner contract 提供。`EffectLifecycleEvaluator` 对 dispel/transform 只产出纯
接受或拒绝决策；既有 semantic action authority 必须先读取该合同，随后才委托
`SurvivalAuthority` fragment 走同一 `append_batch()`。这不把 effect expiry
proposal 升级为通用 lifecycle，也不开放 action/owner/target 注册。

`INF-1P` 只为既有 Construction owner 增加闭源
`effect:maintenance_state_dispel -> state:maintenance_due`：semantic 只能提案，
Construction fragment 在同一 `append_batch()` 里写
`maintenance_state_dispelled` 和该 state 的 exact open obligation cancelled，随后由
project projection 清除 maintenance state。普通 Construction obligation cancel 仍然
zero-write reject；这不代表 repair、payment、material 或 transform 真相，也不开放
generic action registry。

剩余收口分为 `INF-1X`（闭源 RuleSet、effect/resistance、state lifecycle 与 owner
mapping matrix）和 `INF-2X`（到期/重试/取消/补偿所需的 obligation lifecycle）。INF-2X
现已有 construction、Survival 与 Economy wage 的已注册 owner rows；没有已命名 owner
event 的 durable lifecycle、retry 或 compensation 仍必须拒绝，不得由 registry、projection
或 clock 隐式改变状态。

实体 identity、Thing/Environment record、CausalEventRecord 及其与领域 authority
的接入由 [实体档案与因果接入指导](13-实体档案语义因果与元规则.md) 负责；本文件不
重复定义实体档案或因果记录。

## 1. 定位与不变量

标签体系和元规则引擎不是给内容策划使用的可选分类工具，而是 Paralls 各玩法
共享的语义语言与确定性规则执行面。没有它们，战斗、经济、建造、生存、任务、
潜行和修炼就会各自解释“木材”“受伤”“许可”“火焰”“隐身”，最终出现多个
无法回放的世界真相。

必须保持以下不变量：

1. 一个可参与结算的语义定义、effect/resistance 协议或规则都必须有注册定义和版本；
2. 领域包能声明内容，不能携带任意规则解释器或直接写状态；
3. 同一语义快照在相同 revision、输入和 seed 下必须得到相同规则结果；
4. 标签不是状态写入的旁路，所有持久变化仍由各域 authority 原子提交；
5. 快速路径和通用路径输出同一结构化事实并接受同一 replay；只有新增语义/跨域
   adapter 才物化预提交 `SettlementPlan`；
6. 规则链必须有相位、优先级、冲突策略、深度/预算和循环检测。

## 2. 标签体系

### 2.1 标签类别

| 类别 | 回答的问题 | 例子 | owner |
| --- | --- | --- | --- |
| `type` | 它是什么 | character、door、farm、weapon | Entity/Semantic Core |
| `material` | 它属于哪类构成 | wood、metal、flesh、bone | Semantic Core |
| `substance` | 它具体由什么构成 | oak、iron、water、mithril | Semantic Core |
| `property` | 相对稳定的可计算属性 | flammable、hardness、conductivity | Semantic Core + domain fact |
| `state` | 当前正在经历什么 | burning、wet、injured、sealed | owning domain |
| `capability` | 当前可做什么 | can_open、can_forge、can_trade | derived projection |
| `relation/context` | 它与谁/何处的关系 | owned_by、inside、licensed_in | relation/domain owner |

`type/material/substance/property/state` 不能混用。材料是通用分类，物质为其提供
具体参数；性质相对稳定，状态为时间性条件。只有明确的规则可让长期状态改变
持久性质，例如腐蚀降低硬度。

### 2.2 效应、抵抗与制度上下文不属于标签类别

`effect` 是规则可施加的类型化变化，`resistance` 是组件、装备、状态和环境在
规则求值中提供的受限输入；两者分别由 effect/resistance registry 与闭源 Rule
Engine 解释，不能被当作任意实体标签赋值。`policy` 与
`CivilizationCapability` 则是由辖区、治理和文明 authority 发布的激活上下文，
不是标签继承图的一部分。

```text
EffectDefinition(effect_ref, input_schema, stack_policy, version)
ResistanceProfile(source_ref, effect_ref, modifier_policy, revision)
PolicyActivationContext(jurisdiction_ref, policy_revision,
  civilization_capability_refs, effective_tick)
```

`SemanticSnapshot` 可以引用已固定的 `PolicyActivationContext`，但不能拥有或
改写它。规则只能从 `ActiveWorldRevision` 取得已启用的 registry revision 和
制度上下文；内容包不能靠添加 `tax_enabled` 或 `immune_fire` 标签越过治理或规则
协议。

### 2.3 注册定义与赋予实例

```text
TagDefinition
  tag_ref, category, parent_refs, parameter_schema
  merge_policy, allowed_entity_kinds, stability, visibility, version

TagAssignment
  entity_ref, component_ref, tag_ref, parameter_values
  source_ref, lifecycle, assigned_at, expires_at, revision

SemanticSnapshot
  entity_ref, component_refs, resolved_tags, resolved_parameters
  statuses, relations, policy_context_ref, source_revision_vector, digest
```

定义与实例必须分离。`material:wood` 是定义；“这扇门的门板由橡木构成”是绑定
在 `component:door_leaf` 上的 assignment。任何规则读取的是 immutable
`SemanticSnapshot`，不允许每个 handler 重新拼接一套自由字典。

### 2.4 继承、参数覆盖与冲突

标签继承只可沿已注册 parent graph 解析，启动/发布时拒绝环。参数必须声明合并
策略，而不是最后写入者获胜：

| `merge_policy` | 用途 |
| --- | --- |
| `replace_by_specificity` | 橡木覆盖木材的燃点等具体物质参数 |
| `additive` | 多个来源提供的热量、护甲或临时修正 |
| `minimum` / `maximum` | 抵抗下限、容量上限、阈值限制 |
| `exclusive` | 互斥形态、阵营、主控制权 |
| `compose` | 有顺序的部位、容器、权限链 |

实体、组件、装备、环境、政策的优先级和 scope 由 definition 固定。任何不明确
的覆盖、同级冲突或未知参数都 fail closed，并在创作者模拟报告中给出解释。

### 2.5 活动语义集与所有权矩阵

世界不能在运行时从“所有已安装标签和规则”中随意挑选。每个 session/world tick
固定一个可重建的活动语义集：

```text
ActiveSemanticSet
  world_ref, semantic_registry_revision, active_tag_revisions
  effect_registry_revision, active_rule_revisions, policy_context_refs
  activated_at_tick, digest
```

| 对象 | 定义 owner | 实例/状态 owner | 结算写入 owner |
| --- | --- | --- | --- |
| TagDefinition | Semantic Registry + signed content revision | 不适用 | 不适用 |
| EffectDefinition / ResistanceProfile | Semantic/Effect Registry + Closed Rule Engine | 不适用 | 不适用 |
| PolicyActivationContext | Governance/Civilization Authority | 不适用 | 不适用 |
| TagAssignment | Semantic Core schema | Entity/组件对应领域 | 对应领域 authority |
| StateDefinition | Semantic Core schema | Body/Inventory/Construction 等领域 | 对应领域 authority |
| MetaRuleDefinition | 受治理玩法包 | 不适用 | 只产生 proposal |
| RuleHandler / evaluator | Closed Core | 不适用 | 不直接写入 |
| SemanticSnapshot / RuleTrace | Closed Core projection | 从 committed events 派生 | 不可由外部直接写入 |

这份矩阵避免两个常见错误：把标签 registry 当成实体状态 owner，或让元规则
handler 绕过领域 authority 直接改变余额、库存、身体和产权。

### 2.6 查询契约与事实边界

```text
SemanticSelector
  entity_kind, component_scope
  require_all_tags, require_any_tags, exclude_tags
  parameter_predicates, status_predicates, relation_predicates
  policy_context, requested_fields
```

selector 是受限、可编译的声明式查询，不是任意脚本。闭源 Rule Engine 只在
`authority_evaluation_view` 上运行 selector，以读取结算所需的完整、受政策约束
事实；角色、玩家和模型只能读取 `actor_perception_view`；创作者调试只读取按
scope 与 data classification 裁剪的 `creator_debug_view`。后两者不能替代前者的
规则输入，也不能因外部 grant 改变正式结算结果。

标签不是万能字段容器。金额归经济账本、库存位置归 Inventory Authority、身体
资源归 Survival/Body Authority、所有权归 Ownership Authority；标签只能描述可
复用的语义或引用这些事实的受控派生视图。`derived` capability 与临时有效属性
默认不持久化，只有具体 owner 提交事件后才成为持久事实。

## 3. 元规则模型

### 3.1 规则定义与闭源 handler 分离

```text
MetaRuleDefinition
  rule_ref, revision, phase, trigger_selector, predicates
  formula_ref, effect_templates, priority, conflict_policy
  suppression_refs, chain_budget, declared_capabilities, explanation_template

RuleHandler
  handler_ref, core_version, typed_input_schema, typed_output_schema
```

创作者编辑的是 `MetaRuleDefinition`，例如“温度高于燃点时施加燃烧 effect”；
`RuleHandler` 是闭源、版本化、无任意 I/O 的 typed capability。规则不能携带
Python、GDScript、shell、网络请求或自由表达式执行器。

### 3.2 执行相位与优先级

```text
1. normalize：验证 intent/fact、固定 semantic snapshot 与 revision
2. eligibility：资格、权限、资源、区域和 civilization gate
3. derive：匹配 effect、抵抗、部位、环境与关系上下文
4. resolve：按 phase/priority/conflict policy 计算候选状态变更
5. propagate：受预算控制地生成下游 effect/causal proposal
6. settle：交给领域 authority 原子提交或整体拒绝
```

优先级不是简单整数覆盖。至少区分：自然基线规则、区域/世界政策、装备或技术
增强、超自然覆盖、抵抗/免疫/反制、持续状态。每个覆盖必须声明作用域、持续
时间和 counterplay，避免“任意魔法直接改写世界”。

### 3.3 冲突、链式触发与安全阀

每个规则运行附带 `causal_chain_id`、parent event、visited rule/entity pairs、
最大深度、每 tick effect/实体预算和幂等 key。重复 pair、预算耗尽、抑制命中、
互斥冲突或 revision 不匹配时，返回结构化拒绝/截断结果，不产生部分提交。

元规则可描述：材料与火焰、伤害与护甲、消费与饥饿、生产事故、税务资格、
舆论压力和技术解锁；但规则计算后只能生成预提交 typed `SettlementPlan`，不能
跨域直接改写 projection。

### 3.4 效应与状态生命周期

一次性影响、持续 effect 和持久性质改变必须分开：

```text
EffectApplication
  effect_ref, target_component_ref, magnitude, source_refs
  apply_policy, stack_key, expires_at, causal_chain_id

StateDefinition
  state_ref, stack_policy(add|replace|refresh|reject)
  stack_limit, expiry_policy, dispel_policy, transform_policy
```

元规则先决定是否产生 `EffectApplication`，再由状态 owner 依据 stack、refresh、
duration、immunity、dispel 和 transform policy 生成 proposal。到期、周期伤害、
腐蚀、恢复等都成为幂等的 `ScheduledObligation`，不能在读投影时悄悄改变状态。
长期 effect 只有经明确规则才能写入 property，例如持续腐蚀降低结构硬度。

## 4. 规则输入、确定性与解释链

```text
RuleInputEnvelope
  intent_or_fact_refs, semantic_snapshot_digests, evidence_refs
  world_tick, active_rule_revisions, policy_revisions
  numeric_scale, deterministic_seed, causal_chain_id

RuleEvaluationTrace
  rule_ref, matched_selectors, skipped_predicates, input_digest
  output_digest, conflict_decision, budget_decision, visibility_policy
```

正式规则使用整数或固定精度 Decimal，不依赖宿主语言浮点误差、墙钟、网络、
未记录随机数或模型回复。需要随机性时，只能使用由 command/event 固定的 seed，
并把 seed、抽样算法版本和结果写进 receipt。相同 envelope、registry、ruleset 和
world tick 必须得到相同 output；同优先级规则以 specificity、显式 conflict policy、
稳定 `rule_ref` 顺序仲裁。

`RuleEvaluationTrace` 是调试、审计和创作者模拟的解释源，不能泄漏被过滤的事实。
它记录命中与跳过原因、输入摘要、冲突裁决、预算截断和输出摘要，而不是暴露
原始角色记忆、其他项目资料或内部 handler 实现。

## 5. 动态字段、扩展语义与创作者治理

| 类型 | 能否参与正式结算 | 控制 |
| --- | --- | --- |
| 已注册核心字段 | 可以 | 稳定 schema 与 migrator |
| 扩展属性包 | 可以，但只被声明的规则读取 | 类型、范围、默认值、作用域、版本验证 |
| 叙事字段 | 不可以 | 只供记忆、文本与表现消费 |
| 未识别候选字段 | 不可以 | proposal/review 队列 |

新标签、新物质、新 effect 或新规则的控制面流程是：

```text
draft -> schema/graph/conflict validation -> preview simulation
-> replay oracle -> editor review -> admin signature
-> staging/canary -> scheduled activation -> audit
```

`reader` 可读取已授权的 schema、已发布 definitions 和过滤后的命中解释；
`editor` 可创建定义草案、运行验证与模拟；`admin` 才能发布、启用、迁移、回滚。
任何角色都不能导出内部 handler、修改 production semantic snapshot 或篡改事件。

definition revision 一经被正式事件、存档或已发布包引用，不得原地删除或修改
语义。弃用使用 `retired` 状态，新 revision 使用显式 alias/migrator，并在
activation 前验证历史事件、projection 和内容包兼容性。包 namespace 归项目
所有，跨包复用必须声明版本范围与导出权限，避免两个作者把同一 tag 名称解释成
不同规则。

## 6. 性能与可解释性

发布时扁平化标签继承并编译 selector index；运行时按 entity/component 维护带
revision 的 semantic snapshot cache。高频普通移动、基础资源消费可走 fast path，
复杂材料、环境、跨域或高叙事事件回退通用路径。两者都输出标准化 facts、rule hit
summary 和 explanation digest；只有需要多领域 event mapping 的新增 adapter 才另行输出
预提交 `SettlementPlan`。

缓存的 key 至少包含 entity revisions、semantic registry revision、active ruleset、
policy/civilization revision 与 environment context。输入或 revision 变化立即失效；
司命预测只能预热 cache，不能预先提交结果。

## 7. 验收样板与实现顺序

第一条样板使用“霜冻农田”或“火焰橡木门”：

1. 注册实体、组件、材料/物质、性质、状态、effect 和规则；
2. 提交环境或行动 intent，生成 `PhysicalFact`/`LogicalFact`；
3. 固定 semantic snapshot，解析 effect、抵抗、优先级与链式影响；
4. 生成跨域 `SettlementPlan`，由 `planned` coordinator 或该 V0 的领域 transaction
   adapter 映射事件后，仍通过既有 `GameplayEventStore.append_batch` 原子提交；
5. 检查实体、经济、生存、任务、角色记忆和 Godot 各自过滤投影；
6. 验证成功、拒绝、冲突、循环截断、重复命令、full replay、checkpoint + tail。

只有这条样板通过后，才扩大到 Econ-1、完整战斗、炼金、文明树或大规模经济。
