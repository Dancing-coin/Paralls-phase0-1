# 调度、跨域结算与回放接入指导

状态：`INF-2 的 construction、Survival、Ecology 与 Economy event-derived obligation 闭源行已验证；已验证共享的事件重放/受预算 due 读视图，但它不创建 scheduler 或 writer；既有 Economy account ledger 与 fixed simple-debt settlement 均已补 formal envelope/plan/append spine；三个 owner-specific activation pending merge 已验证，其中 Survival expiry 已验证 cold/dehydrated/overheated 三条 closed row；通用跨域 lifecycle 与 generic activation-obligation binding 仍未完成`

现有 `world_runtime/scheduling.py` 仍只处理角色唤醒、cadence 和人口负载选择；P2/P3
另有受限经营窗口、world mode、pause/resume、obligation evaluation 和 catch-up 实现。
它已有唯一显式 `SimulationClock` 和 fragment-based coordinator，但仍不是完整的
事件派生通用义务 lifecycle、经济/生存周期结算或跨域 policy closure。
下列内容只是需要进入正式 spec/plan 的扩展清单，不是新 runtime 授权。

## 1. SimulationClock

最小候选契约需要能够表达：世界当前 tick 与日历/暂停政策；一项周期义务的主体、
到期点、来源 revision、幂等键和处理状态。具体名称、存储和调度算法应由正式设计
决定，不能在分析文档中固化。

生产完成、需求衰减、工资、租金、税期、报价重算、许可证过期、状态恢复和
任务期限都转换为 scheduled obligation。调度器必须限制 catch-up，避免停服后
一次性结算导致世界跳变。

## 2. 消费模式接入边界

游戏、持续模拟和推演三种消费模式的产品语义与角色激活策略由
[世界消费模式与群体模拟指导](14-群体模拟世界模式与文明演进.md) 负责。本文件只
约束它们如何复用既有事件/revision/回放脊柱：模式不能创建第二套事实模型、时钟、
角色副本或提交路径。角色激活必须以同一角色记录为根，并在批量写入与交互写入之间
使用 revision 检查和幂等合并。

## 3. 跨域结算协议

下列是 `planned` 的多领域调度/结算 adapter 约束。现有已落地的领域 authority 继续
直接构造事件并调用 `GameplayEventStore.append_batch`，不要求先经过新的 coordinator。

```text
scheduled command -> read pinned projections -> optional SettlementPlan (pre-commit)
-> validate domains and map domain events -> GameplayEventStore.append_batch
-> committed outbox -> projectors -> mirror/audit
```

提案固定各域 revision 和 ruleset；任一域 revision 冲突、权限不足、资源不足、
证据失效或 policy 过期，都必须零部分提交。任何将来接口的结果至少要能关联
committed event、投影摘要、结构化拒绝和审计引用。

## 4. 事件与回放

所有已实现玩法域沿用 store-first、bus-second：先提交 canonical event，再由 outbox
分发。checkpoint + tail replay 必须得到与 full replay 相同的已实现投影 hash；未来的
技能、关系、任务、设施、税务和组织投影分别在其独立 spec/plan 完成后加入该要求。
revision 迁移只能调用受信任 migrator，不能在 replay 中执行任意创作者代码。

## 5. NPC 批量运行

规则层处理常规采购、休息、库存补货和税期；计划层按小时/日批量生成意图；
心智层只处理冲突、谈判、机会和剧情高光。批量计划仍须经过同一 authority，
因此“NPC 很聪明”不能成为绕过约束的理由。
