# 实体档案与因果接入指导

状态：`INF-1 event-derived entity/causal projection implemented and verified; domain-complete causal settlement remains planned`

## 1. 定位：接入既有世界基础设施

玩法目录已按具体游戏领域拆分，但这些领域若没有共同的世界本体和因果语言，
最终会退化成互相直接写状态的模块。本文件描述的是对既有 `world_runtime` / ESM /
`raw_fact_event` / Gameplay authority 链的增量扩展：它不是另一个玩法域，也不是
并列运行时，更不应成为包罗一切的 ESM。

标签注册、继承、参数合并、规则执行相位和治理 contract 由
[00-标签体系与元规则引擎.md](00-标签体系与元规则引擎.md) 规范；本文件说明
它如何与实体档案、因果事件和领域 authority 接合。

```text
Entity records -> semantic snapshot -> effects/resistance -> meta-rules
-> SettlementPlan (pre-commit; only when a new cross-domain adapter needs it)
-> domain event mapping -> GameplayEventStore.append_batch
-> events/projections/presentation
```

## 2. 万物档案与领域投影

每个能被拥有、使用、损坏、生产、交易、继承或影响的对象应有稳定 identity。

```text
EntityRecord
  entity_id, entity_kind, type_tags, location_ref, event_refs, lifecycle

ThingRecord / EnvironmentRecord
  component_refs, property_refs, status_refs, ownership_ref, domain_projections

RelationshipRecord
  source_ref, target_ref, relation_kind, terms_ref, visibility

CausalEventRecord
  trigger_ref, causal_parent_refs, affected_entity_refs, observed_by
  rule_revision_refs, evidence_refs, settlement_refs
```

实体记录保存事实连接；经济、库存、建造、生存、任务等只保存自己的 projection。
例如农田更换所有者时，土地、作物、肥力和灾害历史不迁入角色档案；角色只保存
所有权引用。事件档案则记录谁触发了霜冻、影响了谁、哪些角色观察到它、使用了
什么规则以及后续产生了什么因果事件。

因果父子关系是 append-only event reference 的反向投影：新的因果事件只记录
自己的 `causal_parent_refs`，查询层再导出 children。不得在旧
`CausalEventRecord` 上维护可变 `causal_children` 列表，否则回放与分支会出现
历史被原地改写的假象。

## 3. 因果交互结算链

```text
ActionIntent
  -> PhysicalFact 或 LogicalFact
  -> SemanticEvaluationInput（固定源/目标/环境语义快照）
  -> EffectTemplateList
  -> MetaRule evaluation
  -> SettlementPlan（预提交）
  -> domain validation and event mapping
  -> GameplayEventStore.append_batch
  -> CausalEventRecord / projections / presentation
```

交易、生产、欺诈和社交承诺多从 `LogicalFact` 开始；挥剑、爆炸、火灾和采矿
多从 `PhysicalFact` 开始。二者在语义解析后汇合，因此不需要为战斗、经济和
建造各自建立一套最终状态写入协议。

已经落地的 inventory/economy/body/interaction 等 authority slice 继续保留“各自
读取事实 -> 校验 -> 直接构造事件 -> `append_batch`”的路径；并不是所有成功结算
都必须先落成一个独立 `SettlementPlan`。`SettlementPlan` 只服务于尚未收口完成、
需要跨语义/跨领域 event mapping 的新增 adapter。

## 4. 所有权与执行边界

INF-1 已从已提交 `GameplayEvent` 重建 Entity/Thing/Environment/Relationship 与
append-only CausalEvent dossiers，并有 checkpoint-tail 等价和零写入拒绝证明。受限
effect/resistance lifecycle、phase/conflict/chain-budget 元规则 trace 与语义 authority
到 `SettlementPlan`/event-store/outbox/scoped projection 垂直路径已经验证；完整跨域
owner 覆盖、通用规则语言与多领域 `SettlementPlan` 生成仍属于 `planned` 的闭源核心
收口目标；P1-P5 已验证 typed fact、evidence provenance、revision、权限投影和领域
事件映射的受限路径。当前入口仍是 `backend/app/world_runtime/*`、
ESM、`raw_fact_event`、现有 Gameplay Authority 与 `GameplayEventStore.append_batch`。
创作者能定义标签、材料、性质、状态、效应模板和声明式规则，但必须经 schema、
依赖、冲突、预算、模拟和签名发布 gate。Godot、角色智能体、司命和 MCP 只能提交
意图、事实证据或规则 proposal。

## 5. 第一条垂直样板

先实现“霜冻作用于农田”，因为它验证的范围比单纯扣血更广。这里的 V0 只是对既有
运行时路径的增量指导切片，不是新的并行 world loop：

```text
weather event -> farm EntityRecord -> crop/soil semantic snapshot
-> frost effect + resistance/meta-rules -> SettlementPlan
-> crop loss / land-value / food-price / owner-affect / aid eligibility
-> event causality / quest evidence / Godot presentation / replay
```

验收应包含成功、抗性减损、规则冲突、重复提交、checkpoint + tail replay、
过滤视图和同一事件在游戏/模拟/推演三种模式下的等价语义结果。
