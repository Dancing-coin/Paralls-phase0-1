# 第一阶段核心基建范围与依赖矩阵

状态：`phase-one foundation scope; non-authorizing until P1A spec and matching plan are approved`

本文件从八月分析中筛选真正跨玩法的核心基建，作为第一阶段工作台到正式 spec 的范围
依据。它不新增 runtime、event store、bus 或 scheduler，也不把建造、经济、生存、组织
或群体模拟领域误写成通用底座。

## 1. 筛选标准

只有同时满足以下条件的能力，才进入“核心基建”：

1. 至少两个结构不同的玩法都会依赖它；
2. 它定义跨边界的 identity、输入、结算、回放、权限或版本语义，而不是某个玩法的数值；
3. 它可以扩展现有 owner，不需要第二个事实源、总线、运行时或隐藏调度器；
4. 它能用 focused test、replay 和 Harness profile 证明；
5. 它不会把样板专用字段、NPC 状态或创作者界面细节塞进 core schema。

### 3.1 Reservation 是共享 contract，不是新 Authority

资源域已经实现了受限 reservation。第一阶段只抽象生命周期和值对象，继续让各 owning
authority 写自己的事实：

```text
proposal -> reserve
  -> consume/commit
  -> release | expire
  -> compensation fact when required
```

材料、工具、工资、税费、许可证、生产时段和生存消费都只能保存 reservation/obligation
引用；不能复制余额、库存数量或设施进度。

### 3.2 Creator Control Plane 的边界

第一阶段冻结 package、revision、compatibility、权限 projection 和 activation 的核心
contract，但不实现：

- UI list/checkbox；
- CLI/MCP 产品 API；
- reader/editor/admin 成员管理；
- 在线发布、分润和资产市场。

这些属于 Creator Control Plane 的独立 spec/plan。第一阶段只保证未来 UI、CLI、MCP
都必须调用同一受治理 contract，不能导入内部结算函数或直接追加 Production event。

## 4. 不进入核心基建的领域实现

| 领域 | 第一阶段位置 | 原因 |
| --- | --- | --- |
| Construction/Production | Econ-1 domain spec | 依赖 lot、reservation、skill、facility、organization，无法脱离样板确定完整语义 |
| Survival Authority | Econ-1 domain spec | 复用资源/身体/status/state-group，但需求、消费和后果属于领域事实 |
| Economy journal/quote/payroll/tax | Econ-1 domain spec | 现有经济是 primitive，不应提前宣称商业系统完成 |
| Organization/Government | Econ-1 domain spec | 岗位、预算、permit、inspection 和 policy 有独立 owner |
| Dynamic market/order book | 后置经济 spec | 第一阶段只需要固定 quote 和参数化公开 profile |
| Environment/ecology/disaster | V0 或后续 domain spec | 霜冻只验证 effect/resistance 和小范围环境事实，不实现生态模拟 |
| Knowledge/belief/rumor | 后续社会投影 spec | 不属于 P1 通用结算底座 |
| Population Simulation | 独立后续 spec | 当前没有人口 authority，不得生成 NPC canonical state |

## 5. 依赖图

```text
Existing Gameplay Foundation
  -> identity/reference/entity + causal
  -> semantic/effect/resistance + selector/query
  -> ActionIntent/PhysicalFact/LogicalFact
  -> Rule IR/proposal + Reservation/Hold
  -> SettlementPlan -> append_batch
  -> time/obligation/profile/revision pinning
  -> projection/privacy/evidence + package compatibility
  -> V0 contract sample
  -> Econ-1 domain authorities
  -> second heterogeneous sample
  -> Population Simulation (post-foundation)
```

依赖图中的箭头表示 spec/implementation 依赖，不表示要建立新的 runtime 层。每一项
新增代码都必须落回现有 `backend/app/gameplay/*`、world runtime/ESM、projection 或
已批准的领域 package。

## 6. 对 P1A/P1B 的回写要求

P1A formal spec 必须新增或明确引用：

1. ActionPrimitive、ActionIntent、PhysicalFact、LogicalFact 和 evidence envelope；
2. SemanticSnapshot、ActiveSemanticSet、ActiveWorldRevision 的关系；
3. Reservation/Hold 的状态机、owner 和失败语义；
4. world consumption profile 与 creator environment 的正交关系；
5. State-group/profile activation 的 ruleset revision 语义；
6. GameplayPackageManifest/domain-extension manifest 的 owner、生命周期、兼容性和迁移声明；
7. 对现有 embodied interaction、Patch、resource reservation 的复用证明。

P1B Harness 至少需要增加：

- action/fact 到 settlement 的成功、拒绝和证据链；
- reservation 重复、过期、释放和消费的幂等证明；
- profile 粒度变化不改变事件语义的 replay 证明；
- package dependency/schema/capability conflict 的 fail-closed 证明；
- state group disabled 时没有隐式 tick 或写入的证明。
