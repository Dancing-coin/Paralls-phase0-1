# 通用基础契约收口

状态：`planned closure guidance; reuses current authority substrate`

目标不是“先做完所有世界基础设施”，也不是为某个垂直样板拼出最小可用代码，而是
冻结一组跨玩法、跨领域、可扩展的最小稳定通用 contract。具体的基建筛选边界见
[第一阶段核心基建范围与依赖矩阵](06-第一阶段核心基建范围与依赖矩阵.md)。已实现的
Gameplay event/replay spine 不重复设计；新增能力必须挂接既有 owner。

“通用”有三个可检验含义：

1. 新领域只需增加 schema、authority、projection/package，不增加第二个 store、bus、
   runtime 或隐藏 scheduler；
2. 同一 identity、semantic/effect、causal、settlement、time、replay contract 能
   被不同结构的样板复用；
3. 样板专用字段不能渗入核心 schema，规则输入、结果和失败类型必须可固定 revision、
   可追踪、可迁移。

## 收口顺序

1. 固定 identity/reference、生命周期、tag/effect、causal parent、revision 和 evidence ref；
2. 固定 ActionPrimitive、ActionIntent、PhysicalFact/LogicalFact、selector/query、Rule IR、effect application
   的输入、失败类型和 deterministic trace；
3. 固定 Reservation/Hold 生命周期、`SettlementPlan -> domain event mapping -> append_batch`
   的边界，以及 obligation/tick 的幂等、重试和补偿语义；
4. 固定 world consumption profile、state-group/profile activation、ActiveSemanticSet 和
   package compatibility，不把 creator environment 当成 world mode；
5. 用至少两个结构不同的领域样板验证同一 contract，而不是只在 V0 内自证；
6. 才允许 Econ-1 依赖这些 contract，禁止先编写自己的规则解释器、影子状态或调度器。

## 完成定义

完成本文件不代表通用底座已经具备泛化能力。只有以下条件同时成立，才算通用契约
门禁通过：

- V0 的所有 canonical fact 都有明确 owner；
- 不新增平行 event store、L6 bus、L1 loop 或 scheduler；
- Rule/semantic 输入固定 revision，失败时零提交；
- online replay 与 checkpoint + tail replay 一致；
- actor、creator debug 和 Godot 只读取各自过滤 view；
- 至少两个异质样板复用相同 contract，且没有样板专用字段进入核心 schema；
- Action/fact、reservation/profile 和 package compatibility contract 可被样板复用；
- 新领域接入只增加 schema/authority/projection/package，不新增 store、bus、runtime 或隐藏 scheduler；
- 有对应正式 spec、plan、focused tests 和 Harness report。
