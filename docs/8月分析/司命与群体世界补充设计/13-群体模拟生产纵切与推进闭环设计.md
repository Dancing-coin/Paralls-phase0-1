# 群体模拟生产纵切与推进闭环设计

状态：`proposed; one vertical formalization input; analysis/design only; no runtime authorization`

本文件补充“群体模拟如何真正推进世界”的最小生产纵切。它不把司命变成第二个
世界真相 owner，也不把群体 planner 限制成只会生成报告，而是明确一条可以被正式
合同、测试和 Harness 验证的闭环：

```text
授权 projection
  -> 群体批次计算
  -> owner-bound intent
  -> 静态 capability admission
  -> 领域 owner settlement
  -> 正式 world event / owner receipt
  -> scoped projection
  -> 群体下一轮与角色连续性种子
```

本文件选择“计划门控的供应承诺（`schedule_gated_supply`）”作为第一条生产纵切。
它复用现有组织排程、供应候选、activation pending 和 owner receipt 方向，不声称
已经拥有通用粮食、人口或社会真相 owner。霜冻、干旱等生态事实可以作为这条纵切的
上游压力来源，但必须先经过已准入的生态/组织 consumer contract，不能把生态聚合
结果直接当作供应事实。

这条纵切的证明目标是“群体模拟可以通过既有领域 owner 推进一个真实生产 vertical”，
不是证明粮食库存、价格、农业产量、人口迁移、社会传播或文明演化已经完成。后续
vertical 必须逐条取得自己的 owner contract，不能从本纵切推导通用世界写入权。

## 1. 要解决的要求

第一条纵切必须同时证明：

1. 玩家不在场时，批次仍能按已提交 cadence 运行；
2. 批次结果能够改变生产世界，而不绕过领域 owner；
3. owner 拒绝、版本过期和重复提交不会产生部分写入；
4. owner receipt 能回流到下一轮 projection 和群体计划；
5. 受影响角色能获得最新动态状态和带暴露依据的记忆种子；
6. 角色激活后，只有 Character Core 能把合格候选物化进五池；
7. full replay 与 checkpoint-tail replay 得到同一派生结果；
8. 失败恢复不会把 candidate、branch 或 preview 提升为生产事实。

## 2. 纵切边界

### 2.1 生产对象

```text
输入：已提交的组织 schedule projection、家庭/角色公开投影、cadence projection
行为：计算一个固定窗口内是否需要供应承诺
生产写入：由 OrganizationAuthority 结算既有 commerce commitment owner fragment
派生输出：组织 projection、群体下一轮输入、角色 runtime state delta、SeedDelta
```

第一版只允许固定的 `supply` intent。调用方不能把 `intent_kind` 改成任意工作、
交易、人口或关系动作；未知类型必须 zero-write。

### 2.2 不在纵切内的内容

- 不新增 `SimulationClock`、scheduler、event store、bus 或 generic writer；
- 不把“区域缺粮压力”直接写成库存、价格或人口事实；
- 不自动创建人口、迁移、社会关系或文明状态 owner；
- 不把霜冻预测、模型判断或表现结果当成已结算事件；
- 不在远场逐角色运行完整 LLM；
- 不让司命直接选择目标 stream、event family 或 owner。

后续纵切顺序建议为：

```text
1. schedule_gated_supply -> OrganizationAuthority
2. weather:frost -> 已准入 Survival cold consumer
3. 生态/资源 projection -> 已准入 Economy 或 Production consumer
4. scoped propagation -> 角色 Observation/Knowledge candidate
```

每条纵切都必须独立完成 source、capability、owner、event、receipt、replay、privacy
和角色连续性验收；未完成的纵切保持 `blocked` 或 zero-write。

## 3. 参与者和 owner

| 参与者 | 负责什么 | 明确不负责什么 |
| --- | --- | --- |
| World/Environment owner | 提供已提交的天气、生态和区域 projection | 不接受群体 planner 任意写入 |
| OrganizationAuthority | 校验并结算组织排程/供应承诺 | 不接受 caller 自选 event family |
| PopulationPlanner | 选择 cohort、冻结输入、计算 `supply` candidate | 不追加生产世界事件 |
| Siming | 读取授权态势、设置叙事/激活优先级、提交受治理意图 | 不读取原始私有记忆、不直接 append |
| Character Core | 结算角色连续性状态、验证 memory candidate、物化五池 | 不改变客观组织或生态事实 |
| GameplayEventStore | 追加 owner 已批准的正式事件并支持回放 | 不替 caller 选择 owner 或业务结果 |

## 4. capability 与 owner contract 草案

这不是运行时注册表，而是未来应进入既有 immutable
`GovernedAuthorityContractCatalog` 的一个静态 admission entry。具体名字和字段在
formal spec 阶段必须与现有 catalog 对齐。

| 字段 | 第一版约束 |
| --- | --- |
| `capability_id` | 复用既有 `activation-binding:schedule-gated-supply:v1`，不得运行时注册新 entry |
| `caller` | PopulationPlanner / Siming guarded execute |
| `target_owner` | `actor_gameplay.organization_domain` / `OrganizationAuthority` |
| `intent_kind` | `supply`，closed enum |
| `source_projection` | 冻结的 organization schedule + household/social scoped input |
| `source_event_vector` | 本批次固定的 owner event vector |
| `expected_revisions` | organization projection 与 mode/policy revision 必须匹配 |
| `target_stream` | 由冻结的既有 owner plan 解析为 `gameplay:organization:{organization_ref}` |
| `event_family` | 仅允许 `gameplay.organization.commerce_commitment_accepted` |
| `idempotency` | `intent:{batch_ref}:supply`，重复消费返回同一 receipt |
| `privacy` | 仅使用 caller 被授予的 actor/organization scope |
| `receipt` | append-derived `SettlementReceipt`，包含 event refs、revision 和 digest |
| `failure` | `capability_not_admitted`、`stale_read_set`、`owner_rejected`、`idempotent_replay` |

调用方提交的 payload 只包含业务允许的 typed fields，例如 organization、counterparty、
commitment、schedule work order 和 source refs。调用方不得提交 `stream_id`、任意
`event_type`、最终库存数或“已成功”标志。

## 5. 批次前、中、后

### 5.1 批次前：冻结输入和权限

批次必须固定：

```text
world_mode_ref/revision
cadence_source_ref/revision
base_checkpoint
tail_boundary
source_revision_vector
policy_revision
selector_revision
deterministic_seed
budget
report_scope
```

然后执行以下检查：

1. cadence 来自已提交 projection，而不是墙钟或模型自行决定；
2. source vector、scope 和 policy revision 未过期；
3. cohort 成员来自可见的角色/家庭/组织引用；
4. capability entry 存在且 catalog revision 匹配；
5. 当前批次没有同一 `intent_ref` 的已消费 receipt。

任何检查失败都产生审计记录和 `no_op/requeue`，不产生生产 append。

### 5.2 批次中：计算候选而不是宣称事实

PopulationPlanner 对冻结输入运行确定性规则，得到：

```text
BatchReport
  - selected_cohort
  - source_digest
  - schedule_pressure
  - candidate_order
  - budget_usage
  - selector_revision

BatchIntentCandidate
  - intent_ref
  - intent_kind = supply
  - organization_ref
  - commitment_ref
  - schedule_work_order_ref
  - expected_revisions
  - idempotency_key
  - privacy_scope
```

候选仍不是世界事实。司命可以编辑候选优先级、叙事解释和 activation hint，但不能
把候选文本改成“供应已经完成”。

### 5.3 批次后：准入、结算和回流

生产执行必须按以下顺序进行：

```text
candidate
  -> capability admission
  -> GameplayCommandEnvelope
  -> SettlementPlan
  -> OrganizationAuthority.validate
  -> OrganizationAuthority.settle
  -> GameplayEventStore.append_batch()
  -> append-derived receipt
  -> outbox / scoped projection
```

只有 `receipt.status = committed` 时，组织状态才可以进入下一轮群体输入。

成功后记录。组织 owner 的 revision 必须保留为分域向量，不能把一次组织 receipt
误当成所有角色游标都已推进：

```text
owner_revision_vector["organization"]     = receipt.to_revision
projection_revision_vector["organization"] = receipt.to_revision
last_receipt_ref   = receipt.receipt_ref
source_digest      = receipt.source_digest
```

失败后的处理：

| 结果 | 允许动作 | 禁止动作 |
| --- | --- | --- |
| `stale_read_set` | 丢弃候选，基于新 projection 重算 | 用旧 revision 强行 append |
| `owner_rejected` | 记录拒绝原因，按 policy requeue 或终止 | 换 owner 或换 event family 重试 |
| `idempotent_replay` | 返回原 receipt，不重复写入 | 追加第二份相同事实 |
| `capability_not_admitted` | 记录 zero-write 审计 | 动态注册 capability |
| 进程/模型超时 | no-op、B0 降级或 requeue | 把超时转换成默认成功 |

## 6. receipt 如何驱动下一轮和角色连续性

owner receipt 回流后分成三条派生路径：

```text
receipt
  -> Organization scoped projection
  -> Population next-batch input
  -> CharacterSimulationSeed / continuity checkpoint
```

### 6.1 群体下一轮

下一批只能读取 receipt 已确认的 projection。候选、拒绝理由、旧读集和 branch 结果
不能作为生产事实输入。

### 6.2 角色动态状态

受影响角色的有效投影由 Character Core 生成一个带 owner receipt 引用的状态增量，例如：

```text
state_delta:
  supply_pressure += 0.08
  current_goal_hint = "确认家庭供应安排"
  obligation_pressure += 0.05
```

这个状态增量不是司命直接写角色 runtime store；它进入角色连续性结算路径，经过
角色 revision、幂等和 checkpoint 校验后物化。

### 6.3 记忆候选

只有满足角色暴露条件的候选才能进入 SeedDelta：

```text
memory_candidate:
  candidate_kind = event_experience | factual_knowledge | observation
  source_receipt_ref
  exposure_basis
  visibility
  valid_at / recorded_at
  materialization_policy = on_activation
```

例如，直接负责供应安排的角色可以得到 Event Memory 候选；只看到公开排队的角色
只能得到 Observation Memory 候选；没有观察、告知或直接后果的角色没有候选。

### 6.4 Character Core 连续性结算

世界 owner receipt 不能直接写角色 runtime store 或五池。角色连续性必须经过单独的
Character Core typed settlement：

```text
Organization owner receipt
  -> Character Continuity Settlement
  -> Character Core revision/idempotency/exposure check
  -> runtime state update
  -> SeedDelta append
  -> character continuity receipt
  -> activation-time five-pool materialization
```

最小逻辑 contract 为：

```text
character_ref
source_owner_receipt_ref
expected_character_revision
state_delta
memory_candidate_refs
visibility / exposure
idempotency_key
```

司命和 PopulationPlanner 只能提交候选或请求这条结算，不能直接 append `SeedDelta`。
Character Core receipt 成功后，才允许推进角色的 `state_cursor` 或
`experience_cursor`；五池物化成功后才推进 `memory_cursor`。

## 7. 从霜冻到供应的示例

### 7.1 上游事实

环境 owner 已提交：

```text
evt:frost:101
region_ref = region:north
crop_projection_revision = 14
visibility = public
```

群体模拟只能读取这条事实及其授权 crop/schedule projection。它不能把“霜冻会导致
缺粮”直接写入 Economy 或 Organization。

### 7.2 形成供应候选

固定窗口内，PopulationPlanner 发现 bakery 组织的排程和供应承诺受到影响，产生：

```text
intent_kind = supply
organization_ref = org:bakery
commitment_ref = commitment:batch-101
schedule_work_order_ref = work:bread
expected_revisions = {organization: 23, mode: 7}
idempotency_key = intent:batch-101:supply
```

### 7.3 owner 结算

OrganizationAuthority 校验组织状态、排程窗口、版本和幂等键。通过后由 owner 追加
`gameplay.organization.commerce_commitment_accepted` 到
`gameplay:organization:{organization_ref}` 并返回 receipt；失败则保持 zero-write。

### 7.4 角色连续性

receipt 回流后，直接负责烘焙或家庭供给的角色获得状态增量和经历候选；远处没有暴露
的角色不因为司命知道霜冻而自动知道供应承诺。角色激活时，Character Core 再把合格
候选分别物化为 Event、Observation 或 Knowledge Memory。

### 7.5 下一轮

下一批读取新的 organization projection。如果 owner 后续撤回或补偿，系统追加
supersession/retraction，重算派生计划；已经形成的角色主观记忆保留历史并追加更正，
不静默删除。

## 8. 纵切验收门

进入实现前，必须为本纵切建立正式 spec、plan、focused tests 和 Harness，至少验证：

1. 未知 `intent_kind` zero-write；
2. caller 不能选择 stream/event/owner；
3. stale source、scope 扩大和 catalog mismatch zero-write；
4. 成功 settlement 只有一个 append-derived receipt；
5. 重复 idempotency key 不产生第二份事件；
6. owner rejection 不更新下一轮 projection；
7. full replay 与 checkpoint-tail replay digest 一致；
8. receipt 能驱动下一批读取和角色 SeedDelta；
9. 无暴露角色不产生 memory candidate；
10. Character Core 激活前五池不被司命或 planner 写入；
11. LLM 超时只产生 no-op/requeue，不产生事实；
12. 失败恢复不提升 candidate/branch/preview；
13. fixed seed、budget 和 selector revision 下候选顺序可重现；
14. batch、owner settlement、projection、seed 和 activation trace 可以串成一条审计链。

建议 Harness profile：

```text
population-schedule-gated-supply-owner-loop
```

## 9. 推进闭环的完成定义

本纵切只有在以下条件全部满足后，才能称为“群体模拟能够通过 owner 推进一个生产
vertical”：

```text
同一批次输入可重放
  + 候选经过静态 capability admission
  + 领域 owner 真正结算并 append
  + receipt 回流到 projection
  + 下一批消费新 projection
  + 角色状态和记忆种子按权限更新
  + replay、privacy、idempotency、rejection、recovery 证据齐全
```

这只是第一条窄纵切。它不等于已经完成完整人口、社会、文明或任意跨域模拟。后续
每一条 vertical 都必须复制同样的 owner contract、receipt、回放和角色连续性门禁。
