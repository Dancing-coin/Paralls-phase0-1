# 角色模拟记忆种子与连续性设计

状态：`proposed future-mainline amendment; analysis/design only; no runtime authorization`

本文件把“个人种子”正式化为角色连续性协议，解决以下问题：

1. 群体模拟能够推进角色离线期间的最新状态；
2. 有意义的离线经历不会丢失；
3. 司命和群体模拟不直接读写角色五池记忆；
4. 角色激活后不会提前知道不应知道的内容；
5. 所有变化可按时间、来源、版本和隐私范围回放；
6. 记忆运行不依赖逐角色、逐 tick 的大模型调用。

本设计对应正式 contract：

- `docs/superpowers/specs/world-character-siming-authority-mainline/2026-08-22-character-simulation-memory-seed-continuity-design.md`

本文件是中文整体设计和分析入口，不单独授予实现权限。

## 1. 核心决策

“个人种子”不设计成一个可以被司命反复覆盖的大 JSON，而设计成：

```text
角色模拟种子 = 追加式增量账本 + 最新连续性快照
```

完整链路为：

```text
群体模拟输入
  -> SeedDelta
  -> 已准入的世界/玩法 owner 结算（如有）
  -> 角色 runtime state 物化
  -> 角色经历账本
  -> 连续性 checkpoint
  -> 激活时五池记忆物化
```

三项目标同时成立：

| 目标 | 实现方式 |
| --- | --- |
| 行为连续性 | 动态状态和当前角色投影在模拟结算后立即更新 |
| 记忆连续性 | 有意义的经历先保存为带证据的 memory candidate，激活时进入五池 |
| 可审计回放 | 增量不可变、带来源/版本/游标/digest/receipt，可重算和修正 |

## 2. 真相与 owner 边界

### 2.1 三类 owner

| 数据 | owner | 允许的操作 |
| --- | --- | --- |
| 客观世界/玩法事实 | 对应世界或领域 authority | 结算、提交、回放、投影 |
| 角色主观五池记忆 | Character Core / Character Agent runtime | 读取、验证、物化、修正、压缩 |
| 模拟候选和调度信息 | Siming / Population derived layer | 生成候选、记录审计、请求激活 |

大模型不是 memory owner。大模型最多产生摘要、显著性、主观解释或 L2
delta 候选，最终写入权仍属于 Character Core。

### 2.2 静态档案与最新角色画像

群体模拟不能直接修改 authored dossier。角色的“最新”应拆成：

```text
authored profile truth
  + long_term_personality_drift_layer（通过晋升闸门）
  + 当前 domain projection
  + runtime state
  = effective character view
```

因此：

- 姓名、起源、人格 baseline、价值红线等 authored truth 保持原 revision；
- 长期人格变化进入 drift candidate，满足证据门槛后形成新的 overlay revision；
- 当前职业、家庭、组织、资产等由各自 domain projection 提供最新状态；
- 需求、情绪、张力、目标、身体和当前义务属于 runtime state，模拟结算后应立即物化。

### 2.3 禁止的 owner 合并

不能因为司命看到了某条世界事实，就让角色自动知道；不能因为群体模拟生成了
候选，就让世界事实自动成立；不能因为角色形成了主观记忆，就反向覆盖客观事实。

```text
世界事实 != 角色知识
角色知识 != 司命全局知识
模拟候选 != 已结算事实
五池记忆 != 世界真相
```

## 3. 角色模拟种子对象

### 3.1 `CharacterSimulationSeed`

这是逻辑 contract，不是新的通用 store。实现必须复用 Character Core、既有
population continuity、GameplayEventStore、既有 checkpoint/tail replay 和领域 owner。

```text
CharacterSimulationSeed
├── seed_id
├── schema_revision
├── actor_ref
├── world_ref
├── from_tick / to_tick
├── base_checkpoint_ref
├── base_revision_vector
├── source_event_refs
├── source_scope
├── ruleset_revision
├── selector_revision
├── model_revision（可选）
├── deterministic_seed
├── state_deltas
├── memory_candidates
├── drift_candidates
├── activation_hints
├── presentation_seed（可选、可丢弃）
├── owner_receipt_refs
├── visibility_scope
├── privacy_disposition
├── apply_status
├── cursor_vector
├── result_digest
├── idempotency_key
├── supersedes / superseded_by
└── recorded_at
```

规则：

- schema 必须 closed，未知字段拒绝；
- seed delta 追加后不可原地编辑；
- 修正通过新记录表达；
- `presentation_seed` 只用于表现或预热，不能进入世界事件流；
- `activation_hint` 只改变调度优先级，不改变角色记忆；
- `owner_bound_intent` 必须映射到既有静态 capability 和对应 owner。

### 3.2 `MemoryCandidate`

`MemoryCandidate` 是“角色可能经历了什么”的受治理候选，不是五池记录。

```text
MemoryCandidate
├── candidate_id
├── actor_ref
├── candidate_kind
├── source_event_refs
├── event_valid_at
├── event_recorded_at
├── knowledge_available_at
├── exposure_basis
├── summary
├── subject_ref / target_ref（可选）
├── confidence
├── salience
├── visibility_scope
├── privacy_disposition
├── materialization_policy
├── dedup_key
├── source_revision_vector
├── branch_ref（可选）
├── status
└── provenance_digest
```

`candidate_kind` 只能取以下值：

```text
event_experience
perceptual_observation
factual_knowledge
social_impression
higher_order_belief
```

### 3.3 角色连续性游标

不能只保存一个 `last_simulation_tick`。每个角色至少维护四个游标：

```text
ContinuityCursor
├── owner_cursor
├── state_cursor
├── experience_cursor
└── memory_cursor
```

例：

```text
owner_cursor      = 120
state_cursor      = 120
experience_cursor = 120
memory_cursor     = 97
```

这表示当前状态已经追到 tick 120，但 98-120 的经历还未物化到五池；不能把
角色标记成“所有记忆都最新”，但也不能把 runtime state 回退到 97。

### 3.4 连续性 checkpoint

```text
ContinuityCheckpoint
├── actor_ref
├── checkpoint_sequence
├── as_of_tick
├── cursor_vector
├── authored_dossier_ref / revision
├── effective_profile_revision
├── runtime_state_snapshot
├── pending_memory_count
├── open_conflict_refs
├── source_revision_vector
├── ledger_digest
└── recorded_at
```

checkpoint 是恢复加速视图，不替代增量历史和生产 replay。

## 4. 五池物化规则

Character Core 在物化前必须重新执行 visibility、exposure、时间、revision、
dedup 和 branch scope 检查。

| 候选 | 允许物化到 | 最低证据 |
| --- | --- | --- |
| `event_experience` | Event Memory | 角色参与、承受或收到 owner 确认的后果 |
| `perceptual_observation` | Observation Memory | 角色在当时的空间、时间和感知通道内可观察 |
| `factual_knowledge` | Knowledge Memory | 观察、告知或有范围的传播 |
| `social_impression` | Social Memory | 角色自身互动或收到有效的他人信息 |
| `higher_order_belief` | Higher-Order Memory | 明确证明“谁知道什么”的沟通/观察证据 |

同一世界事件对不同角色可以产生不同候选，也可以没有候选。

### 4.1 Event Memory

表示“我经历或承受了某事”，不表示世界上发生过某事就足够。

```text
世界事件：粮食短缺
农民 char_a 受到库存损失 -> Event candidate
远处的 char_b 没有接触 -> 无 Event candidate
```

### 4.2 Observation Memory

必须提供：

```text
place_ref
time_window
visibility_channel
distance/hearing/public_scope
```

司命全局读模型不能直接变成角色观察。

### 4.3 Knowledge Memory

必须保留来源和置信度：

```text
source_kind = observed | told | propagated | inferred
confidence
disclosure_ref
```

角色可以知道、怀疑、误解或完全不知道同一客观事实。

### 4.4 Social Memory

Social Memory 是有方向的 actor-private 认知：

```text
char_a -> char_b
trust_delta
suspicion_delta
obligation_hint
evidence_refs
```

它不能创建或撤销客观雇佣、债务、产权或关系事实。

### 4.5 Higher-Order Memory

只能在有明确证据时记录：

```text
char_a believes char_b knows event_x
```

司命知道 event_x，不等于 char_a 知道 char_b 知道 event_x。

### 4.6 物化流程

```text
SeedDelta
  -> 候选 visibility/exposure 校验
  -> 事件 settlement 和时间校验
  -> 去重/冲突校验
  -> Character Core typed writeback candidate
  -> 选择一个合格五池
  -> materialization receipt
```

修正通过 `superseding` 或 `retraction` 追加记录，不能静默删除角色已经形成的
主观记忆。

## 5. 历史记录可见性

历史可见性是记录字段，不是 UI 最后再做的过滤。

### 5.1 四层历史

1. **Simulation Ledger**：批次输入、规则、source vector、结果 digest、receipt 和状态。
2. **Character Experience Ledger**：角色相关的模拟经历和待物化候选。
3. **Five-Pool Memory**：角色私有主观记忆。
4. **Public/Player History Projection**：公开、玩家观察或明确授权的摘要。

其中前两层是逻辑记录，必须复用现有 owner、timeline、event/replay 或 projection
边界，不得建立一个能绕过权限的万能历史库。

### 5.2 可见性 scope

```text
public
actor_observable
actor_private
authority_only
siming_internal
branch_only
```

每条历史至少携带：

```text
valid_at
recorded_at
source_owner
redaction_state
materialization_status
source_event_refs
```

禁止以下提升：

```text
siming_internal -> character knowledge
branch_only -> production memory
authority_only -> actor social memory
raw actor_private -> Siming
```

### 5.3 各读取者看到什么

| 读取者 | 允许读取 |
| --- | --- |
| Character Core | 本角色授权的完整连续性记录和五池 |
| 角色激活上下文 | 相关 runtime state、检索到的记忆卡片和当前事件 |
| Siming | 公开事实、授权 projection、脱敏 seed history、owner receipt |
| 其他角色 | 自身实际观察到或被传播到的内容 |
| 玩家 | 玩家观察到的事实、公开事件和授权叙事摘要 |
| 审计系统 | 按权限读取完整 provenance、修正链和 replay digest |

同一事件可以有不同合法视图：世界事实、角色 A 的主观记忆、司命脱敏摘要、玩家
公开投影互相关联但不能互相替代。

## 6. 时间、版本与合并

每个批次固定：

```text
from_tick / to_tick
base_checkpoint_digest
base_revision_vector
ruleset_revision
selector_revision
deterministic_seed
```

如果来源或目标 revision 已变化：

```text
stale_read_set
-> 不做部分合并
-> 保留候选和审计
-> 重新计算
```

### 6.1 字段级合并策略

| 字段族 | 合并规则 |
| --- | --- |
| affect、pressure、fatigue | 按事件顺序重算或 CAS 替换 |
| counters | 绑定 source event 的幂等增量 |
| sets/tags | 带 provenance 的 union |
| goals | 追加目标转移事件，再重建当前视图 |
| drift | 累积 candidate，达到门槛后 promotion |
| memory candidates | source event + dedup key 去重 |
| presentation seed | 可重建、可丢弃 |

禁止使用“所有数字相加、所有列表追加”的通用兜底。

### 6.2 激活合并顺序

```text
获取 activation lock
  -> 补算 owner/state cursor
  -> 记录 experience tail
  -> 物化符合条件的 memory candidate
  -> 推进 memory cursor
  -> 生成 checkpoint
  -> release/requeue
```

激活期间发生玩家交互时，玩家路径使用新 base revision；旧模拟增量如有冲突，进入
requeue，不强行叠加。

## 7. 司命 RWEE 权限矩阵

| 能力 | 司命允许 | 司命禁止 |
| --- | --- | --- |
| Read | scoped world projection、公开事件、脱敏 seed history、owner receipt | 原始五池、私有关系图、隐藏知识状态 |
| Write | 追加 SeedDelta、memory/drift candidate、audit、activation hint | 五池记录、runtime store、world truth |
| Edit | 新的规则、selector、候选或解释 revision | 编辑锁定事实、改写历史、删除 receipt |
| Execute | 静态准入 capability、请求 Character Core 物化 | 任意选择 owner/stream/event、直接调用 memory store/Godot |

Population planner 使用相同或更窄的候选权限，不能借群体规模扩大司命 read scope。

## 8. 角色记忆 owner 与 LLM

### 8.1 owner 不由大模型承担

Character Core / memory writeback policy 负责：

- exposure、privacy、temporal eligibility；
- 候选 schema 校验；
- 去重、冲突、修正和 materialization；
- 五池选择和持久化；
- cursor、checkpoint、replay 和 compaction。

大模型不能拥有 append、merge、correction、compaction 或 replay 权限。

### 8.2 LLM 的可选职责

```text
B0 基线行为       规则，0 次 LLM
B1 局部反应       规则或小模型
B2 关系协商       必要时使用受限模型
B3 高价值事件     完整 LLM，使用 scoped context
```

LLM 可以提出：

- 记忆摘要；
- 显著性；
- 主观解释；
- L2 belief/social/higher-order delta。

但输出必须标记为 `untrusted proposal`，由 Character Core 再校验。

模型 prompt 只包含：

```text
当前 runtime state
相关记忆卡片
当前事件
授权关系摘要
```

不把完整五池历史、司命内部信息或其他角色私有记忆传给模型。

## 9. Token 与性能控制

token 爆炸的根因不是“记忆有五池”，而是把所有历史逐 tick 全量序列化给模型。

采用四级运行层：

```text
L0 Canonical Ledger   来源和 receipt，不进入 token
L1 Typed Memory       五池结构化记录，不进入 token
L2 Retrieval Cards    按场景/关系/显著性检索少量卡片
L3 LLM Context        只发送当前相关的 top-k 卡片
```

普通远场角色不逐 tick 调用 LLM。低价值状态使用规则和结构化 delta；只有重大事件、
玩家交互、关系冲突和长期人格信号才升级到模型。

## 10. 生命周期、checkpoint 与压缩

SeedDelta 生命周期：

```text
generated
-> admitted
-> owner_settled
-> state_materialized
-> experience_recorded
-> memory_pending
-> memory_materialized
-> checkpointed
-> compacted
```

异常状态：

```text
rejected
requeued
stale
privacy_denied
superseded
retracted
```

### 10.1 可压缩内容

已 owner 结算、已更新 runtime state、已记录经历、已物化五池、没有冲突且不再被
branch/replay 引用的低价值变化，可以 rollup 到 checkpoint。

压缩摘要必须保留：

```text
source tick range
state before/after
source event range
ruleset revision
original digest
compaction policy
```

### 10.2 不可丢弃内容

- 未物化的高显著候选；
- 未解决冲突；
- 隐私保留期内的记录；
- 玩家可见或审计要求的记录；
- 仍被 branch 引用的记录；
- 尚未完成 drift promotion 的证据。

## 11. 泄露风险与防护

### 11.1 提前知道未来

候选必须满足：

```text
knowledge_available_at <= actor_current_tick
```

未来事件、预测结果、分支结果和司命内部推断只能成为 activation hint 或内部审计，
不能成为角色 Knowledge Memory。

### 11.2 全局事实变角色知识

每条候选必须有 `exposure_basis`：

```text
observed_directly
heard_from_actor
public_propagation
authority_disclosure
affected_directly
```

没有暴露证据，Character Core 拒绝物化。

### 11.3 聚合结果反推隐私

cohort 结果不得通过单人、稀有身份或唯一事件暴露私密信息。需要使用既有 scope、
最小聚合阈值、脱敏摘要和 branch/production 隔离。

### 11.4 LLM 上下文泄露

模型只接收 actor-scoped retrieval cards；任何 raw actor-private memory、hidden truth、
Siming internal signal 或其他 actor private evidence 都必须在 prompt 构建前被过滤。

## 12. 记忆种子的明确作用与整体运转示例

### 12.1 记忆种子到底是什么

记忆种子是**群体模拟和角色智能体之间的受治理连续性中间态**。它把离线模拟
产生的三类信息分开保存：

```text
已结算的角色状态变化
有来源但尚未物化的角色经历
仍需激活或高精度处理的候选提示
```

它的作用不是替代五池，也不是让司命获得角色记忆权限，而是解决远场模拟和近场
角色之间的三个断点：

1. **状态断点**：角色离线期间的疲劳、压力、目标、职业和当前义务不能丢失；
2. **经历断点**：角色经历了重要事件，但不能因为没有激活就丢掉这段经历；
3. **权限断点**：群体模拟不能直接写五池，角色激活时又必须知道哪些经历有资格进入哪一个池。

因此，记忆种子必须同时具备：

| 能力 | 种子承担的内容 |
| --- | --- |
| 携带最新状态 | `state_deltas`、owner receipt、state cursor、checkpoint |
| 携带待物化经历 | `memory_candidates`、exposure basis、visibility、materialization policy |
| 携带审计依据 | source events、revision vector、ruleset、digest、supersession chain |
| 携带激活信息 | activation hint、显著性、未处理候选数量、冲突 refs |

记忆种子不承担以下职责：

- 不保存一份完整的五池副本；
- 不成为第二个角色真相源；
- 不把司命的全局知识直接灌入角色；
- 不替代世界/玩法 authority 的结算；
- 不替代 Character Core 对主观记忆的最终判断。

### 12.2 端到端示例：霜冻、粮食短缺与角色老石

假设 `char_a` 是农民老石。模拟开始前，角色已经处于：

```text
当前世界 tick       = 100
owner_cursor         = 100
state_cursor        = 100
experience_cursor   = 100
memory_cursor       = 100
```

老石已有五池记忆：

```text
Event Memory：去年霜冻导致一季减产
Observation Memory：看见镇西粮店排队
Knowledge Memory：知道镇议会发布了春耕公告
Social Memory：认为邻居 char_b 守信
Higher-Order Memory：知道 char_b 也知道春耕公告
```

这些是 Character Core 的私有记忆，司命和群体 planner 不直接读取。

#### 第一步：世界事实发生

tick 101，生态/环境 owner 结算了一个公开霜冻事件：

```text
event_ref       = evt:frost:101
区域公开        = true
农田受损        = owner-confirmed
粮食供应压力    = projection update
```

这个事实只表示“世界发生了什么”，不表示所有角色都知道。

#### 第二步：群体模拟读取授权投影

Population Simulation 读取：

```text
char_a 的公开身份投影：农民
char_a 的农田/库存影响 projection
区域公开霜冻事件
角色位置和工作区域的授权摘要
```

它不读取老石的原始五池，也不知道老石对邻居的私密信任细节。

#### 第三步：产生记忆种子增量

模拟生成一个 `SeedDelta`：

```text
from_tick = 100
to_tick   = 101
source_event_refs = [evt:frost:101]
```

其中包括：

```text
state_delta:
  hunger_pressure += 0.12
  safety_pressure += 0.08
  current_goal_hint = "补充家庭粮食"

memory_candidates:
  - candidate_kind: event_experience
    summary: "霜冻导致老石负责的农田产出下降"
    exposure_basis: affected_directly
    materialization_policy: on_activation
    salience: 0.78

  - candidate_kind: factual_knowledge
    summary: "区域出现霜冻并影响春耕"
    exposure_basis: public_propagation
    confidence: 0.90
    materialization_policy: on_activation
```

这里的种子作用是：

- 立即携带老石的状态变化；
- 保存老石可能形成的两条不同记忆候选；
- 记录每条候选为什么有资格被老石知道；
- 等待 Character Core 在激活时决定是否物化。

它不是直接把两条记录写入 Event Memory 和 Knowledge Memory。

#### 第四步：批次结束后更新连续性

如果对应 owner 结算成功，批次结束后：

```text
owner_cursor       = 101
state_cursor       = 101
experience_cursor  = 101
memory_cursor      = 100
pending_memory     = 2
```

老石的 runtime state 立即更新：

```text
安全压力上升
生理压力上升
当前目标倾向于补充粮食
```

但五池仍暂时保持 tick 100 的内容。两条候选进入角色经历账本和 continuity
checkpoint，等待激活。

如果老石从未被玩家接近，系统也不会丢掉这两条经历；它们会留在种子/经历账本中，
并在后续 checkpoint 中保留 pending 状态。

#### 第五步：角色被激活

tick 103，玩家进入老石所在区域，系统获取 activation lock：

```text
activation lock
-> 读取 checkpoint 和 SeedDelta tail
-> 检查 event_valid_at / knowledge_available_at
-> 检查 actor exposure、privacy、dedup、revision
```

两条候选的物化结果：

```text
event_experience
  -> Event Memory
  “霜冻使我的农田产出下降”

factual_knowledge
  -> Knowledge Memory
  “这片区域受霜冻影响，春耕会受阻”
```

Character Core 还可以在激活时让 L2/LLM 生成一个受限的主观解释：

```text
“今年又要少收成，得先想办法保住家里的粮。”
```

但模型只是提出解释，不能直接决定写入哪个池。

物化成功后：

```text
memory_cursor = 101
materialization_status = materialized
```

老石此时获得的是“他有资格形成的记忆”，而不是司命知道的全部霜冻信息。

#### 第六步：没有暴露的角色不会获得同样记忆

假设 `char_b` 在另一个区域，没有看到霜冻，也没有被告知。

```text
char_b:
  无 event_experience
  无 perceptual_observation
  无 factual_knowledge
```

即使司命知道霜冻影响了整个区域，也不能把这条事实直接写入 char_b 的 Knowledge
Memory。

如果 `char_c` 在市场现场看到粮价上涨，则它可以获得：

```text
perceptual_observation -> Observation Memory
```

但不能自动获得“霜冻是原因”，除非它后来看到公告或被可信角色告知。

#### 第七步：世界事实被修正

tick 105，环境 owner 修正结论：霜冻实际影响小于最初估计。

系统不能删除老石已经形成的主观记忆，而是追加：

```text
correction_ref
supersedes = evt:frost:101
```

未来检索可以得到：

```text
旧经历：我曾认为农田会严重减产
新知识：后来确认实际损失低于初始估计
```

老石保留“当时的担忧”是合理的角色历史，而不是数据错误。

### 12.3 示例总结

这个例子中，五池的变化不是：

```text
世界事件发生 -> 司命直接写五池
```

而是：

```text
世界事实
-> 群体模拟计算角色受影响程度
-> 记忆种子保存状态增量和带证据候选
-> runtime state 立即物化
-> Character Core 在激活时决定五池物化
-> 角色获得符合其经历、时间和隐私范围的主观记忆
```

记忆种子在整个过程中是“连续性桥梁”：既防止离线经历丢失，又防止司命绕过
Character Core 直接制造角色记忆。

## 13. 与现有仓库的映射

### 可复用实现

- `backend/app/character_agent/models/*`：五池和 runtime typed models；
- `backend/app/character_agent/storage/memory_store.py`：五池存储边界；
- `backend/app/character_agent/mind/writeback_policy.py`：候选到写回的策略边界；
- `backend/app/character_agent/logic/drift_accumulator.py`：长期 drift candidate；
- `backend/app/population_continuity/activation.py`：activation lock / pending / requeue；
- `backend/app/population_continuity/models.py`：batch、revision、receipt 结构；
- `backend/app/gameplay/event_store.py`：生产事实 append/replay；
- `backend/app/character_agent/gateway/context_builder.py`：受限记忆上下文构建。

### 当前缺口

- 尚无正式 `CharacterSimulationSeed` schema；
- `PendingChange` 目前不是通用角色连续性账本；
- 尚无独立的 memory candidate materialization contract；
- 尚无四游标的生产实现；
- 尚无本设计对应的 Harness profile；
- population/NPC/social truth owner 仍不能由本设计自动补齐。

## 14. 验收门

进入实现前必须有 focused tests 和独立 Harness，至少证明：

1. 客观事实没有 exposure 就不能成为角色知识；
2. future/branch-only 事件不能进入生产记忆；
3. Siming 不能读取原始五池；
4. 每类候选只能进入合格的五池；
5. 重复模拟不会重复追加记忆；
6. stale merge 不产生部分写入；
7. state cursor 可以领先 memory cursor；
8. full replay 与 checkpoint-tail replay 结果一致；
9. 修正保留历史主观记忆并追加 supersession；
10. LLM 失败不会直接写入记忆；
11. public/player projection 不泄露 actor-private history；
12. prompt 只包含 scope 合法的检索卡片；
13. 低价值远场模拟不触发逐角色完整 LLM 循环。

建议未来 Harness profile：

```text
character-simulation-memory-seed-continuity
```

## 15. 非目标

- 不创建通用 population truth owner；
- 不让司命成为全知角色记忆读取者；
- 不启动逐角色常驻 LLM background loop；
- 不自动修改 authored dossier；
- 不把 branch 结果直接晋升为生产角色记忆；
- 不替换现有五池 memory store；
- 不以本设计宣称完整人口/社会模拟已经完成。

## 16. 设计结论

角色记忆的最终 owner 是 Character Core；世界真相层提供客观事实；司命和群体模拟
产生带来源、时间、隐私和暴露证据的候选。动态状态在 owner 结算后立即更新，主观记忆
可延迟到角色激活时物化，但经历账本不能丢失。

大模型只负责少数高价值事件的主观解释，不负责记忆所有权、权限、持久化、版本、回放
或修正。这样才能同时满足角色连续性、记忆连续性、历史可见性、隐私安全和 token 预算。
