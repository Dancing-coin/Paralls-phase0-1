# 司命受控能力面

状态：`proposed amendment; existing event consumer/producer and audit are implemented bounded`

对应母规格：[Character Simulation Memory Seed And Continuity Design](../../superpowers/specs/world-character-siming-authority-mainline/2026-08-22-character-simulation-memory-seed-continuity-design.md)，映射范围：RWEE、guarded execute、owner-bound intent 和 zero-write rejection。

## 为什么

群体模拟需要司命读取全局态势、维护叙事工作状态并发起有限动作，但现有实现由多个窄服务组成。若直接把图谱或模型接到领域写入，会把司命变成 generic coordinator。

## 继承

- 司命只消费有资格读取的 authority event/projection；
- `siming.*` 只能是高层事件或审计，不是物理成功事实；
- `GameplayEventStore.append_batch()` 是唯一生产提交脊柱。

## 司命总体架构与群体模拟定位

这里的“架构层”是职责边界，不要求每层都成为独立进程、数据库或总线。司命是上层
authority，群体模拟是司命内部的一项受控能力，PopulationPlanner 是该能力中负责
广域批量计算的内部模块。

```text
┌──────────────────────────────────────────────┐
│ Siming Authority / 司命核心                   │
│ observe · scoped read · policy · decision     │
│ capability admission · audit · activation     │
└──────────────────────┬───────────────────────┘
                       │ 授权 scope/cadence/policy/budget
                       v
┌──────────────────────────────────────────────┐
│ Population Simulation / 司命群体模拟能力域    │
│ cohort selector · batch rules · propagation   │
│ ┌──────────────────────────────────────────┐  │
│ │ PopulationPlanner                        │  │
│ │ 计算 BatchReport 和各类 candidate        │  │
│ └──────────────────────────────────────────┘  │
└──────────────────────┬───────────────────────┘
                       │ 候选返回司命审阅
                       v
┌──────────────────────────────────────────────┐
│ Governed Execution / 司命受控提交             │
│ owner-bound intent · static capability        │
└──────────────────────┬───────────────────────┘
                       v
┌──────────────────┐       ┌────────────────────┐
│ Domain Owner     │       │ Character Core     │
│ 世界事实结算      │       │ 状态/Seed/五池结算 │
└──────────────────┘       └────────────────────┘
```

四个容易混淆的关系必须固定：

| 名称 | 是什么 | 不是什么 |
| --- | --- | --- |
| 司命 | 全局态势观察、策略、叙事治理、能力准入和受控提交 authority | 不是世界事实 owner，也不是五池 memory store |
| 群体模拟 | 司命用来让离线世界持续演化的完整流程/能力域 | 不是独立 truth owner 或第二世界 |
| PopulationPlanner | 群体模拟内部的 cohort/batch 计算器，产出报告和候选 | 不是第二个司命，不能独立执行或写入 |
| Domain Owner / Character Core | 分别结算客观世界和角色连续性 | 不接受司命绕过合同的任意写入 |

因此，PopulationPlanner 的矩阵是内部模块的最小权限护栏，不是给它新增外部身份。
Planner 结果必须回到司命，由司命决定 `no-op`、`requeue`、`owner-bound intent` 或
激活请求；只有后续 Owner/Character Core receipt 成功，结果才离开派生层。

## 修订

| 能力 | 可做 | 不可做 | 未来 formal contract |
| --- | --- | --- | --- |
| Read | 读取 scoped event、graph view、state snapshot、audit | 读取角色未共享私有记忆或绕过 privacy | reader scope/digest/revision |
| Write | 追加 Siming candidate、decision、audit、派生图谱记录 | 追加领域世界事实 | Siming-owned event family/receipt |
| Edit | 修订可编辑故事线、候选解释、激活优先级并留 revision | 改写 locked fact 或删除审计 | editable state lifecycle |
| Execute | 通过静态 capability 提交 typed intent 或记录 no-action | 直调 ESM/角色/Godot，或选择任意 owner/stream/event | capability-to-owner mapping |

## 司命如何真正推进群体模拟

司命可以推动群体模拟改变世界真相，也可以促成角色记忆变化；但它不直接拥有这两类数据的最终写入权。群体模拟属于司命的受控能力域，`PopulationPlanner` 只是司命内部负责 cohort 批量计算的模块，不是独立 authority。司命负责观察、授权计算、策略决策和受治理提交；领域 Owner 和 Character Core 分别负责最终结算。

```text
授权 projection / cadence
  -> 司命调用 PopulationPlanner 选择 cohort 并计算批次
  -> BatchReport + owner-bound intent candidate
  -> 司命策略判断与静态 capability 准入
  -> 领域 owner 校验、结算并追加正式 world event
  -> owner receipt / scoped projection
  -> CharacterContinuityCommand
  -> Character Core 更新 runtime state、追加 SeedDelta
  -> 角色激活时按暴露证据物化五池
```

这里必须区分三个结果：

1. `candidate` 只是模拟提出的可能动作，不是世界事实；
2. `owner receipt` 表示领域 owner 已把动作结算为世界事实，但不自动表示所有角色知道；
3. `SeedDelta`/memory candidate 是角色连续性账本，五池记录仍由 Character Core 在激活物化路径中决定和写入。

因此，司命不能直接追加世界 event、`SeedDelta`、五池记录或 actor runtime state。它的 `Execute` 是提交一个由静态 capability 绑定 owner 的 typed intent；例如 `schedule_gated_supply` 只能交给 `OrganizationAuthority` 校验和结算。司命不能自选 owner、stream、event family，也不能在 owner 拒绝后换一个 owner 试写。

角色侧同样按暴露证据分流：亲自参与的角色可得到 `event_experience`，只看到公开排队的角色只能得到 `perceptual_observation`，没有观察、参与、告知或实际后果的角色没有 memory candidate。司命知道全局事实，不等于角色自动知道或记得该事实。

完整的群体模拟内部模块边界见 [03-群体模拟与角色分级连续性](03-群体模拟与角色分级连续性.md) 的 `PopulationPlanner` 正式矩阵；该矩阵不授予它独立的司命、Owner 或 Character Core 权限。字段、receipt、游标和物化规则以母规格为准。

### 关键澄清：禁止绕过 owner，不禁止受治理执行

“司命不能直接执行世界真相”只表示司命不能绕过领域 owner，直接调用
`GameplayEventStore`、任意 event stream 或领域内部写接口。它不表示司命不能推动
世界变化。司命和群体模拟必须能够通过已准入的 capability 发起受治理执行：

```text
scoped projection
  -> owner-bound typed intent
  -> capability admission
  -> 目标领域 owner 校验规则、expected revision 和幂等键
  -> owner settlement
  -> GameplayEventStore.append_batch()
  -> owner receipt
  -> scoped projection / graph / seed 更新
```

因此，司命的 `Execute` 是“提交一个由固定 capability 绑定目标 owner 的意图”，不是
“自己宣称世界已经发生变化”。只有 owner settlement 成功并产生 receipt，世界真相
才前进；拒绝、过期、冲突或补偿都必须回到审计和 requeue/重算路径。

| 操作含义 | 允许的推进方式 | 禁止的越权方式 |
| --- | --- | --- |
| Read | 读取授权 projection 和固定 read-set | 读取未授权原始真相库或私有状态 |
| Write | 写入 intent、candidate、audit、派生记录 | 直接 append 领域事实 |
| Edit | 追加规则/候选/故事线 revision；请求 owner correction | 原地改写 locked event 或删除历史 |
| Execute | 调用静态 capability，让目标 owner 结算 | 自选 owner/stream/event 或绕过 admission |

## 执行状态

正式 spec 必须先定义 `GovernedSimingCapability` 的 immutable admission/read contract；计划不得新增运行时注册表。实现顺序为 Read scope -> Write/Edit audit -> one Execute consumer vertical -> independent Harness。

## 最小运行协议

司命一次受控工作循环固定为：`observe -> scoped read-set -> candidate -> policy/feasibility -> decision -> guarded execute -> owner result/audit`。每一段都有明确产物，任何段都不能偷偷承担下一段的权限：

| 阶段 | 司命允许产出 | 必须固定或引用的证据 | 不能做的事 |
| --- | --- | --- | --- |
| Observe | 观察请求、范围说明 | reader principal、visibility scope、`valid_at`、`recorded_at` | 从未授权的私有记忆或未 scoped 的全局读模型取数 |
| Scoped read-set | 不可变的投影/图谱切片 | source event vector、policy revision、scope digest | 以之后变化的读模型替换本轮依据 |
| Candidate | 叙事解释、激活提示、owner-bound intent 候选 | causation/correlation 标签、来源 digest、候选 idempotency key | 将相关性描述为已发生的领域事实 |
| Policy/feasibility | 接受、拒绝或延后理由 | admitted capability、预算、规则 revision、zero-write 条件 | 在失败时偷偷切换 owner 或降级为无合同写入 |
| Decision | Siming 决策与审计记录 | decision revision、read-set digest、reason code | 覆盖已锁定事实或删除旧审计 |
| Guarded execute | 固定 capability 对应的 typed intent | capability id、target owner fragment、expected revision、idempotency key | 调用方选择 stream/event，或直接调用 ESM、角色、Godot |
| Result/audit | owner receipt 的引用、下一轮候选 | receipt ref、outcome、compensation/refusal reason | 把“已发送 intent”误记为“世界已结算” |

`GovernedSimingCapability` 不是第二个 catalog/registry。它只能作为既有、immutable、source-controlled `GovernedAuthorityContractCatalog` 中的一个静态 admission entry，和现有 owner contract 同一次代码审查、发布和版本化；不得运行时注册、由 package 加载、由提示词生成或从数据库发现。一个条目至少固定 `capability_id`、reader scope、允许的候选 schema、唯一 target owner fragment、允许的 event family、receipt schema、privacy policy、revision policy、idempotency domain 与 no-action 条件。它的职责是证明“这个意图可以提交给谁”，而不是根据提示词或模型输出动态决定“该写到哪里”。

正式合同还必须定义 catalog 绑定的拒绝面：缺失/未知 capability、catalog revision 不匹配、候选 schema 不匹配、目标 fragment 或 event family 不匹配、caller 试图扩大 privacy scope、source vector 或 expected revision 已过期，均在 `SettlementPlan` 建立前返回 `capability_not_admitted` 或 `stale_read_set`，并保证零 production append。一次部署只能通过明确的 source-controlled catalog revision 加入新 entry；这不是运行时路由或统一结算器。

## 拒绝、无动作与补偿

司命的成功不是“模型给出了故事”，而是审计链可解释。下列结果都必须是一等结果，而非异常吞掉：

- `no_observable_change`：证据不足、影响低于阈值或只需更新表现种子；零生产写入。
- `privacy_denied`：scope 不足；不得返回足以反推私有内容的理由。
- `stale_read_set`：source vector 或 policy revision 已失效；候选必须重新计算。
- `capability_not_admitted`：没有静态准入能力；只记录审计/报告，不尝试替代 owner。
- `owner_rejected`：目标 owner 的业务规则、expected revision 或 idempotency 检查拒绝；司命保留 receipt/refusal 并按明确的 requeue 政策处理。
- `compensated`：owner 对先前结算作出补偿；司命只能基于补偿后的投影重新派生图谱和计划，不能自行反向改写其它 owner。

因此，Edit 仅能修订司命自有的故事线、优先级或候选解释，并以追加 revision 表示；它不是对领域事实的编辑权限。一次 execute 被拒绝后不得“换一个 owner 试试”，除非下一轮已从新的、正式准入 capability 得到不同且可审计的候选。
