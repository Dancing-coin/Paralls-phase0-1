# 全面闭源核心保护矩阵

状态：`incremental closed-core protection guidance; not implementation authorization`

日期：2026-08-06

## 1. 范围与当前事实

本文件只回答“哪些实现和运行态必须留在闭源核心、用什么技术边界保护”。它不定义
`reader/editor/admin` 的权限语义、对外命令、内容 revision 生命周期或 Workbench 流程；
这些由 [10-创作者权限与闭源控制面方案.md](10-创作者权限与闭源控制面方案.md) 唯一拥有。

当前可证明的基础是：受信任 Patch capability 边界、Gameplay event/replay 脊柱、受限
trusted-local 镜像读取 scope 和角色 dossier 的投影分层。`CreatorControlPlane`、项目 grant、
签名发布、`ActiveWorldRevision`、一般化 semantic/scheduler/social/society authority 仍是
`planned`，不能被描述成已保护的生产服务。

闭源的目标不是隐藏创作者自己的内容。项目内 authored dossier、剧本、资产和声明式
规则应当可按授权读取和修改；需要保护的是核心算法、canonical writer、跨域结算、
runtime-private 数据、签名密钥以及其他项目的数据。

## 2. 保护矩阵

| 逻辑域 | 留在闭源 core 的实现与真相 | 创作者可处理的声明式内容 | 外部绝不能直接获得 |
| --- | --- | --- | --- |
| Character Core | dossier 解释、L1-L4、记忆语义、目标仲裁、隐私投影、状态写回 | persona、关系/能力种子、剧情约束、允许的 layer proposal | raw memory、L2/L3 workspace、`replace_dossier_layer()` 直连写权限 |
| World Record / Semantic / Rule | identity、组件/关系事实、registry 校验、selector 编译、effect/resistance、冲突/预算/trace | entity seed、tag/effect/rule draft、资源引用 | 任意 rule handler、任意代码、`authority_evaluation_view` |
| Gameplay Authority | 库存/容量、身体资源、技能判定、产权、账户/分录、建造/任务/冲突结算 | item、技能、配方、蓝图、难度/参数、表现资源 | 余额/库存/身体/产权/事件的直接写入口 |
| Social / Society | 感知过滤、知识/关系写回、组织委托、税务负债、信用/公共秩序结算 | 感知通道、组织结构、税则、许可证、社会内容与 policy draft | 全居民私密资料、监管超级权限、跨域直接写入 |
| Runtime / Platform | revision pinning、migrator、event append、outbox/replay、审计、私钥、服务密钥 | manifest、依赖、已注册 migrator 引用、订阅范围 | 删除或重写历史、任意迁移、签名私钥、跨项目数据 |
| Presentation / Model Adapter | 无 canonical world truth；只保留最小必要的本地状态 | Godot 场景、UI、音频、动画、advisory model binding | 用本地表现、VLA 或模型回复确认世界成功 |

未来的 World Record、Semantic Registry、Rule Engine、Scheduler、Perception/Social、
Economy/Organization/Governance 等是逻辑 owner，当前必须从既有 `world_runtime`、ESM、
`raw_fact_event` 和 Gameplay authority 路径增量收口，不能因此创建另一套“受保护 runtime”。

## 3. 四层技术防线

1. **模块边界**：核心函数和原始运行态标记为 internal-only，不从插件/SDK 导出；
   `CharacterDossierLoader`、`replace_dossier_layer()`、event append、memory writeback、
   settlement handler 只能由闭源服务内部调用。
2. **进程与部署边界**：强保护版本把角色心智、authority、密钥和生产数据库放在远程
   闭源服务或受保护进程。本地 Workbench/CLI 只持有短时、项目范围受限凭据。
3. **命令边界**：UI、CLI、MCP 只使用同一 control-plane port 创建 query、draft 或 proposal；
   它们永不获得 Python import、数据库连接或 production event append 的旁路。
4. **内容与数据边界**：内容包只能含声明式 schema/Rule IR/资源引用，必须经过签名、
   capability、依赖、版本与迁移校验；读取一律是按 project scope 与数据分类裁剪的投影。

这四层缺一不可。仅仅把 Python 包改为私有、把 YAML 打包，或隐藏 UI 按钮，都不能阻止
本地 import、篡改或直接写库；仅部署远程服务但给 MCP 暴露内部函数也同样失效。

## 4. 三类数据视图

| 视图 | 读者与目的 | 边界 |
| --- | --- | --- |
| `authority_evaluation_view` | 闭源 authority/Rule Engine 的完整受政策约束输入 | 不能作为 UI、CLI、MCP、角色或模型的导出视图 |
| `actor_perception_view` | 角色、玩家和模型形成决策与叙事 | 不是完整世界真相，也不能决定结算 |
| `creator_debug_view` | reader/editor/admin 获授权的 schema、trace、replay 与诊断 | 必须按项目和 data classification 过滤，且不改变 authority 输入 |

“可读取”不等于“可编辑”，更不等于“可管理”。三档角色的具体 grants 与命令允许面
只见 [10](10-创作者权限与闭源控制面方案.md)；本文件只要求无论角色如何授权，都不能
把任一视图升级为 canonical writer。

## 5. 本地创作与正式运行

本地 Workbench 可以读写草案、运行隔离 Preview、进行 replay 和提交发布请求；正式
Production 才持有真实玩家、正式账户/库存/产权和事件历史。线上数值调整也是新 revision
经过预览、审核、签名和指定 tick 激活，不是直接改生产内存。

单机或私有部署可以在创作者机器上放置 Production Runtime，但只能得到完整性与授权
控制，不能承诺绝对防止反编译/篡改。要求强闭源时，核心算法、私密运行态、模型密钥和
生产签名必须留在远程闭源服务或受保护进程。两种部署都必须保留 append-only 历史、
revision pinning、受批准 migrator 和审计，而不是用“离线例外”取消这些约束。

## 6. 分阶段收口与验证

| 阶段 | 需要完成的保护能力 | 尚不宣称 |
| --- | --- | --- |
| A：内部边界冻结 | internal-only exports、数据分类、现有 writer 的旁路扫描、角色 dossier 层保护 | 外部 control plane 或绝对本地防护 |
| B：受治理创作 | project grants、统一 query/command、draft/preview 隔离和审计 | 多租户平台、资产市场或完整远程发布 |
| C：生产防线 | 签名 revision、staging/activation、session/replay pinning、远程/受保护 core 部署 | 任意离线机器上的不可逆保护 |
| D：平台化 | 密钥轮换、协作审核、配额、依赖/贡献归因 | 将创作者商业分账混入游戏世界经济 |

首批 Harness/安全验收应证明：外部 surface 无法导入或调用核心 mutation；reader/editor/admin
分别只能得到被授予的 `creator_debug_view`；draft/preview event 永不进入 Production；未注册
代码、migrator 或 capability 均 fail closed；发布 revision、正式 receipt、checkpoint 和
replay 可追溯到相同 digest；客户端和模型输出不能直接形成 canonical event。
