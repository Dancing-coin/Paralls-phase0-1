# 剩余目标解除堵塞操作手册与提示词

- 日期：2026-08-05
- 用途：将当前 Goal 的外部审核、运营批准、人工评审和仓库内验证债务，转化为可直接转发的提示词与可执行收口步骤。
- 适用范围：`obj_archive_door` 物理具身、Door verifier 债务、三角色 TTS final closure、VLA semantic-quality promotion、Wave 2/3 reviewed binding，以及 Lore 提交归属整理。
- 不替代：正式 spec、plan、authority contract、资产权利或安全运营流程。

## 使用规则

这份手册不是通过 local fallback、放宽约束或伪造 evidence 绕过 gate 的授权。

- 不新增依赖、第二套 action asset registry 或第二个 locomotion owner。
- Godot 只负责本地具身和呈现，不能直接写 object/environment world truth。
- 禁止 raw-bone stream、远程高频 pose 驱动与 VLA direct control。
- 不得将 semantic door probe 说成 physical embodiment success。
- API key、secret、签名 URL、原始音频、原始对话和 base64 payload 不得进入 Git、tracked evidence 或本手册。evidence 只能使用 opaque run ID、非秘密 approval reference 和 redacted metadata。
- 每个审核结论必须包含审核人/角色、日期、review reference 与明确结论；“看起来可以”不是可实施输入。

已完成的 Gameplay Foundation、Patch runtime、trusted-local mirror/WebSocket 和 fresh LLM closure 不需要重新开启。最终 `all` 仍会因 Door applied-open success 缺失而失败，这是正确的 fail-closed 行为。

## 总体执行顺序

1. 取得 Door 可达 anchor 的审核结论和新的 `binding_revision`。
2. 同步 binding 后证明 Door 的 applied-open success 与三条失败路径。
3. 独立补齐 Door duplicate/idempotency、stale-state 与 plan/verifier inventory 债务。
4. 取得三角色 TTS 最终 voice approval，以同一个 opaque run ID 执行 guarded live proof。
5. 完成 20 个 VLA candidate 的人工 semantic truth review。
6. 取得 Wave 2/3 reviewed object/social binding 与 authority contract，再按小切片实施。
7. 每个切片先跑 focused tests/profile，再跑 `gameplay-foundation-all`；所有 required gate 绿后才最后跑 `all`。
8. 对归属明确、已验证的改动按 Lore protocol 分开提交；不混入用户原有修改。

前置输入缺失时，记录 external blocked。不要把未通过 gate 改写为“已完成”。

## Door：场景、rig 与 interaction anchor 审核

### 已知事实和禁止绕过

当前 reviewed `binding_revision=2` 的 `ContactAnchor` 约为 `[0.81, 3.324, -3.958]`。已发货角色链 `Bip001 R UpperArm -> Forearm -> Hand` 对它的实测误差约 `0.87m`，contract tolerance 为 `0.08m`。因此 success scenario 正确返回 `ik_alignment_tolerance_exceeded`、rejected settlement、`commit_count=0`，没有 `object_state_result`，门叶/blocker/occlusion 保持 closed。

不能用放宽 tolerance、teleport/move PlayerShell、语义成功替代物理成功，或 Godot 本地开门来解除该阻塞。

### 给场景/动画审核人的提示词

```text
你是 Godot 3D 场景与角色交互审核人。请审核 MainDemo 中 obj_archive_door 的
“角色实际手部可达的开门接触点”，为 authority-owned physical embodiment vertical
slice 提供可实施 binding；不要调整代码以掩盖当前错误。

事实：binding_revision=2 的 ContactAnchor 约为 [0.81, 3.324, -3.958]；已发货角色
Bip001 R UpperArm -> Forearm -> Hand 的实际误差约 0.87m，而 tolerance 为 0.08m，
所以 runtime 正确 fail-closed。

请在实际场景和实际角色 asset 上审核，并返回以下完整结构化清单：
1. object_id：obj_archive_door。
2. 可提交 ContactAnchor NodePath；若须新建，请给父节点、local transform、world transform，
   并说明它会随门/把手正确运动。
3. approach stance 的 world position、角色 forward、position/yaw tolerance。
4. 接触手（right_hand/left_hand）与对应骨骼/attachment。
5. 可达性实测：链起点、Hand endpoint、误差、测量方法；必须证明不大于既定 0.08m，
   或给出经审核的新 tolerance 及真实几何依据。
6. committed open/closed 将影响的门叶、碰撞 blocker、occlusion、navigation 节点/资源，
   以及拒绝时允许的表现。
7. 新的单调递增 binding_revision，不能复用 2。
8. reviewer、日期、review reference、风险与回退方式。

禁止建议放宽 tolerance 迁就不可达 anchor、teleport PlayerShell、Godot 写世界真相，
或将语义 door probe 当物理成功。请只返回审核数据与结论，不提交 secret 或原始资产。
```

### 收到审核结论后的仓库操作

1. 校验上述八项字段齐备。缺 node path、transform、误差、新 revision 或 review reference 时退回审核。
2. 由实施者在**同一 reviewed revision**中同步 scene bridge、ESM policy、WebSocket fixture、backend contract test、Godot probe、replay expectation。revision 不一致必须继续返回 structured rejection。
3. authority settlement 成功且取得 authoritative `object_state_result` 后，才可变更门叶 transform、blocker/occlusion，以及审核明确允许的 navigation 状态。
4. settlement 前可播放 prepare/local alignment，但必须可回退，不能改变门状态、碰撞、遮挡、导航或 replay world truth。
5. 仅当 evidence 显示 `applied-open`、settlement、committed object state 及 Godot 物理表现已关联，Door 主阻塞才解除。

## Door：仓库内 verifier 债务

该任务不依赖新 anchor，但也不能替代 applied-open success。当前 focused profile 只有 success、distance、revision、stance 四行；duplicate/idempotency 和 `door_state_stale` 有 backend unit evidence，但没有独立 live focused row。

### 给实施/测试代理的提示词

```text
你负责 obj_archive_door physical embodiment vertical slice 的 verifier 与计划清单对齐，
只可修改已有 Door 测试、verification scripts、harness profile、replay evidence 和必要的
计划 inventory。你不是 anchor 审核人。

当前 ContactAnchor 不可达，success 必须继续 fail-closed；不得修改 anchor、tolerance、
CharacterMotor ownership，不得将 rejected result 伪造成 open success。

请先逐项对照 2026-08-04 Door vertical-slice plan、现有 pytest、Godot probe、harness
profile 和 evidence report。然后按 failing test/probe 先行，完成：
1. duplicate submission/idempotency 的独立 live focused runtime/replay 行，证明相同
   idempotency key 只产生一次 authority commit、一次 ledger event、一次可见 committed transition；
2. `door_state_stale` 的独立 live focused 行，证明结构化拒绝、零 commit、门物理状态不变、
   local recovery 完成；
3. 计划中不存在或已被其他 contract 覆盖的 test/evidence 项，做精确 inventory reconcile，
   不得制造虚假文件名；
4. hostile/forged receipt 若仍是 required gate，补最小真实 coverage；若不是，明确其 owner、
   理由和后续计划，不能冒充已验证。

对每项输出修改文件、前置 failing test、通过命令、artifact 路径，以及 attempt_id、grant_id、
settlement_id、ledger sequence、replay reference 的关联方式。

硬约束：不新增依赖；不创建第二 registry/locomotion owner；Godot 不写 world truth；
不使用 raw bone/high-frequency remote pose/VLA direct control；保留已有 worktree 修改。
```

### 收口判定

- duplicate live row 证明重复 submission 不产生第二 commit、第二 ledger event 或第二次门状态改变。
- stale live row 证明明确 error code、rejected settlement、`commit_count=0`、物理状态不变和 recovery complete。
- 若 plan inventory 与实际代码不一致，修订正式 Door plan 的 test/evidence 清单；不要保留不可执行的预期文件名。
- 至少重跑 Door focused profile 与 docs profile；本任务不单独触发 `all`。

## TTS：三角色最终 voice approval 与 live closure

### 给运营/权利审核人的提示词

```text
请为 char_a、char_b、char_c 完成最终 TTS voice profile 的运营与权利审核。仓库已有
catalog/binding validation、approval preflight、fallback、redaction 和 guarded live verifier；
本次需要可执行的最终外部输入，不是临时试听链接。

请按每个 actor 返回一行或一份记录，必须包含：
- actor_id；
- provider、model、catalog revision、voice identifier（均为非秘密标识）；
- non-secret approval reference；
- source/voice rights 状态和 revocation 状态（不适用也要明确）；
- live synthesis 的生效范围、到期和撤销条件；
- 审核人、日期、关联工单/记录。

另请指定本轮三角色共用的 opaque evidence_run_id，并确认 credentials/quota 由部署或
环境秘密管理提供，而不是写进仓库。

禁止提交 API key、secret、signed URL、原始音频、原始对话或 base64 音频。最终资产通过
部署管理的 assets/tts/voice_catalog.json、assets/tts/voice_bindings.json 或
TTS_VOICE_CATALOG_PATH、TTS_VOICE_BINDINGS_PATH 注入；example files 不是批准结果。
```

### 收到批准后的操作和验收

1. 用受控部署资产注入非秘密 mapping；参考 `assets/tts/voice_catalog.example.json` 和 `assets/tts/voice_bindings.example.json`，不得把 example 当 production binding。
2. 在安全环境提供 credential，绝不回显、记录或写入 `.harness`。
3. 三角色用**同一个** opaque run ID 执行：

```powershell
python scripts/verification/verify_tts_provider_live.py --allow-live-call --evidence-run-id <opaque-id> --actor-id char_a --actor-id char_b --actor-id char_c
python scripts/verification/verify_tts_godot_playback.py --allow-live-call --evidence-run-id <opaque-id> --actor-id char_a --actor-id char_b --actor-id char_c --godot-exe D:\godot\Godot_v4.6.3-stable_win64_console.exe
python scripts/verification/harness.py --profile tts-voice-profile-adapter
```

4. evidence 只能含 redacted metadata、approval reference、actor ID、catalog/binding revision、run ID、provider/Godot pass/fail、fallback/revocation 判定。
5. 三角色同轮 provider 与 Godot playback 都通过才算 final closure；句级 audio clip queue/streaming 不在本轮 scope。

```text

docs/verification/vla-advisory-replay-annotation-manifest.json，并对
.harness/verification/vla-replay-candidate-captures.json 中的候选逐条人工审核。
```

### 分批实施规则

- 每个 reviewed object/interaction 是一个独立窄切片：先写 failing backend contract test 和 Godot runtime probe，再接线；不要一次泛化 containers、shelves、lights、room controls、social。
- binding、ESM policy、settlement、replay、Godot evidence 都必须带相同的 revision/attempt/grant/settlement/ledger linkage。
- 每个失败 fixture 证明 local recovery 和 world/physical state unchanged。
- 每个切片先过 focused pytest/profile，再扩大到 `embodied-interaction-foundation-all`、`gameplay-foundation-all`、`mainline-unified-runtime` 和 docs；`all` 只能最后执行。

## Lore commit：归属整理

这不是运行时主 blocker，但 Goal 关闭前应留下可审计 decision record。当前 worktree 有用户既有修改，禁止 `git add .`、reset、checkout、revert 或把不同 vertical slice 混入同一 commit。

```text
你负责对当前 dirty worktree 做只读归属盘点和 Lore commit 切分建议，不执行 reset、checkout、
revert 或批量 stage。请按文件列出：用户已有改动、已验证 Door slice、Gameplay Foundation、
TTS、VLA、文档 evidence、未知归属；每项说明建议 commit 边界和依赖。

对每个建议 commit，生成符合 AGENTS.md Lore protocol 的 message：第一行说明为什么；正文说明
约束和取舍；只使用有事实依据的 Constraint、Rejected、Confidence、Scope-risk、Reversibility、
Directive、Tested、Not-tested trailers。不要捏造测试通过，不覆盖用户改动，不将 secret/evidence
payload 放入 commit message。
```

只有归属被人工确认且相关 focused verification 通过时，才逐个 stage/commit。无法确认的文件保持 unstaged 并记录为待归属。

## 撤销 Goal 前的核对

可以撤销当前 Goal 的前提不是“所有任务已完成”，而是你已理解剩余工作需要上述外部输入，并已把每个 blocker 的责任人、回传字段、验收命令和禁止绕过项明确交接。撤销后保留本手册、正式 plans 和 `.harness/verification/` evidence，避免未来重复发现同一阻塞。
