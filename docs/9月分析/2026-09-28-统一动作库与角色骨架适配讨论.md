# 统一动作库与角色骨架适配讨论

日期：`2026-09-28`

状态：资产和动作库参考记录。其语义动作索引、骨架 realization、BodyProfile、IK 和
动作风格规则已并入角色动作底座渐进替代方案；本文不作为独立运行时实施方案。

## 1. 关于一次性导入动作库、角色按索引调用

### 用户问题

我会把所有动作都做好重定向并且只适配于对应骨架。动作底座和资产库相关的设计文档多少有提到我希望将动作库一次性导入到项目中，然后每个建模根据索引来调用，请分析可能性。

### 讨论结论

可行，而且和现有设计方向基本一致。但应实现为“统一语义动作索引 + 每个骨架自己的已重定向动画包”，不要把不同骨架的原始动画直接共用。

核心设计文档包括：

- `docs/character/character-action-asset-interface.md`
- `docs/character/character-asset-integration.md`
- `docs/character/character-action-foundation-current-state.md`
- `docs/character/character-runtime-design-drift-audit.md`
- `docs/superpowers/specs/2026-09-14-unified-character-action-foundation-and-inf-tag-contract-design.md`
- `docs/superpowers/specs/2026-09-14-character-animation-asset-qualification-and-concurrent-realization-subspec.md`
- `docs/superpowers/plans/2026-09-14-character-animation-asset-qualification-and-concurrent-realization-implementation-plan.md`
- `docs/superpowers/plans/2026-09-28-street-animationtree-application-plan.md`

这些文档共同表达了以下方向：

1. 运行时按语义/tag 请求动作，而不是直接写死 clip 名称。
2. 外部模型先经过 deform-to-canonical skeleton mapping、rest pose、单位、轴向、动作轨道和 root motion 资格化。
3. 运行时只消费已登记的 realization profile。
4. `CharacterEmbodimentAssetRegistry` 是动作资产注册、预加载和 realization plan 的入口。
5. AnimationTree 负责本地动作表现，`CharacterMotor` 负责身体位移和碰撞，动作资产不能写世界真相。

推荐结构：

```text
统一语义动作索引
    action:locomotion.run
    action:melee.unarmed_punch
    action:melee.sword_slash
            |
            v
角色骨架适配索引
    female_t_external -> running_for_t
    female_jk_external -> running_for_jk
            |
            v
对应角色自己的 AnimationLibrary / AnimationTree
```

索引建议使用稳定的语义键：

```json
{
  "semantic_action_id": "action:locomotion.run",
  "skeleton_profile_id": "humanoid.v1",
  "package_id": "female_jk_external",
  "clip_ref": "running",
  "state_name": "run",
  "realization_mode": "drive_locomotion",
  "qualification_status": "qualified"
}
```

数字索引可以作为缓存或序列化优化，但不应作为唯一业务标识。业务调用应优先使用：

```text
package_id + semantic_action_id
```

这样插入新动作不会造成旧动作索引漂移，也能保留动作来源、骨架版本和资格化报告。

当前仓库已经有 `CharacterEmbodimentAssetRegistry.gd`，包含：

- `register_motion_asset`
- `preload_assets_for_semantics`
- `compose_realization_plan`
- 按 `package_id + action_id + claims` 解析动作的能力

因此不需要再创建一套平行动画系统，应该继续扩展现有 registry。

## 2. 同一套骨骼、不同身材比例时能否共用一个动画库

### 用户问题

我们将对所有角色使用一套骨骼（不同建模，骨骼长度可能会有所变化），因此可以使用一个动画库，你觉得可行吗？我提及过身高体重动作风格等对骨骼和动作权重的影响，不知道能不能做好。

### 讨论结论

可行，而且比“每个角色一套动画库”更适合长期扩展。共享应定义为：

> 共享骨骼语义、动画库、AnimationTree 结构和动作索引；每个角色只提供身材参数、校准参数和必要的 IK 修正。

如果所有角色满足以下条件，同一个 `AnimationLibrary` 可以被多个角色的 `AnimationTree` 使用：

- 骨骼层级一致；
- 骨骼名称和左右方向一致；
- rest pose、轴向、单位一致；
- 动画轨道路径一致；
- root、pelvis、手脚等关键骨骼语义一致。

身高和四肢长度不同，主要会影响：

- 长腿角色步幅更大；
- 矮胖角色动作覆盖范围更小；
- 手脚接触点出现偏差；
- 根运动和碰撞体速度不能直接照搬。

因此，旋转动画可以高度共享，接触位置和位移需要校准。

建议增加独立的 `BodyProfile`：

```json
{
  "profile_id": "body:tall_slim",
  "height_scale": 1.08,
  "mass_class": "light",
  "leg_length_ratio": 1.12,
  "arm_length_ratio": 1.03,
  "shoulder_width_ratio": 0.94,
  "gait_scale": 1.06,
  "reach_scale": 1.02,
  "foot_ik_enabled": true,
  "hand_ik_enabled": true
}
```

运行时解析可以采用：

```text
语义动作
+ humanoid.v1
+ body profile
+ motion style
-> 共享动画 clip
-> 角色专属校准参数
-> AnimationTree + IK
```

### 身高、体重、比例的职责

身高和骨骼长度主要影响：

- 目标高度和角色整体缩放；
- 步幅、脚步落点和骨盆轨迹；
- 手部 reach 和武器挂点；
- 碰撞体、受击体和交互距离。

“体重”不应直接修改骨骼动画帧，更适合影响：

- 加速度和减速度；
- 起步、停步和转身时间；
- 落地压缩；
- 身体倾斜；
- 动作混合时间；
- 攻击后摇与动作节奏；
- 碰撞体和受击体参数。

### 动作风格

动作风格应作为独立维度，不要混入骨骼名称或角色模型包：

```text
motion_style: athletic
motion_style: heavy
motion_style: cautious
motion_style: elegant
motion_style: aggressive
```

同一个 `run` 可以通过以下方式变化：

- AnimationTree BlendSpace 的速度和加速度参数；
- additive lean；
- 起步/停止动画；
- 角色专属 blend time；
- 上半身姿态；
- 脚步和落地修正；
- 身体重心偏移。

如果风格差异非常大，例如普通奔跑和夸张卡通奔跑，应保持同一语义 ID，但提供不同 realization：

```text
action:locomotion.run
  -> style:athletic
  -> style:heavy
  -> style:cartoon
```

### IK 和后处理需求

共享关键帧不能完全解决以下问题：

1. 脚部贴地、膝盖方向和坡面适配。
2. 手部抓取、武器对齐和交互接触。
3. 攻击接触点与目标位置修正。
4. 不同腿长导致的步幅和脚滑。
5. 不同身高导致的双人交互高度差。

建议使用：

- 脚部 IK；
- 手部 IK；
- 武器和装备 socket；
- 必要的 motion warping；
- `CharacterMotor` 驱动的根运动校准。

不同身材角色不应直接使用同一个绝对米制 root motion。建议动画只提供姿态、步频和相对位移，最终位移由 `CharacterMotor` 结合 `gait_scale` 处理。

### 共享动画的适用分级

| 身材差异 | 处理方式 |
| --- | --- |
| 小幅差异 | 共用动画 + IK + 参数校准 |
| 中等差异 | 共用动画 + BodyProfile + 局部派生 clip |
| 大幅差异 | 同一语义 ID，使用独立 realization |
| 极端差异 | 单独动作族或单独 skeleton profile |

可以先把约 10% 到 15% 的身材差异作为初始测试区间，但最终应根据脚部、手部、武器接触和根运动验证决定，不能作为硬性资格规则。

## 3. 建模3 是否没有 IK

### 用户问题

`E:\下载\建模3  金色卷发jk女 T字版  多动作版.blend` 是不是没做 IK？

### 检查结论

根据项目现有导出记录：

> 建模3的源 `.blend` 做过控制器/约束驱动，应该包含 IK/FK 类作者级控制；但导入项目后的运行时资产没有保留可实时驱动的 IK。

项目记录显示：

- 源文件包含 344 根作者骨骼、68 根变形骨骼；
- 源文件包含 controller/constraint animation；
- 导出时把控制器和约束求值结果烘焙到 68 根变形骨骼；
- runtime GLB 使用 deform-skeleton boundary；
- controller、IK/FK、reference bones 不进入运行时骨架边界。

相关记录：

- `assets/active/female_jk_external/README.md`
- `assets/active/female_jk_external/manifest.json`
- `assets/active/female_t_external/README.md`

因此需要区分三层：

| 层级 | 状态 |
| --- | --- |
| Blender 源文件作者级 IK/约束 | 有，至少存在控制器/约束动画 |
| 导出的动画结果 | 有 IK/约束计算后的烘焙姿态 |
| Godot 运行时实时 IK | 建模3当前没有通用配置 |

当前 `StreetCharacterSkin` 绑定的是 `AnimationPlayer`、`Skeleton3D`、`AnimationTree` 和 root motion；没有为建模3创建通用的 `SkeletonIK3D`。项目中的 `KnightRoleSkin` 虽然有 `SkeletonIK3D` 交互路径，但那是骑士角色的专用实现，不能说明建模3已经拥有运行时 IK。

建模2的 `running` 应用到建模3时，采用的是：

```text
建模2的动画姿态
-> 按 deform bone remap
-> 烘焙到建模3骨架
```

这不会把建模2 Blender 中的 IK 控制器、Pole Target 或约束一并带到建模3。

因此当前建模3可以播放跑步、攻击等烘焙动画，但如果需要：

- 不同身高导致的脚底贴地；
- 手部抓取和武器对齐；
- 攻击接触点修正；
- 不同腿长造成的步幅偏差；

还需要在 Godot 中增加独立的脚部 IK、手部 IK 或接触修正层。

## 4. 综合建议

最终目标可以定义为：

> 一套 canonical skeleton、一套主动作库、一套 AnimationTree 状态结构；每个角色拥有独立的身材参数、运动风格参数、接触校准和 IK 配置。

推荐运行时结构：

```text
中央动作库
  action:locomotion.run
  action:melee.sword_slash
  action:jump
        |
        v
统一骨骼配置
  humanoid.v1
        |
        v
角色 BodyProfile
  female_jk
  female_t
  female_bandage
        |
        v
AnimationTree + IK + Motor
```

对建模2和建模3，适合先使用建模2的 `running` 作为统一跑步基准，在建模3上验证：

- 脚步落点；
- 骨盆高度；
- 步幅；
- 根运动；
- 脚滑；
- 碰撞体和角色速度。

通过后，再将其提升为中央动作库中的：

```text
action:locomotion.run
```

最终判断：

**统一动作库可行，但“共享”应包括动作索引、骨架语义和 AnimationTree 结构，不代表每个角色完全不需要身材参数、IK、接触校准和运动风格配置。建模3源文件有作者级 IK/约束痕迹，但当前导入的运行时 GLB 是烘焙后的变形骨骼，不是可直接实时驱动的 IK 资产。**

## 5. 动作库文件夹投递与审核入库要求

### 用户补充要求

以后动作文件可以直接放在动作库文件夹里，自动或手动触发审核程序；审核通过后直接标记，进入正式动作库。

### 目标流程

```text
动作文件投递目录
    -> 自动发现或手动触发审核
    -> 动作资产解析
    -> 骨架/轨道/时序/root motion/接触标记检查
    -> 生成审核报告
    -> 通过后写入正式索引
    -> 角色按语义动作索引调用
```

建议目录分层：

```text
assets/motion_library/
  incoming/       # 新投递文件，不能直接被运行时使用
  review/         # 审核中和审核报告
  approved/       # 审核通过的正式动作资源
  rejected/       # 审核失败及原因
  manifests/      # 动作索引和版本清单
```

正式运行时只允许读取 `approved/` 及其 manifest，禁止直接读取 `incoming/` 或 `review/`。

### 自动审核

自动审核可以在以下时机触发：

- 文件进入 `incoming/` 后由文件监视器触发；
- 启动动作资产审核命令时批量扫描；
- CI 或 Harness profile 中执行动作库资格化；
- 资源包发布前执行全量复核。

自动审核至少应检查：

1. 文件格式、文件完整性和哈希；
2. 目标骨架版本或 canonical skeleton profile；
3. rest pose、单位、前向轴和根骨骼；
4. 动画轨道是否绑定有效骨骼；
5. 帧率、时长和关键标记；
6. root motion 是否符合声明的策略；
7. 是否存在未声明的 pelvis/root/lower-body 影响；
8. 动作是否满足 full-body exclusive、upper-body concurrent 或 additive 条件；
9. 接触窗口、手脚落点和武器槽位是否有资格化证据；
10. 动作语义 ID、版本、来源和 package digest 是否完整；
11. 是否与正式库中已有动作发生 ID、版本或内容冲突。

自动审核通过后，不应只根据文件名或目录名入库，必须生成机器可读的 qualification report 和 manifest。

### 手动审核

手动审核用于自动检查无法可靠判断的内容，例如：

- 动作风格是否符合角色定位；
- 身体重量感、节奏和夸张程度；
- 脚滑、穿模、手部姿态和视觉质量；
- 攻击准备、接触和恢复是否自然；
- 动作是否适合共享 AnimationTree 状态；
- 是否需要新增 body profile、motion style 或 IK 修正。

手动审核可以在审核工具中完成，也可以通过 manifest 或审核命令显式确认。手动确认必须记录审核人、时间、审核意见和审核报告版本。

### 标记和状态

每个动作资源应具备明确状态：

```text
incoming       新投递，未审核
reviewing      审核中
passed         自动审核通过，等待人工确认或入库策略确认
approved       已进入正式动作库，可被运行时 registry 注册
approved_with_fallback 通过但只能按声明的 fallback 使用
rejected       审核失败，不得进入正式库
deprecated     已被新版本替代，不再给新角色选择
quarantined    哈希、来源或兼容性异常，等待处理
```

建议正式库入库使用不可变版本，而不是覆盖原文件：

```text
motion:locomotion.run@1
motion:locomotion.run@2
```

动作语义 ID 保持稳定，具体资源通过版本和 realization profile 解析。已被角色使用的版本不能静默替换；新版本应经过重新审核后再切换默认索引。

### 入库动作索引

正式 manifest 至少应记录：

```json
{
  "semantic_action_id": "action:locomotion.run",
  "motion_asset_id": "motion:locomotion.run@2",
  "skeleton_profile_id": "humanoid.v1",
  "source_file": "approved/locomotion_run_athletic_v2.glb",
  "source_digest": "sha256:...",
  "realization_mode": "drive_locomotion",
  "motion_style": "athletic",
  "body_profile_compatibility": ["humanoid.default", "body:tall_slim"],
  "qualification_status": "approved",
  "qualification_report": "review/locomotion_run_athletic_v2.report.json"
}
```

`CharacterEmbodimentAssetRegistry` 启动或收到资源库刷新事件后，读取正式 manifest，注册通过审核的动作。角色运行时只提交 `semantic_action_id`、动作上下文和 claims，不直接提交文件路径或未经审核的 clip 名称。

### 入库安全边界

- 审核程序只读取和产出报告，不写角色 Transform、Velocity、伤害、库存或世界状态。
- `approved/` 的动作仍需通过角色骨架和 AnimationTree 的运行时绑定检查，不能仅凭离线审核结果宣称可播放。
- 失败动作保留原文件和失败报告，不能删除审核证据。
- 已注册动作的内容哈希、来源、重定向方法和审核报告必须可追溯。
- 正式库刷新应是原子操作：先生成新索引，验证完整后再切换 registry 使用的索引版本。
- 动作文件被替换、哈希变化、骨架版本变化或审核规则版本变化时，应自动降级为 `reviewing` 或 `quarantined`。

### 适合本项目的第一版

第一版可以先采用手动命令触发，避免在 Godot 运行时直接监听文件系统：

```text
python tools/motion_library_qualification.py scan
python tools/motion_library_qualification.py review <asset_id>
python tools/motion_library_qualification.py approve <asset_id>
python tools/motion_library_qualification.py rebuild-index
```

后续再增加文件夹监视器，实现 `incoming/` 文件落地后的自动扫描。无论自动还是手动，最终都必须走同一个审核器、同一个 manifest schema 和同一个正式索引生成器。

### 新增验收标准

1. 把动作文件放入 `incoming/` 后，可以被扫描发现。
2. 自动审核能生成成功或失败报告，并给出明确原因。
3. 手动审核可以确认、拒绝或退回动作。
4. 审核通过的动作自动获得 `approved` 标记并进入正式 manifest。
5. 未通过审核的动作无法被 `CharacterEmbodimentAssetRegistry` 注册。
6. 角色只能通过语义索引调用正式动作，不能绕过 registry 读取投递目录。
7. 动作版本、哈希、重定向来源、骨架版本和审核记录可以追溯。
8. 替换或修改正式动作后，旧版本保持可回滚，新版本必须重新审核。
