### 1.1 历史讨论中最重要的产品洞察

历史对话反复指向同一个目标：玩家要的不是无限预写的事件，而是无限的因果涟漪。小镇因此不能只是“居民站在固定地点说台词”，而应满足：

1. 世界在玩家不在场时仍按受治理的节拍推进；
2. 居民的日常行为由程序和状态调制，关键关系节点才唤醒完整智能体；
3. 玩家做过的事进入关系、记忆、事物和事件档案；
4. 司命可以总结、提示、命名和催化，但不能强制改写角色私有记忆或替角色决定；
5. 重要结果能在玩家下一次回来时被看见、听见或被角色提起。

这些是本稿的设计原则，不是对当前产品已完成程度的声明。

## 2. 小镇的产品定义

### 2.1 一句话

`[本线程提议]`

小镇是一个以旅游、短住、公共活动和地方记忆为核心的公共社会入口与长期关系底座；个人区域是小镇中的私域节点；剧本、桌游和共建是关系产生长期涟漪的活动场。小镇不承担农业、采矿、重生产或城市级供给职责。

```text
小镇公共生活
  -> 认识居民、观察关系、接受活动
  -> 选择锚点朋友
  -> 朋友介绍本地朋友圈
  -> 个人区域来访与桌游
  -> 共同经历写回关系和记忆
  -> 剧本角色作为外来关系增量进入小镇
```

### 2.2 体验参考的边界

小镇可以参考星露谷物语的“可步行小镇、居民日常、地点记忆和季节节奏”，个人区域可以参考动物森友会的“私域归属、来访和共同布置”。

这些仅是体验参考。初代不复制相关 IP 的名称、角色、地图、规则、任务文本、卡牌、图标、美术、音乐或整体包装。

### 2.3 小镇不是什么

首发小镇不是：

- 完整开放世界；
- 全天候精确模拟所有居民的城市模拟器；
- 依靠抽卡或无条件收集角色的招募大厅；
- 一个与现有 Gameplay authority 平行的第二世界；
- 让低密度运行的居民被误写成永久“背景居民物种”的舞台；所有居民仍共享同一角色账本。

### 2.4 旅游小镇定位

`[本线程提议]`

小镇的核心客流来自短途游客、剧本来访者、返乡居民和玩家朋友，而不是来自农业、采矿或城市级生产。小镇保留工作坊、杂货铺/游客服务站和河岸维护，是因为这些地点能把“地方特色”转化为可参与的体验与关系事件，同时满足基本日常生活，而不是为了建立完整生产链。

首发的旅游职能包括：

- 旧车站抵达、访客登记和剧本入口；
- 茶馆、酒馆、桌游和晚间聚会；
- 工作坊手作体验、修理和公共设施共建；
- 河岸散步、观景、纪念物和低压力私聊；
- 杂货铺/游客服务站的日用品、纪念品、预约和地方服务；
- 大型公寓、茶馆楼上、短住屋和玩家个人区域形成的长租/短住住宿网络；
- 广场节庆、公告、地方档案和居民带路活动。

首发明确不承担：农田、作物成长、采矿、矿石加工、重型货运、城市级商业街、税收或完整游客经济模拟。游客只改变活动密度、预约和关系机会，不成为需要独立 authority 的资源人口系统。

### 2.5 旧车站与档案馆的明确功能

旧车站和档案馆是北部相邻的两个独立节点，不是一个复合建筑：旧车站负责移动、城市接驳和短住抵达；档案馆负责公开地方记忆、事实边界和允许公开的剧本回流。两者都不是政府机关、物流中心或角色私有记忆仓库。

#### 档案馆负责什么

1. **公开地方记忆**：保存小镇地标、公共项目、节庆、旧建筑、河岸路线和已公开的居民共同经历。它回答“这个地方发生过什么”，不回答角色心里真正怎么想。
2. **访客与剧本登记**：记录玩家、剧本角色和短住者的公开抵达、离开、访问期限和允许公开的事件摘要，作为剧本角色进入小镇关系网的入口。
3. **事实核验与公开边界**：许宁等角色负责区分传闻、已观察事实、公开记录和不可公开的私有信息。档案馆可以拒绝记录未经证实的内容，也不能把角色私有记忆自动公开。
4. **地点导览**：维护小镇、树林和山地的公开地图、历史地名与安全提示。城市列车班次、进货和专业服务由相邻旧车站负责。
5. **剧本前置与回流**：开启首发剧本，保存剧本结束后允许公开的地方事件摘要；不保存完整案件私密证据，不替玩法 authority 结算案件。

#### 档案馆不负责什么

- 不管理居民的全部私有记忆、关系数值或人格档案；
- 不决定谁必须参加活动，不替居民接受邀请；
- 不直接供应杂货、燃料、水、电或建筑材料；
- 不负责列车班次、行李、城市采购或短住接待；
- 不承担城市行政、税务、物流、旅店库存或小镇经济 authority；
- 不把“玩家看见的演出”自动变成所有居民都知道的事实。

因此，档案馆的玩法价值不是“查资料拿奖励”，而是让玩家理解地点和关系的公开边界，并把剧本、访客登记和小镇长期记忆连接起来。城市接驳、进货和短住抵达则通过相邻旧车站完成。

### 2.6 旧车站的独立功能

旧车站是小镇连接外部城市的交通节点，和档案馆共用北部步行区，但拥有独立建筑、入口、营业时段和交互状态。

- 玩家抵达小镇、离开小镇或前往城市都从旧车站完成；
- 处理城市采购、杂货铺/旅店/茶馆的大宗进货、水电、专业维修、医疗和行政服务的委托；
- 提供列车班次、行李寄存、短住抵达和旅店接待；
- 剧本开始前，玩家在车站完成“出发”；剧本结束后，角色在车站完成“返回”；
- 车站不保存地方历史，也不判断哪些关系事实可以公开。

旧车站的最小玩法是“决定是否离镇、委托谁去城市、等待多久、回来后发生了什么”；它不需要首发制作一张完整城市地图。

### 2.6 个人区域核心地块与外缘扩展带

玩家个人区域不是“住宅核心地块 + 另一张公共树林地图”，而是一块连续的长期空间，由核心地块和外缘扩展带组成。住宅、桌游房、工作台、纪念区、树林、山坡和溪谷在同一块连续区域中；小镇只在河岸公园一侧设置公共入口和短桥，不在核心地块与外缘之间制造加载式边界。

首发外围不做完整开放世界，而是做可逐步开放的扩展带：

- **林缘带**：从玩家前院或侧院直接进入，散步、采风、寻找建造灵感和低风险材料；
- **山脚带**：从林缘带继续上行，观景、短途攀登、拍摄地点和公共设施维护路线；
- **山坡/溪谷带**：后续扩建个人工作室、纪念区、观景平台或小型共建项目；
- **城市接驳带**：通过旧车站离开小镇，处理小镇不承担的日常供给和专业服务。

外围扩展与个人区域共享同一个 `Personal Area State`，但“连续空间”不等于玩家可以无条件占有所有土地。扩建必须经过地点 authority、公共通行边界和相关居民/小镇项目的协商；林缘和山地可以保留公共步道、观景权和居民维护路线。

## 3. 空间设计：一条能走完的关系街区

本章的可执行地图细节已拆分到 [小镇地图与空间循环设计](2026-09-小镇地图与空间循环设计.md)；居民 roster、住所组团和工作地点已拆分到 [首发居民、住所与工作地点设计](2026-09-首发居民住所与工作地点设计.md)。

### 3.1 设计目标

初代小镇应让玩家在 5～10 分钟内走完主要区域，并在第二次返回时凭记忆寻找人和地点。地图不追求面积，追求：

- 地点有明确社会功能；
- 每个地点至少关联一组居民；
- 同一地点可以因为时间、关系和事件改变含义；
- 玩家能从公共地点自然进入个人区域和剧本事件。

### 3.2 首发布局

```text
                               北
          北林边界/观景坡 —— 旧车站老街 —— 旅店 —— 东北住宿坡
                |              |       \          |
          北侧观景台 —— 档案馆 —— 中央商业区 —— 大型公寓楼
                |              |    /  |  \          |
          河湾码头 —— 河岸公园 —— 中央广场 —— 居民街
                |           /      |      \          |
          西侧林缘 —— 短桥入口 —— 工作坊 —— 娱乐综合楼 —— 东侧居民街
                |              \      |       /          |
          个人核心 —— 个人外缘 —— 社区休闲中心 —— 活动草坪
                |                  |       |        |
          西南森林步道 —— 南侧溪谷 —— 户外运动带 —— 东南山地环线
```

地图不是一张被动放大的大平面，而是“中心社会核 + 四个外围分区 + 中心短环/全镇长环”的扩容结构：中心短环服务第一小时，全镇长环服务第一周和重复探索。

1. **中心商业与公共核心**：中央广场、公告栏、杂货铺/游客服务站、咖啡馆/茶馆综合楼。玩家在这里接收公开信息、完成日用采买、预约体验、遇见多人并决定今天的社交方向。
2. **北部接驳与记忆区**：旧车站、旅店、档案馆、北侧观景台。旧车站负责城市接驳和剧本出入；档案馆负责公开地方记忆和事实边界；两座建筑相邻但不可互相替代。
3. **东部住宿生活区**：大型公寓、居民街、短住院落和东南山地环线入口。玩家在这里遇到居民的工作、接待、休息、互助和冲突。
4. **南部工作与社区休闲区**：工作坊、社区休闲中心、桌游馆、活动草坪、户外运动带和河岸步道。负责手作体验、共建、运动、桌游和一周事件，不承担重生产。
5. **西南连续私域与风景区**：河湾公园、河湾码头、个人核心、林缘、南侧溪谷和森林步道。负责散步、共建、桌游和探索扩展。

建议首发包含 32 个主要节点和 80～100 个可辨识子地点；中心商业/社区节点在第一小时和第一周开放，外围景区与运动节点按路线逐步开放：

| 地点 | 首发功能 | 关系与记忆价值 |
| --- | --- | --- |
| 中央广场 | 偶遇、公告、集合、节庆 | 观察居民关系和主动社交的主场 |
| 居民街 | 住宅、门口互动、日常路线 | 让玩家记住“谁住在哪里” |
| 工作坊 | 修理、制作、共建准备 | 让能力和互助变成关系事件 |
| 杂货铺/游客服务站 | 购买日用品和纪念品、交换手作、预约体验和游客问询 | 连接日用需求、游览活动、公共项目和店主关系 |
| 咖啡馆/茶馆/台球厅综合楼 | 咖啡、茶饮、轻松聊天、台球约局和露天座位 | 形成白天到夜间的垂直社交入口 |
| 酒吧与夜间庭院 | 夜间聚会、居民演出、关系协商和桌游复盘 | 传播晚间公共信息和朋友圈关系 |
| 社区休闲中心与桌游馆 | 社区活动、室内休闲、原创桌游和雨天替代活动 | 连接居民、玩家、运动带和公共项目 |
| 户外运动带 | 球场、综合草地、慢跑、看台和露天活动 | 提供低压力重复活动和能力展示，不占中央广场 |
| 公告栏 | 活动、请求、公共项目 | 把系统事件转成可理解的社会入口 |
| 河岸公园 | 散步、观景、少量采集、私聊、短暂避开人群 | 支持低压力关系推进和地点记忆，不形成采集生产链 |
| 旧车站 | 抵达、离开、城市接驳、行李、短住和剧本出入 | 把小镇与城市服务连接起来，不把城市搬进小镇 |
| 档案馆 | 公开地方记忆、事实核验、公开访客档案和剧本回流 | 把允许公开的共同经历接回小镇，不公开角色私有记忆 |
| 河岸步道/观景小路 | 采风、带路、节庆布置和受控外部输入 | 给小镇循环一个可控的旅游外部输入，不扩成开放世界 |

玩家个人区域从河岸公园进入，不放在地图外的独立菜单里。它在空间上属于小镇旅游步行网，但在权限和状态上属于玩家私域。大型公寓楼则提供公共门厅和长租/短住单元，成为居民与访客的住宿交叉节点。

### 3.3 地图节点的可玩闭环

每个地点至少要提供一项可重复动作、一条关系入口和一个会回流小镇的结果。地点不是传送点，也不是只能触发对白的背景。

| 地点 | 玩家可重复动作 | 可能遇见 | 结果如何回流 |
| --- | --- | --- | --- |
| 中央广场 | 查看今日公告、参加短活动、观察居民关系 | 多名居民、临时来访者 | 公开事件、活动出席、关系目击记录 |
| 居民街 | 访问门廊、帮忙处理小请求、观察回家路线 | 锚点朋友及其朋友圈 | 承诺、拒绝、邀请和家庭/朋友关系变化 |
| 工作坊庭院 | 交付材料、修理设施、推进一次共建工序 | 手艺型居民、协作对象 | 公共项目进度、共同劳动记忆、可用设施 |
| 杂货铺/游客服务站 | 购买日用品和纪念品、交换手作、预约体验或提交公共项目需求 | 店主、游客、来参加活动的居民 | 货架、展示架、体验席位、店主信任和次日活动 |
| 咖啡馆/茶馆/台球厅综合楼 | 咖啡、茶饮、预约席位、台球约局和低压力闲聊 | 朋友圈成员、游客、晚间约局者 | 预约名单、约局记录、共同经历和关系变化 |
| 酒吧与夜间庭院 | 夜间聚会、居民演出、桌游复盘和关系协商 | 朋友圈成员、返乡居民、短住者 | 晚间活动、公开传闻、邀请或暂缓 |
| 社区休闲中心与桌游馆 | 社区活动、原创桌游、规则教学、雨天替代活动 | 居民、玩家朋友、活动参与者 | 公共组局、活动结果、再次邀请条件 |
| 户外运动带 | 球场、综合草地、慢跑、拉伸和小型比赛 | 居民、游客、愿意约局的角色 | 运动约局、能力表现、活动照片或公告 |
| 公告栏 | 接取一项居民请求或公共项目任务 | 司命投影的公开摘要 | 任务承诺、期限、完成/失约后果 |
| 河岸公园 | 散步、收集少量材料、进行私聊 | 需要安静空间的居民 | 私人关系节点、共建材料、生活简报素材 |
| 旧车站 | 抵达、开启/结束剧本、登记短住、乘车去城市 | 剧本角色、旅客、接待员 | 剧本 session、城市服务结果、住宿承诺 |
| 档案馆 | 查阅公开地方记忆、核验公开事实、整理允许公开的事件摘要 | 档案保管者、记录员、玩家 | 公开知识、地方事件记录、关系边界 |
| 河岸步道/观景小路 | 进行一次短途观景、采风或接待活动 | 远方消息或一次性访客 | 下一日公告、活动变化、可选访客种子 |

地点的动作必须有明确成本或承诺，例如时间段、材料、邀请名额或关系风险。这样玩家不能在一个地点无限刷同一奖励，居民也不会被迫重复回应同一请求。

### 3.4 杂货铺：日用采买、游客服务和关系入口

首发只做一家“杂货铺/游客服务站”，不做大型商业街或自由交易市场。它负责居民、玩家和短住者的日常采买，也负责游客问询、纪念品、有限手作交换和体验预约，是一个有自己边界的居民工作场所。小镇的日常供给只支持生活、活动与维护，不发展成城市供应链。

#### 商店的六类服务

| 服务 | 玩家行为 | 首发边界 | 社会回流 |
| --- | --- | --- | --- |
| 日用货架 | 购买少量食物、清洁用品、简单药品、灯具、文具、工具耗材和桌游消耗品 | 每日固定基础库存，不无限刷新稀有物 | 玩家可以维持生活、准备来访或回应请求 |
| 纪念品与小物 | 购买少量本地手作、地图册和活动小物 | 每日固定基础库存，不无限刷新稀有物 | 玩家可以准备来访、共建或回应请求 |
| 次日预订单 | 预订明确的日用品、桌游耗材或活动小物 | 仅限有限目录；缺货时店主可协商替代或拒绝 | 形成次日路线、承诺和店主信任 |
| 手作交换 | 用活动成果、公共项目凭证或玩家制作物交换另一类小物 | 只允许有限配方和当日额度 | 交换会改变店主对玩家可靠性的判断 |
| 体验预约 | 预约工作坊、河岸导览或节庆准备时段 | 需要提前承诺；满席时店主可协商替代或拒绝 | 形成次日路线、公告或朋友求助 |
| 公开活动单 | 查看店主和居民共同需要的活动、接待和维护事项 | 只展示公开事实，不泄露任何角色私有记忆 | 连接工作坊、公告栏、茶馆和公共项目进度 |

商店不首发完整价格波动、股票式交易、无限出售或玩家间自由市场。展示物和体验席位变化必须来自公开活动、公共项目消耗或受治理的 `simulation` 结果；正式交易仍由既有 authority 结算。

#### 商店营业节奏

```text
上午：开门、日用补货、接收预订单
下午：处理交换、日用补货、体验预约、店主与居民往来
傍晚：关店；店主可能在茶馆、广场或自家门廊出现
```

店主不应永远站在柜台。玩家可以在营业时间购买日用品、预约体验或谈交换，在闭店后通过住宅门廊、公寓公共厅或茶馆进行关系互动，但不能把闭店访问当作强制交易入口。

#### 商店的可见状态

玩家应能从货架、门牌、公告和店主行动理解商店状态：今日缺货、预订单待取、公共项目专用箱、店主暂缓某项交换。客户端只消费 authority 结算后的库存和订单投影，不能自行把“买到”写入小镇状态。

#### 咖啡馆、茶馆、台球厅与酒吧

商业娱乐区采用垂直复合楼，而不是把所有设施摊成孤立建筑：一层是面向主街的咖啡馆和露天座，二层是较安静的茶馆与阳台，三层是台球厅；酒吧位于侧翼或后院，有独立入口、夜间营业时段和小型演出空间。共享后勤不等于共享访问边界，角色可以只接受咖啡馆见面、拒绝酒吧聚会或改约台球局。

咖啡馆承担白天游客服务和初次相识；茶馆承担熟人聊天和关系协商；台球厅承担低压力轻竞技；酒吧承担傍晚聚会、居民演出、镇闻和桌游复盘。酒水、约局和营业状态仍由地点/活动 authority 结算，不做独立经济系统。

#### 社区休闲中心、桌游馆与户外运动带

社区休闲中心位于工作坊南侧、居民区与南部运动带交界处，不放在中央广场。它包含社区接待大厅、多功能活动室、桌游馆、社区厨房、室内运动室、居民议事室、储物和面向户外的长廊。外侧连接活动草坪、多功能硬地球场、综合草地、慢跑步道、半开放雨棚、看台与器材亭。

中央广场保持开放通行和公共集合功能；运动、赛事、露天电影和大型社区活动在南部休闲带完成。桌游馆是公共组局空间，个人区域桌游房仍是受邀请的私域空间。

### 3.5 居民房屋：日常锚点与访问边界

居民房屋不是可随意进入的装饰室内，而是角色生活的固定锚点。首发每名核心居民都有一处可识别住宅或住宅单元；店主可以住在杂货铺楼上，档案角色可以住在旧车站后室，但都必须有自己的私域边界。

#### 房屋三层空间

| 层级 | 玩家可做什么 | 角色权利与限制 |
| --- | --- | --- |
| 公共门槛 | 在门廊、门口或窗边问候、交付公开请求、观察是否在家 | 角色可以回应、拒绝或表示稍后再谈 |
| 半私域门廊 | 在被邀请或已有稳定关系后短暂停留、进行低压力对话 | 角色可以提出时间、人数和话题边界 |
| 私域室内 | 只有角色明确邀请或预约后进入；可发生深度对话、共同制作或纪念活动 | 私有物品、五池记忆和未公开关系不因玩家进入而自动暴露 |

玩家不能用家具、路线或系统提示强制打开居民房门。拒绝、暂缓、闭门和改约都是合法关系结果，并应留下可解释的短期状态而非惩罚性黑名单。

#### 首发住宅配置

| 住宅类型 | 居民生活锚点 | 特色互动 | 可变状态 |
| --- | --- | --- | --- |
| 锚点朋友住宅 | 门廊、共享物架、个人工作台 | 预约拜访、查看共同项目、讨论朋友圈邀请 | 是否在家、是否愿意单独谈、是否准备带朋友来 |
| 朋友圈成员住宅 | 各自的兴趣物件和安静角落 | 条件式来访、修复关系、交换个人请求 | 对玩家的信任、是否愿意参加群体活动 |
| 店主住宅/店铺楼上 | 货单本、库存箱、休息区 | 闭店后的关系对话、解释缺货或替代品 | 货单、预订单、店主对玩家可靠性的判断 |
| 档案/剧本角色住宅单元 | 行李、地方档案或外来物件 | 来访登记、回顾剧本经历、决定是否暂住 | 访问期限、居住承诺、与镇民的关系扩散 |

房屋状态至少包含：`home_presence`（是否在家）、`visit_permission`（访问许可）、`hosting_plan`（是否准备接待活动）、`private_boundary`（当前不可谈/不可入范围）。这些是产品层状态映射，正式写入仍通过小镇/角色 authority。

#### 房屋与日循环

居民房屋应让玩家在一天的不同阶段有不同理由来访：

- 上午：门廊交付请求、确认店主预订单或观察居民是否出门；
- 下午：预约进入半私域空间，完成修理、共同制作或关系协商；
- 傍晚：接受聚会邀请、在门廊等待朋友，或发现某人因关系冲突没有回家。

房屋不提供无限可刷的礼物和好感度。每次访问至少消耗一个行动窗口、兑现一项承诺或承担一次关系风险。

### 3.6 地点不是静态 UI

同一地点应允许出现不同社会含义：

- 广场：第一次是认识居民，后来可能是朋友集合或公开争执的地方；
- 工作坊：第一次是教程协作，后来可能变成某个角色主动提出共建的地方；
- 咖啡馆/茶馆/台球厅与酒吧：第一次在咖啡馆或茶馆听到镇闻，后来可能在台球厅约局或酒吧听到关于玩家或剧本角色的不同版本；
- 河岸：第一次是安静对话，关系紧张后可能成为角色主动避开的地方；
- 旧车站：第一次是玩家到达，后来是剧本角色来访或离开的地方。

地点状态和关系事件都应通过结构化事件产生，不靠客户端单独改变文字或布景。

### 3.7 居民锚点与可变路线

每名首发居民拥有“固定锚点 + 可变路线”两层地图存在：

- 固定锚点回答“玩家总能在哪里找到他”：住宅门廊、工作坊工位、酒馆角落或河岸长椅；
- 可变路线回答“今天为什么在别处”：公开请求、朋友邀约、未完成承诺、关系冲突或公共项目进度。

首发不需要全天候自由模拟，但每个活动时段至少为核心居民生成一条可解释路线：

```text
上午：住宅/工作坊锚点 -> 采购或处理个人目标
下午：工作坊/广场 -> 协作、拜访或响应公告
傍晚：茶馆/台球厅/酒吧后院/桌游馆/河岸 -> 聚会、私聊、桌游或回家
```

玩家第二次返回时，应能通过公开结果理解路线变化，例如“工作坊修理延误，所以锚点朋友今晚没有来茶馆”，而不是看到无法解释的随机换点。

## 4. 居民构成与世界存在模式

### 4.1 统一角色前提

`[本线程提议；吸收对话5/8/9/11]`

三层人口模型不应被理解为三种居民物种，也不应把“核心角色 / 活跃居民 / 背景人群”写成永久身份等级。小镇中的角色原则上都是同一类完整角色智能体，只是在不同时间、地点、关注度和玩法需求下，采用不同的连续性 fidelity tier。八月正式设计还区分世界消费模式 `game`、`simulation`、`replay`；它们回答世界如何被消费，不是角色人口类型。

“首发 3～5 名重点角色”描述的是首发需要验证近场完整 agent 的角色数量，不是说其他居民永远不完整。可见居民数量可以大于 3～5，但他们在没有进入高密度交互时，不必持续运行完整的表现和推理链。

### 4.2 八月正式模型在小镇中的映射

`[已有设计] + [本线程产品映射；不是新增 runtime contract]`

本节对照八月的 [第三阶段范围与运行模式边界](../8月分析/第三阶段推进/01-第三阶段范围与运行模式边界.md) 与 [群体模拟与角色分级连续性](../8月分析/司命与群体世界补充设计/03-群体模拟与角色分级连续性.md)。

#### 世界消费模式

| 正式模式 | 小镇中的用法 | 写入边界 |
| --- | --- | --- |
| `game` | 玩家即时走访小镇、进入个人区域、参与剧本或桌游 | 局内意图由玩法/领域 authority 结算，成功后才写入正式事件 |
| `simulation` | 玩家离场后按小时/日级 cadence 推进居民计划、行为种子和 owner-bound intent | 群体模拟不能直接写世界，必须经过既有 owner admission 和 receipt |
| `replay` | 重建小镇、个人区域和局内结果，验证固定输入、回放和投影 | 零 production write |

#### 同一角色的连续性 fidelity tier

| 正式 tier | 小镇中的表现 | 最小边界 |
| --- | --- | --- |
| 远场批量 | 玩家离开小镇时，角色仍按自己的身份、关系、资源和目标推进生活 | 读取 scoped owner projection，输出计划、行为种子或 owner-bound intent；不创建 shadow NPC |
| 中场预热具身壳 | 角色进入玩家邻域或公共活动范围时，先以有位置、有动作的具身壳出现 | 只载入同一 `CharacterRecord` 的 canonical snapshot、当前任务和可见种子；不载入私有五池记忆，不产生独立关系状态 |
| 近场完整 agent | 玩家直接对话、桌游、共建或触发重大关系节点时，角色作为有立场的参与者行动 | 获取 activation lock 后运行完整 L1-L4；结果必须经过 revision checked merge/requeue 和领域 authority |

角色生命周期沿用八月状态机：

```text
dormant -> batch_planned -> prewarm -> active -> pending_merge -> dormant
```

读集过期、锁冲突或预算不足时回到较低 tier 或 `requeue`；不能双写、冻结旧身份或生成第二份记忆。玩家远离小镇时，角色从 `game` 回到 `simulation`；需要证明同一结果时，使用 `replay` 重建而不是再跑一次生产逻辑。

如果需要面向产品文案使用 `world_continuity`、`local_presence`、`agent_agency`，必须标注为九月解释性 shorthand：

```text
world_continuity ~= 远场批量 + dormant/batch_planned
local_presence  ~= 中场预热具身壳 + prewarm
agent_agency    ~= 近场完整 agent + active
```

它们不是八月正式 runtime 名称，也不与 `game/simulation/replay`、生命周期状态或控制优先权一一对应。

### 4.3 连续性 tier 与控制模式不是一回事

`[已有设计映射]`

连续性 tier 回答“角色以多高的计算预算、具身密度和认知精度存在”；控制模式回答“当前由谁拥有执行优先权”。二者不能混为一谈：

| 组合示例 | 含义 |
| --- | --- |
| `中场预热具身壳 + agent_full_auto` | 角色在现场，并自主决定下一步受限动作 |
| `近场完整 agent + player_priority_assisted` | 角色完整理解和规划，但玩家拥有执行优先权，角色输出建议而非强制命令 |
| `中场预热具身壳 + away_conservative_takeover` | 角色仍在现场，但临时由受限接管处理狭窄动作 |
| `远场批量 + agent_full_auto` | 角色在离场连续性队列中推进自己的生活；这是压缩执行其个体账本，不是统计平均 |

当前仓库已有 `agent_full_auto`、`player_priority_assisted`、`away_conservative_takeover` 和 `scripted_override` 控制模式。它们是现有运行时控制面；本稿只是把八月正式连续性设计映射到小镇产品，不能声称完整小镇产品协议已经实现。

### 4.4 所有 tier 共享同一份角色账本

`[本线程提议；吸收对话5的“个体状态压缩与还原协议”]`

任何模式都不能创建角色副本。角色切换时必须继续使用同一份：

- CharacterProfile / authored identity；
- 多重身份和当前目标；
- `NeedTensionState`、`CharacterDynamicState` 等运行态；
- 五池记忆和关系记忆；
- 当前地点、物品、资源和活动承诺；
- 未解决张力、生活简报和待执行蓝图。

从远场批量进入近场完整 agent 时，系统做的是“压缩状态还原”，不是临时生成一个看起来像该角色的新 NPC。从近场完整 agent 回到远场批量时，智能体产生的结构化结果、事件记忆和关系变化必须先经过既有写回/authority 边界，再回到群体模拟队列。

### 4.5 首发的角色规模与可见人口

首发建议有 **54 名有名字的可识别居民**：6 名核心居民，外加 48 名家人、朋友、邻居和工作伙伴。每天根据时段、工作和关系事件，玩家实际看到其中约 12～20 名；其余居民可能在工作地点、住所、短途外出或远场批量中。详细 roster 见 [首发居民、住所与工作地点设计](2026-09-首发居民住所与工作地点设计.md)。

- 3～5 名角色需要具备近场完整 agent 的验证覆盖；
- 6 名核心居民都有完整档案、住所、工作地点和关系种子；
- 48 名网络居民都有名字、住所或稳定居住安排、一个社会锚点和至少一条关系边，但首发主要运行远场批量或中场预热具身壳；
- 卫星居民可以因玩家持续关系、家庭冲突、工作请求、桌游席位或重大事件进入近场完整 agent；
- 不允许用“背景居民”标签绕过角色连续性，也不允许为节省成本创建与正式角色分离的 shadow state。

54 名是产品层的可见人口规模，不是当前仓库已实现的人口数量。首发实现应优先验证一组核心居民和 2～3 名网络居民的完整关系纵切，再扩展其他居民的行为覆盖。

### 4.6 首发居民、住所与工作地点

`[本线程提议，待正式 spec/plan]`

首发不把居民设计成“职业标签 + 一句台词”，而是为每人同时配置住所、工作地点、日常目标和关系边。工作地点负责把个人目标接入小镇公共循环，住所负责表达生活边界和邀请关系。

#### 首发居民 roster

| 居民 | 角色定位 | 住所 | 主要工作地点 | 固定锚点 | 关系作用 | 首发运行密度 |
| --- | --- | --- | --- | --- | --- | --- |
| 林澈 | 修理师、公共项目发起者；玩家的默认锚点朋友 | 工作坊旁的小院，门廊有共享物架 | 工作坊庭院 | 工作台、广场公告栏 | 带玩家认识许宁和周野；最早提出共建请求 | 近场完整 agent 重点验证 |

| 周野 | 茶馆主持人，善于组织活动但不喜欢替别人承诺 | 复合娱乐楼茶馆楼上的小房间 | 茶馆、台球厅、酒吧后院和桌游馆 | 靠窗座位、二层阳台、桌游馆入口 | 负责把本地朋友圈带到桌游；对公开冲突很敏感 | 近场完整 agent 重点验证 |
| 顾岚 | 杂货铺店主，可靠但对欠约和临时改约敏感 | 杂货铺楼上或大型公寓长租单元 | 杂货铺/游客服务站 | 日用货架、展示架、预约台、公共门厅 | 连接日用采买、游客体验、活动预约和公共项目；可以合理拒绝缺乏准备的玩家 | 近场完整 agent 重点验证 |

这六人是首发小镇的核心居民，不是小镇的全部人口。林澈、许宁、周野、顾岚构成首发 3～5 名近场完整 agent 验证池；唐禾和罗闻不是永久的“背景居民”，而是首发预算下先以较低 fidelity 运行，遇到长期承诺、重大冲突、公共项目决策或玩家持续关系后可以升级。

#### 住所分布与共同住户

居民街和周边不是“十八栋互不相干的房子”，而是六个有公共门槛的生活组团。组团让玩家能看见家人和朋友自然相遇，也让住所数量保持在首发可制作范围内：

| 生活组团 | 主要住户 | 公共门槛 | 日常社会含义 |
| --- | --- | --- | --- |
| 工作坊小院 | 林澈、林晚、叶成 | 共享物架、修理台 | 家人、师徒和公共项目冲突会在同一院落留下痕迹 |
| 车站档案组团 | 许宁、许秋、沈桥 | 档案室前廊 | 公开记录与家庭记忆在同一入口发生边界协商 |
| 茶馆后院 | 周野、白芷、周遥（借住） | 茶馆后门、楼梯口 | 聚会筹备、临时借住和来访者消息交汇 |
| 杂货铺后院 | 顾岚、顾槐 | 后门展示/预约箱 | 日用服务、游客体验安排和亲属意见直接影响商店营业 |
| 大型公寓楼 | 多组长租居民、周遥等短住者 | 公共门厅、共享厨房、观景露台 | 家人、旧友、返乡者和访客在同一住宿节点交叉，但不共享私人房间 |
| 河岸小屋群 | 唐禾、唐青、池木 | 河岸长椅、观景台 | 维护、观景和兄妹分歧形成低压力公共路线 |
| 居民街公共住宅 | 罗闻、罗聆；杜衡租住 | 公告栏旁资料桌 | 公共事务、调解和居民请求在住宅门口交汇 |
| 居民街租屋 | 赵禾 | 门廊和观景路线入口 | 接待伙伴保持独立住处，不被误写成顾岚的附属角色 |

组团内部可以共享门廊、院落或工作台，但卧室、个人物件和私有记忆仍属于各自角色。共同住户不等于自动共享所有关系和知识；一次家庭争执也不应自动成为全镇公开事实。

卫星居民首发的最小档案包括：`resident_id`、`home_anchor`、`work_or_activity_anchor`、一条核心关系、一个当前目标、一个可拒绝条件和一条公开记忆摘要。只有进入近场完整 agent 时，才加载其获准私有记忆；不能因为玩家看见卫星居民在街上，就把它们当作无边界的公开 NPC。

#### 工作地点的六种公共作用

| 工作地点 | 负责的公共作用 | 居民工作中的玩家介入 | 结果回流 |
| --- | --- | --- | --- |
| 工作坊庭院 | 修理、手作体验、共建工序 | 预约体验、选择修理优先级、协助一段工序 | 公共设施进度、工作记忆、游客活动记录 |
| 旧车站 | 城市接驳、剧本出入、短住抵达 | 查看班次、登记抵达、委托城市服务 | 剧本入口、住宿承诺、城市服务结果 |

| 咖啡馆/茶馆/台球厅/酒吧后院 | 白天聊天、台球约局、夜间聚会、镇闻和桌游排期 | 预约席、约局、邀请参与者、处理公开误会 | 活动名单、共同经历、朋友圈关系 |

每个工作地点只承担一个主要公共作用和一个主要关系入口，不首发完整职业树、工资系统、生产链或自由市场。工作地点的正式库存、项目进度、任务和活动安排仍由小镇/Gameplay authority 通过事件写入。

#### 居民的住所—工作地点关系

住宅和工作地点不能互相替代：

- 工作地点回答“这个人今天在为小镇处理什么”；
- 住所回答“这个人在下班后愿意让谁靠近”；
- 玩家在工作地点可以先获得公开事实和共同任务，再通过住所请求更私人的协商；
- 工作地点的失败可以改变住宅访问许可，例如欠缺材料导致顾岚暂缓接待；
- 住所中的关系事件可以改变第二天的工作路线，例如许宁与玩家修复关系后愿意在档案馆安排公开查阅时段。

#### 大型公寓的住宿规则

大型公寓是旅游小镇的低层住宿地标，不是无限容量的酒店后台。建议产品层配置为 3～4 层、8～12 个长租单元、4～6 个短住单元，以及一层公共门厅、共享厨房、洗衣/晾晒区和小型活动室。屋顶或高层露台只承担观景和夜谈，不承载第二套桌游或人口 authority。

公寓的最小状态包括：

- `unit_id`：具体住宅或短住单元；
- `occupancy_plan`：长期、短期、空置或待协商；
- `common_room_access`：公共厅是否开放、可容纳多少人；
- `guest_permission`：住户是否允许玩家或其他居民来访；
- `stay_commitment`：短住者的离开日期、返程承诺或延期提案。

玩家可以在公共门厅偶遇住户，可以被邀请进入某个单元，也可以向公寓居民发出明确的来访请求；进入公寓不等于获得全部单元的访问权。剧本角色若暂住公寓，仍保留其 Canonical Character State 与小镇角色的连续性，离开时只结束住宿安排，不抹除关系或记忆。

#### 一日路线样例

```text
林澈：工作坊旁小院 -> 工作坊庭院 -> 广场查看公告 -> 茶馆/门廊
许宁：档案馆住宅 -> 档案馆开放 -> 公告栏/河岸核验 -> 预约访客
周野：茶馆楼上 -> 茶馆开门 -> 广场招呼朋友 -> 茶馆聚会
顾岚：店铺楼上/公寓 -> 杂货铺开门 -> 货架/预约台/公告栏 -> 茶馆或住宅休息
唐禾：河岸小屋 -> 河岸公园 -> 观景小路 -> 河岸长椅
罗闻：公共住宅 -> 公告栏/广场 -> 各地点确认活动 -> 广场收尾
```

路线不是硬编码的完整日程。每个时段只需要锁定一个可解释锚点和一个可变目的地；请求、预订单、关系冲突、公共项目延误或玩家邀约可以改变可变目的地，并在生活简报中留下原因。

### 4.7 锚点朋友

玩家只需要认识一个小镇朋友，就能进入完整的社交网络。这个角色称为锚点朋友，不是收集奖励，而是玩家在小镇社会中的第一个关系支点。

锚点朋友至少拥有：

- 自己的住宅和日常路线；
- 两名本地朋友圈成员；
- 一个能和玩家共同完成的活动；
- 一条与朋友圈成员的亲近或依赖关系；
- 一条尚未解决的分歧、边界或顾虑；
- 邀请朋友来个人区域的主动目标。

锚点朋友可以介绍朋友，但不能替朋友接受邀请；朋友可以合理拒绝、暂缓或提出条件。

### 4.8 剧本角色的进入方式

剧本角色不是小镇原住民的替代品。首个剧本完成后，角色获得的是进入小镇关系网络的机会：

- 角色可以回到原世界；
- 可以来小镇短暂访问；
- 可以和玩家或镇上朋友建立独立关系；
- 可以拒绝长期居住；
- 可以因为剧本中的共同经历改变对已有居民的态度。

这使剧本成为“关系增量”，而不是“角色来源的唯一入口”。

## 5. 居民生活节拍

### 5.1 三种运行密度

吸收对话8提出的三层生活密度，但将其映射到初代小镇：

1. **惯性生活**：程序和既有状态投影驱动。居民工作、走路、回家、进行简单交谈；行为参数受到精力、压力、人格投影和关系状态调制。
2. **反应时刻**：由轻量反应逻辑或有限角色运行时处理。居民收到消息、被玩家偶遇、遇到轻微成功/挫折时，产生一条有原因的反应。
3. **深度内省**：完整角色智能体被唤醒。触发于玩家关键互动、关系破裂/修复、重大活动、目标重组、创造性共建或剧本后写回。

首发不需要让所有居民持续调用大模型，但必须保证被唤醒的核心角色能看到足够上下文：近期事件、当前关系、未解决张力、目标、记忆证据和当前地点。

### 5.2 三个活动时段

为了让玩家有清晰预期，首发采用三个粗粒度时段，不做每秒级全镇模拟：

| 时段 | 居民常态 | 适合的玩家行为 |
| --- | --- | --- |
| 上午 | 工作、采购、整理、处理个人目标 | 观察路线、帮助居民、进行短对话 |
| 下午 | 广场活动、拜访、工作坊协作 | 推进关系、接受活动邀请、共建准备 |
| 傍晚 | 茶馆、台球厅、酒吧后院、桌游馆、运动带和河岸露台 | 组织朋友圈桌游、约局、运动、处理关系和事件 |

时段改变的是活动候选和可见行为，不是把角色的长期记忆清零。角色离线或未被激活时，世界运行时仍只提交受治理的连续性结果。

### 5.3 生活简报

参考对话8的“生活简报”概念，角色被唤醒前应接收压缩上下文，而不是重新扫描全部历史：

```text
锚点朋友的生活简报
- 今日活动：上午在工作坊修理公共长椅
- 近期模式：连续两次错过与朋友的约定
- 与玩家关系：信任上升；仍担心玩家只在需要时出现
- 未解决张力：朋友甲不愿参加桌游
- 近期共同经历：玩家帮助完成个人区域的桌游桌
- 当前意图：今晚邀请玩家和朋友甲来一局，但准备先私下确认
```

生活简报是角色运行时的输入投影，不是新的长期记忆 owner。正式记忆仍按现有角色记忆边界写回。

### 5.4 可玩可循环的三层小镇循环

小镇的循环不是单纯“每天刷新礼物”，而是让玩家在有限时间内做取舍，并让取舍改变下一次相遇。

#### 日循环：一次返回就有完整闭环

```text
进入小镇
  -> 查看公告/公开镇闻
  -> 选择一个上午行动
  -> 在路线中遇见居民或触发请求
  -> 选择帮助、旁观、邀请、拒绝或暂缓
  -> 下午处理一个承诺或关系节点
  -> 傍晚参加聚会、桌游、私聊或回家
  -> 结算公开结果与可写回的共同经历
  -> 形成下一次返回的线索
```

首发每个小镇日只保证 2～3 个有意义的行动窗口，不做体力/金钱的复杂经营模拟。限制来自时间、关系承诺、材料和角色是否愿意参加，而不是强制任务清单。

#### 周循环：公共项目把居民重新组织起来

一周内至少有三条可并行但不能全部完成的线：

1. **居民请求线**：完成一名居民的具体请求，获得信任、信息或新的邀请条件；失败或拒绝会留下可解释后果。
2. **公共项目线**：玩家和居民共同修复一个小镇设施，例如广场遮棚、工作坊工具台、社区中心长廊、运动带看台或河岸座椅。每次只推进一到两个工序，完成后改变地点功能或可见路线。
3. **社交活动线**：安排一次桌游、台球约局、散步、运动活动、工作坊协作、茶馆聚会或酒吧后院演出。参与者的接受/拒绝会改变朋友圈关系，而不是只发放奖励。

玩家可以只完成其中一条。周末或周循环结算时，公共项目状态、关系记忆和下周活动候选一起更新；没有完成的线进入下一周的生活简报，而不是静默重置。

#### 章节/季节循环：改变语境，不扩大系统

首发只做一个章节季节，每隔若干周改变一次公共装饰、公告主题、河岸材料和居民活动偏好。章节变化只需要影响：

- 一个公共项目外观或用途；
- 一组居民活动候选；
- 一条地方记忆或短事件；
- 一款桌游的场景包装或邀请条件。

不首发完整农业季节、天气经济、作物成长或四季生产链。章节季节的职责是让玩家感到小镇在继续生活，而不是引入第二套经济 authority。

### 5.5 三类可重复活动

为了让地图不是一次性教程，首发至少提供三类可重复活动，每类活动都必须能影响角色关系或公共状态：

| 活动 | 适合地点 | 重复价值 | 最小结果 |
| --- | --- | --- | --- |
| 帮忙与共建 | 公告栏、工作坊、河岸 | 每次推进不同工序或暴露不同协作关系 | 公共项目进度、共同劳动记忆、设施可用性 |
| 小型社交 | 广场、居民街、河岸、咖啡馆、茶馆、酒吧后院 | 角色因当天目标和关系状态改变回应 | 信任、承诺、邀请条件或暂缓 |
| 室内/户外活动 | 台球厅、桌游馆、社区活动室、球场、综合草地、慢跑道 | 角色能力、偏好和关系边界改变活动结果 | 约局记录、共同经历、再次邀请或替代活动 |
| 私域同桌活动 | 个人区域、个人区域外缘 | 受邀请朋友参加桌游、共建或纪念活动 | 局内结果、共同经历、下一次私域邀请意愿 |

每项活动都要有“再次做但不会完全一样”的来源：不同参与者、不同公开请求、不同关系张力或不同公共项目工序。变化来自角色状态和事件输入，不依赖无限生成新地图。

### 5.6 玩家回镇的理由

每次返回至少由以下三类信号中的两类组成：

- **人**：居民主动邀约、拒绝后的重新协商、朋友之间发生了玩家能介入的分歧；
- **事**：公告栏新请求、公共项目进入下一工序、剧本角色来访或地方记忆被发现；
- **地**：某个地点的功能或路线发生可见变化，例如工作坊开放新工位、河岸出现纪念物、茶馆今晚有桌游。

司命可以把这些信号汇总成可关闭的生活简报，但不能凭空制造不存在的事件。若三类信号都没有，系统应允许玩家安静散步或离开，不用强制弹窗维持活跃度。

## 6. 社会关系模型

### 6.1 首发关系维度

对话2提出了比单一好感度更丰富的关系字段。本稿不把它们全部做成玩家可见数值，而是划分为内部维度和玩家可理解状态：

| 内部关系维度 | 玩家可感知表现 |
| --- | --- |
| `trust` | 愿不愿意告诉玩家真实想法、接受邀请 |
| `affinity` | 是否主动来访、愿不愿意一起玩 |
| `obligation` | 是否记得玩家帮助、是否提出回报或偿还 |
| `suspicion` | 是否保留信息、推迟决定或询问动机 |
| `respect` | 是否认真听取玩家意见、是否承认玩家能力 |
| `dependency` | 是否在特定事情上需要玩家或朋友 |
| `rivalry` | 是否在活动中竞争、比较或争执 |
| `shared_secret` | 是否拥有不愿公开的共同知识 |
| `betrayal_memory` | 是否记得被隐瞒、失约或伤害 |

首发 UI 只显示可解释的关系状态，如“愿意来访”“愿意介绍朋友”“暂缓参加”“正在修复关系”。不把所有内部维度压成一个可刷的好感度。

### 6.2 关系状态推进

```text
认识
  -> 有过共同经历
  -> 愿意单独来访
  -> 愿意介绍本地朋友
  -> 稳定朋友
```

关系推进需要证据：共同完成活动、兑现承诺、公开支持、尊重边界、分享信息等。单次送礼或重复点击不应直接跨越多个状态。

关系也可以倒退，但倒退必须有可理解原因：失约、隐瞒、公开羞辱、共同项目失败后的责任分配、桌游中违背约定等。

### 6.3 关系不是单向玩家数值

锚点朋友和其朋友圈成员之间也有独立关系。玩家的行为可能改变：

- 锚点朋友对玩家的信任；
- 朋友甲对玩家的看法；
- 锚点朋友与朋友甲之间的压力；
- 朋友圈是否愿意在下一次活动中共同出现。

玩家不能通过单独提高与锚点朋友的关系，自动获得整个朋友圈的忠诚。

## 7. 新手教程与第一局桌游

### 7.1 教程路线

```text
旧车站抵达
  -> 中央广场被居民主动问候
  -> 居民街认识两名居民
  -> 工作坊完成一次小协作
  -> 玩家选择一名锚点朋友
  -> 河岸发生一次低压力私聊或合理拒绝
  -> 锚点朋友提出介绍本地朋友圈
  -> 傍晚回到个人区域完成第一局桌游
```

教程至少让三个居民主动与玩家产生联系，但玩家只需重点培养一个锚点朋友。这样“朋友带朋友来”是关系结果，不是教程中一次性生成的队伍。

### 7.2 第一局桌游的社会意义

第一局桌游承担的是“朋友圈首次共同经历”：

- 锚点朋友发起邀请；
- 朋友成员分别接受、拒绝或暂缓；
- 玩家决定是否接受司命建议或自行安排；
- 每名智能体只读取自己的合法信息视图；
- 玩法 authority 结算局内结果；
- 结算后生成关系/共同经历写回候选；
- 下一次小镇访问能观察到关系变化。

司命可以提供可折叠、透明、可关闭的建议，例如“朋友甲可能更在意被尊重而不是输赢”，但不应显示真实私有记忆，不应替角色决定参加，也不应强制玩家采用建议。

## 8. 司命在小镇中的位置

### 8.1 可以做什么

参考对话9的可拒绝选项设计，司命可以：

- 提供今日镇闻或关系线索；
- 在玩家长时间犹豫时给出 2～3 个思路；
- 标注建议依据，如近期共同经历、公开事件和已知关系；
- 预览可能风险，但明确预测可能不准确；
- 在重大关系节点后生成叙事摘要或纪念性命名；
- 在玩家离场后对事件进行低频整理，形成生活简报或地方记忆素材。

### 8.2 不能做什么

司命不能：

- 直接写入角色私有记忆；
- 替角色接受或拒绝邀请；
- 把一个建议强制变成玩家命令；
- 越过玩法 authority 结算桌游；
- 直接制造玩家看不到因果依据的关系变化；
- 直接改写小镇物理状态或个人区域状态。

司命建议关闭后，小镇仍然正常运行；玩家拒绝建议后，世界不会惩罚玩家，也不会反复追问。

## 9. 一个首月关系案例

以下是产品体验示例，不是首发剧本或实现承诺。

### 第一天：认识锚点朋友

玩家在工作坊帮助居民林澈修好一张公共长椅。程序结算材料消耗和工作进度，林澈的角色运行时在结束时被唤醒：他认可玩家愿意花时间，但仍观察玩家是否只是为了教程奖励。

事件写回：

- 长椅状态从 `broken` 变为 `repaired`；
- 玩家与林澈形成“共同完成工作”的事件记忆；
- 林澈对玩家的信任小幅上升；
- 广场居民知道长椅修好，但不知道林澈的全部私下想法。

### 第三天：朋友介绍朋友

林澈在下午主动找到玩家，说想带朋友许宁来玩家区域看看桌游桌。许宁与林澈关系亲近，但对陌生人谨慎。玩家可以接受、推迟或拒绝这次活动；司命可给出提示，但不强制。

许宁暂缓参加并不是失败，而是关系事实：她需要先在广场或河岸与玩家单独交谈一次。

### 第五天：第一局桌游

玩家、林澈、许宁和一名人类朋友完成一局原创合作桌游。许宁在局内使用自己合法的信息和能力，没有读取玩家手牌或系统隐藏状态。最终虽然桌游只取得部分成功，但玩家在关键时刻尊重了许宁的判断。

事件写回：

- 桌游局内状态结束；
- 生成一条共同经历；
- 许宁从“暂缓参加”变为“愿意再次来访”；
- 林澈记住玩家愿意让朋友表达不同意见；
- 个人区域桌游桌新增一次可见使用痕迹或纪念标记。

### 第十四天：剧本角色进入小镇

玩家在旧车站参与短剧本，认识角色沈砚。沈砚与玩家共同经历了一次案件分歧，但他不自动成为朋友，也不自动入住。玩家回到小镇后，可以邀请他来访；林澈和许宁对沈砚的态度各自不同，形成新的关系起点。

这就是初代想证明的“增量”：小镇原有关系没有被剧本清空，剧本角色也没有被当作一次性 NPC 消耗。

## 10. 状态与 authority 边界

### 10.1 四类状态

| 状态 | 内容 | 唯一正式写入者 |
| --- | --- | --- |
| `Canonical Character State` | 人格、长期记忆、关系、目标、能力证据 | 角色写回策略和既有 authority 边界 |
| `Canonical Town State` | 地点、居民身份、公共项目、活动安排、公共事件 | 小镇/Gameplay authority 通过既有事件路径 |
| `Personal Area State` | 住宅、桌游桌、共建项目、纪念物、访问权限 | 个人区域对应的既有/后续 authority |
| `Session State` | 剧本证据、桌游手牌、临时目标、回合资源 | 对应玩法 authority；结束后生成写回候选 |

### 10.2 事件链

```text
居民意图 / 玩家结构化输入
  -> Character Agent / 玩法规则产生 typed proposal
  -> ESM 或对应 Gameplay authority 进行约束检查
  -> GameplayEventStore.append_batch()
  -> event spine / outbox / mirror
  -> 小镇、个人区域、角色记忆和观察投影
```

角色智能体不能直接写小镇真相；Godot 不能因为本地动画播放完就确认关系或建造成功；桌游不能建立自己的 event store；司命只能输出高层催化和建议。

### 10.3 记忆写回

参考对话2的五池记忆边界，小镇事件可以生成：

- Event Memory：发生了什么桌游、共建或拜访；
- Observation Memory：角色亲眼看见什么；
- Knowledge Memory：角色因此知道什么公开事实；
- Social Memory：角色如何理解玩家和其他居民；
- Higher-Order Memory：这次经历说明了什么关系模式或自我认识。

局内手牌、隐藏信息和未公开私有事实不能因为玩家看到演出，就自动进入其他角色的知识记忆。

以下是本设计建议的最小验收面，均属于待正式化目标：

| ID | 证明内容 | 最小证据 |
| --- | --- | --- |
| TOWN-A | 小镇可步行入口 | 旧车站、广场、居民街、工作坊、杂货铺、咖啡馆/茶馆综合楼、酒吧、社区休闲中心、户外运动带、个人区域可达；54 名首发居民具有可识别身份，六名核心居民档案稳定 |
| TOWN-B | 主动居民 | 三次不同原因的居民主动接触；不是同一条随机台词重复播放 |
| TOWN-C | 锚点朋友 | 两到三次共同经历后，关系状态变为“愿意介绍朋友”；可解释、可回放 |
| TOWN-D | 朋友圈邀请 | 朋友分别接受、拒绝或暂缓；拒绝零写入非法关系状态 |
| TOWN-E | 个人区域来访 | 至少两名智能体实际进入个人区域并完成一局桌游 |
| TOWN-F | 合法信息视图 | 智能体不能读取其他玩家手牌、牌库或隐藏状态；服务端和测试同时证明 |
| TOWN-G | 共同记忆 | 桌游/共建结果生成角色可读取的事件和社会记忆，并改变下一次互动 |
| TOWN-H | 剧本增量 | 剧本角色可访问小镇；可接受、拒绝或暂缓；不覆盖原有居民关系 |
| TOWN-I | 离场连续性 | 玩家离开后，有限居民节拍仍推进；回来时能看到一条可追溯变化 |
| TOWN-J | 回放边界 | Town、Personal Area、Session 三类状态可区分重放；重复提交幂等 |
| TOWN-K | 地图可玩闭环 | 32 个主要节点分为中心商业短环、娱乐社交环、滨水景区环和全镇长环；商业、娱乐、社区休闲、运动和景区节点各有可重复动作、关系入口和回流结果；玩家能在一次返回中完成“公告 -> 遇见 -> 选择 -> 结算” |
| TOWN-R | 娱乐与运动空间 | 咖啡馆、茶馆、台球厅、酒吧、桌游馆、社区活动室和户外运动带均有独立状态；运动设施不占中央广场，露天空间可被活动和居民路线使用 |
| TOWN-L | 周循环 | 居民请求、公共项目、社交活动三条线至少有一条产生未完成状态，并在下一轮生活简报中保持可追溯 |
| TOWN-M | 回镇动机 | 连续三次返回中，至少两类“人/事/地”信号发生可见变化；没有信号时不会强制弹窗制造活跃度 |
| TOWN-N | 商店循环 | 商店完成一次购买、交换或预订单；库存/订单经 authority 结算；闭店后店主能在其他公共地点出现 |
| TOWN-O | 房屋边界 | 同一居民的公共门槛、半私域门廊和受邀请室内产生不同访问结果；拒绝/暂缓不产生非法写回 |
| TOWN-P | 居民工作绑定 | 六名核心居民各有可识别住所、工作地点和至少一条可解释路线；工作结果能回流公共项目、供给或关系事件 |
| TOWN-Q | 家人朋友网络 | 48 名网络居民有自己的居住安排、社会锚点和关系边；至少 12 条跨核心圈关系能在公开活动或生活简报中被观察 |

## 12. 首发范围与延后

### 首发

- 一个四倍以上面积的小镇地图：32 个主要节点、80～100 个可辨识子地点，中心商业短环、娱乐社交环、滨水景区环和全镇长环并存；
- 旧车站与档案馆为相邻独立建筑，另有大型公寓、旅店、河湾、溪谷和山地外围；
- 54 名有名字的可识别居民：6 名核心居民与 48 名家人/朋友/工作伙伴；
- 3～5 名需要近场完整 agent 验证覆盖的角色；
- 一个锚点朋友及 2～3 名本地朋友圈成员；
- 一个个人区域；
- 一张桌游桌和一款原创桌游；
- 一个短剧本入口；
- 关系状态、邀请/拒绝/暂缓、来访、共同记忆和一次共建；
- 三种活动时段和受治理的离场连续性；
- 日循环、周循环和三类可重复活动的最小闭环；
- authority、事件回放、私有信息隔离和拒绝零写入证据。

### 延后

- 完整青石镇式多年人口、婚姻、家庭和代际系统；
- 全镇动态经济、税收、政治和文明树；
- 让每个居民同时以最高密度运行完整心智链；
- 无限建造、体素、SDF、Construct 图；
- 多个小镇、跨镇旅行和跨服务器人口迁移；
- 多个剧本和桌游生态；
- 司命动态注入任意新规则的生产能力；
- 让玩家直接编辑元规则或居民底层档案。

- 个人区域与小镇的状态连接；
- 朋友带朋友来桌游的关系协议；
- 剧本角色进入小镇的访问/居住协议；
- Town-A～Town-J 对应的正式 spec、plan、测试和 Harness profile。

## 14. 设计结论

初代小镇不需要先成为一个完整文明。它只需要让玩家相信：

> 这里的人有自己的生活，彼此认识，记得发生过什么；玩家可以进入这张关系网，但不能把所有人变成自己的道具。

最小可行的小镇不是“地图 + NPC + 好感度”，而是：

```text
地点有社会功能
  -> 居民有自己的关系
  -> 日常由程序持续推进
  -> 关键时刻唤醒完整角色
  -> 玩家行为留下事件、记忆和关系涟漪
  -> 下一次回来时世界给出可观察回应
```

这条链与当前仓库的角色心智、world_runtime、Gameplay authority 和事件回放边界相容，但完整小镇产品仍然是本线程提出的后续产品目标，不应误报为当前已实现。
