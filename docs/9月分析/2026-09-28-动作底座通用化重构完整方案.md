日期：`2026-09-28`

状态：`长期架构参考；不作为当前独立执行入口`

本文的语义动作、Registry、BodyProfile、capability、root motion 和资产 qualification
约束已吸收到
[角色动作底座渐进替代设计](../superpowers/specs/2026-09-28-character-action-foundation-series-completion-design.md)。

## 0. 文档定位

本文是九月分析层的独立方案，回答以下问题：

1. `KnightRoleSkin` 为什么不能继续作为通用角色表现底座；
2. 2026-09-14 动作底座 Task 1–15 到底完成到什么程度；
3. `CharacterActor`、`CharacterReplica`、`RoleAnimationController`、
   `RootMotionSampler` 和资产 Registry 应怎样继续收敛；
4. 统一动作库、共享骨骼语义、不同身材和不同动作风格如何同时成立；
5. 完成后的 `scripts/character`、`scripts/street_combat` 和角色场景应具备什么职责边界；
6. 在什么证据出现之前，不能宣称“通用角色动作底座完成”。

本文不替代正式 spec、implementation plan、代码测试或 Harness 证据，也不把本
文的建议当作实现授权。正式执行入口仍是：

- `docs/superpowers/specs/2026-09-28-character-action-foundation-series-completion-design.md`
- `docs/superpowers/plans/2026-09-28-character-action-foundation-series-completion-implementation-plan.md`
- `docs/superpowers/specs/2026-09-14-unified-character-action-foundation-and-inf-tag-contract-design.md`

分析层只负责说明目标、判断、边界和验收逻辑；实现必须回到正式 spec/plan，并
以代码、测试、Godot 运行证据和 Harness 结果闭合。

## 1. 一句话结论

当前已经完成的是：

> 一个包含共享 Controller/Arbiter/Motor、资产资格化、语义 ActionAttempt、Mode B
> 传输以及 `CharacterActor` 迁移接缝的动作底座纵切。

当前尚未完成的是：

> 一个不依赖 Knight 专用脚本、能够让多个不同角色包通过同一套表现运行时、动作索引、
> 身材参数、动作风格、接触校准和可选能力模块运行的通用角色表现底座。

因此，不能把现状描述为“Task 1–15 全部完成”，也不能把 `KnightRoleSkin` 继续
扩展成通用基类。正确做法是冻结现有纵切，建立通用表现运行时，再逐步把 Knight
逻辑降级为一个角色包的 profile/capability 实现。

## 2. 当前状态判定

### 2.1 证据层级

当前仓库同时存在四种容易混淆的“完成”：

| 口径 | 当前判断 | 依据 |
| --- | --- | --- |
| 代码曾经落地过 Task 1–15 的片段 | 是 | `9f2e3075` 及其后续提交、现有脚本和测试 |
| 一个 Mode B 双角色纵切可运行 | 是，已有证据 | `.harness/verification/unified-character-action-foundation-runtime-verifier.json` |
| 主计划 Task 1–15 的 completion gate 全部闭合 | 否 | 主计划 checkbox、失败矩阵和发布门未全部形成新鲜证据 |
| 通用角色表现底座已完成 | 否 | Knight 逻辑仍是专用实现，通用 realization runtime 尚未闭合 |

### 2.2 9 月 28 日 pilot 已经带来的正确变化

当前代码已经有以下正确方向：

- `CharacterActor.gd` 作为行为实现宿主出现；
- `CharacterReplica.gd` 继承 `CharacterActor`，承担兼容入口；
- `RoleAnimationController.gd` 负责 `AnimationTree`/`AnimationPlayer` 的基础状态机、
  one-shot lock、held pose 和诊断字段；
- `RootMotionSampler.gd` 只采样根轨道并输出一次性 delta，不直接写身体变换；
- `CharacterMotor.gd` 仍是 `move_and_slide()`、重力、碰撞、朝向和身体位移的 owner；
- `StreetCharacterSkin.gd` 已开始使用共享动画控制器和 root sampler；
- Registry 已按 `package_id + semantic_action_id + claims` 解析 qualified profile；
- ActionAttempt/AuthorityResult 和 Mode B 语义边界已有运行纵切；
- `KnightRoleSkin` 不再是所有新角色必须直接依赖的唯一 skin。

这些变化说明迁移方向已经正确，但它们只形成了“通用化的基础接缝”，并没有自动
把所有旧职责变成可替换、可扩展的系统。

### 2.3 仍然存在的结构性问题

#### A. `CharacterActor` 仍过于庞大

当前 `CharacterActor` 仍承接移动决策、感知、巡逻、玩家同步、Agent 消费、动作兼容、
root motion 汇总、姿态反馈和角色表现入口。它比旧 `CharacterReplica` 更接近目标，
但仍是“大宿主”，不是最终的组件化 actor。

后续必须把它收敛为编排器：

```text
ControllerPort / RuntimeState / Arbiter / Composer / Motor
                         |
                         v
                CharacterPresentationRuntime
                         |
                package + capabilities
```

感知、巡逻、交互导航、事实发射器、调试和具体动作能力应通过组件或明确接口接入，
不能继续向 `CharacterActor.gd` 堆积专用逻辑。

#### B. `CharacterReplica` 仍是活跃兼容面

`CharacterReplica` 已经成为兼容壳的方向，但场景、探针、旧调用方仍可能按其名称和
方法表发现角色。兼容壳可以存在，但必须满足：

- 不新增行为；
- 不持有第二套状态机；
- 不拥有身体位移、动画播放或世界真相；
- 只转发到 `CharacterActor` 或新的 typed interface；
- 每个兼容方法都记录迁移 owner、调用方和删除条件。

#### C. `RolePresentationAdapter` 还是边界外壳

它已经能阻止 presentation 输入写入 `transform`、`velocity`、`damage`、`hit`、
`inventory`、`status` 和 `authority_result`，但真正的动画 realization 仍由具体 skin
自己解释 profile。适配器存在，不等于通用表现运行时已经完成。

#### D. `KnightRoleSkin` 仍然混合了包数据和运行时能力

它同时包含：

- Knight 的 clip map；
- Knight 的动作和 locomotion profile；
- Knight 的骨骼查找和骨骼索引；
- Knight 的姿态 refinement；
- Knight 的材质/变体外观；
- KnightCombatModifier；
- ArchiveDoorReachModifier；
- Sword/shield 计时和动作反馈；
- 右手 IK/reach；
- root motion 采样辅助。

这些内容并非同一层职责。它们必须拆分为：

```text
通用运行时：播放、分层、标记、根运动、挂点、能力调度
Knight profile：Knight 的 clip、mask、style、body calibration
Knight capability：Knight 的 combat modifier、手部 reach、专用交互修正
Knight package：模型、骨架映射、manifest、qualification report
```

## 3. 目标系统的设计原则

### 3.1 统一的是语义和接口，不是把所有原始 clip 强行共用

业务层只请求稳定的语义动作：

```text
action:locomotion.idle
action:locomotion.walk
action:locomotion.run
action:locomotion.jump
action:melee.unarmed_punch
action:melee.sword_slash
action:interaction.reach
```

业务层不请求 raw clip、AnimationPlayer 路径或 Knight 节点名。具体 clip、state、mask、
root profile 和 fallback 由本地 Registry 根据角色包、骨架 profile、身材 profile、
动作风格和 claims 解析。

### 3.2 一个动作库可以被多个角色使用，但必须经过角色 realization

统一动作库不是“一个原始动画文件直接驱动所有模型”，而是：

```text
共享语义动作索引
        |
        +-- canonical skeleton profile
        |
        +-- 角色包 deform-to-canonical mapping
        |
        +-- body profile / motion style / contact calibration
        |
        +-- realization profile
        |
        +-- 角色自己的 AnimationLibrary / AnimationTree
```

同一个语义动作可以有多个 realization：

```text
action:locomotion.run
  -> humanoid.v1 + style:athletic -> running_for_jk
  -> humanoid.v1 + style:heavy    -> running_for_bandage
  -> humanoid.v1 + style:elegant  -> running_for_custom_role
```

### 3.3 身材、重量和动作风格必须是独立参数

不把身高、体重、动作风格写进骨骼名称或 Knight skin 逻辑。角色包应声明类似：

```json
{
  "body_profile_id": "body:tall_slim",
  "height_scale": 1.08,
  "leg_length_ratio": 1.12,
  "arm_length_ratio": 1.03,
  "shoulder_width_ratio": 0.94,
  "mass_class": "light",
  "gait_scale": 1.06,
  "reach_scale": 1.02,
  "foot_ik_enabled": true,
  "hand_ik_enabled": true,
  "motion_style_id": "style:athletic"
}
```

职责分配：

| 参数 | 主要影响 | 处理层 |
| --- | --- | --- |
| 身高/骨长 | 目标高度、脚底、手部 reach、挂点 | BodyProfile + SkeletonBinding + IK |
| 体重类别 | 加减速、落地压缩、转身、后摇、混合时间 | MotionStyle + Motor 参数 |
| 动作风格 | 重心、摆臂、节奏、倾斜、blend | AnimationGraph + additive layer |
| 角色装备 | socket、挂点、动作 claims、hit volume | EquipmentAttachmentRuntime |
| 交互对象高度 | 手脚接触、目标偏移、容差 | Capability module + typed target |

动画旋转可以高度共享；绝对米制位移、接触位置、脚步和手部 reach 不能无条件照搬。

### 3.4 所有表现输出都必须是观察或贡献

允许：

- 播放语义动作；
- 采样 root motion；
- 产生 marker observation；
- 产生 `MotionContribution`；
- 请求或清除 capability；
- 读取已提交的 authority projection。

禁止：

- skin 写 `global_position`、`position`、`velocity`；
- skin 调 `move_and_slide()`；
- marker 直接确认命中、伤害、拾取或占用；
- AnimationTree 直接产生世界事件；
- Agent/INF/Siming 选择 raw clip 或写骨骼姿态到网络；
- presentation 层绕过 Arbiter、Motor 或 Authority。

## 4. 目标运行时分层

### 4.1 Actor 层

```text
CharacterActor
  ├─ CharacterRuntimeState
  ├─ CharacterControllerPort
  ├─ ActorActionArbiter
  ├─ MotionContributionComposer
  ├─ CharacterMotor
  ├─ CharacterPresentationRuntime
  ├─ Perception / Navigation adapters
  └─ Debug / telemetry adapters
```

`CharacterActor` 只负责组装和按固定 tick 编排：

1. 收集 player、agent、program、debug proposal；
2. 交给 ControllerPort 做边界校验；
3. 交给 Arbiter 做 lease/action admission；
4. 生成一个 immutable intent frame；
5. 交给 presentation runtime 生成表现观察和 root contribution；
6. Composer 生成一个 `PhysicsMotionCommand`；
7. Motor 执行身体运动并采集 contact evidence；
8. 将 marker + physics evidence 组成 ActionAttempt candidate；
9. 接收 AuthorityResult 并更新 projection；
10. 记录 replay/debug snapshot。

### 4.2 表现层

```text
CharacterPresentationRuntime
  ├─ CharacterAnimationGraph / RoleAnimationController
  ├─ CharacterSkeletonBinding
  ├─ CharacterPoseLayerStack
  ├─ CharacterRootMotionSampler
  ├─ CharacterMarkerObserver
  ├─ CharacterEquipmentAttachmentRuntime
  ├─ CharacterModifierStack
  └─ CharacterPresentationCapability registry
```

| 组件 | 职责 | 明确禁止 |
| --- | --- | --- |
| `RoleAnimationController` | AnimationTree/AnimationPlayer、状态、过渡、one-shot、hold/recovery | 写 actor 身体、结算世界事实 |
| `CharacterSkeletonBinding` | canonical bone 到实际 Skeleton3D 的绑定和校验 | 按名称猜骨骼并静默补映射 |
| `CharacterPoseLayerStack` | locomotion、upper-body、additive、full-body claims 的层管理 | 创建第二个运动 owner |
| `RootMotionSampler` | 依据 qualified profile 采样一次 root/pelvis contribution | 直接写 transform |
| `CharacterMarkerObserver` | 产生同 tick marker observation | 直接产生 damage/hit |
| `CharacterEquipmentAttachmentRuntime` | socket、hand anchor、attachment mode | 改 inventory 或 authority 状态 |
| `CharacterModifierStack` | 调度已登记的姿态/IK/recoil/接触修正模块 | 让任意 modifier 改身体位移 |
| `CharacterPresentationCapability` | 可选能力接口，如 hand reach、foot IK、recoil | 依赖某个角色名称作为通用契约 |

### 4.3 数据流

```text
human / agent / program / debug
        |
        v
CharacterControllerPort
        |
        v
IntentProposal -> ActorActionArbiter -> CharacterIntentFrame
                                      |
                                      v
                         CharacterRuntimeState projection
                                      |
                                      v
                    CharacterPresentationInput
                                      |
                                      v
          PresentationRuntime(package + profile + capabilities)
                    |                         |
                    v                         v
             marker observations       root contributions
                    |                         |
                    +------------+------------+
                                 v
                    MotionContributionComposer
                                 |
                                 v
                       one PhysicsMotionCommand
                                 |
                                 v
                          CharacterMotor
                                 |
                                 v
                    PhysicsContactEvidence(T)
                                 |
                 marker + evidence same-tick join
                                 |
                                 v
                         ActionAttempt candidate
                                 |
                                 v
                      ESM / Gameplay / Composite
                                 |
                                 v
                         AuthorityResult
                                 |
                                 v
                    committed runtime projection
```

## 5. 统一动作库和资产包方案

### 5.1 资产目录和状态

动作投递和正式运行时必须分开：

```text
assets/motion_library/
  incoming/       # 新投递，不能被运行时读取
  review/         # 审核结果、预览、失败诊断
  approved/      # 通过审核的不可变版本
  rejected/       # 失败资源及原因
  manifests/      # 语义动作索引和版本清单
```

状态至少包括：

```text
incoming
reviewing
passed
approved
approved_with_fallback
rejected
deprecated
quarantined
```

正式运行时只能读取 `approved` 及其 manifest/report，不读取 `incoming` 或 `review`。
动作资源使用不可变版本，例如 `motion:locomotion.run@1`。语义 ID 保持稳定；版本、
来源 digest、骨架 profile 和 realization profile 参与解析。

### 5.2 Manifest 最小字段

```json
{
  "package_id": "female_jk_external",
  "package_version": "1.0.0",
  "skeleton_profile_id": "humanoid.v1",
  "body_profile_id": "body:tall_slim",
  "motion_style_id": "style:athletic",
  "canonical_mapping": {},
  "rest_pose": {},
  "axis_unit_policy": {},
  "attachment_slots": {},
  "actions": [
    {
      "semantic_action_id": "action:locomotion.run",
      "realization_profile_id": "female_jk_external:run:athletic",
      "clip_ref": "running",
      "mode": "drive_locomotion",
      "claims": ["world_motion", "root_translation"],
      "root_motion_policy": "qualified_bounded",
      "markers": [],
      "fallback": {}
    }
  ],
  "qualification_report_ref": "...",
  "source_digest_sha256": "..."
}
```

### 5.3 动作审核流程

```text
投递文件
  -> 完整性与 digest
  -> skeleton/rest pose/单位/轴向
  -> canonical mapping
  -> clip 轨道和 marker 检查
  -> root/pelvis/lower-body 影响分析
  -> realization mode 判断
  -> 接触、挂点、动作窗口审核
  -> 自动 qualification report
  -> 人工视觉复核
  -> approved manifest
  -> Registry admission
```

自动审核必须检查文件完整性、mapping、rest pose、轨道、marker、root/pelvis 影响、
upper-body mask、full-body 并发声明、接触 envelope、语义 ID、版本和 digest 冲突。
人工审核负责脚滑、穿模、手部姿态、攻击接触、风格质量和默认 realization 决策。

## 6. 骨架、身材和动作适配

### 6.1 Canonical skeleton

`humanoid.v1` 只定义语义骨骼，不要求运行时模型拥有作者级控制骨骼：

```text
root / pelvis / spine / chest / neck / head
left_upper_arm / left_lower_arm / left_hand
right_upper_arm / right_lower_arm / right_hand
left_upper_leg / left_lower_leg / left_foot
right_upper_leg / right_lower_leg / right_foot
```

Blender 中的 controller、IK/FK、pole、twist、reference bones 可以存在，但只要
导出时烘焙到 deform skeleton 并完成 mapping，就不进入运行时 canonical boundary。

### 6.2 共享动画的适用等级

| 差异等级 | 允许的实现 |
| --- | --- |
| 小幅身材差异 | 共享 clip + BodyProfile + foot/hand IK |
| 中等身材差异 | 共享语义动作 + 局部派生 clip + calibration |
| 大幅比例差异 | 同一 semantic ID，不同 realization profile |
| 极端差异 | 独立 skeleton profile 或独立动作族 |

不得用一个固定百分比替代 qualification。脚步、手部、武器接触、根运动和碰撞体
必须经过实际报告验证。

### 6.3 Root motion 规则

- `hold`：动画根轨道不贡献身体位移；
- `bounded_continue`：只在 envelope 内贡献；
- `drive_locomotion`：root contribution 驱动该 tick 的 locomotion；
- `replace_locomotion`：替代等价 lease，避免双重位移；
- `additive`：只能提供声明过的局部贡献；
- 缺少必需轨道、超出 envelope、support 不满足或 profile 失效时 fail closed。

同一 tick 中，lease velocity 与等价 root contribution 只能保留一个有效位移来源。
RootMotionSampler 采样一次，Composer 去重，Motor 消费一次并记录 consumption token。

## 7. `KnightRoleSkin` 的降级和拆分方案

### 7.1 不再承担的职责

`KnightRoleSkin` 不再作为通用角色基类、统一动作状态机、通用骨骼查找器、通用装备
系统、通用交互 IK 系统、通用 root-motion owner 或测试体系的默认表现规范。

### 7.2 保留为 Knight package 的内容

```text
KnightPresentationProfile
  - Knight clip aliases
  - Knight locomotion refinement
  - Knight style parameters
  - Knight body calibration

KnightCombatCapability
  - sword/shield presentation hints
  - KnightCombatModifier registration
  - declared hand/weapon slots

KnightReachCapability
  - right-hand reach calibration
  - archive-door interaction pose correction
  - required anchor and tolerance declaration
```

ArchiveDoor 的能力应按 `interaction_reach` 或明确 capability ID 注册，不能让
`CharacterReplica` 或通用 Actor 直接知道 `ArchiveDoorReachModifier` 这个类名。

### 7.3 推荐的迁移结果

```text
KnightRoleSkin.tscn
  -> CharacterPresentationRuntime
  -> QualifiedPackage: crusader_knight
  -> KnightPresentationProfile
  -> KnightCombatCapability (optional)
  -> KnightReachCapability (optional)
```

最终 `KnightRoleSkin.gd` 只能是很薄的 package adapter，或被 runtime/profile 取代并
保留兼容转发；不能继续包含通用动作调度和身体运动逻辑。

## 8. `GenericRoleSkin` 和 `StreetCharacterSkin` 的目标

### 8.1 `GenericRoleSkin`

它不能只是灰盒 fallback，应遵守同一 contract：

- 有最小 SkeletonBinding；
- 有 idle/walk/run/jump semantic state；
- 没有 qualified attack 时明确返回 unavailable/fallback；
- root motion 没有资格时不伪造真实位移；
- marker 只产生 observation；
- 所有能力通过 capability registry 查询。

### 8.2 `StreetCharacterSkin`

它应作为 manifest-driven reference implementation：

- 通过统一 `CharacterPresentationRuntime` 初始化；
- 不直接暴露 raw clip 给 StreetCombatCoordinator；
- boxing/sword 通过 semantic action ID + claims 进入 Registry/Arbiter；
- 当前未通过 upper-body qualification 的动作保持 `full_body_exclusive`；
- AnimationTree、RootMotionSampler、marker observer 和 fallback reason 可诊断；
- 不承担 ActionAttempt settlement。

### 8.3 角色之间的唯一差异来源

角色表现差异只能来自 package manifest、skeleton mapping、body profile、motion style、
realization profile、registered capability 和装备/挂点声明。不能来自
`if package_id == ...` 散落在通用 actor、adapter 或 coordinator 中。

## 9. `scripts/character` 最终职责

| 文件 | 最终职责 |
| --- | --- |
| `CharacterActor.gd` | 角色编排和兼容 API 的唯一实现宿主 |
| `CharacterReplica.gd` | 历史场景兼容壳，只转发，不新增行为 |
| `CharacterControllerPort.gd` | 所有输入来源的 typed ingress |
| `CharacterRuntimeState.gd` | immutable projection、lease/action、authority 和 presentation 状态 |
| `ActorActionArbiter.gd` | claim、priority、queue/reject/cancel、同 tick 决策 |
| `MotionContributionComposer.gd` | 组合 lease/root/impulse/correction 成一个 command |
| `CharacterMotor.gd` | 唯一 body motion owner |
| `CharacterEmbodimentAssetRegistry.gd` | manifest/report admission 与 semantic profile resolution |

| `RoleAnimationController.gd` | 动画状态机实现层 |

## 10. `CharacterReplica` 最终应该变成什么

最终目标：

```gdscript
extends CharacterActor
class_name CharacterReplica

# 仅保留旧场景、旧探针、旧脚本所需的兼容方法。
# 不在此文件新增移动、动画、感知、交互或 authority 逻辑。
```

允许保留类名、场景兼容、旧方法转发、迁移告警以及旧字段到新 typed contract 的
转换。必须删除或迁出 direct transform/velocity writer、具体 skin 方法调用、
Knight/ArchiveDoor 判断、raw clip 选择、第二套 action lock/root-motion loop 和
world-truth settlement。

删除兼容壳的前提是迁移报告确认活跃 scene、PlayerShell/phase0 bridge、Agent/INF
adapter、StreetCombat coordinator、interaction probes、backend-facing verification
scripts、editor tooling 和 debug panel 都不再依赖具体 `CharacterReplica` 行为。

## 11. 迁移顺序

### 阶段 A：冻结当前 pilot

- 把 9 月 28 日 pilot 标记为已落地的纵切；
- 记录已通过的 runtime evidence 和未通过的门；
- 禁止新功能直接调用 `KnightRoleSkin`；
- 禁止新功能新增 `CharacterReplica` 具体行为；
- 所有新动作请求只接受 semantic action ID。

### 阶段 B：收敛表现接口

- 定义 typed `CharacterPresentationInput`；
- 统一 `RoleAnimationController` 的 state/action/hold/cancel/recovery；
- 统一 `RootMotionSampler` 的 profile、envelope 和 consumption token；
- 引入 SkeletonBinding、PoseLayerStack、MarkerObserver；
- 将 `StreetCharacterSkin` 的包加载接入统一 runtime。

### 阶段 C：迁移 Knight

- 把 clip map、refinement、variant 和骨骼映射移入 Knight profile；
- 把 combat/reach/ArchiveDoor 变成 capability；
- 删除通用 actor 对 Knight 类名的直接引用；
- 让 Registry 通过 package/capability 声明发现这些能力；
- 对现有 archive-door 场景保留兼容适配，但不让它定义通用接口。

### 阶段 D：统一动作库与多角色验证

- 选择至少两个骨架比例不同的角色包；
- 使用同一 semantic action catalog；
- 使用各自 realization profile 和 body calibration；
- 验证 idle/walk/run/jump/turn、一个 full-body action、一个可并发 action；
- 验证手部挂点、脚部接触、root motion、碰撞和 marker timing；
- 证明新增角色不需要复制 Knight 专用脚本。

### 阶段 E：关闭旧入口和文档漂移

- 替换直接读取 Knight source 的静态测试；
- 将测试目标改为 interface、package、capability 和 ownership contract；
- 更新 Task 1–15 的状态矩阵；
- 让 current-state、operator guide、status register、INDEX、spec、plan 口径一致；
- 用新鲜 evidence 关闭对应门，而不是用旧提交名称代替验收。

## 12. 验收门槛

### 12.1 表现门

至少三个角色包通过同一 `CharacterPresentationRuntime`：idle、walk、run、jump、turn，
以及一个 boxing 或 sword 动作；同时证明 one-shot lock、hold、cancel、recovery、
AnimationTree/fallback 和 package/skeleton/state/clip/fallback 诊断。

### 12.2 运动门

player、NPC、agent、program 全部经过同一 ControllerPort → Arbiter → Composer → Motor；
只有 Motor 调用 `move_and_slide()`、写身体 velocity/重力/朝向/位移；root contribution
每 tick 只消费一次；lease 和 root 不重复施加等价位移；墙、坡、台阶、失去支撑和
停止/重启都有证据。

### 12.3 资产门

package 有 digest、canonical mapping、rest pose、body profile 和 report；语义动作与
raw clip 解耦；full-body clip 不得伪装为 upper-body concurrent；fallback 是显式 profile；
rejected package 无法进入 Registry；新增角色只需新增 package/profile。

### 12.4 authority 门

marker + physics evidence 只形成 ActionAttempt candidate；ESM/Gameplay/Composite 负责
世界后果；duplicate 返回原 transaction；changed duplicate、旧 revision、旧 epoch 被
拒绝；local-only 失败没有世界写入；Mode B 与未来 body stream 分离；不声明 raw-pose
replication、rollback 或 authoritative multiplayer physics。

### 12.5 文档门

九月分析、9 月 28 日 completion spec/plan、2026-09-14 master plan、current-state ledger、
operator guide、actor/agent architecture、debug/verification、`docs/INDEX.md`、status
register、Harness profile 和新鲜 evidence 必须描述同一个状态。

## 13. 不能接受的“完成”方式

以下情况不能算通用底座完成：

1. 只把 `KnightRoleSkin` 改名为 `GenericRoleSkin`；
2. 在 `KnightRoleSkin` 里增加更多 `if package_id` 分支；
3. 让每个新模型复制一份 Knight skin；
4. 只验证两个角色移动，不验证第三个角色和动作 realization；
5. 只运行静态 pytest，不跑真实 Godot 表现证据；
6. 只证明 Registry 能返回 profile，不证明 runtime 能消费 profile；
7. 让 root motion 在 skin、actor 和 Motor 中重复消费；
8. 用字符串匹配替代真实 ownership 证据；
9. 把 full-body fallback 描述成 upper-body concurrency；
10. 用旧 `.harness/verification` 报告覆盖当前代码状态；
11. 只更新文档 checkbox，不补 completion gate 证据；
12. 为了通过旧测试继续保留 Knight-specific public methods 作为新系统接口。

## 14. 推荐的最终判断口径

在通用化工作完成之前，对外应使用：

> 动作底座的共享控制、仲裁、Motor、资产准入、ActionAttempt 和 Mode B 纵切已经
> 落地；9 月 28 日 pilot 已建立 `CharacterActor`、动画控制器和 root-motion sampler
> 的迁移接缝。通用角色表现运行时、跨身材 realization、能力模块化、Knight 专用逻辑
> 降级和全量 completion gate 仍在收口中。因此当前不能宣称 Task 1–15 全部完成，
> 也不能把 `KnightRoleSkin` 当作通用角色底座。

完成后才可以使用：

> 多个角色包通过同一 semantic action、skeleton binding、presentation runtime、
> root contribution、Motor 和 authority boundary 运行；Knight 只作为一个可替换
> package/capability 实现存在。
